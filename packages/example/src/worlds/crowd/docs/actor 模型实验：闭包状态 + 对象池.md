## 一、为什么做这个实验

### 1.1 起点：一个具体的不顺手

`packages/saboteur/` 已按 v3 ECS 形态完整落地（M0–M7，242 例测试）。它的一个 NPC 是这样构成的：

- 实体结构 `ActorEntity` 有 **21 个字段**（`src/game/types.ts`）
- 字段来自 **5 个系统**的 `enter()` 切片（locomotion / perception / interaction / alarm / behaviour）
- 再加 `actor.tsx` 的 `enters` 数组拼装 + `role` 注入

也就是说：**「一个客人是什么」这个问题，答案分散在 5 个文件里。** 想读懂一个 NPC，必须来回跳。

作者（本项目所有者）对此的描述是：

> 我对这个 demo 的设想其实是有很多内容的制作打算的，我想看看这样的模式会不会更符合我的思维模型，是否会对于我来说更简单一些。

即：**这是为「后续大量内容制作」做的架构选型实验，不是为了解决某个已发生的 bug。**

### 1.2 要验证的假设

> 把「实体的状态」放回组件闭包，把「实体的动作」放进实体池，是否让「加一个新 NPC 类型」变得更简单？

对照组是现状：加一个新角色类型（例如巡逻保安）需要动 `types.ts` + 至少一个 system 的 `enter` + `instance.ts` 接线 + `actor.tsx` 的 `enters` 数组。

### 1.3 为什么用独立小 demo，而不是重写 saboteur

**如果重写 saboteur，实验结论无效。** 因为第二遍必然更顺手，原因与架构无关：

1. 已经懂这个玩法（恐慌要延迟、尸体要被感知）
2. 已经踩完了坑（空数组 truthy、恐慌不过期、目标选到自身格）
3. 需求已经精确（下药后多久死、警报涨多少）

这个偏差无法用「复用 `world/` 来抵消」——恰恰相反，**复用的部分越多，测出的差异越小**。所以选一个**自包含的小 demo**：它没有关卡设计、没有寻路、没有美术资产可以顺便复用，两边都是从零开始，此时的手感判断才是干净的。

**结论（已定）**：实验场地为 `packages/example/src/worlds/crowd/`，注册进 `worlds/index.tsx` 的卡片列表。**完全不复用 saboteur 的代码**。

## 二、方案形态

### 2.1 核心差别

|            | 现状（v3 ECS）                                   | 本实验                        |
| :--------- | :----------------------------------------------- | :---------------------------- |
| 状态存放   | 实体信号（扁平数据，`Map<EntityId, Signal<T>>`） | 组件闭包里的信号              |
| 池里放什么 | 信号（数据）                                     | 带方法的对象（动作）          |
| 逻辑位置   | 系统（`game/systems/*`）                         | 对象方法（`obj.update(dt)`）  |
| 帧入口     | `createGame([...updates])` 参数顺序              | 遍历池调 `obj.update(dt)`     |
| 渲染订阅   | `use(entity, () => entity().x)`                  | `use(state, () => state().x)` |

**关键发现（已实测，见 §5.1）**：两类方案里的「状态」**都是信号**。差别不在信号，而在**这个信号由谁创建、逻辑写在谁身上**。

### 2.2 目标写法（作者草图）

```tsx
function Npc(props: NpcProps, ctx: Context) {
  const { use } = ctx;

  // 状态 = 组件闭包里的信号。每个组件实例一份（Each 展开时天然隔离）
  const state = use({ x: 0, y: 0, mood: "wander" as Mood, idleLeft: 1 });

  // 动作 = 注册进池的对象。池里不存数据，只存「这个实体能做什么」
  useGame({
    add() {
      /* 进池 */
    },
    update(dt: number) {
      const self = state();
      state({ ...self, x: self.x + 10 * dt });
    },
  });

  return <div>{use(state, () => `${state().x}px`)}</div>;
}
```

### 2.3 组件实例 = 实体实例（已实测成立）

「20 个 NPC 的闭包怎么容纳 20 份状态」这一疑虑**不成立**：组件函数每被调用一次，`use({...})` 就产生**独立信号实例**。实测见 §5.1。

### 2.4 附带收益：切片合并机制变得不必要

现状里 `useEntity(ctx, ...enters)` 存在的主要工作是**合并各系统的数据切片**：

```ts
// worlds/engine/index.ts（现状）
const merged = {} as T;
for (const enter of enters) {
  Object.assign(merged, enter(id, ctx)); // 5 个系统各贡献若干字段
}
const signal = use<T>(merged) as EntitySignal<T>;
```

这套机制之所以必要，**只因为状态由各系统分散提供**。状态回到闭包后：

- 组件自己给出完整初始值 → 无需合并
- `ActorEntity` 那个 21 字段的联合类型 → 不再需要（对象自己定义形状）

**注意一处不能省**：跨实体读取仍需要一份共享的形状认知——感知系统要读别人的 `dead` / `x` / `y`。actor 方案里这份认知由 TypeScript 结构类型承担（鸭子类型），不需要在注册时强制声明。但**这是否足够、会不会失去编译期保护，是本实验要观察的点之一。**

## 三、已知的结构性问题

以下是**动手前就能预判**的问题，记录在此以便对照实测。**它们不构成「不要做」的理由**——恰恰相反，如果实验中出现这些现象，那正是有价值的数据。

### 3.1 帧内顺序（最重要）

现状的帧结构是**阶段化**的：

```
所有 locomotion 跑完 → 所有 perception 跑完 → 帧末统一提交
```

这保证「perception 判定的是本帧所有实体移动完之后的位置」，且**与遍历顺序无关**。

若 `update(dt)` 一口气做完移动与感知，则变成：

```
A 移动 → A 感知 → B 移动 → B 感知 → ...
```

于是 **A 感知时看到 B 的上一帧位置，B 感知时看到 A 的本帧位置**——不对称，且顺序由 `Set` 的插入顺序（不可见）决定。

**参考**：主流引擎全部保留阶段——Unity `Update`/`LateUpdate`/`FixedUpdate`，Godot `_process`/`_physics_process`，Unreal `Tick`/`PostActorTick`。没有一个让对象一口气做完所有事。

**可能的解法**（记录备选，不在 demo 里预先采用）：

```ts
type Sync = { move(dt: number): void; perceive(world: World): void };
for (const o of pool) o.move(dt); // 阶段 1
for (const o of pool) o.perceive(world); // 阶段 2
```

代价：阶段就是系统，只是改了写法。**因此本次 demo 的取舍是：先按「一个 update 全搞定」写，让问题自然暴露。**

#### ✅ 结果：预测得到验证（首要发现）

问题**确实自己暴露了**，而且很强烈——但表现与预期不同：

- 预期的是「位置读取不对称」（A 看到 B 的旧位置）
- **实际发生的是「恐慌按遍历顺序传播」**：20 个 NPC 排成 5×4 网格，点掉第一个后，**单帧内整列 4 人都变红**（实测 y=211/351/491，间距恰好 140px 一格）

机制：`advance` 在同一次遍历里既读又写。前一个 NPC 刚被写入「恐慌」状态，后一个 NPC 读到的就是**本帧刚更新的值**——于是恐慌一跳接一跳地在单帧内传完。首帧就有两人相隔 281px、421px（远超 170px 视距）被传染。

**修法**：帧首快照。`peers` 在循环开始前一次性取好，本帧所有读取都基于同一份快照：

```ts
const snapshot = [...pool];
const peers = snapshot.map((a) => a.info()); // ← 帧首定稿
for (const actor of snapshot) actor.update?.(dt, { peers: () => peers });
```

修后传播变成逐帧的：第 1 帧 1 红、第 2 帧 2 红、第 3 帧 3 红——**由几何决定，不由遍历顺序决定**。

**这个修正与 ECS 版「帧末统一提交」是同一个思想**（读状态与写状态分属不同时间点），但代价差很多：这里只需一次 `map`，不需要帧管理器。

**教训**：actor 方案**不是天然错**，但它的默认写法（对象一口气读完写完）会踩这个坑。而 ECS 用 `frame/flush` **结构上避免了它**——这是 ECS 的实实在在的优势，不是理论优越性。

### 3.2 写入次数不再合并（已实测，成本比预期低）

现状的帧管理器（`worlds/engine/index.ts`）是**写时拷贝 + 帧末 flush**：系统内写多次，信号只提交一次。

- `frame(id, (e) => { e.x += 1 })` 两次 → 复用同一副本
- 帧末 `flush()` 一次性提交 → 下游派生只重算一次

本实验里 `state({ ...state(), x })` 是直接信号写入，**每次立即通知**。实测（§5.2）：

| 写入方式   | 一级派生重算 | **DOM 层写入** |
| :--------- | :----------- | :------------- |
| 分 3 次写  | 3 次         | **1 次**       |
| 1 次批量写 | 1 次         | 1 次           |
| 同值重复写 | 1 次         | 1 次           |

结论：**成本只在派生重算，DOM 写入仍然被截断。** 因为 `recomputeDerivation` 的等价性守卫（`newResult !== state.cachedValue`）在传播链上逐级生效——派生的结果没变就不往下传。

代价因此是 `O(写入次数 × 派生函数复杂度)` 的纯计算，而非 DOM 抖动。对 5–20 个实体、每个派生只读一两个字段的场景，可忽略。

**但有一条纪律随之而来**：既然是「每次写都通知」，就应该**一次写完**（`state({ ...self, x, y, hp })`），而不是拆成多次。`frame()` 那层合并在 actor 方案里没有了。

### 3.3 跨实体引用

实体变成对象后，`class Guest { update() { this.world.findNearest(...) } }` 这种写法**结构上变得可能**（现状 ECS 用 `frame(id)` 物理上阻止了它）。

风险：测试一个 `Guest` 要构造半个世界。

**纪律解法**：实体不持有 world，`update(world)` 当参数传。但纪律靠自觉。

### 3.4 `useGame` 的形态（已定：替换，非包装）

现状 `useEntity(ctx, ...enters)` 做四件事：合并切片、创建信号、挂 `id`、`onMount` 进池 / `onUnmount` 出池。

§2.4 已说明「合并切片」在 actor 方案里不再必要，因此 `useGame` **不是包装 `useEntity`，而是替代它**。它需要保留的能力只剩：

- 创建/接收状态信号（由组件传入）
- `onMount` 进池 / `onUnmount` 出池
- 注册「帧循环该调哪个方法」

`id` 是否还需要，取决于池用 `Set<object>` 还是 `Map<symbol, object>`。**倾向直接存对象引用，连 `id` 都不需要**——这是 actor 方案相对现状的又一处简化。待实现时确认。

## 四、渲染怎么接上

### 4.1 结论：不需要任何桥接（对文档前版的修正）

**本文前一版在此处写错了。** 前版推测：池里放非信号对象后，「方法改了闭包变量，谁来通知渲染」会成为问题，因此需要一个每帧递增的 `tick` 信号做粗粒度失效。

**这个推测是错的。** 因为作者的草图里，`state` **本身就是信号**：

```tsx
const state = use({ x: 0, y: 0, mood: "wander" }); // ← 这就是信号
useGame({
  update(dt) {
    const self = state();
    state({ ...self, x: self.x + 10 * dt }); // ← 写的就是这个信号
  },
});
return <div>{use(state, () => `${state().x}px`)}</div>; // ← 订阅的也是它
```

**通知链天然是通的**：对象方法写信号 → 信号触发派生 → DOM 更新。实测见 §5.1，无需 `tick`、无需改 core、无需自定义信号。

前版之所以想岔，是因为把它想成了「状态存在普通闭包变量里」。那是**另一种**设计（§4.3 方案 A/B 描述的对象），不是作者提出的这个。

### 4.2 仍然成立：kiaao 不支持自定义响应式容器

作者提出的疑虑：**「感觉我们像是缺少类似于 Vue 的 customRef 的能力」**。实测结论是**对的，但缺口比 customRef 更窄也更根本**。

这个缺口**不影响本实验**（因为状态就是普通信号），但它是一个独立的、真实的框架观察，记录在此。

**能做的**（探针一、二）：

- `use(x)` 在单参数且 `isUse(x)` 时**原样返回**该信号
- `isUse` 只检查 `v[REACTIVE]` 是否存在
- `REACTIVE` 与 `getSignalState` **都是公开导出**（`src/core/index.ts:77`、`:82`）

因此可以手工捏一个「类信号」：

```ts
const custom: any = (...args: any[]) => (args.length ? write(args[0]) : read());
custom[REACTIVE] = { value: raw, subs: new Set(), stop: () => {} };
```

它**是合法信号**：可作依赖、可被订阅、会被 `triggerDerivations` 遍历到。

**不能做的**（探针三）：**写入时通知下游**。`src/core/signal.ts` 里传播逻辑是私有的：

```ts
function triggerDerivations<T>(state: DefinitionState<T>): void {
  /* 未导出 */
}
function recomputeDerivation<T>(state: DerivationState<T>, setterValue?: T): void {
  /* 未导出 */
}
```

也没有 activeEffect / 动态依赖收集（全仓 grep 为空），依赖是**静态列表**。

所以自定义信号想传播，只能**把 core 的私有逻辑抄一遍**。实测抄通了（值正确传播），但立即暴露两个代价：

1. **丢掉等价性守卫**——core 靠 `newResult !== state.cachedValue` 才继续向下传播；手抄版重复写同值也会重算（实测计算次数 2 → 3）。这个守卫既省算力，也**天然截断传播链**（§3.2 的 DOM 去重正是靠它）。
2. **抄的是私有实现**，core 一改就漂。

**准确的表述**：

> kiaao 的信号内核只暴露了「被订阅」的能力，没有暴露「触发传播」的能力。因此任何用户态的自定义响应式容器（customRef 只是其中一种）都做不出来。

这与《依赖注入 API 设计讨论》的结论同构——当时否掉用户态 provide/consume 的理由之一，就是「需要全局版本 tick + 粗粒度失效」。**同一机制在第二处出现，说明它可能是 kiaao 目前这类需求的自然解法。**

### 4.3 如果将来真需要 tick（不在本实验范围）

只有当「状态不是信号」（普通闭包变量 / class 私有字段）时才需要。届时的最小形态：

| 方案           | 做法                                                    | 代价                     |
| :------------- | :------------------------------------------------------ | :----------------------- |
| A. 手搓信号    | 抄 core 传播逻辑（§4.2）                                | 抄私有代码、易漂、丢守卫 |
| B. 改回信号    | 把状态挪回信号（即本实验的形态）                        | ——                       |
| C. 粗粒度 tick | `const tick = use(0)`；帧末 `tick(tick() + 1)` 驱动重算 | 每帧全量重算派生         |

**本实验不采用其中任何一个**，因为不需要。**待 demo 跑起来后再回头讨论**：要不要把传播原语暴露出去。现在讨论 API 形状是空谈。

## 五、实测记录（动手前已完成的探针）

以下探针跑完后均已删除，未进入工作树。

### 5.1 闭包信号 + 外部对象写入 + 派生订阅 ✅ 通知链成立

```
初始: t1 = 0px   t2 = 100px
一帧后: t1 = 10px  t2 = 110px
两帧后: t1 = 20px  t2 = 120px
两个实体信号是否独立: true
池大小: 2
```

同一组件函数被调用 3 次 → 3 个独立信号。`Each` 展开的行为与之一致。

**意义**：§2.3 的疑虑解除；**§4.1 的结论成立——不需要 tick 桥**。

### 5.2 写入次数对传播的影响

```
--- 分 3 次写（每字段一次）---
posX 重算次数: 4            （初始 1 + 3 次写入）
--- 1 次写（一次带上全部变更）---
posX 重算次数增量: 1
--- 同值写入（等价性守卫）---
posX 重算次数增量: 1
```

两级派生（`state → posX → label`）：

```
初始: 0px | 一级重算: 1 二级重算: 1
3 次写后: 1px | 一级重算: 4 二级重算: 2
→ 一级被通知了 3 次，真正传到 DOM 层的只有 1 次
```

**意义**：§3.2 的结论——成本在派生重算，DOM 写入被等价性守卫截断。

### 5.3 手工对象能否被 `use` 接受 ✅ 成立

```
isUse(手工对象) = true
use(fake) 原样返回 = true
初始派生值 = 20  计算次数 = 1
改 raw 后派生的 subs 数量 = 1
派生值（应仍为 20 若无通知）= 20
```

**意义**：可被订阅，但**值改后不会传播**（最后一行证明）。§4.2 的结论。

### 5.4 抄 core 传播逻辑能否跑通 ⚠️ 能，但有代价

```
初始: 值:20 派生计算次数: 1
写 50 后: 值:100 订阅者数: 1
重复写 50: 值:100 计算次数（应不变）: 3     ← core 版本不会重算
写 51 后: 值:102 计算次数: 4
```

**意义**：§4.2 的代价记录。

### 5.5 实现过程中实测到的三个真 bug（最有价值的数据）

以下都是**写完跑起来才发现的**，纯逻辑推理没有推出来。记录在此，因为「会踩什么坑」比「省多少行」有用得多。

#### ① 键名不匹配导致瞬移（测试逮到）

`randomGoal()` 原本返回 `{ x, y }`，被 `wander` 里 `...goal` 展开时**直接覆盖了状态的 `x`/`y`**——NPC 直接瞬移到随机点（实测从 (100,100) 跳到 (736,318)）。

修法：让 `randomGoal()` 返回 `{ goalX, goalY }`，**键名与状态字段对齐**，从根上消除这类错误。

**这暴露了 actor 方案的一个特点**：状态字段直接就是对象键，没有「切片声明」那一层保护。ECS 版的切片合并虽然繁琐，但字段名不匹配会在类型层报错。

#### ② 恐慌震荡锁死（实测 500 帧移动 1px）

早期版本每帧重新取「当前最近威胁」作为逃离参照点。当 NPC 被两个威胁（尸体 + 另一个恐慌者）夹在中间时，**逃离方向来回抵消，人原地卡死、恐慌永不到期**。

```
帧50:  moyLeft=5.18 位置=(100.0,41.2)
帧250: moodLeft=1.98 位置=(100.0,0.0)   ← 卡在边界
帧350: moodLeft=0.38 位置=(100.0,0.0)   ← 一直没动
```

修法：**参照点粘滞**——进入恐慌时定下 `fleeFrom`，之后不再重选。语义上也更对：人跑开的是「吓到他的那个东西」，不是每帧重新评估的最近危险。

**这与 saboteur 那三个「全体停滞」bug 是同一类**（跨实体循环依赖 + 无粘滞状态），说明这类问题**与数据模型无关**。

#### ③ 恐慌周期性复发（最严重，且**降级为设计缺口而非 bug**）

尸体永久存在 + 恐慌者也可以传染 → 恐慌会反复烧起来。

**最初我把它当成了「不收敛」bug，试了多种参数。后来发现判断标准错了：**

| 尝试                       | 结果                      | 结论                  |
| :------------------------- | :------------------------ | :-------------------- |
| 现状（`reacted` 按源去重） | 5 次运行 3 次「不收敛」   | ↓                     |
| 仅尸体传染（不链式）       | 峰值只 3，失去链式传播    | ✗ 丢了卖点            |
| + 冷却期                   | 变成周期爆发（0→19→0→19） | ✗ 未解决              |
| 去重 + 沿途累积            | 「30/30 收敛，中位 8 秒」 | ⚠️ **这个结论是错的** |

**为什么「30/30 收敛」是错的结论**：收敛判据是「连续 1 秒无恐慌者」。但那只是**局部静默**——之后又烧起来。把模拟延长到 120 秒采样，真相是：

```
每5秒: 0s:0 5s:19 10s:0 15s:0 20s:18 25s:19 30s:0 … 50s:19 … 85s:16 … 105s:2
```

即 **0→19→0→18→0→19 的周期振荡**，不是单向收敛。

**机制**：`reacted` 是**每个 NPC 各自**的清单。A 反应过尸体后，仍会因「看到 B 恐慌」而再次恐慌——它从没反应过 **B**。所以恐慌会在**新配对上反复复发**，直到所有 `(观察者, 源)` 配对耗尽。理论上有界（20×20），但耗尽很慢。

**为什么这是设计缺口而非 bug**：demo 里尸体永不消失，NPC 会不断闲游走进它的视野——现实中「一具尸体被反复发现」本来就会反复引起恐慌。真正缺的是**「事情已经过去了」的机制**（比如尸体被发现后有人报警、或恐慌者离场）。

**因此没有「修复」它**——停下来是正确的。加了冷却、尸体时效、或全局限次都是掩盖，而且会削弱「群众会互相传染」这个要观察的东西。

**修正后的断言**（`render.test.ts`）：不断言「最终全不红」（那不是现状），而断言**级联会落下去**（不存在只涨不跌的单向累积）：

```ts
let peak = 0, fellAfterPeak = false;
for (…) {
  const n = 恐慌数;
  peak = Math.max(peak, n);
  if (peak >= 10 && n <= 1) fellAfterPeak = true;
}
expect(peak).toBeGreaterThan(0);
expect(fellAfterPeak).toBe(true);
```

**另一处与 saboteur 的对照**：saboteur 的 `accounted` 集为什么不会无限复发？因为它同时有**终局条件**（杀满 2 人即胜）——游戏在复发之前就结束了。demo 没有终局，所以复发变得可见。

**这一条的真正教训**：我最初用了一个**太松的收敛判据**（连续 1 秒静默），于是把一个没解决的问题误记为「已解决」。**度量方式错了，结论就错了。** 这与先前那次「预测 dead 降到 1 处、实际 12→11」是同一类错误。

### 5.6 收敛性测量（修正后的度量）

**原度量（已作废）**：连续 1 秒无恐慌者 → 「30/30 收敛，中位 8 秒」。这是局部静默，不是收敛。

**修正后的度量**：采样 120 秒，观察是否**周期性复发**：

```
固定种子(1)：0s:0 5s:19 10s:0 15s:0 20s:18 25s:19 30s:0 … 50s:19 … 85s:16
```

**结论：恐慌不收敛，而是周期振荡。** 这是设计缺口的直接体现（无终局条件 + 尸体永存）。

测试因此断言**可稳定成立的性质**（级联峰值存在 + 会落下去），而非「最终全不红」。固定种子后连跑 20 次全通过。

## 六、Demo 范围

### 6.1 必须包含（否则测不出模型特征）

1. **闭包持有状态** —— `const state = use({ x, y, hp, mood })`
2. **池里放方法对象** —— `useGame({ add, update })`
3. **渲染从闭包状态订阅** —— `use(state, () => ...)`
4. **行为切换** —— `mood: "wander" | "flee"`（**这是重点**）

第 4 点不可省：本实验真正要回答的是「**一个 NPC 的完整生命史能否写在一个组件里**」。只有位移测不出这个。

### 6.2 明确不做

- 不复用 `saboteur/` 的任何代码（包括 `world/`）
- 不引入关卡、寻路、视线——需要空间关系时用最朴素的写法（欧氏距离即可）
- 不做美术（色块即可）
- 不改 kiaao core

### 6.3 目录（已实现）

```
packages/example/src/worlds/crowd/
├── docs/
│   └── actor 模型实验：闭包状态 + 对象池.md   ← 本文
├── index.tsx        # 75 行  App：Each 出 20 个 Npc（5×4 网格）
├── npc.tsx          # 104 行 Npc 组件：状态 + 注册 + 渲染订阅
├── behaviour.ts     # 254 行 纯逻辑：行为规则（零 kiaao / 零 DOM）
├── use-game.ts      # 110 行 引擎：帧循环 + 对象池 + useGame
└── __tests__/
    ├── behaviour.test.ts   # 276 行 / 32 例  纯逻辑
    └── render.test.ts      # 226 行 / 9 例   端到端
```

**命名说明**：`crowd`（人群）而非 `actors`。理由：`actors` 在游戏语境里指向 Unreal 的 `AActor`、在并发语境里指向 Actor 模型，而本实验与两者都无关；`crowd` 直接描述 demo 里的东西（会互相影响的一群 NPC），也让路由 `/crowd` 自解释。

并在 `packages/example/src/router.tsx` 与 `worlds/index.tsx` 注册路由与卡片。

### 6.4 实现时的一处偏离（重要）

§6.3 原计划把行为规则写在 `npc.tsx` 里（因为「一个文件读完」是这个方案的主张）。**实际拆出了 `behaviour.ts`**，理由与 saboteur 拆 `world/` 完全一样：

- 纯逻辑才能被独立测试——`behaviour.test.ts` 的 32 例**完全不碰 kiaao**，不需要渲染组件、不需要跑帧循环
- 对照 ECS 版：行为测试要构造 frame 管理器、注册切片、跑系统

**这个偏离不影响方案主张**——`behaviour.ts` 是**对所有 NPC 共享**的纯函数，不是「每个 NPC 散在那里的状态」。一个 NPC 的**状态**（它长什么样、当前什么心情）仍全在 `npc.tsx`。而且拆出后，加新 NPC 类型确实只需写一个组件。

**教训**：「一个 NPC 能在一个文件里读完」不应与「所有逻辑必须在一个文件里」混淆。纯逻辑与状态归属是两回事。

## 七、实现记录（2026-09-30）

**总结：demo 已可运行，41 例测试通过，构建通过。手感受判待定。**

| 项             | 结果                                          |
| :------------- | :-------------------------------------------- |
| 文件           | 4 源文件 + 2 测试文件 + 1 文档                |
| 源码行数       | 543（含引擎 110 行）                          |
| 测试行数       | 502（41 例）                                  |
| 测试通过       | 41/41（固定种子后连跑 20 次稳定）             |
| 全仓测试       | 66 文件 / 794 通过                            |
| 构建           | ✅ `crowd` chunk 3.92 kB                      |
| `tsc --noEmit` | ✅ 无错误                                     |
| 恐慌行为       | ⚠️ **周期振荡**（非收敛）——设计缺口，见 §5.5③ |

**引擎的最终形态**（`use-game.ts`，110 行）：

- 池：`Set<Actor>`，只存对象引用（**连 `id` 都不需要**，对比 ECS 版的 `Map<EntityId, Signal>` + `Symbol` id）
- `Actor = { info: () => PeerInfo; update?: (dt, source) => void }`
- 帧循环：帧首快照 `peers`（§3.1 的关键修正）、`dt` 上限 50ms、池空自停
- `useGame(ctx, actor)`：`onMount` 进池 + 启动 / `onUnmount` 出池 + 池空即停

**对比 ECS 版引擎（260 行含系统库）的三处简化**：

1. 无帧管理器（`frame` / `flush` / 写时拷贝）——对象直接写自己的信号
2. 无切片合并（`useEntity` 的 `Object.assign` 循环）——状态由组件给出
3. 无 `id` 与 `EntitySignal`——直接存对象，`info.id` 自报家门

**但有两处代价**：

1. **帧首快照是手动写的**。ECS 版里这件事由 `frame/flush` 结构保证，actor 版里靠开发者记得加。忘了加就是一个隐蔽的时序 bug（§3.1）。
2. **无终局条件的系统会暴露复发**。saboteur 的恐慌能「自然结束」部分因为游戏很快结束（杀满 2 人即胜）；demo 没有终局，恐慌的各种周期振荡就暴露出来了（§5.5③）。

## 九、验收方式

本实验的结论**不是**「哪套行数少」，而是：

1. **手感判断**（主、尚未完成）：作者读完/写完 actor 版后，是否更愿意在这个模型上继续做内容
2. **§3 的四个问题是否实际发生**：✅ P3 实际发生且很严重（§3.1）；§3.3 也暴露了（键名 bug）
3. **事后对照预测**：✅ 4/6（§8.2）

**最终检验（可选，最有力）**：拿一个**两边都没有的新功能**（例如「NPC 恐慌时可以躲进柜子，躲进去就不再被抓」），在两套实现里各写一遍。这对两边都是新需求，**完全抵消第二遍效应**。

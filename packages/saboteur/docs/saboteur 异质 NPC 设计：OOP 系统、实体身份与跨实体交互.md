## 一、目标：异质 NPC 是主体，不是边角

现状（M0–M7 的垂直切片）里 NPC 是同质的：6 个客人共用一套行为，只有 `role: "player" | "guest"` 两个取值，`npcSpawns` 是无差别的 `SpawnPoint[]`。

**最终预期与之相反**：NPC 之间的区别会很大，每个 NPC 可能有相当深度的独立内容。已经出现的具体例子：

| 例子                                   | 需要处理别的实体吗 | 形态          |
| :------------------------------------- | :----------------- | :------------ |
| 有的 NPC 会**观察**（盯梢、记录）      | 是                 | 感知 + 记忆   |
| 有的 NPC 之间**缔结关系**              | 是                 | 配对 + 关系图 |
| 有的是**有安全感的性格**               | **否**             | 阈值参数      |
| 一起来 party 的会**联系、不定时碰头**  | 是                 | 意图 + 协调   |
| 保安有**无线通讯**，无需碰头即同步发现 | 是                 | 信道          |

这个预期的直接后果：**「OOP 作为系统」从可选变成必需**——同质实体用 ECS 组织，异质实体各自的内容需要「定义在一处」的载体。

但四个例子里**三个要看别人**（观察、关系、碰头）。这决定了本文不能只讲 OOP 系统：**跨实体交互才是深度的主战场**（§六）。

## 二、判据：不是「特殊吗」，而是「特殊在哪一轴」

「普通 NPC」与「特殊 NPC」的分界是模糊的。用单一刻度判断会一直含糊；改问「**特殊在哪一轴**」则每条轴都可操作。

| 差异形态 | 例子                           | 载体          | 复用方式               |
| :------- | :----------------------------- | :------------ | :--------------------- |
| **参数** | 安全感（恐慌阈值）、视距、速度 | 实体字段      | 同一系统读不同的数     |
| **参与** | 有人有关系、有人没有           | `enters` 列表 | 同一系统，池里有或没有 |
| **机制** | 缔结关系、定时碰头、无线电     | 系统          | 一个机制一个系统       |
| **时序** | 卧底在特定时刻做特定事         | 状态对象      | 见 §五                 |

前三条**不需要新机制**——`enters` 列表（哪些 `enter` 参与）与 `updates` 数组（系统有哪些、什么顺序）已经是全部的选择权。

**修正一处早期判据**：`define 改造.md` §8.3 写的是

> 判据：**要不要看别的实体**。不看 → state 方法；看 → 系统。

这条**过严了**（见 §三末尾）：给了查找入口之后，方法也能看别人。它仍然是有用的**起点**，但不再是硬边界。

## 三、OOP 系统：形态与边界

### 3.1 它是模块，不是内核原语

结论（2026-10-02 讨论）：

> **核心不支持任何一个范式，因此支持两个。**

`saboteur` 与 breakout 的引擎内核只有三件事：**系统 + 实体池 + 帧循环**。`createGame` 只认识 `Update<T>`，不需要知道「actor」是什么。

「OOP 作为系统」的正确落法：**当作普通系统挂进 `updates` 数组**，位置与数量由使用者决定。

```ts
createGame([
  movement.update,
  collision.update,
  oop.update, // ← 位置由你定，这就是异质逻辑的控制点
  rules.update,
]);
```

**改进来自「它在流水线上」，不来自「它叫 OOP」**——crowd 实验里把所有逻辑塞进一个 `update`，导致「移动 vs 感知」的先后无从控制。系统化的收益首先是**顺序可控**。

### 3.2 载体：方法与名字映射（详见能力文档）

两条引擎能力已经实测可用，**不需要任何新 API**：

**① `state` 上可以放方法**——闭包捕获 `state` 自己，不需要 `frame` / `id`：

```ts
const state = {
  x: 0,
  hp: 3,
  isLive: true,
  kill() {
    state.isLive = false; // ← 闭包捕获 state 自己
  },
};
const entity = define(ctx, movement.enter)(state);
```

**② `enter` 里可以建「名字 → id」映射**——`: `ctx.onMount`/`onUnmount` 维护一张表，供跨实体查找。

实测证据与完整边界（含「方法会被 `flush` 拷进渲染信号」、「`state.id` 不可用」）见 `docs/game/Kiaao 游戏实体：深状态与异质实体的能力边界.md` §2.1、§2.2、§3.4。

> **订正**：早期讨论里我说过「`frame` 每帧新建，所以方法签名会和系统签名一样长，`this` 不值钱」。**这个论据是错的**——方法本来就不需要 `frame`。当时的结论（`this` 可有可无）恰好对，理由是错的。

### 3.3 边界：方法只能拥有「没有系统认领的字段」

`movement.update` 遍历 `movePool` 写 `e.x += e.vx * dt`。如果 `state` 上也有 `move()` 写同一个 `x`——**两个主人**。

这不是 bug，是 OOP 系统的核心代价：

> **方法只能拥有「没有系统认领的字段」。**

所以异质化之前必须先划清：哪些字段是几何的（系统共享），哪些是私有的（只有它自己关心）。

## 四、实体身份：两种名字，两张表

### 4.1 问题

`EntityId` 是 `Symbol`——对机器友好，对人类不可读。要做「去找 alice 碰头」这类玩法，需要**稳定的人类可读标识**。

项目里已有先例：breakout 的 `dataId`（球关联实体目录数组项，规则系统按它过滤数组，**免掉一张 `id → 数组项` 的映射表**）。本节是同一招的延伸。

### 4.2 命名方案：`enter` 建映射（实测可行）

```ts
// OOP 系统内
const byName = new Map<string, EntityId>();

const enter: Enter<Named> = (id, ctx, state) => {
  ctx.onMount(() => byName.set(state.name, id));
  ctx.onUnmount(() => byName.delete(state.name));
};
```

实测：两个 NPC 通过名字互相找到对方、成功跨实体写入——

```text
byName 映射: bob,alice
alice.greeted: true | bob.greeted: true
```

**时序前提已实测**：实体在挂载期全部入池，第一帧就能看到彼此（不是「逐个挂载、边挂边跑」）。所以「A 在第一帧找 B」是安全的。

### 4.3 名字有两种性质，必须分开

| 名字       | 指称   | 唯一性       | 例子             | 载体                         |
| :--------- | :----- | :----------- | :--------------- | :--------------------------- |
| **实体名** | 某一个 | **必须唯一** | `alice`、`bob`   | `Map<string, EntityId>`      |
| **类型名** | 某一类 | 天然多值     | `guest`、`guard` | `Map<string, Set<EntityId>>` |

现状代码里的 `role: "guest"` 是**类型名**（6 个客人共用），而「去找 alice」用的是**实体名**——**两种都存在，现在只有前者**。

> **两种表各司其职，不是「二选一」**。需要唯一的地方用 `Map`，需要多值的地方用 `Map<string, Set>`。

### 4.4 同名会静默覆盖（实测，需定规则）

```text
两个同名 guest，映射里剩: 1 个
映射指向 = Symbol()
← a 被 b 覆盖了？ true
```

`Map.set` 是覆盖语义，**不报错，只表现为「有时找不到人」**。

因为实体名**必须唯一**（指名道姓是它的用途），建议：**`enter` 时检测重复并报错**。这要求在关卡数据层就能表达不同的实体名（见 §九 Q1）。

## 五、状态对象：按 NPC 类型换一整套

### 5.1 现状与目标

现在 `states.ts` 是**一套全局共享**的状态对象，靠 `mood` 字段切换：

```ts
export type Mood = "wander" | "linger" | "panic";   // 全局枚举
export function createStates(random): Record<Mood, ActorState> { ... }
// 使用：states[self.mood].update(ctx, delta)
```

**目标（已定）：按 NPC 类型换一整套状态集**，而非把全局枚举加长。

```ts
guest: {
  (wander, linger, panic);
}
guard: {
  (patrol, chase, panic);
}
```

### 5.2 类型代价（实测三种写法）

| 写法                              | 拼错状态名      | 语义错配（保镖用 `wander`） |
| :-------------------------------- | :-------------- | :-------------------------- |
| `mood: string`                    | ❌ 运行时才发现 | ❌ 运行时才发现             |
| `mood: 全局联合`                  | ✅ 编译期报错   | ❌ 运行时才发现             |
| `mood` 按 `kind` 收窄（判别联合） | ✅              | ✅                          |

实测输出：

```text
合法: ok
拼错: runtime miss: guest.wandr
语义不匹配（guard 用 wander）: runtime miss: guard.wander
```

**判别联合最严，但代价是 `ActorEntity` 从「一个类型」变成「一个判别联合」**——而它现在被 `playerEntity` / `listActors()` 当共享类型用。这个代价是否值得，已定（§8.3）：不改。

### 5.3 与 §三的关系

状态对象与 OOP 方法**不冲突，是两层**：

- **状态对象**：有时序的、可切换的行为段（`enter` / `update` / 时长）
- **方法**：无时序的、随时可调的动作（`kill()`）

「被吓到后逃跑」是前者（有时间线）；「杀了他」是后者（瞬时）。

## 六、自有记忆：信息来源可组合

### 6.1 本意（一次被写偏的地方）

初稿把这里写成「真相 / 认知 / 信道」三层，并声称 `alarm` 是「全知」的。**两处都错**：

```ts
// alarm.ts —— 读 dead 之前已经用 visibleIds 过滤过
for (const targetId of observer.visibleIds) {   // ← 只在「看得见」的集合里遍历
  const target = frame(targetId);
  if (!isAbnormal(target)) continue;
```

`alarm` **从来没有全知**——「知道」的前置就是「看见」，而这已经是想要的语义。（把「读真相字段」与「全知」混为一谈了。）

而且地形与视野**本来就在游戏里**（`world/grid` 的 `opaque` + `perception` 的视锥与射线遮挡），不需要另造一层。

### 6.2 真正的命题

用户的本意是一个**具体的信息结构**，不是抽象分层：

> **A 去找 B，在到达之前不知道 B 死了。**

拆开来看，关键问题不是「怎么知道那是尸体」，而是：

**A 凭什么去某个地方找 B？**

| 情形         | 依据                                   |
| :----------- | :------------------------------------- |
| 刚分开       | 记得刚才在哪                           |
| 分开很久     | 记得**最后见到**的地方（可能已经过时） |
| 从没一起过   | 无从找起（除非有别的信息源）           |
| 保安有无线电 | **不需要找**，直接问                   |

所以缺的能力是：**「最后见到某人在哪」这类自有记忆**。

`fleeFrom` 就是它的同构物——`fleeFrom` 是「我最后看见**威胁**的地方」，存的是一个**当时的位置**而非实时坐标：

```ts
// alarm.ts —— 记的是「我在哪看见的」，不是威胁的当前位置
self.fleeFrom = threat;
```

恐慌者冲向「记忆中的危险点」的反方向，**即使威胁早就走了**。机制已经是对的。

### 6.3 信息来源可组合（这是「深度」的来源）

用户的原话：

> 这些可能性都会有……不同 NPC 可能会有某个或者某几个可能性。

**所以不该为「哪种」设计机制，而应把信息来源做成可组合的积木**：

| 来源       | 含义                           | 现状                                  |
| :--------- | :----------------------------- | :------------------------------------ |
| **看见**   | 视锥内直接得知（受地形遮挡）   | ✅ `perception.visibleIds` 已有       |
| **被告知** | 不经过看见（无线电、口头传话） | ❌ 无。需自建                         |
| **推断**   | 到点没等到 → 推出可能出事      | ❌ 无。但**可能不需要新机制**（见下） |

**「推断」的两种形态差别很大**，需先定：

- **纯本地**：A 有「约会记录 + 计时」，到点没等到就自己判 → **用已有状态对象就能表达**
- **全局**：「警察宣布死亡」才作数（全城广播）→ 需要一个**全局事件源**

### 6.4 存哪：自有数据（已定）

用户的取向：**属于 NPC 实例的自有数据**。

但要注意引擎侧的后果（见 `docs/game/Kiaao 游戏实体：深状态与异质实体的能力边界.md`）：

- 记忆表是**嵌套容器** → 一旦放进实体，就踩上「嵌套就地改」的坑
- 当前能「工作」是因为引擎每帧无条件提交（那个文件 §3.3）；**两者的耦合是个陷阱**

对照：`alarm` 的 `accounted`（「我对谁反应过」）住在**系统闭包**里，不进实体、不进 flush、不被渲染——所以它没有这个问题。**它是纯机制内部的状态，不是 NPC 的知识**。

### 6.5 同步 vs 异步

「发起意图」有两种形态：

|            | 同步（`find` + 直接改）      | 异步（发起意图 + 投递）            |
| :--------- | :--------------------------- | :--------------------------------- |
| 时机       | 本帧立即生效                 | 下帧或更晚                         |
| 需要系统吗 | 不需要                       | **需要**（有人负责投递）           |
| 适合       | 「我现在确认你在不在」       | 「我想约你，但你未必在/同意」      |
| 风险       | 绕过「每个字段一个写者」纪律 | 意图需有人收拾（过期、拒绝、重复） |

**用户的取向：两者都保留，按需取用**。理由正是 §6.3 的组合性——不同 NPC 会用不同的那种。

用户对「碰头」的补充：**不能在发起意图的同时就知道是否成立**，而且**对方已死也要考虑进去**。这两条都指向异步。

## 七、关卡与类型绑定：两个待评估的设想

本节记下用户提出的两个想法。它们**互相配对**：第二个解开了第一个的僵局。
**状态：记录，不做**——待第二个 NPC 类型出现后再评估。

### 7.1 设想一：地图只标记位置，类型在实例创建时绑定

**内容**：地图上的符号只是「这里有个出生点」（如 `1` `2` `3`），转换时**不知道**它们是什么；实例创建时自行选择用哪个位置。

与「地图符号扩表」（`G`=保镖、`C`=厨师）的差别只有一处：

> **类型信息写在哪** —— 代码里（本设想） vs 地图里（扩表）。

**这个设想指出了一个真问题**（比“地图复用”更根本）：**符号表是一个封闭词汇表，而「每个 NPC 都独特」意味着类型会持续增加**——词汇表会一直膨胀。而且它会把 game 概念漏进 `world` 层。

### 7.2 现状已经承认「关卡 ≠ 地图」

```ts
export type LevelDef = {
  name: string;
  rows: string[]; // ← 地图
  objective: Objective; // ← 不是地图：killGoal / timeLimit
};
```

`objective` **已经是「关卡的逻辑与数据」**——它在地图之外。所以「关卡 = 地图」从来就不成立，只是现在**只写了两个字段**。

### 7.3 设想二：关卡应当包含逻辑与数据（不只地图）

**用户的原话**：关卡其实并不意味着只有地图，也许还要有一些对应的逻辑和数据。

这**解开了 §7.1 的僵局**。之前卡在「位置与类型的绑定放在哪」，三个选项都有问题：

| 绑定处                       | 问题                                                       |
| :--------------------------- | :--------------------------------------------------------- |
| 地图符号（扩表）             | 词汇表膨胀；game 概念漏进 world                            |
| 代码（实例自己挑位置）       | 谁挑哪个？→ 需要一份声明 → 双数据源                        |
| 地图之外的**独立文件**声明   | 坐标与地图可能不一致（`parse.ts` 反对的就是它）            |
| **写在同一份 `LevelDef` 里** | ← 它与地图**同处一个数据源**，所以「双数据源」的反对不成立 |

关键是：`parse.ts` 反对的是「地图一个文件、坐标声明另一个文件」：

> 出生点不在此声明——它们内嵌在 ASCII 图中。**单一数据源，避免地图与坐标声明不一致。**

但若两者**同属一份 `LevelDef`**，就仍是单一数据源：

```ts
export const manor: LevelDef = {
  rows: [...],                  // 地图（位置）
  objective: { ... },           // 目标
  roster: [                     // ← 关卡自己的阵容（类型绑定）
    { slot: 0, kind: "guard" },
  ],
};
```

### 7.4 两个真问题（未解）

**① `world` 层的类型污染取捨**

`world/levels/types.ts` 现在不知道任何 game 概念（除了已经在漏的 `PropKind = "booze"`）。若 `LevelDef` 要写 `kind: "guard"`：

- 要么 `world` 认识 `"guard"` → game 概念漏进 world
- 要么 `kind` 是 `string` → 丢掉类型检查

**已有先例可循**（`SpawnFacing` 的处理方式）：

```ts
// world/levels/types.ts —— 注释自己就是先例
/** 此处用宽松的 `string`——`world/` 不依赖 `game/`（分层单向），
 *  实际取值由 `SPAWN_SYMBOLS` 限定。 */
```

即：`world` 层用 `string`，**类型检查放在 game 层**（NPC 类型表负责校验 kind 在不在表里）。

**② 「关卡逻辑」是数据还是行为（取 B：插件）**

用户已确认是 **B（插件）**，不是 A（更多声明式字段）：关卡可以带自己的系统/行为。

**但这意味着 `LevelDef` 从「纯数据」变成「模块」**：

- 纯数据（`{ killGoal: 2 }`）→ `world` 层能装
- 带行为（`onTick() {…}`）→ 会依赖系统、`frame`、其它系统……

**这个跳跃的具体形态未谈，待后续讨论。** 本文不编结构。

### 7.5 一个可立即验证的小问题（不需等第二个 NPC 类型）

上面的「world 层承载 game 概念」，**现在已经有一处实例**：

```ts
// world/levels/types.ts
export type PropKind = "booze";

// game/types.ts —— 注释自己就承认了这是重复
// 与 world/levels/types.ts 的 `PropKind` 取值一致，但**不是同一个类型**：
export type ItemKind = "booze";
```

**两处靠注释约定同步，没有编译期联系，也没有测试。** 加一个道具要改两处，忘一处不报错。

它与用户的设想是**同一个病**（`world` 层承载 game 概念），但：

- 它**已存在**（不是假设的）
- **现在就能修**，不需等第二个 NPC 类型
- 修它的经验会直接告诉后来人：扩表到底会不会让 `world` 层腐烂

## 八、实施记录

两部分：**S1–S3**（异质 NPC 的类型与状态集，2026-10-02）与
**私有数据与方法实验**（2026-10-08，§8.6–8.7）。

### 8.1 S1–S3 分步的理由

预设了三步，且**顺序是有意的**：

| 步  | 内容                                   | 目的                               |
| :-- | :------------------------------------- | :--------------------------------- |
| S1  | 地图能表达类型，保镖「同行为、异数值」 | 先验证「类型能传进来」，单一变量   |
| S2  | 保镖持有自己的状态集                   | 再验证「行为真正分化」             |
| S3  | 收口：量重复，回答 Q6                  | 最后才谈结构，因为此时才看得到重复 |

一上来就同时改两件事，失败时分不清是出生表达还是状态集的问题。

### 8.2 S1：类型从地图传进来

**改动**：`SpawnKind`（`player | guest | guard`）+ `SpawnSpec`；`SPAWN_SYMBOLS` 的值由「朝向」改为「类型与朝向」；`SpawnPoint` 加 `kind`；新增符号 `G`。

**S1 当场暴露了 §7.5 记的那个病**：加一个 `guard`，`Role` 与 `SpawnKind` 就必须同步——而两边各写一份、靠注释约定。

修法：`Role = SpawnKind`。`game` → `world` 是允许的单向依赖（分层规则只禁 `world` → `game`），所以直接引用比重复声明好。**§7.5 记的病，在这一处治好了**（`ItemKind` / `PropKind` 那处仍未治）。

**另一个当场暴露的问题**：代码里把「不是玩家」写成了「是客人」（`role === "guest"`）——两种角色时二者等价，加 `guard` 后立刻坏掉（保镖出生了却站着不动，实测 `path=0 goal=无`）。新增 `isNpc(role)` 显式表达。

### 8.3 S2：保镖持有自己的状态集

**结构**：

```ts
type RoleStateSet = {
  entry: Mood;                                  // 默认状态
  states: Partial<Record<Mood, ActorState>>;    // 只拥有一部分
};
createStates(random): Record<NpcRole, RoleStateSet>
// guest: { entry: "wander", states: { wander, linger, panic } }
// guard: { entry: "patrol", states: { patrol, panic } }
```

两个设计点：

- **`entry` 显式声明**，不用「取第一个键」——后者依赖字面量书写顺序，重构时极易静默改变行为
- **`states` 是 `Partial`**——每种 NPC 只拥有一部分状态，这正是 S2 的目的

**最容易错的一步**：`panic` 是**共享状态**（两类型都有），但消退后的归宿因 NPC 而异。原来写死 `transition("wander")`——保镖没有该状态，而 `transition` 对不存在的状态是「静默忽略」，于是会无声卡死。改为 `transition(entryMoodOf(role))`。

> 这类 bug 不报错、只表现为卡死。已补端到端用例（含「全程不得出现 `wander`」断言）。

**`mood` 未改成判别联合**（Q2）：核对发现它全库**只有一个消费点**（`states[mood]` 查表），是**数据不是类型**。判别联合会把 `ActorEntity` 拆碎，而它被 `playerEntity` / `listActors()` 当共享类型用。代价大于收益。

### 8.4 S3：收口——量完之后，结论比预期窄

先量了「一种 NPC 的知识散在几处」：

| #   | 知识     | 位置                    | 加第 3 种类型要改？    |
| :-- | :------- | :---------------------- | :--------------------- |
| 1   | 类型符号 | `world/levels/types.ts` | 加一个符号（必要）     |
| 2   | 数值     | `ACTOR_TRAITS`          | 加一行（表，可接受）   |
| 3   | 岗位规则 | `postFor`               | 条件判断，不易增长     |
| 4   | 参与系统 | `isNpc`                 | 按「是否 NPC」，不增长 |
| 5   | 状态集   | `sets`                  | 加一组（表，可接受）   |
| 6   | 意图来源 | `setIntent`             | ⚠️ **先发现白白重复**  |
| 7   | 样式     | `actor.module.scss`     | 加一个类（表，可接受） |

**Q6 原本担心的是「60 个匿名 `ActorState`」——实测没那么糟**：状态集是**一份表**，不是散落的。

**但发现一处真浪费**（第 6 项）：

```ts
locomotion.setIntent("guest", (e) => pathIntent(e));
locomotion.setIntent("guard", (e) => pathIntent(e)); // 逐字相同
```

每加一种 NPC 就要再加一行一模一样的。根因是**语义放错了层**：意图来源不是「角色的属性」，而是「**驱动方式**的属性」——只有两种（玩家读输入 / NPC 读路径），与 NPC 类型无关。改为 `setIntent("player" | "npc", …)`，新增 NPC 类型不再需要改这里。

**另清掉两处死重量**：

- `patrol` 每帧递减 `moodLeft` 并重掷，但**从不基于它切换状态**（`wander` 才会切 `linger`）。写就要进帧末提交——纯开销。
- 连带的病根是 `duration` 是必填字段，于是 `patrol` 只能写 `{ min: 8, max: 8 }`（用区间表达固定值本就含糊）。改为 `duration?:`（可选）。

**顺手把 `isNpc` 改为类型守卫**（`role is NpcRole`）：原来返回 `boolean`，调用处要写 `role as NpcRole` 抹掉类型信息。

### 8.5 一个由 S3 暴露的测试脆弱

「保镖恐慌消退后回到 patrol」原来断言「第 2500 帧时 `mood === patrol`」。它**一直通过**，但断言的是**时机**而非**契约**：恐慌会传播，保镖可能被另一个恐慌者再次传染（诊断实测迁移序列：`patrol→panic→patrol→panic`）。

去掉 `patrol` 的 `random()` 调用后随机序列改变，NPC 路线随之变化，这个脆弱断言才暴露出来。

改为断言**契约**：迁移序列含 `["panic", "patrol"]`，且全程无 `wander`。

### 8.6 实验：私有数据与方法（2026-10-08）

起因：讨论「能否把很多 sys 变成 oop 中的内部行为」。先量了系统形态（见 §8.7），
再做了一个 119 行的最小实验验证「方法能不能真的用起来」。

**结论：通了，而且成本比预估低。**

| 项              | 实测                                         |
| :-------------- | :------------------------------------------- |
| oopsys 本体     | **51 行**，`update` 只有 5 行有效代码        |
| 私有数据 + 方法 | 68 行（`npcs/guard.ts`）                     |
| 现有文件改动    | **+16 行**（挂进流水线 + 按 role 装配）      |
| 新机制          | **零**——与 `movement` / `collision` 完全同形 |

**验证了本文件 §3.2 的 sketch（方法闭包捕获 `state`，不用 `frame` / `id` / `this`）**：

```ts
state.onFrame = () => {
  for (const id of state.visibleIds) {
    // 读自己的字段
    state.seen.set(id, frameCount); // 写自己的记忆
  }
};
```

实测：两个保镖各记各的（`seen.size` 3 vs 4，是两个不同的 `Map` 实例），
客人 / 玩家身上没有 `seen`。

**两点认识**：

**① 必须用交叉类型，不能改 `ActorEntity`**

实测 `const state: ActorEntity = { seen: … }` 报 excess property。而：

```ts
type GuardEntity = ActorEntity & { seen: Map<…>; onFrame: () => void };
```

可行。**这是好事**：私有字段天然不污染共享类型——§5.2 那个「21 字段膨胀」
的教训被结构性避免了。

**② 一个未解决的代价**

`seen` 是嵌套容器（`Map`），依赖引擎「每帧全量提交」兜底（能力文档 §3.3
记的那个耦合陷阱）。**若将来做选择性提交，`seen.set()` 可能不再被检测到。**
本实验没有解决它，只在代码里写明了。

### 8.7 实测：五个系统各自能否变成方法

实验前先量了系统形态（决定不要「搬系统」）：

| 系统          | 有效代码 | 跨实体读取 | 外部依赖                           | 能否变方法       |
| :------------ | -------: | :--------- | :--------------------------------- | :--------------- |
| `locomotion`  |       78 | **0 处**   | `world/collision`（`moveRect`）    | ⚠️ 需注入 `grid` |
| `behaviour`   |      113 | **0 处**   | `NavigationService` / `Random`     | ⚠️ 需注入服务    |
| `perception`  |       85 | 2 处       | `world/vision`（`canSee`）         | ❌               |
| `alarm`       |       94 | 2 处       | `world/path`                       | ❌               |
| `interaction` |      160 | **8 处**   | `world/path` / `world/interaction` | ❌               |

**即「很多 sys」实际只有 2 个够格，且两者都需要注入 world / 服务**——搬进去会
违反项目已有纪律（实体不持有 world）。故实验只验证了最有价值的那一半：
**私有数据 + 只看自己的行为**。

**由此得到一条新判据**（比 §二 的四轴更进一步）：

| 类型                    | 特征                                | 归属     |
| :---------------------- | :---------------------------------- | :------- |
| **共享机制**            | 多系统读写同一字段、需 world / 服务 | **系统** |
| **私有数据 + 只看自己** | 字段只被自己读写、不需外部依赖      | **方法** |

两者不冲突，是分工。保镖的 `onFrame` 只读自己的 `visibleIds`、只写自己的
`seen`——完全没有 world 依赖，所以它适合当方法。

## 十、已定的结论（汇总）

1. **OOP 作为系统挂载**，不进内核——`updates` 数组的位置与数量由使用者投票（§3.1）
2. **方法定义在 `state` 上**，闭包捕获 `state`，不需要 `frame` / `id`（§3.2）
3. **方法被 `flush` 拷进渲染信号**——接受（能力文档 §3.4）
4. **方法只能拥有「没有系统认领的字段」**（§3.3）
5. **实体名与类型名是两种东西，两张表**（§4.3）
6. **状态对象按 NPC 类型换整套**（§5.1）
7. **自有记忆（最后见到某人在哪）住实体，是 NPC 的知识**；纯机制内部的状态（如 `accounted`）仍住系统闭包（§6.4）
8. **信息来源是可组合的积木**（看见 / 被告知 / 推断）——不为「哪种」设计机制，而是让不同 NPC 选不同的组合（§6.3）
9. **同步与异步都保留**，按需取用（§6.5）
10. **关卡 ≠ 地图**——它可以有逻辑与数据，那个位置应当生长（§7.2–7.3）
11. **关卡的「逻辑」取 B（插件）**——关卡可以带自己的系统/行为，不是更多声明式字段（§7.4）
12. **「地图只标位置、类型代码绑定」与「关卡承载逻辑」是一对**——后者解开了前者的绑定处僵局（§7.3）
13. **私有数据 + 只看自己的行为 → 方法；共享机制（多系统读写同一字段、需 world）→ 系统**（§8.7）
14. **私有字段用交叉类型扩展**（`ActorEntity & { … }`），不改共享类型（§8.6）

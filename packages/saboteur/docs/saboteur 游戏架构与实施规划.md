## 一、目标与范围

### 1.1 做什么

在 `packages/saboteur/` 中实现一个受《Party Hard》启发的俯视潜行游戏示例：玩家混入一场派对，在不被目击的前提下完成击杀，目击者会恐慌、传播、报警。

选这个题材的原因不是复刻，而是它把三类技术压力集中在同一场景里：

- **人群模拟**——多个 NPC 各自有行为状态与视野，彼此通过目击互相影响
- **空间查询**——视线、寻路、可通行性都依赖同一张地图的几何数据
- **细粒度渲染**——数十个实体每帧移动，恰好检验 kiaao 的逐属性 DOM 更新

它是 kiaao 游戏能力的压力测试，而不是一个要发布的游戏。

### 1.2 垂直切片边界

**做：**

- 一张约 32×20 格的小地图
- 一个玩家 + 约 10 个 NPC
- 完整的「目击 → 恐慌 → 传播 → 报警 → 失败」侦测链条
- 一种击杀手法（推落或下药）
- 胜负判定 + HUD + 重开

**不做（本阶段）：**

- 多关卡、存档、进度系统
- 美术资源管线（先用程序化占位）
- 移动端与触屏
- 音效与音乐（M8 可选）
- 联机

**理由**：「看起来像那个游戏」需要的是关卡设计与数值调参，不是代码量。切片的目的是把系统跑通并可验证，把调参留给后续。范围一旦铺开，会死在内容而非架构上。

### 1.3 与 example 的关系

`example` 中的 `worlds/engine/` 是引擎原型，包含 `createGame` / `useEntity` / `FrameManager` 三个薄抽象（约 170 行）。saboteur **不复用、不抽取共享包**，自行实现一套。

判定依据是重叠面：引擎层与 breakout 共用的只有这三个抽象，而同名系统的实现几乎无交集——breakout 是「移动 + 边界 + 形状碰撞」，saboteur 是「网格 + 视线 + 寻路」。共享收益低于耦合成本。

代价是约 170 行重复代码，可接受；换到的是两套引擎形态互不制约，canonical 版本可以各自演进。

## 二、架构分层与边界

### 2.1 四层划分

| 层        | 职责                                     | 是否依赖 kiaao |
| --------- | ---------------------------------------- | -------------- |
| `engine/` | 帧循环、实体池、`useEntity`、`StyleMemo` | 是             |
| `world/`  | 网格、视线、寻路、几何、关卡数据         | **否**         |
| `game/`   | 系统实现、实体结构、全局状态、组装、视图 | 是             |
| `ui/`     | HUD、覆盖层、菜单                        | 是             |

### 2.2 边界规则

**`world/` 不导入 `kiaao`。** 它只导出纯数据与纯函数：输入坐标、输出结果，不持有信号，不注册生命周期。

这条边界是本次架构最重要的约束，理由有三：

- **可测性**——寻路与视线是最容易写错、最需要测试的部分。纯函数可以在 happy-dom 之外直接单测，不需要搭组件树
- **可替换性**——寻路换成流场、视线换成阴影投射，改动被关在 `world/` 内，不影响响应式层
- **心智隔离**——响应式语义（派生、memo、生命周期）与几何算法混在一起后，会出现「这个值该不该是信号」的反复纠结；分开后 `world/` 里根本没有这个问题

**建议**：用 lint 规则（`no-restricted-imports`）固化这条边界，让违规在检查阶段就暴露，而不是靠约定与自觉。

## 四、关键设计决策

| 决策点       | 结论                          | 依据                       |
| ------------ | ----------------------------- | -------------------------- |
| 静态几何载体 | 网格位图，非实体              | 避免 O(移动×静止) 配对     |
| 静态层渲染   | canvas 预绘制                 | 640 个 DOM 节点换 1 个     |
| 感知系统频率 | 定频 ~10Hz，非每帧            | 视线判定是最贵的一环       |
| 相机位置     | 单点更新容器，不进实体派生    | 相机一动不该触发全部重算   |
| 关卡数据     | ASCII 地图 + 图例             | 关卡迭代速度是核心         |
| 实体结构     | 各系统切片合并（`useEntity`） | 沿用 example 已验证形态    |
| 系统间通信   | 组装层注入 `emit` 引用        | 沿用 v3 点对点路由         |
| 精灵动画     | 离散步进 + 派生 memo          | 帧值不变不写 DOM           |
| 实例形态     | 模块级单例，组件只管运行窗口  | 大代码量下的组织效率       |
| 重开机制     | 替换数组信号，不 dispose 实例 | 声明式，池随实体自然重建   |
| 输入方式     | 全键盘，无鼠标                | 消掉坐标换算与拾取判定     |
| 移动方向     | 4 向                          | 无斜向穿墙问题             |
| 朝向         | 等于最后移动方向              | 交互与感知共用，无额外按键 |

### 4.1 静态几何用网格，不用实体

Party Hard 的墙与家具是静态几何。若做成实体并进入碰撞系统，会落入 `createCollisionSystem` 的 O(移动 × 静止) 配对：60 个 NPC × 200 块墙 = 每帧 12000 次形状检测。更关键的是，那个碰撞模型（法线推离、速度交换）根本不是这个玩法需要的——玩家撞墙只需要「能否通过」。

改为位图网格，查询是 O(1) 的数组下标：

```ts
// world/grid.ts
type Grid = {
  cols: number;
  rows: number;
  /** 阻挡通行（墙、家具） */
  blocked: Uint8Array;
  /** 阻挡视线（墙、高家具）——与 blocked 不同：矮桌挡路但看得过去 */
  opaque: Uint8Array;
};
```

**阻挡通行与阻挡视线是两张位图。** 这是设计上的必要区分：酒桌挡路但能看穿，屏风两样都挡，矮沙发挡路但看得过。合成一张位图会让「趴下躲避视线」这类玩法无法表达。

只有**可交互物**（音响、酒瓶、目标人物）才是实体——它们有状态（用没用过、死没死），需要参与帧循环。

### 4.2 静态层用 canvas 预绘制

地图是静态的，画一次即可；DOM 完全不必承载它。32×20 的图意味着 640 个格子，用 DOM 就是 640 个节点，用 canvas 就是 1 个元素一次 `drawImage`。

动态实体（玩家、NPC、尸体、道具）仍走 DOM + `StyleMemo`。那才是 kiaao 的主场——**只检验框架擅长的部分，不拿静态内容去压它**。

canvas 的接入方式是 `direct` 指令：框架里没有 `ref` API，指令函数是唯一能拿到元素引用的途径。指令的 children 先渲染、指令后执行，所以包裹形态成立：

```tsx
const Tilemap = direct((el, props) => {
  const canvas = el as HTMLCanvasElement;
  // draw tiles once from level data
});

<Tilemap>
  <canvas class={style.tilemap} />
</Tilemap>;
```

### 4.3 感知定频，且与渲染解耦

视线判定是最贵的一环：每个 NPC 要对所有潜在目标做「距离 → 视锥角度 → 射线遮挡」三级判定。10 个 NPC × 12 个目标 = 每轮 120 次判定，每帧跑一次就是 7200 次/秒。

NPC 不需要 60Hz 的视觉。系统内维护帧计数器，每 6 帧（约 10Hz）跑一轮，帧预算立刻降到六分之一：

```ts
// game/systems/perception.ts
const update = (frame: FrameManager<T>, delta: number) => {
  tick += 1;
  if (tick % PERCEPTION_INTERVAL !== 0) return;
  // expensive scan runs here
};
```

**定频不改变语义**：感知结果写入实体数据，渲染层照常每帧读取。视觉上察觉不到 100ms 的感知延迟，但算力省下六分之五。

### 4.4 相机不进实体派生

**错误做法**：每个实体的 style 派生里读相机信号。相机一动，全部实体派生重算。

**正确做法**：世界坐标不动，外层套一个容器，只更新这一个容器的 `translate`。相机移动时每帧 1 次 DOM 写入，而不是 N 次。

视野内外的剔除（culling）同理——按需再考虑，切片规模下不必。

### 4.5 关卡用 ASCII 地图

坐标数组无法手工维护，ASCII 一眼可读、可直接编辑、diff 可读：

```
##########
#........#
#..T....N#
#........#
##...P..##
##########
```

配一张图例表（`#`=墙、`.`=地板、`T`=矮家具、`S`=高家具、`P`=玩家出生、`N`/`^v<>`=NPC 出生点与初始朝向）。关卡迭代速度是这个游戏的核心生产力——你最终要调的是关卡节奏，而 ASCII 让「改一行看一次」成为可行。

**家具分两类的理由**：矮家具（酒桌、沙发）阻挡通行但不挡视线，高家具（屏风、柜子）两者都挡。这是「趴下躲视线」「绕柱躲避」这类玩法的前提——若两者合成一种，就只剩下「能不能过」这一个维度了。

**NPC 初始朝向必须可配**，否则开局所有 NPC 都朝同一方向，既不自然也无法做关卡设计。

### 4.6 全局单例与运行生命周期

系统实例、游戏实例、全局状态全部模块级，由 `game/instance.ts` 统一导出。大量模块需要访问实例（系统之间、视图、HUD），模块级导出比逐层传递干净得多；`example` 的 `breakout` 已验证这个形态。

**但「单例」不等于「持久」——两种生命周期必须分开：**

- **运行窗口**（组件生命周期控制）——`onMount(() => start())` / `onUnmount(() => stop())`。`stop` 只暂停帧循环，数据保留，用作离开路由时的挂起
- **一局重置**（游戏逻辑控制）——回到初始状态，玩家可以重新开始

**重置走声明式，不走 `dispose`：**

```ts
// game/instance.ts —— 重置 = 替换实体数组信号
export function resetRun() {
  gameState.actors(createActors(level)); // fresh spawn list
  gameState.alarm(0);
  gameState.kills(0);
  gameState.phase("playing");
}
```

替换数组信号后，`Each` 卸载全部旧实体（`onUnmount` 中 `pool.delete(id)`），新实体挂载时 `enter` 重新执行，系统池自然重建。**不需要 `dispose`**——它的语义是「清空池、一去不回」，没有恢复入口。

**开发期注意**：模块级单例在 HMR 时会被重建，旧实例的帧循环若未 `stop` 会残留。开发期接受少量游离 raf，或在入口处显式处理。

### 4.7 全键盘输入，不用鼠标

去掉鼠标不只是「简化」，而是消掉了一整个子系统的必要性。鼠标方案需要额外解决三件事：

1. 指针坐标 → 世界坐标的换算（还要跟随相机变换）
2. 朝向与指针的耦合（移动方向与瞄准方向不一致时如何取舍）
3. 点击目标的命中判定（屏幕坐标 → 实体拾取）

全键盘方案下三者全部消失。更关键的是，交互对象变成**面朝方向的相邻格**——离散、可枚举，不需要像素级瞄准：

```ts
// game/systems/interaction.ts —— 交互目标 = 面朝方向的下一格
function targetAhead(facing: Facing, pos: Vec2): Vec2 {
  return { x: pos.x + FACE_DX[facing], y: pos.y + FACE_DY[facing] };
}
```

键位映射：

| 键 / Key        | 作用 / Action                        |
| --------------- | ------------------------------------ |
| `WASD` / 方向键 | 4 向移动                             |
| `Shift`         | 潜行（慢速，视野缩小）               |
| `E` / `Space`   | 交互（对面前格：推落 / 下药 / 拾取） |
| `Q`             | 切换道具                             |
| `Tab`           | 视野提示（显示 NPC 视野锥）          |
| `Esc`           | 暂停                                 |

`Tab` 与 `Space` 必须 `preventDefault`，否则触发浏览器默认行为（焦点切换、滚动）。现有 `createInputSystem` 已在路由表命中时统一 `preventDefault`，形态可直接沿用。

**判定依据**——4 向而非 8 向：网格潜行游戏里 4 向判定更清晰，且**不必处理斜向穿墙**（对角缝隙的碰撞特例）。朝向等于最后移动方向，不单独设按键：交互与感知共用这一个字段，避免「移动一个方向、面朝另一个方向」的心智负担。

## 五、系统流水线

### 5.1 系统清单与执行顺序

`createGame` 的参数顺序即执行顺序，按数据依赖排列：

| 顺序 | 系统          | 职责                                     | 池       | 频率           |
| ---- | ------------- | ---------------------------------------- | -------- | -------------- |
| 1    | `input`       | 键盘事件 → 意图信号（源系统，无 update） | —        | 事件驱动       |
| 2    | `interaction` | 玩家意图 → 交互结果（用道具 / 击杀判定） | 交互池   | 每帧           |
| 3    | `navigation`  | 目标选择 + A* 重算路径                   | 需寻路池 | 每帧（含节流） |
| 4    | `behaviour`   | NPC 状态机：游荡 / 社交 / 逃离           | AI 池    | 每帧           |
| 5    | `locomotion`  | 沿路径移动 + 网格碰撞 + 朝向更新         | 移动池   | 每帧           |
| 6    | `perception`  | 视线与听觉判定                           | 感知池   | 定频 ~10Hz     |
| 7    | `alarm`       | 目击 → 恐慌 → 传播 → 报警                | 全局     | 每帧           |
| 8    | `audio`       | 事件 → 音效播放                          | —        | 每帧           |

**顺序依据**：先算意图（1-2），再决定去哪（3-4），再移动（5），最后判定谁看见了谁（6-7）。感知放在移动之后，保证判定的是本帧的位置；若放在之前，会出现「已经走到眼前但看不见」的时序错觉。

### 5.2 实体结构

各系统通过 `enter` 贡献自己的数据切片，`useEntity` 合并为完整实体：

```ts
// game/types.ts
type ActorEntity = {
  /** 最后移动方向（0=N, 1=E, 2=S, 3=W）——跨系统共享字段 */
  facing: Facing;
  // locomotion slice
  x: number;
  y: number;
  vx: number;
  vy: number;
  speed: number;
  // navigation slice
  waypoints: Vec2[];
  goal: Vec2 | null;
  replanIn: number;
  // behaviour slice
  mood: Mood;
  moodTimer: number;
  // perception slice
  sightRange: number;
  sightArc: number;
  // identity slice
  role: Role;
  alive: boolean;
};
```

**`facing` 刻意不归入任何切片。** 它由 `locomotion` 写入（跟随移动方向），被 `interaction` 与 `perception` 读取，还被渲染层用于精灵翻转。放进感知切片会造成所有权错觉——谁写它、谁读它，应当在类型定义上就分开。

**静态池纪律**：不动的实体（待机 NPC、尸体、未使用的道具）绝不写帧数据。理由见第六节——实体信号每次提交都是新对象引用，写入即触发下游派生重算。

### 5.3 全局状态

非实体数据（游戏阶段、警报值、击杀计数、时限）放模块级信号，作为 deps 注入系统：

```ts
// game/state.ts
export const gameState = {
  /** 实体目录（声明式生灭的数据源：Each 订阅，重置时整体替换） */
  actors: use<ActorSpawn[]>([]),
  phase: use<Phase>("playing"),
  alarm: use(0),
  kills: use(0),
  timeLeft: use(120),
};
```

判定尺子沿用 ECS 文档 5.3：**有位置、参与帧循环的才是实体；其余是信号**。

**`actors` 是 4.6 重置机制的枢轴**：它不是实体本身，而是实体的**出生目录**（同 breakout 的 `balls`）。重置时替换整个数组，`Each` 按 keyed 差异卸载旧实体、挂载新实体，`enter` 重新执行完成系统池重建。

## 六、渲染与样式策略

### 6.1 三层职责划分

| 层       | 载体                   | 用途                  |
| -------- | ---------------------- | --------------------- |
| 全局     | `styles/global.scss`   | CSS 变量、reset、字体 |
| 静态布局 | `styles/*.module.scss` | 类名，编译期哈希      |
| 逐帧变化 | `StyleMemo`            | `el.style` 逐属性写入 |

**两层不冲突**：`StyleMemo` 只写 `el.style`，类名由元素创建阶段设置，走不同通道，可安全共存于同一元素。

**布局尺寸以 CSS 变量暴露**（如 `--tile: 32px`），组件样式与 StyleMemo 共享同一真值，避免 JS 与 SCSS 两处硬编码。

### 6.2 派生 memo 是细粒度更新的前提

`StyleMemo` 的每属性写入依赖派生层的 memo 语义：重算结果与缓存值 `!==` 时才通知下游。因此「位置没变的实体不写 DOM」是自动成立的——但**前提是实体信号本身没被写入**。这回到第五节的静态池纪律：写入即新对象，新对象必然 `!==`，memo 失效。

### 6.3 精灵动画

角色动画（走 / 站 / 死）用 `background-position` 的离散步进：

- 帧号派生自单调计数器与朝向，值以整除收敛到帧序号
- 帧序号不变的帧不写 DOM（memo 生效），实际写入频率取决于动画帧率而非渲染帧率

朝向用 `scaleX(-1)` 翻转，不额外准备镜像图集。

### 6.4 深度排序

俯视游戏需要按 y 排序遮挡。两种做法：

- **推荐**：`zIndex` 派生自 y，并**量化到格子精度**（`Math.round(y / TILE)`）。量化后相邻帧多数取值相同，memo 生效，写入频率大幅下降
- 不推荐：每帧重排 DOM 节点顺序——成本高，且会打断浏览器的合成层优化

### 6.5 占位美术

先用程序化占位：几何色块 + CSS 画的人形，不同角色用不同颜色区分。

理由：**接口先定死，素材后补**。若先找素材，会把时间花在切图与图集对齐上，而接口设计才是这个阶段真正要验证的东西。图集接口一旦定下（`background-position` 的帧宽高约定），后换素材是纯替换。

## 八、已定决策

本节记录全文确认的设计选择与依据，供实施时直接照办，不再讨论。

### 8.1 里程碑范围

按 M0–M7 推进，M8 留作可选。

M5 是第一个可玩检查点（可交互闭环），M7 是完整循环。不建议在半途停下——缺了传播链就拿不到这个题材的内核实证。

### 8.2 静态层渲染方式

canvas 预绘制。

备选是纯 DOM（640 个格子用 640 个 `div`）。选 canvas 的理由不只是性能，还有**调试体验**——DOM 方案下元素检查器会被 640 个格子淹没，找动态实体反而困难。

### 8.3 美术方案

先程序化占位，后换像素素材。图集接口一旦定下（`background-position` 的帧宽高约定），后换素材是纯替换。

### 8.4 胜负条件

击杀指定目标 N 人。

「杀光所有客人」是《Party Hard》原味，但难度与节奏极难调，且需要地图内 NPC 数量足够多才有意义。切片阶段用目标制，把「杀光」作为后续关卡的变体。

### 8.5 实例形态与重置

模块级单例，组件只管运行窗口（`start` / `stop`）。重置走声明式——替换 `gameState.actors` 数组信号，而非调用 `dispose`。详见 4.6。

### 8.6 输入与移动

全键盘输入，无鼠标；4 向移动；朝向等于最后移动方向。详见 4.7。

### M0：engine + 舞台 + 相机 + 样式体系（2026-09-28 完成）

**交付**：

| 模块                    | 内容                                                    |
| ----------------------- | ------------------------------------------------------- |
| `engine/types.ts`       | `EntityId` / `EntitySignal` / `FrameManager` / `Update` |
| `engine/game.ts`        | `createGame`（拆为帧缓冲 / 帧循环 / 实体注册三块）      |
| `engine/directives.tsx` | `StyleMemo`                                             |
| `game/config.ts`        | 尺寸常量（与 `global.scss` 的 CSS 变量互为镜像）        |
| `game/instance.ts`      | 模块级单例组装层                                        |
| `game/views/stage.tsx`  | 相机跟随（夹在世界边界内）+ 世界层平移                  |
| `game/views/debug.tsx`  | 帧率与实体计数面板                                      |

**脚手架**（M2 落地时删除）：`systems/scaffold.ts`（圆周运动）、`views/marker.tsx`（标记实体）、`systems/frame.ts`（帧统计）。

**实施中发现并修正的几点**：

- **节流必须在信号源头，不能在派生里**。调试面板最初设计为「派生里按时间窗口取值」，那仍是 60Hz 重算。正解是帧统计系统按采样间隔才写 `fps` 信号，下游派生天然获得 memo 收益。这一条对所有高频信号适用。
- **类名不能写在指令元素上**。`<StyleMemo class="...">` 无效——指令的 props 传给指令函数，不作用于 DOM 元素。类名必须写在子元素上。
- **`onMount` / `onUnmount` 回调需为块体**。箭头函数简写返回 `Map` / `boolean` 会与 `void | Promise<void>` 签名冲突。
- **`useEntity` 返回信号**，读值需调用（`entity()`），不是属性访问。

**测试**（18 例，含 `render.test.ts` 的 10 例端到端）：

覆盖两类构建成功无法证明的部分——引擎时序契约（写时拷贝、帧内读缓存、帧末统一提交、池随生命周期增减、`start`/`stop` 幂等、`update` 按参数顺序）与端到端通路（真实挂载后实体注册、帧循环启动、**帧推进后 DOM 的 `translate` 真的变化**、卸载后停止）。

最后一条是「实体 → DOM」通路的实证，也是后续所有里程碑的回归基线。

### M1：ASCII 关卡 → 网格 → canvas 预绘制（2026-09-28 完成）

**交付**：

| 模块                     | 内容                                                  |
| ------------------------ | ----------------------------------------------------- |
| `world/grid.ts`          | 瓦片网格与查询（`isBlocked` / `isOpaque` / `tileAt`） |
| `world/levels/types.ts`  | `Tile` 常量、符号映射、`LevelDef` 类型                |
| `world/levels/parse.ts`  | ASCII → 网格 + 出生点；`validateLevel` 校验           |
| `world/levels/manor.ts`  | 首个关卡（宅邸宴会厅，32×24）                         |
| `game/views/paint.ts`    | 绘制纯计算（`planTiles`）+ 上下文薄壳（`paintGrid`）  |
| `game/views/tilemap.tsx` | `Tilemap` 指令                                        |

**实施中发现并修正的几点**：

- **指令作用于子元素，而非指令元素本身**。`<Tilemap grid={...} />` 自闭合写法不会执行——`handleDirectiveMode` 遍历的是 children 中的元素。必须写成包裹形态：`<Tilemap grid={g}><canvas /></Tilemap>`。失败是静默的（页面只是空白），因此加了「`getContext` 被调用」的用例盯死这条。
- **canvas 绘制在测试环境不可验证**。happy-dom 的 `getContext("2d")` 返回 `null`。因此绘制拆为两层：`planTiles`（纯函数，可单测「哪些格被画成什么」）与 `paintGrid`（上下文薄壳，测其尺寸设置与无上下文时的静默返回）。
- **`enum` 不可用**。tsconfig 的 `erasableSyntaxOnly` 禁掉它，改用 const 对象 + 联合类型。
- **`LevelDef` 不声明出生点**。出生点内嵌在 ASCII 图中，避免地图与坐标两个数据源不一致。`ParsedLevel` 承载解析结果。
- **世界尺寸从关卡推导**（`grid.cols * TILE`），不在 config 硬编码——否则改地图要同步改配置。

**测试**（28 例，累计 46）：

- `world/__tests__/grid.test.ts`（14）——越界安全、通行性与视线分离、解析与校验
- `world/__tests__/manor.test.ts`（7）——关卡数据健全性：校验通过、出生点不在墙里、**全图连通（洪泛填充验证无孤岛）**、边界封闭、两类家具都被使用
- `game/views/__tests__/paint.test.ts`（7）——绘制清单与薄壳边界

关卡健全性用例值得特别说明：手写 ASCII 图出错是静默的（网格错位、区域不通、出生点落在墙里都不会报错），只在跑起来后表现为「AI 卡住」，很难定位。洪泛填充验证把所有地板与 NPC 都在同一连通域，这类问题被挡在关卡编辑阶段。

**M1 后续修正：视口与地图不匹配（同日）**

首版视口硬编码为 960×640，而地图是 1024×768。结果是右墙与下墙落在视口之外，画面看起来像「地图没画完”——绘制本身没错，是取景范围错了。这是设计疏漏：规划文档未定义视口与地图的关系。

修正为**视口由关卡推导，并设上限**：

- 地图不超过上限时，视口等于地图——整张地图（含四周边界墙）一屏可见，相机静止
- 地图超过上限（1280×800）时视口封顶，相机自动转为跟随卷轴

上限存在的意义：地图放大后若仍一屏看全，实体在屏幕上会小到不可辨。同一表达式（`clamp` 到 `worldSize - viewportSize`）在两种情形下都正确，地图长大时无需改代码。

修正同时补上了缺失的测试：`game/__tests__/config.test.ts`（6 例，累计 52）覆盖上限两侧的行为，以及端到端用例锁定「视口不小于地图」。这类跨层约束此前无人检查——`world/` 不知道视口，视口属于 `game/`。

### M2：键盘输入 + 玩家移动 + 墙体碰撞（2026-09-28 完成）

**交付**：

| 模块                         | 内容                                                                                             |
| ---------------------------- | ------------------------------------------------------------------------------------------------ |
| `world/geometry.ts`          | `TILE` 尺度与 `Rect`。`TILE` 从 `game/config.ts` 移来——它是「格子 ↔ 像素」的换算尺度，属世界几何 |
| `world/collision.ts`         | 分轴扫掠碰撞解算（`moveRect` / `rectBlocked`）                                                   |
| `game/systems/input.ts`      | 键盘源系统：方向键 / Shift 潜行 / 失焦清空                                                       |
| `game/systems/locomotion.ts` | 位置积分 + 碰撞 + 朝向写入，意图驱动                                                             |
| `game/state.ts`              | 玩家实体注册表（相机跟随的桥梁）                                                                 |
| `game/views/actor.tsx`       | 玩家与 NPC 视图                                                                                  |
| `game/views/camera.ts`       | 相机跟随玩家                                                                                     |

**M0 脚手架已删除**：`systems/scaffold.ts`、`views/marker.tsx`（及样式）。

**设计要点**：

- **碰撞是精确扫掠，不是步进试探**。按格边界直接算出第一个阻挡格并贴边：试探会在墙前留下最多一个步长的缝隙，且高速下可能穿透。用例锁定了「单帧位移远超地图宽度也不会穿墙」。
- **分轴解算（先 X 后 Y）**：撞墙时受阻轴贴边、另一轴照常移动，即沿墙滑行。整体停下会让斜向撞墙手感发滞。
- **意图与输入解耦**：`locomotion` 只认 `{ dx, dy, sneaking }`，不读键盘。玩家意图来自输入信号，M3 的 NPC 意图来自路径跟随——同一套移动逻辑。
- **`facing` 由 `locomotion` 独家写入**，且仅在实际产生位移时更新（顶着墙走不改变朝向）。
- **输入是源系统，不走实体注册**。它不属于任何实体，故只借用一个生命周期上下文（`input.attach(ctx)`），而非 `enter(id, ctx)` 形态。
- **`TILE` 归入 `world/`**：碰撞解算与渲染共用同一换算尺度，两处硬编码同一致是隐患。

**实施中发现并修正的几点**：

- **`flip` 不是合法的 CSS 属性**。首版用 `flip: scaleX(-1)` 做朝向镜像，浏览器会静默丢弃。改用真实属性 `scale`（值 `-1 1` / `1 1`）。
- **`Uint8Array` 迭代产出 `number`**：`Tile` 的 `as const` 对象在网格位图迭代时需显式断言回 `Tile`。
- **测试时钟必须可控**。同步 tick 时 `performance.now()` 只推进几微秒，`delta ≈ 0`、实体几乎不动，基于时间的断言（如「走到墙边」）会因走不完距离而失败。驱动替身改为固定步长推进虚拟时钟。
- **测试替身必须写回真实信号**。首版 harness 写内部 Map，验的是测试自己而非框架行为；修正为把 flush 结果写回实体信号。
- **相机跟随需要实体注册表**。玩家实体在 `Actor` 组件体内创建，而框架没有 ref API，组件树无法向上传出信号。`game/state.ts` 的 `playerEntity` 作注册表，`Actor` 在 `role === "player"` 时写入。

**测试**（41 例，累计 93）：

- `world/__tests__/collision.test.ts`（15）——自由移动、四向贴边、分轴滑动、极端位移不穿透、越界安全、矮家具阻挡
- `game/__tests__/movement.test.ts`（17）——方向映射（含 WASD 与方向键等价、后按键优先）、朝向四向切换、顶墙不转向、潜行减速、键盘事件与失焦清理
- `game/__tests__/interaction.test.ts`（9）——**端到端**：真实键盘事件 → 玩家在 DOM 中移动、撞墙停下且贴住墙沿、朝向反映到 `scale`、潜行标记生效

端到端用例是这一步最有价值的产出：单测只覆盖各段，而链路的接缝（信号未接线、监听未挂载、朝向未写进 DOM）只有端到端能发现。其中「撞墙后贴住墙的左沿而非停在半途」这条锁定了扫掠解算的精度。

### M3：NPC 生成 + A* 游荡 + 深度排序（2026-09-28 完成）

**交付**：

| 模块                         | 内容                                                                 |
| ---------------------------- | -------------------------------------------------------------------- |
| `world/path.ts`              | A* 寻路（二叉堆开放集）、`cellAt` / `cellCenter` / `collectWalkable` |
| `world/random.ts`            | 可复现的线性同余伪随机（含 `int` / `pick`）                          |
| `game/systems/navigation.ts` | 目标规划 + 路径推进 + 卡死看门狗 + `pathIntent`                      |
| `game/systems/behaviour.ts`  | NPC 状态机（闲游 / 驻足）                                            |
| `game/views/actor.tsx`       | 增加深度排序（zIndex 量化到格）                                      |

**设计要点**：

- _*A* 用 4 邻域，与移动的 4 向位移一致_*。若寻路给出斜向路径，移动系统走不出来，NPC 会在拐角卡住或抖动。4 向下的曼哈顿启发式可采纳，故为最优解。
- **寻路按实体节流**。只有「需要新路径」的实体才跑 A*；路径在实体上（`path` / `goal`），无需额外表。堆与 `Float64Array` 都在局部，不跨请求保留——换来的是一次分配，省掉状态清理。
- **路径推进（弹出已到达的点）归 navigation**。`path` 的写者只有它；`locomotion` 的意图来源只读 `path[0]` 求方向，不修改。单写者纪律。
- **看门狗计时语义是「距上次推进」而非「整条路径已跟随多久」**。首版按整条计时（6s），但一条 30 格的路径以 78px/s 走完需十几秒——正常路径会被误杀。改为「超过 4s 无推进」才放弃。
- **行为不直接指挥移动，而是影响 navigation 的目标选择**（`linger` 时不让 navigation 规划）。这样 locomotion 与意图来源都不知道「状态机」存在，行为切换只改一处。
- **行为切换等路径走完**。在路中间切换状态会让 NPC 突然停在空地中央，看起来像卡住。
- **意图来源按 `role` 分派**（`setIntent(role, source)`）。玩家读输入、客人读路径是本质不同的两类来源，用单一来源再内部分支会让组装层多一层间接。
- **固定随机种子**（`createRandom(20260928)`）：NPC 的目的地序列每次运行一致，便于对照与调试，也让测试可断言精确序列而非仅范围。

**实施中发现并修正的几点**：

- **`cellAt` 对非有限坐标返回 `{ col: null, row: null }`**（`Math.floor(NaN)` 为 `NaN`，写入 `Int32Array` 变 0）。这是真实的健壮性漏洞——实体 `x/y` 未写出的瞬间（如单独注册 navigation 而不注册 locomotion）会触发。改为返回 `null`，调用方显式处理。
- **`enabled` 字段的教训**：`Uint8Array` 迭代产出 `number`，与 `Tile` 断言处同理。

**测试**（31 例，累计 124）：

- `world/__tests__/path.test.ts`（17）——直线 / 绕行 / 最优性 / 完全封闭返回 `null` / 起终点重合返回空数组 / 越界 / 坐标换算互逆
- `game/__tests__/navigation.test.ts`（9）——目标规划、路径终点即目标、路径全程可通行、**固定种子序列可复现**、到达即弹出、看门狗触发与不误触发、行为状态切换
- `game/__tests__/wander.test.ts`（5）——**端到端**：NPC 真的移动、50 秒内不穿墙、多 NPC 不重合、zIndex 随 y 变化

端到端用例里「NPC 始终待在可通行格内」是最有价值的一条：它把寻路、路径推进、移动、碰撞四个环节的输出串起来验证。局部单测全绿但某一处接线错误时，NPC 就会穿墙，这条能抓住。

**实测**：模拟 60 秒，6 个 NPC 在三个区域间穿行，停留过 14000+ 个位置采样，最长静止帧数为 0（无卡死）。

### M4：视线判定 + 视锥可视化（2026-09-28 完成）

**交付**：

| 模块                          | 内容                                                            |
| ----------------------------- | --------------------------------------------------------------- |
| `world/vision.ts`             | 射线遮挡（Amanatides & Woo 体素遍历）、精确可见判定、视锥多边形 |
| `game/systems/perception.ts`  | 定频感知（~10Hz），写入 `visibleIds`                            |
| `game/views/vision.ts`        | 视锥计算的纯函数层 + canvas 绘制薄壳                            |
| `game/views/vision-layer.tsx` | 订阅帧计数的视锥图层（Tab 开关）                                |
| `game/state.ts`               | 角色注册表（视锥层遍历用）+ 视野开关信号                        |

**设计要点**：

- **判定与可视化分开，因为精确度要求不同**。玩法判定用「观察者中心 → 目标中心」的精确直线；可视化才用扇形采样。**采样射线不能用于判定**——它是离散的，目标恰好在两条射线之间时会被误判为看不见（或反之从墙缝漏过）。
- **对角缝特判**：射线恰好穿过格点时，要求两侧相邻格都不透明。否则视线会从两面墙对角相接的缝隙漏过去——棋盘式地图上很常见。
- **起点所在格不参与遮挡判定**：观察者自己的格不该挡住自己的视线。
- **遮挡读 `isOpaque` 而非 `isBlocked`**：矮桌挡路但看得穿，这是「趴下躲视线」类玩法的前提（规划文档 4.1）。
- **定频 ~10Hz**（每 6 帧一轮）：感知结果写入实体数据，渲染层照常每帧读取。100ms 延迟视觉上察觉不到，算力省下六分之五。
- **感知只写变化**：`visibleIds` 与上轮相同则不写。这是 memo 生效的前提——每轮都写会让所有订阅者无谓重算。
- **视锥层订阅帧计数而非各实体位置**：重绘是「全量重画一层」，一次订阅即可；订阅 N 个实体就有 N 次重绘请求。
- **`Vec2` 归入 `geometry.ts`**：此前 `path.ts` 与 `geometry.ts` 各声明一份，合并为单一定义。

**实施中发现并修正的几点**：

- **`computeCone` 对非正射程 / 张角产出退化多边形**：首点加零长度射线构成的多边形填色后是个小黑点，反而误导调试。改为返回空数组。
- **`sameIds` 需容忍未初始化状态**：实体已入池但尚未跑过一轮扫描时 `visibleIds` 是 undefined，直接比较 length 会抛错。「未初始化」是合法中间态。
- **`sightAngle` 与判定的角度约定必须一致**：屏幕坐标 y 轴向下，`FACING_ANGLES` 定义为「0 为正东、顺时针为正」，与 `Math.atan2(dy, dx)` 一致，因此视锥判定可直接相减比较；`normalizeAngle` 处理跨越 ±PI 的边界。

**测试**（41 例，累计 165）：

- `world/__tests__/vision.test.ts`（25）——空地 / 隔墙 / 高家具挡而矮家具不挡 / **对角缝不漏** / 起点不挡自身 / 命中点位置 / `maxDist` 限制 / 视锥对称性 / 三级判定各自独立生效 / **跨越 ±PI 的角度边界**
- `game/__tests__/vision.test.ts`（16）——视锥多边形数量与朝向差异 / 被墙裁剪 / Tab 开关与 `preventDefault` / **感知能真正检测到目标**（正对可见、背对 / 超射程 / 隔墙均不可见）

最后一条是这一步最关键的验证：前 12 例只证明视锥「画出来了」，而「可见 / 不可见」的正反用例才证明判定链本身正确——否则可能整个感知都是坏的，只是画面上看不出来。

**实测**：模拟 500 帧后打印视锥覆盖图，可确认扇形方向随朝向正确、被墙正确裁剪、贴墙 NPC 的视锥被完全裁掉。

### M5：可交互物 + 下药击杀 + 尸体（2026-09-28 完成）

**交付**：

| 模块                          | 内容                                              |
| ----------------------------- | ------------------------------------------------- |
| `world/interaction.ts`        | 面朝格、背后 / 正面判定（点积）、触及距离         |
| `world/levels/types.ts`       | 可交互物符号（`o`=酒瓶），与瓦片符号分开          |
| `world/levels/parse.ts`       | 解析 `propSpawns`（道具不落地为瓦片，其格为地板） |
| `game/systems/interaction.ts` | 拾取 / 下药 / 中毒倒计时 / 死亡                   |
| `game/views/prop.tsx`         | 酒瓶视图（拾取后 `Show` 隐藏）                    |
| `game/views/hud.tsx`          | 持有道具与交互提示                                |

**交互链**（规划文档 4.7 的面朝格模型）：

1. 按 `Space` → 算出手心格（玩家面朝方向的下一格）
2. 手心格上有酒瓶 → 拾取
3. 手心格上有活着的客人且持有酒瓶 → 下药（消耗酒瓶，启动 4.5s 倒计时）
4. 倒计时归零 → 客人死亡，尸体留在原地

**设计要点**：

- **可交互物符号与瓦片符号分开**。道具是实体（有 `taken` 状态、参与帧循环），不是瓦片；其所在格必须是地板，否则玩家够不着。`parseLevel` 产出独立的 `propSpawns`。
- **交互键用计数器而非布尔标志**。布尔标志需要「消费后清零」的双边协议；计数器只需消费方记住上次看到的值即可判定边沿（`新值 > 旧值`），一帧内按多次也不会漏。
- **`useEntity` 泛型化以容纳异形实体**。道具不是角色，形状不同。（用 `NoInfer` 阻止从参数推断默认类型，需显式指定时写 `useEntity<PropEntity>(...)`。）
- **死者由各系统各自跳过**，而非从池中移除。尸体要留在场景里被看见（M6 的目击输入），所以实体必须存活；`navigation` / `behaviour` / `locomotion` / `perception` 各自判 `dead` 早退。这是「一个字段，多个读者」的合理用法——写入者只有 interaction。
- **中毒者继续游荡直到毒发**（有意设计）。因此尸体位置不等于下药位置——玩家需要预判或跟随。为免等待期成为无反馈的黑箱，加了头顶的中毒标记（小绿点）。
- **尸体在渲染上可与活人一眼区分**：旋转 90° + 压暗冷色。M6 的目击判读依赖这个区分。

**实施中发现并修正的几点**：

- **客人未注册交互切片**：首版只在玩家的 `enters` 里加了 `interaction.enter()`，结果客人的 `dead` / `poisonLeft` 全是 `undefined`。交互切片是**两类角色共有**的——玩家需要（持有与下药），客人同样需要（被下药、变尸体）。只有导航与行为是客人专属。
- **`interaction` 需要实体信号而非裸数据**：判定要同时用位置 / 朝向（读值）与 id（排除自己、写回持有状态），而实体数据本身不含 id。

**测试**（23 例，累计 188）：

- `world/__tests__/interaction.test.ts`（12）——四向面朝格 / 未知朝向不误移 / 触及距离含边界 / 背后与正面判定 / 正侧方两者都不算 / 重合不算背后 / 归一化不产生 NaN
- `game/__tests__/kill.test.ts`（11）——**端到端**：道具渲染 / 拾取成功且酒瓶消失 / 空手下药失败 / 持瓶下药成功且延迟后死亡 / **尸体留在原地不再移动** / 尸体渲染可区分 / 长按不重复触发 / 松开后可再次触发

端到端那条「尸体留在原地不再移动」是 M5 验收标准里最容易悄悄坏掉的部分：若某个系统忘了判 `dead`，尸体会自己走起来，而单测各自全绿。

**实测**：拾取 → held=booze 且地图少一个 `o`；下药 → poisonLeft=4.48 且酒瓶消耗；毒发 → 客人变尸体留在原地。

## 一、目标与范围

### 1.1 做什么

在 `packages/saboteur/` 中实现一个受《Party Hard》启发的俯视潜行游戏示例：玩家混入一场派对，在不被目击的前提下完成击杀，目击者会恐慌、传播、报警。

选这个题材的原因不是复刻，而是它把三类技术压力集中在同一场景里：

- **人群模拟**——多个 NPC 各自有行为状态与视野，彼此通过目击互相影响
- **空间查询**——视线、寻路、可通行性都依赖同一张地图的几何数据
- **细粒度渲染**——数十个实体每帧移动，恰好检验 kiaao 的逐属性 DOM 更新

它是 kiaao 游戏能力的压力测试，而不是一个要发布的游戏。

### 1.2 垂直切片边界

**做：**

- 一张约 32×20 格的小地图
- 一个玩家 + 约 10 个 NPC
- 完整的「目击 → 恐慌 → 传播 → 报警 → 失败」侦测链条
- 一种击杀手法（推落或下药）
- 胜负判定 + HUD + 重开

**不做（本阶段）：**

- 多关卡、存档、进度系统
- 美术资源管线（先用程序化占位）
- 移动端与触屏
- 音效与音乐（M8 可选）
- 联机

**理由**：「看起来像那个游戏」需要的是关卡设计与数值调参，不是代码量。切片的目的是把系统跑通并可验证，把调参留给后续。范围一旦铺开，会死在内容而非架构上。

### 1.3 与共享引擎包的关系

初版规划的结论是「**不复用、不抽取共享包**」——理由是引擎层与 breakout 共用的只有 `createGame` / `useEntity` / `FrameManager` 三个薄抽象，而系统实现几乎无交集，约 170 行重复可接受，换两套引擎形态互不制约。

**该结论已于 2026-10-02 推翻**（见 `saboteur 引擎迁移：切换到 engine 包.md`）。前提变了：

- 引擎被抽成独立包 `packages/engine`，不再内嵌于 breakout demo
- `define` 改造完成（数据归组件、系统只声明参与），验证了 `Enter<Need>` 幻影类型 + 交集检查
- `createPool` / `createEvent` 泛化并移入 engine 包

于是重复的 260 行不再换来「两套形态互不制约」，只换来两处要同步维护的 bug——事实上已经发生：为帧内 `stop` 补的 `inFrame` 守卫在新引擎里丢失了。现在 saboteur **直接使用 `packages/engine`**，自带的 `src/engine/` 已删除。

## 二、架构分层与边界

### 2.1 四层划分

| 层                | 职责                                                    | 是否依赖 kiaao |
| ----------------- | ------------------------------------------------------- | -------------- |
| `packages/engine` | 帧循环、实体注册（`define`）、实体池、`StyleMemo`       | 是             |
| `saboteur/world/` | 网格、视线、寻路、几何、关卡数据                        | **否**         |
| `saboteur/game/`  | 系统实现、实体结构、全局状态、组装、视图                | 是             |
| `saboteur/ui/`    | HUD、覆盖层、菜单（实际落在 `game/views/`，单列无意义） | 是             |

### 2.2 边界规则

**`world/` 不导入 `kiaao`。** 它只导出纯数据与纯函数：输入坐标、输出结果，不持有信号，不注册生命周期。

这条边界是本次架构最重要的约束，理由有三：

- **可测性**——寻路与视线是最容易写错、最需要测试的部分。纯函数可以在 happy-dom 之外直接单测，不需要搭组件树
- **可替换性**——寻路换成流场、视线换成阴影投射，改动被关在 `world/` 内，不影响响应式层
- **心智隔离**——响应式语义（派生、memo、生命周期）与几何算法混在一起后，会出现「这个值该不该是信号」的反复纠结；分开后 `world/` 里根本没有这个问题

**建议**：用 lint 规则（`no-restricted-imports`）固化这条边界，让违规在检查阶段就暴露，而不是靠约定与自觉。

> **实测现状（2026-10-08）**：仓库里**并没有**这个 lint 配置——`world/index.ts` 原先写着「这条边界由 lint 规则固化」，那是**假的**。该注释已改正。目前只能靠人工遵守（§13 仍列此待办）。

## 四、关键设计决策

| 决策点         | 结论                                       | 依据                                    |
| -------------- | ------------------------------------------ | --------------------------------------- |
| 静态几何载体   | 网格位图，非实体                           | 避免 O(移动×静止) 配对                  |
| 静态层渲染     | canvas 预绘制                              | 640 个 DOM 节点换 1 个                  |
| 感知系统频率   | 定频 ~10Hz，非每帧                         | 视线判定是最贵的一环                    |
| 相机位置       | 单点更新容器，不进实体派生                 | 相机一动不该触发全部重算                |
| 关卡数据       | ASCII 地图 + 图例                          | 关卡迭代速度是核心                      |
| 实体结构       | 各系统自声明 `Enter<Need>`，数据由视图写全 | 编译期字段检查，无 `Object.assign` 拼接 |
| 系统间连接     | 组装层注入引用（`setIntent` / 回调）       | 沿用 v3 路由形态                        |
| 实例形态       | 模块级单例，组件只管运行窗口               | 大代码量下的组织效率                    |
| 重开机制       | 递增局号触发声明式重建                     | 池随实体自然重建，不用 dispose          |
| 输入方式       | 全键盘，无鼠标                             | 消掉坐标换算与拾取判定                  |
| 移动方向       | 4 向                                       | 无斜向穿墙问题                          |
| 朝向           | 等于最后移动方向                           | 交互与感知共用，无额外按键              |
| 恐慌传播       | 复用感知系统，不建传播表                   | 恐慌者被看见即传染                      |
| 「去哪」的决策 | 全部集中在 `navigation`                    | 行为切换只改状态，不碰路径              |

### 4.1 静态几何用网格，不用实体

Party Hard 的墙与家具是静态几何。若做成实体并进入碰撞系统，会落入 `createCollisionSystem` 的 O(移动 × 静止) 配对：60 个 NPC × 200 块墙 = 每帧 12000 次形状检测。更关键的是，那个碰撞模型（法线推离、速度交换）根本不是这个玩法需要的——玩家撞墙只需要「能否通过」。

改为位图网格，查询是 O(1) 的数组下标：

```ts
// world/grid.ts
type Grid = {
  cols: number;
  rows: number;
  /** 阻挡通行（墙、家具） */
  blocked: Uint8Array;
  /** 阻挡视线（墙、高家具）——与 blocked 不同：矮桌挡路但看得过去 */
  opaque: Uint8Array;
};
```

**阻挡通行与阻挡视线是两张位图。** 这是设计上的必要区分：酒桌挡路但能看穿，屏风两样都挡，矮沙发挡路但看得过。合成一张位图会让「趴下躲避视线」这类玩法无法表达。

只有**可交互物**（音响、酒瓶、目标人物）才是实体——它们有状态（用没用过、死没死），需要参与帧循环。

### 4.2 静态层用 canvas 预绘制

地图是静态的，画一次即可；DOM 完全不必承载它。32×20 的图意味着 640 个格子，用 DOM 就是 640 个节点，用 canvas 就是 1 个元素一次 `drawImage`。

动态实体（玩家、NPC、尸体、道具）仍走 DOM + `StyleMemo`。那才是 kiaao 的主场——**只检验框架擅长的部分，不拿静态内容去压它**。

canvas 的接入方式是 `direct` 指令：框架里没有 `ref` API，指令函数是唯一能拿到元素引用的途径。指令的 children 先渲染、指令后执行，所以包裹形态成立：

```tsx
const Tilemap = direct((el, props) => {
  const canvas = el as HTMLCanvasElement;
  // draw tiles once from level data
});

<Tilemap>
  <canvas class={style.tilemap} />
</Tilemap>;
```

### 4.3 感知定频，且与渲染解耦

视线判定是最贵的一环：每个 NPC 要对所有潜在目标做「距离 → 视锥角度 → 射线遮挡」三级判定。10 个 NPC × 12 个目标 = 每轮 120 次判定，每帧跑一次就是 7200 次/秒。

NPC 不需要 60Hz 的视觉。系统内维护帧计数器，每 6 帧（约 10Hz）跑一轮，帧预算立刻降到六分之一：

```ts
// game/systems/perception.ts
const update = (frame: FrameManager<T>, delta: number) => {
  tick += 1;
  if (tick % PERCEPTION_INTERVAL !== 0) return;
  // expensive scan runs here
};
```

**定频不改变语义**：感知结果写入实体数据，渲染层照常每帧读取。视觉上察觉不到 100ms 的感知延迟，但算力省下六分之五。

### 4.4 相机不进实体派生

**错误做法**：每个实体的 style 派生里读相机信号。相机一动，全部实体派生重算。

**正确做法**：世界坐标不动，外层套一个容器，只更新这一个容器的 `translate`。相机移动时每帧 1 次 DOM 写入，而不是 N 次。

视野内外的剔除（culling）同理——按需再考虑，切片规模下不必。

### 4.5 关卡用 ASCII 地图

坐标数组无法手工维护，ASCII 一眼可读、可直接编辑、diff 可读：

```
##########
#........#
#..T....N#
#........#
##...P..##
##########
```

配一张图例表（`#`=墙、`.`=地板、`T`=矮家具、`S`=高家具、`P`=玩家出生、`N`/`^v<>`=NPC 出生点与初始朝向）。关卡迭代速度是这个游戏的核心生产力——你最终要调的是关卡节奏，而 ASCII 让「改一行看一次」成为可行。

**家具分两类的理由**：矮家具（酒桌、沙发）阻挡通行但不挡视线，高家具（屏风、柜子）两者都挡。这是「趴下躲视线」「绕柱躲避」这类玩法的前提——若两者合成一种，就只剩下「能不能过」这一个维度了。

**NPC 初始朝向必须可配**，否则开局所有 NPC 都朝同一方向，既不自然也无法做关卡设计。

### 4.6 全局单例与运行生命周期

系统实例、游戏实例、全局状态全部模块级，由 `game/instance.ts` 统一导出。大量模块需要访问实例（系统之间、视图、HUD），模块级导出比逐层传递干净得多；`example` 的 `breakout` 已验证这个形态。

**但「单例」不等于「持久」——两种生命周期必须分开：**

- **运行窗口**（组件生命周期控制）——`onMount(() => start())` / `onUnmount(() => stop())`。`stop` 只暂停帧循环，数据保留，用作离开路由时的挂起
- **一局重置**（游戏逻辑控制）——回到初始状态，玩家可以重新开始

**重置走声明式，不走 `dispose`：**

落地形态是**递增局号**（初版设想的是「替换实体数组信号」）：

```ts
// game/instance.ts —— 重置 = 递增局号 + 状态归零 + 重启帧循环
export const runId = use(0);

function restartRun(): void {
  stop(); // 重建期间不跑帧（否则读到半旧的实体状态）
  alarm.reset();
  resetGameState(level.objective.timeLimit);
  runId(runId() + 1); // 递增 → 全部实体 key 变化（同步完成）
  start(); // 必须在最后：帧循环不会因组件重建而自动恢复
}
```

**`start()` 不能省**（既有缺陷，2026-10-02 修复）：初版以为「组件重建时会 `start`」，但 `start()` 只在根组件 `onMount` 时执行一次，而递增 `runId` 只重建 `Each` 的子项——画面会冻在终局那一帧。详见迁移文档 §3.2。

角色与道具由 `Each` 渲染，key 里含局号：

```tsx
<Each value={actors} keyed={(a) => `${a.run}-${a.role}-${a.col}-${a.row}`}>
```

局号变化 → 全部 key 变化 → 框架卸载旧条目、挂载新条目。实体池随 `onUnmount` 清空、`enter` 重新执行给出全新初始状态。**不需要 `dispose`**——它的语义是「清空池、一去不回」，没有恢复入口。

> **「`enter` 重新执行」的含义在 2026-10-02 迁移后变了**：现在是 `define(ctx, ...enters)(state)` 重新执行——`enter` 只负责把新实体登记进各系统的池，字段初值由视图的 `state` 字面量（各系统的 `spawn()`）给出。

**为什么不用「替换数组信号」**：那要求维护一份出生数据并在重置时重建它，而地图数据已经存在于 `level` 中；递增一个计数器更简单，也不会让两份数据不同步。

**开发期注意**：模块级单例在 HMR 时会被重建，旧实例的帧循环若未 `stop` 会残留。开发期接受少量游离 raf，或在入口处显式处理。

### 4.7 全键盘输入，不用鼠标

去掉鼠标不只是「简化」，而是消掉了一整个子系统的必要性。鼠标方案需要额外解决三件事：

1. 指针坐标 → 世界坐标的换算（还要跟随相机变换）
2. 朝向与指针的耦合（移动方向与瞄准方向不一致时如何取舍）
3. 点击目标的命中判定（屏幕坐标 → 实体拾取）

全键盘方案下三者全部消失。更关键的是，交互对象变成**离散的格**——可枚举，不需要像素级瞄准：

```ts
// game/systems/interaction.ts —— 交互候选格 = 脚下 + 面前
const targetCells = (actor) => [centerOf(actor), cellInFront(centerOf(actor), actor.facing)];
```

**候选格是两个，不是一个**（2026-10-08 实玩修正）。最初只查「面朝方向的相邻格」，实玩反馈「必须正对着那一格才能操作，很别扭」——往往要反复转身对齐。加上脚下格后，走近即可操作。

判定优先级：**脚下的格子**（不用瞄准，是「我正站在上面」这个无争议的事实）先于**面前的格子**。两者都有东西时取其下者。拾取的优先级还有个例外：已持有同款时拾取是空操作，此时让位给下药（否则站在酒瓶上就没法给面前的客人下药）。

键位映射：

| 键 / Key        | 作用 / Action                        |
| --------------- | ------------------------------------ |
| `WASD` / 方向键 | 4 向移动                             |
| `Shift`         | 潜行（慢速，视野缩小）               |
| `E` / `Space`   | 交互（对面前格：推落 / 下药 / 拾取） |
| `Q`             | 切换道具                             |
| `Tab`           | 视野提示（显示 NPC 视野锥）          |
| `Esc`           | 暂停                                 |

`Tab` 与 `Space` 必须 `preventDefault`，否则触发浏览器默认行为（焦点切换、滚动）。现有 `createInputSystem` 已在路由表命中时统一 `preventDefault`，形态可直接沿用。

**判定依据**——4 向而非 8 向：网格潜行游戏里 4 向判定更清晰，且**不必处理斜向穿墙**（对角缝隙的碰撞特例）。朝向等于最后移动方向，不单独设按键：交互与感知共用这一个字段，避免「移动一个方向、面朝另一个方向」的心智负担。

## 五、系统流水线

### 5.1 系统清单与执行顺序

`createGame` 的参数顺序即执行顺序，按数据依赖排列。以下为**实际落地**的顺序：

| 顺序 | 系统          | 职责                                           | 池              | 频率     |
| ---- | ------------- | ---------------------------------------------- | --------------- | -------- |
| —    | `input`       | 键盘事件 → 意图信号（源系统，无 update）       | —               | 事件驱动 |
| 1    | `interaction` | 拾取 / 下药 / 中毒倒计时 / 死亡 + 击杀计数     | 角色池 / 道具池 | 每帧     |
| 2    | `behaviour`   | NPC 状态机：闲游 / 驻足 / 恐慌（驱动导航服务） | 客人池          | 每帧     |
| 3    | `locomotion`  | 沿路径移动 + 网格碰撞 + 朝向更新               | 移动池          | 每帧     |
| 4    | `perception`  | 视线判定（定频 ~10Hz）                         | 感知池          | 定频     |
| 5    | `alarm`       | 目击 → 恐慌 → 传播 → 报警                      | 客人池          | 每帧     |
| 6    | `rules`       | 胜负判定、时限递减、终局停止                   | —               | 每帧     |
| 7    | `frame`       | 帧计数与帧率（调试）                           | —               | 每帧     |

**`navigation` 不在流水线里**——它是**服务**而非系统（无 `enter`、无池、无 `update`）。`behaviour` 驱动状态对象，状态通过导航服务算路径，因此「决策 + 规划 + 推进」都发生在 `behaviour.update` 内。这是 2026-09-30「恐慌 → 状态对象」重构的结果（`c9b1dfc`）。

**顺序依据**（三个必须的先后关系）：

- **`perception` 在 `locomotion` 之后**：保证判定的是本帧的位置；若放在之前，会出现「已经走到眼前但看不见」的时序错觉。
- **`alarm` 紧跟在 `perception` 之后**：它消费本轮的 `visibleIds` 产生恐慌。
- **`rules` 在最后**：它读本轮结束时的击杀数与警报值判终局，放前面会用上一帧的数据。

**与初版规划的两处差异**：初版把 `navigation` 列为流水线一员（现已退化为服务）；初版的 `audio` 系统未实现（属 M8）。

### 5.2 实体结构

**实体形态自 2026-10-02 迁移后一直是：各系统各自声明 `Enter<Need>`，数据由视图的 `state` 字面量写全**（旧版的「系统切片 + `useEntity` 合并」已废弃）。

`ActorEntity` 仍保留，但**角色变了**（D1）：它不再作为「注册契约」（那个职责已下发给各系统的 `Enter<Need>`），而是作为

- **注册表与调试层的共享类型**——`playerEntity` / `listActors()` 需要它（`Signal` 在 TS 里不变，没有这个共享类型会很难表达）
- **字段与写者的文档**——每个字段仍标注【谁写】，保持单一写者纪律

以下是实际落地的字段与写者（每个字段的【写者】必须在帧循环里唯一）：

```ts
// game/types.ts — 分组即「谁写」（不是「谁的切片」：数据已不来自系统）
type ActorEntity = {
  // 【locomotion 写】位置与速度
  x: number;
  y: number; // 世界坐标（左上角）
  speed: number;
  sneakFactor: number; // 速度与潜行倍率
  sneaking: boolean;

  // 【behaviour 写】行为与路径（navigation 是服务，无 enter，由驱动者负责初值）
  path: Cell[]; // 待走的格序列；空表示已到达或未规划
  goal: Cell | null; // 当前目标格
  idleLeft: number; // 剩余驻足时间
  followTime: number; // 距上次路径推进的时长（看门狗用）

  // 【perception 写】视锥与结果栅
  sightRange: number;
  sightArc: number;
  visibleIds: EntityId[]; // 本轮能看见谁

  // 【behaviour 写】行为状态
  mood: Mood; // wander / linger / panic
  moodLeft: number;

  // 【alarm 写】目击记忆与逃跑参照
  witnessed: boolean; // 是否目击过异常（永久）
  fleeFrom: Cell | null;

  // 【interaction 写】持有、死亡与中毒
  held: ItemKind | null;
  dead: boolean; // 尸体
  poisonLeft: number | null; // 中毒剩余存活时间

  // 【locomotion 写】跨系统共享：交互与感知都读它
  facing: Facing;

  // 【注册时定】身份
  role: Role; // player / guest
};
```

**`facing` 刻意不归入任何系统。** 它由 `locomotion` 写入，被 `interaction` 与 `perception` 读取，还被渲染层用于镜像翻转。归入某个系统的字段需求会造成所有权错觉——谁写它、谁读它，应当在类型定义上就分开。

**`dead` 由多个系统读取，但写者只有 `interaction`**。尸体必须留在场景里被看见（M6 的目击输入），所以不能从池中移除；改由 `locomotion` / `behaviour` / `perception` / `alarm` 各自判 `dead` 早退。这是「一个字段、多个读者」的合理用法。

**静态池纪律**：不动的实体（待机 NPC、尸体、未使用的道具）绝不写帧数据。理由见第六节——实体信号每次提交都是新对象引用，写入即触发下游派生重算。

**异形实体**：道具（酒瓶）不是角色，有自己的形状（`PropEntity`）。同一个 `define` 可以容纳两种形态（`Prop` 组件传 `interaction.enterProp` 与 `spawnProp`）。

**各系统的字段需求（`Enter<Need>`）**：

| 系统        | 需要字段                                                                  |
| :---------- | :------------------------------------------------------------------------ |
| locomotion  | `x y speed sneakFactor sneaking facing role dead`                         |
| perception  | `x y facing dead visibleIds`                                              |
| behaviour   | `mood moodLeft path goal idleLeft followTime witnessed fleeFrom dead x y` |
| alarm       | `dead witnessed fleeFrom visibleIds x y`（注册时读 `role`）               |
| interaction | `x y facing dead held poisonLeft path goal`                               |
| frame       | 无（`Record<string, unknown>`）                                           |

`define` 把它们求交集作为 `state` 的必填项——**漏写任一个就在调用处报错**，这是旧 `Object.assign` 拼接没有的编译期保护。

**初值的产出方式**：各系统导出 `spawn()` 纯函数（不接触 `ctx`、不迸池），视图负责组合：

```tsx
// game/views/actor.tsx
const state: ActorEntity = {
  ...locomotion.spawn(speedProps(col, row, role, facing)),
  ...perception.spawn(),
  ...interaction.spawn(),
  ...alarm.spawn(),
  ...behaviour.spawn(),
  role,
};
const entity = define(ctx, ...enters)(state);
```

这不是「系统提供数据」的回潮：`enter` 只进池，`spawn` 只算初值，两者职责分明。「初值怎么算」留在最清楚它的系统侧（如 `behaviour.spawn` 需要掷 `moodLeft` 的随机时长），视图只负责组合与渲染。

**行为字段两类角色都给**（实体形态统一）：玩家也写 `mood` / `path`，但因为没有注册 `behaviour.enter`，这些字段永不被读写。谁跑状态机由「注册了哪个 `enter`」决定，而非由字段有无决定。

**两个通道必须分开**：`define` 返回的 `EntitySignal<T>` **只承载渲染快照**，不携带活状态。

| 用途                   | 入口        | 语义                                |
| :--------------------- | :---------- | :---------------------------------- |
| 读渲染快照（驱动 DOM） | `entity()`  | 帧末由 `flush` 提交，**不要写**     |
| 读身份（不是数据）     | `entity.id` | `Symbol`，传给 `frame(id)` / 注册表 |
| 读写实体数据           | `frame(id)` | 系统的事务通道（帧内直接改）        |

系统从 `update(frame, delta)` 拿到它；测试与调试层从 `game.frame(id)` 拿（同一个函数）。

`entity.id` 是本项目里唯一需要从信号上读的非信号属性——因为 `id` 由 `define` 内部生成，组件拿不到却又必须交给出去（`playerEntity(entity)` 注册的就是「信号 + `id`」，而 `interaction` 需要它取活对象、排除自己）。它不属于 `state`：`state` 是「组件的字段」，会被 `flush` 每次浅拷贝；`id` 是运行时身份。

> **设计演变（曾走过弯路）**：迁移时曾在信号上挂 `.state` 指向活对象，好让测试直接写入。但回头数使用者——33 处全在测试，生产代码唯一一处是死代码。那等于把「系统的数据」挂到「组件的句柄」上，两个通道混在一起。现已改为 `game.frame`，并把「帧管理器不随帧重建」也一并修了（它本来就无状态）。

旧的 `frame(id, fn)` 写时拷贝形式已不存在（本项目 11 处调用点已全部清空）。

### 5.3 全局状态

非实体数据（游戏阶段、警报值、击杀计数、时限）放模块级信号，作为 deps 注入系统：

```ts
// game/state.ts
export const gameState = {
  phase: use<Phase>("playing"),
  /** 已达成的击杀数 */
  kills: use(0),
  /** 剩余时间（秒） */
  timeLeft: use(0),
  /** 本局耗时（秒），结算展示用 */
  elapsed: use(0),
};
```

判定尺子沿用 ECS 文档 5.3：**有位置、参与帧循环的才是实体；其余是信号**。

**出生目录不在 `gameState` 里。** 初版规划把它列入，实际落在 `app.tsx` 的 `useSpawns(ctx, runId)`——因为它的数据源是**关卡**（`level.playerSpawn` / `npcSpawns` / `propSpawns`），而关卡只在 `instance.ts` 解析一次。把它放进 `gameState` 会让「游戏状态」反向依赖关卡数据。

**`runId` 才是重置机制的枢轴**（4.6）：递增它 → `useSpawns` 重算 → 丙出新的 `run` → `Each` 的 key 全部变化 → 卸载旧的、挂载新的 → 实体池随 `onUnmount` / `onMount` 自然重建。

## 六、渲染与样式策略

### 6.1 三层职责划分

| 层       | 载体                       | 用途                         |
| -------- | -------------------------- | ---------------------------- |
| 全局     | `styles/global.scss`       | 调色板 CSS 变量、reset、字体 |
| 静态布局 | `game/views/*.module.scss` | 类名，编译期哈希             |
| 逐帧变化 | `StyleMemo`                | `el.style` 逐属性写入        |

**两层不冲突**：`StyleMemo` 只写 `el.style`，类名走另一个通道，可安全共存于同一元素。

**尺寸不在 CSS 变量里**：初版设想把 `TILE` / 视口尺寸写成 CSS 变量供两边共享，实际改为「JS 单一真值 + 运行时注入」（视口尺寸由 `computeViewport` 算出后直接写在 `style` 上）。原因：视口尺寸**依赖关卡数据**，是动态的，写死在样式表里反而会与地图不一致——这正是 M1 那个「边界墙看不见」bug 的根因（详见 §11）。

**`class` 必须传信号才响应**：写 `class={cond ? a : b}` 或数组拼接会在渲染时求值一次就固定。需要随状态切换的类名必须用派生信号——这是本项目中反复踩到的坑（§11 的 M7 一节）。

### 6.2 派生 memo 是细粒度更新的前提

`StyleMemo` 的每属性写入依赖派生层的 memo 语义：重算结果与缓存值 `!==` 时才通知下游。因此「位置没变的实体不写 DOM」是自动成立的——但**前提是实体信号本身没被写入**。这回到第五节的静态池纪律：写入即新对象，新对象必然 `!==`，memo 失效。

### 6.3 精灵动画（未实现）

规划的做法是：角色动画（走 / 站 / 死）用 `background-position` 的离散步进，帧号派生自单调计数器与朝向，帧号不变时不写 DOM；朝向用水平翻转复用同一图集。

**当前未实现**：角色是程序化色块（几何形状 + 渐变），没有动画帧。

**一处修正（2026-10-08）**：本节曾写「朝向翻转已实现（`scale: -1 1`），接入图集后可直接复用」——**那是错的**。`scale: -1 1` 确实在写 DOM，但占位形体**左右对称**，镜像一个对称形状等于没变，屏幕上完全看不到朝向。实玩反馈「每个单位都不显示朝向」，根因就在这里。

现在的做法：朝向由一个**不对称的方位箭头**表达（`rotate` 到四个角度），见 `actor.module.scss` 的 `.facing`。接入图集后，翻转可以只作用于**图集**（届时左右有区别），而箭头可留作辅助，也可去掉——两者不冲突。

做的时候注意：翻转要用真实的 CSS 属性 `scale`，不要写自造的 `flip`（后者会被浏览器静默丢弃，见 §11 的 M2 一节）。但**「用对了 CSS 属性」不等于「看得出效果」**——对对称图形做镜像是个静默失败，验证时要看屏幕，不能只看 DOM。

### 6.4 深度排序

俯视游戏需要按 y 排序遮挡。两种做法：

- **推荐**：`zIndex` 派生自 y，并**量化到格子精度**（`Math.round(y / TILE)`）。量化后相邻帧多数取值相同，memo 生效，写入频率大幅下降
- 不推荐：每帧重排 DOM 节点顺序——成本高，且会打断浏览器的合成层优化

### 6.5 占位美术

先用程序化占位：几何色块 + CSS 画的人形，不同角色用不同颜色区分。

理由：**接口先定死，素材后补**。若先找素材，会把时间花在切图与图集对齐上，而接口设计才是这个阶段真正要验证的东西。图集接口一旦定下（`background-position` 的帧宽高约定），后换素材是纯替换。

## 八、已定决策

本节记录全文确认的设计选择与依据，供实施时直接照办，不再讨论。

### 8.1 里程碑范围

按 M0–M7 推进，M8 留作可选。

M5 是第一个可玩检查点（可交互闭环），M7 是完整循环。不建议在半途停下——缺了传播链就拿不到这个题材的内核实证。

### 8.2 静态层渲染方式

canvas 预绘制。

备选是纯 DOM（640 个格子用 640 个 `div`）。选 canvas 的理由不只是性能，还有**调试体验**——DOM 方案下元素检查器会被 640 个格子淹没，找动态实体反而困难。

### 8.3 美术方案

先程序化占位，后换像素素材。图集接口一旦定下（`background-position` 的帧宽高约定），后换素材是纯替换。

### 8.4 胜负条件

击杀指定目标 N 人。

「杀光所有客人」是《Party Hard》原味，但难度与节奏极难调，且需要地图内 NPC 数量足够多才有意义。切片阶段用目标制，把「杀光」作为后续关卡的变体。

### 8.5 实例形态与重置

模块级单例，组件只管运行窗口（`start` / `stop`）。

一局重置走**声明式重建**：递增 `runId` 信号 → 角色 / 道具的 `Each` key 全部变化 → 框架卸载旧条目、挂载新条目 → 实体池随 `onUnmount` 清空、`enter` 重新执行。不调 `dispose`（它清空池后没有恢复入口），也不必逐字段手动复位。详见 4.6。

初版写的「替换 `gameState.actors` 数组信号」在落地时演化为「递增局号」——后者更简单：不必维护一份出生数据，也不必把地图数据再映射一道。

### 8.6 输入与移动

全键盘输入，无鼠标；4 向移动；朝向等于最后移动方向。详见 4.7。

## 九、验证与测试策略

### 9.1 可测试性的分层

`world/` 的纯函数边界带来的直接收益：最易出错的部分可以脱离渲染环境单测。

| 层           | 测试方式                    | 可测内容                                                         |
| ------------ | --------------------------- | ---------------------------------------------------------------- |
| `world/`     | 直接单测，无需 DOM          | 通行性查询、碰撞解算、视线遮挡、A* 路径正确性与最优化、交互几何  |
| `game/` 系统 | 手工造 `frame` + 实体池     | 系统逻辑（给定实体数据，验证输出数据）；状态机与计时             |
| 视图         | 纯计算部分单测 + 端到端挂载 | 绘制清单（`planTiles` / `computeCones`）；DOM 是否真的随信号更新 |
| 整局         | 长时程模拟                  | 胜负、重开、僵死、传播链这类跨系统且需时间累积的行为             |

**实际比初版规划多做了两层**：

- **视图层的纯计算部分被拆出来单测**。canvas 上下文在 happy-dom 中取不到（`getContext("2d")` 返回 `null`），因此绘制拆为「纯计算（可断言画了什么）+ 上下文薄壳（测调用与边界）」两层（见 `paint.ts` / `views/vision.ts`）。
- **端到端挂载测试**。真实渲染组件树 + 真实键盘/时钟驱动，验证「信号 → DOM」与「输入 → 行为」的接缝。单测只盖各段，链路的接缝（信号未接线、监听未挂载、`class` 未响应）只有端到端能发现——本项目最有价值的几个 bug（`class` 不响应、帧内 `stop` 失效）都是这样找到的。
- **长时程模拟**。`stuck.test.ts` 以「所有 NPC 位置连续不变的帧数」为指标跑满整局——三个导致全体停滞的 bug 都只在长时间运行后显现（见 §11 的 M6 修正）。

**已确认**：`packages/saboteur/src/` 下的 `*.test.ts` 会被 `vp test` 自动发现并运行，无需额外配置。

**测试环境的两个限制**（需在设计时避开）：

- **canvas 2D 上下文不可用**：`getContext("2d")` 返回 `null`，绘制结果无法在测试中验证；把纯计算拆出去是唯一出路。
- **模块级单例跨用例共享**：`gameState` / `alarm` 等不会被组件卸载重置，测试需在 `beforeEach` 手动复位（实体随卸载而清理，但信号不会）。

### 9.2 必须覆盖的 `world/` 用例

- 视线：正对目标可见 / 背对不可见 / 中间隔墙不可见 / 矮桌不挡视线而屏风挡 / **对角缝不漏** / 起点所在格不挡自己
- 寻路：直线可达 / 需绕行 / **不可达返回 `null`** / **起终点重合返回空数组**（与 `null` 区分）/ 越界
- 碰撞：四向贴边 / 分轴滑动 / **极端位移不穿透** / 矮家具阻挡
- 网格：越界查询视为墙、写入静默忽略（不抛异常）
- 交互：四向面朝格 / 背后与正面判定（含正侧方两者都不算）/ 未知朝向不误移
- 关卡：**洪泛填充验证全图连通**、出生点不在墙内、边界封闭

这几个用例覆盖了最容易出现静默错误的地方——寻路与视线出错不会崩溃，只会让 AI 做出看起来「有点怪」的行为，靠肉眼很难定位。

**脚手架**（M2 落地时删除）：`systems/scaffold.ts`（圆周运动）、`views/marker.tsx`（标记实体）、`systems/frame.ts`（帧统计）。

**实施中发现并修正的几点**：

- **节流必须在信号源头，不能在派生里**。调试面板最初设计为「派生里按时间窗口取值」，那仍是 60Hz 重算。正解是帧统计系统按采样间隔才写 `fps` 信号，下游派生天然获得 memo 收益。这一条对所有高频信号适用。
- **类名不能写在指令元素上**。`<StyleMemo class="...">` 无效——指令的 props 传给指令函数，不作用于 DOM 元素。类名必须写在子元素上。
- **`onMount` / `onUnmount` 回调需为块体**。箭头函数简写返回 `Map` / `boolean` 会与 `void | Promise<void>` 签名冲突。
- **`useEntity` 返回信号**，读值需调用（`entity()`），不是属性访问。（现行：`define` 返回的 `EntitySignal`，同样是读值需调用；它只有渲染快照，活对象走 `frame(id)`。）

**测试**（18 例，含 `render.test.ts` 的 10 例端到端）：

覆盖两类构建成功无法证明的部分——引擎时序契约（帧末统一提交、池随生命周期增减、`start`/`stop` 幂等、`update` 按参数顺序）与端到端通路（真实挂载后实体注册、帧循环启动、**帧推进后 DOM 的 `translate` 真的变化**、卸载后停止）。

> **2026-10-02 迁移后**：引擎时序契约的测试已移到 `packages/engine/src/__tests__/game.test.ts`（13 例）；saboteur 侧只保留端到端通路。

最后一条是「实体 → DOM」通路的实证，也是后续所有里程碑的回归基线。

### M1：ASCII 关卡 → 网格 → canvas 预绘制（2026-09-28 完成）

**交付**：

| 模块                     | 内容                                                  |
| ------------------------ | ----------------------------------------------------- |
| `world/grid.ts`          | 瓦片网格与查询（`isBlocked` / `isOpaque` / `tileAt`） |
| `world/levels/types.ts`  | `Tile` 常量、符号映射、`LevelDef` 类型                |
| `world/levels/parse.ts`  | ASCII → 网格 + 出生点；`validateLevel` 校验           |
| `world/levels/manor.ts`  | 首个关卡（宅邸宴会厅，32×24）                         |
| `game/views/paint.ts`    | 绘制纯计算（`planTiles`）+ 上下文薄壳（`paintGrid`）  |
| `game/views/tilemap.tsx` | `Tilemap` 指令                                        |

**实施中发现并修正的几点**：

- **指令作用于子元素，而非指令元素本身**。`<Tilemap grid={...} />` 自闭合写法不会执行——`handleDirectiveMode` 遍历的是 children 中的元素。必须写成包裹形态：`<Tilemap grid={g}><canvas /></Tilemap>`。失败是静默的（页面只是空白），因此加了「`getContext` 被调用」的用例盯死这条。
- **canvas 绘制在测试环境不可验证**。happy-dom 的 `getContext("2d")` 返回 `null`。因此绘制拆为两层：`planTiles`（纯函数，可单测「哪些格被画成什么」）与 `paintGrid`（上下文薄壳，测其尺寸设置与无上下文时的静默返回）。
- **`enum` 不可用**。tsconfig 的 `erasableSyntaxOnly` 禁掉它，改用 const 对象 + 联合类型。
- **`LevelDef` 不声明出生点**。出生点内嵌在 ASCII 图中，避免地图与坐标两个数据源不一致。`ParsedLevel` 承载解析结果。
- **世界尺寸从关卡推导**（`grid.cols * TILE`），不在 config 硬编码——否则改地图要同步改配置。

**测试**（28 例，累计 46）：

- `world/__tests__/grid.test.ts`（14）——越界安全、通行性与视线分离、解析与校验
- `world/__tests__/manor.test.ts`（7）——关卡数据健全性：校验通过、出生点不在墙里、**全图连通（洪泛填充验证无孤岛）**、边界封闭、两类家具都被使用
- `game/views/__tests__/paint.test.ts`（7）——绘制清单与薄壳边界

关卡健全性用例值得特别说明：手写 ASCII 图出错是静默的（网格错位、区域不通、出生点落在墙里都不会报错），只在跑起来后表现为「AI 卡住」，很难定位。洪泛填充验证把所有地板与 NPC 都在同一连通域，这类问题被挡在关卡编辑阶段。

**M1 后续修正：视口与地图不匹配（同日）**

首版视口硬编码为 960×640，而地图是 1024×768。结果是右墙与下墙落在视口之外，画面看起来像「地图没画完”——绘制本身没错，是取景范围错了。这是设计疏漏：规划文档未定义视口与地图的关系。

修正为**视口由关卡推导，并设上限**：

- 地图不超过上限时，视口等于地图——整张地图（含四周边界墙）一屏可见，相机静止
- 地图超过上限（1280×800）时视口封顶，相机自动转为跟随卷轴

上限存在的意义：地图放大后若仍一屏看全，实体在屏幕上会小到不可辨。同一表达式（`clamp` 到 `worldSize - viewportSize`）在两种情形下都正确，地图长大时无需改代码。

修正同时补上了缺失的测试：`game/__tests__/config.test.ts`（6 例，累计 52）覆盖上限两侧的行为，以及端到端用例锁定「视口不小于地图」。这类跨层约束此前无人检查——`world/` 不知道视口，视口属于 `game/`。

### M2：键盘输入 + 玩家移动 + 墙体碰撞（2026-09-28 完成）

**交付**：

| 模块                         | 内容                                                                                             |
| ---------------------------- | ------------------------------------------------------------------------------------------------ |
| `world/geometry.ts`          | `TILE` 尺度与 `Rect`。`TILE` 从 `game/config.ts` 移来——它是「格子 ↔ 像素」的换算尺度，属世界几何 |
| `world/collision.ts`         | 分轴扫掠碰撞解算（`moveRect` / `rectBlocked`）                                                   |
| `game/systems/input.ts`      | 键盘源系统：方向键 / Shift 潜行 / 失焦清空                                                       |
| `game/systems/locomotion.ts` | 位置积分 + 碰撞 + 朝向写入，意图驱动                                                             |
| `game/state.ts`              | 玩家实体注册表（相机跟随的桥梁）                                                                 |
| `game/views/actor.tsx`       | 玩家与 NPC 视图                                                                                  |
| `game/views/camera.ts`       | 相机跟随玩家                                                                                     |

**M0 脚手架已删除**：`systems/scaffold.ts`、`views/marker.tsx`（及样式）。

**设计要点**：

- **碰撞是精确扫掠，不是步进试探**。按格边界直接算出第一个阻挡格并贴边：试探会在墙前留下最多一个步长的缝隙，且高速下可能穿透。用例锁定了「单帧位移远超地图宽度也不会穿墙」。
- **分轴解算（先 X 后 Y）**：撞墙时受阻轴贴边、另一轴照常移动，即沿墙滑行。整体停下会让斜向撞墙手感发滞。
- **意图与输入解耦**：`locomotion` 只认 `{ dx, dy, sneaking }`，不读键盘。玩家意图来自输入信号，M3 的 NPC 意图来自路径跟随——同一套移动逻辑。
- **`facing` 由 `locomotion` 独家写入**，且仅在实际产生位移时更新（顶着墙走不改变朝向）。
- **输入是源系统，不走实体注册**。它不属于任何实体，故只借用一个生命周期上下文（`input.attach(ctx)`），而非 `enter(id, ctx)` 形态。
- **`TILE` 归入 `world/`**：碰撞解算与渲染共用同一换算尺度，两处硬编码同一致是隐患。

**实施中发现并修正的几点**：

- **`flip` 不是合法的 CSS 属性**。首版用 `flip: scaleX(-1)` 做朝向镜像，浏览器会静默丢弃。改用真实属性 `scale`（值 `-1 1` / `1 1`）。
- **`Uint8Array` 迭代产出 `number`**：`Tile` 的 `as const` 对象在网格位图迭代时需显式断言回 `Tile`。
- **测试时钟必须可控**。同步 tick 时 `performance.now()` 只推进几微秒，`delta ≈ 0`、实体几乎不动，基于时间的断言（如「走到墙边」）会因走不完距离而失败。驱动替身改为固定步长推进虚拟时钟。
- **测试替身必须写回真实信号**。首版 harness 写内部 Map，验的是测试自己而非框架行为；修正为把 flush 结果写回实体信号。
- **相机跟随需要实体注册表**。玩家实体在 `Actor` 组件体内创建，而框架没有 ref API，组件树无法向上传出信号。`game/state.ts` 的 `playerEntity` 作注册表，`Actor` 在 `role === "player"` 时写入。

**测试**（41 例，累计 93）：

- `world/__tests__/collision.test.ts`（15）——自由移动、四向贴边、分轴滑动、极端位移不穿透、越界安全、矮家具阻挡
- `game/__tests__/movement.test.ts`（17）——方向映射（含 WASD 与方向键等价、后按键优先）、朝向四向切换、顶墙不转向、潜行减速、键盘事件与失焦清理
- `game/__tests__/interaction.test.ts`（9）——**端到端**：真实键盘事件 → 玩家在 DOM 中移动、撞墙停下且贴住墙沿、朝向反映到 `scale`、潜行标记生效

端到端用例是这一步最有价值的产出：单测只覆盖各段，而链路的接缝（信号未接线、监听未挂载、朝向未写进 DOM）只有端到端能发现。其中「撞墙后贴住墙的左沿而非停在半途」这条锁定了扫掠解算的精度。

### M3：NPC 生成 + A* 游荡 + 深度排序（2026-09-28 完成）

**交付**：

| 模块                         | 内容                                                                 |
| ---------------------------- | -------------------------------------------------------------------- |
| `world/path.ts`              | A* 寻路（二叉堆开放集）、`cellAt` / `cellCenter` / `collectWalkable` |
| `world/random.ts`            | 可复现的线性同余伪随机（含 `int` / `pick`）                          |
| `game/systems/navigation.ts` | 目标规划 + 路径推进 + 卡死看门狗 + `pathIntent`                      |
| `game/systems/behaviour.ts`  | NPC 状态机（闲游 / 驻足）                                            |
| `game/views/actor.tsx`       | 增加深度排序（zIndex 量化到格）                                      |

**设计要点**：

- _*A* 用 4 邻域，与移动的 4 向位移一致_*。若寻路给出斜向路径，移动系统走不出来，NPC 会在拐角卡住或抖动。4 向下的曼哈顿启发式可采纳，故为最优解。
- **寻路按实体节流**。只有「需要新路径」的实体才跑 A*；路径在实体上（`path` / `goal`），无需额外表。堆与 `Float64Array` 都在局部，不跨请求保留——换来的是一次分配，省掉状态清理。
- **路径推进（弹出已到达的点）归 navigation**。`path` 的写者只有它；`locomotion` 的意图来源只读 `path[0]` 求方向，不修改。单写者纪律。
- **看门狗计时语义是「距上次推进」而非「整条路径已跟随多久」**。首版按整条计时（6s），但一条 30 格的路径以 78px/s 走完需十几秒——正常路径会被误杀。改为「超过 4s 无推进」才放弃。
- **行为不直接指挥移动，而是影响 navigation 的目标选择**（`linger` 时不让 navigation 规划）。这样 locomotion 与意图来源都不知道「状态机」存在，行为切换只改一处。
- **行为切换等路径走完**。在路中间切换状态会让 NPC 突然停在空地中央，看起来像卡住。
- **意图来源按 `role` 分派**（`setIntent(role, source)`）。玩家读输入、客人读路径是本质不同的两类来源，用单一来源再内部分支会让组装层多一层间接。
- **固定随机种子**（`createRandom(20260928)`）：NPC 的目的地序列每次运行一致，便于对照与调试，也让测试可断言精确序列而非仅范围。

**实施中发现并修正的几点**：

- **`cellAt` 对非有限坐标返回 `{ col: null, row: null }`**（`Math.floor(NaN)` 为 `NaN`，写入 `Int32Array` 变 0）。这是真实的健壮性漏洞——实体 `x/y` 未写出的瞬间（如单独注册 navigation 而不注册 locomotion）会触发。改为返回 `null`，调用方显式处理。
- **`enabled` 字段的教训**：`Uint8Array` 迭代产出 `number`，与 `Tile` 断言处同理。

**测试**（31 例，累计 124）：

- `world/__tests__/path.test.ts`（17）——直线 / 绕行 / 最优性 / 完全封闭返回 `null` / 起终点重合返回空数组 / 越界 / 坐标换算互逆
- `game/__tests__/navigation.test.ts`（9）——目标规划、路径终点即目标、路径全程可通行、**固定种子序列可复现**、到达即弹出、看门狗触发与不误触发、行为状态切换
- `game/__tests__/wander.test.ts`（5）——**端到端**：NPC 真的移动、50 秒内不穿墙、多 NPC 不重合、zIndex 随 y 变化

端到端用例里「NPC 始终待在可通行格内」是最有价值的一条：它把寻路、路径推进、移动、碰撞四个环节的输出串起来验证。局部单测全绿但某一处接线错误时，NPC 就会穿墙，这条能抓住。

**实测**：模拟 60 秒，6 个 NPC 在三个区域间穿行，停留过 14000+ 个位置采样，最长静止帧数为 0（无卡死）。

### M4：视线判定 + 视锥可视化（2026-09-28 完成）

**交付**：

| 模块                          | 内容                                                            |
| ----------------------------- | --------------------------------------------------------------- |
| `world/vision.ts`             | 射线遮挡（Amanatides & Woo 体素遍历）、精确可见判定、视锥多边形 |
| `game/systems/perception.ts`  | 定频感知（~10Hz），写入 `visibleIds`                            |
| `game/views/vision.ts`        | 视锥计算的纯函数层 + canvas 绘制薄壳                            |
| `game/views/vision-layer.tsx` | 订阅帧计数的视锥图层（Tab 开关）                                |
| `game/state.ts`               | 角色注册表（视锥层遍历用）+ 视野开关信号                        |

**设计要点**：

- **判定与可视化分开，因为精确度要求不同**。玩法判定用「观察者中心 → 目标中心」的精确直线；可视化才用扇形采样。**采样射线不能用于判定**——它是离散的，目标恰好在两条射线之间时会被误判为看不见（或反之从墙缝漏过）。
- **对角缝特判**：射线恰好穿过格点时，要求两侧相邻格都不透明。否则视线会从两面墙对角相接的缝隙漏过去——棋盘式地图上很常见。
- **起点所在格不参与遮挡判定**：观察者自己的格不该挡住自己的视线。
- **遮挡读 `isOpaque` 而非 `isBlocked`**：矮桌挡路但看得穿，这是「趴下躲视线」类玩法的前提（规划文档 4.1）。
- **定频 ~10Hz**（每 6 帧一轮）：感知结果写入实体数据，渲染层照常每帧读取。100ms 延迟视觉上察觉不到，算力省下六分之五。
- **感知只写变化**：`visibleIds` 与上轮相同则不写。这是 memo 生效的前提——每轮都写会让所有订阅者无谓重算。
- **视锥层订阅帧计数而非各实体位置**：重绘是「全量重画一层」，一次订阅即可；订阅 N 个实体就有 N 次重绘请求。
- **`Vec2` 归入 `geometry.ts`**：此前 `path.ts` 与 `geometry.ts` 各声明一份，合并为单一定义。

**实施中发现并修正的几点**：

- **`computeCone` 对非正射程 / 张角产出退化多边形**：首点加零长度射线构成的多边形填色后是个小黑点，反而误导调试。改为返回空数组。
- **`sameIds` 需容忍未初始化状态**：实体已入池但尚未跑过一轮扫描时 `visibleIds` 是 undefined，直接比较 length 会抛错。「未初始化」是合法中间态。
- **`sightAngle` 与判定的角度约定必须一致**：屏幕坐标 y 轴向下，`FACING_ANGLES` 定义为「0 为正东、顺时针为正」，与 `Math.atan2(dy, dx)` 一致，因此视锥判定可直接相减比较；`normalizeAngle` 处理跨越 ±PI 的边界。

**测试**（41 例，累计 165）：

- `world/__tests__/vision.test.ts`（25）——空地 / 隔墙 / 高家具挡而矮家具不挡 / **对角缝不漏** / 起点不挡自身 / 命中点位置 / `maxDist` 限制 / 视锥对称性 / 三级判定各自独立生效 / **跨越 ±PI 的角度边界**
- `game/__tests__/vision.test.ts`（16）——视锥多边形数量与朝向差异 / 被墙裁剪 / Tab 开关与 `preventDefault` / **感知能真正检测到目标**（正对可见、背对 / 超射程 / 隔墙均不可见）

最后一条是这一步最关键的验证：前 12 例只证明视锥「画出来了」，而「可见 / 不可见」的正反用例才证明判定链本身正确——否则可能整个感知都是坏的，只是画面上看不出来。

**实测**：模拟 500 帧后打印视锥覆盖图，可确认扇形方向随朝向正确、被墙正确裁剪、贴墙 NPC 的视锥被完全裁掉。

### M5：可交互物 + 下药击杀 + 尸体（2026-09-28 完成）

**交付**：

| 模块                          | 内容                                              |
| ----------------------------- | ------------------------------------------------- |
| `world/interaction.ts`        | 面朝格、背后 / 正面判定（点积）、触及距离         |
| `world/levels/types.ts`       | 可交互物符号（`o`=酒瓶），与瓦片符号分开          |
| `world/levels/parse.ts`       | 解析 `propSpawns`（道具不落地为瓦片，其格为地板） |
| `game/systems/interaction.ts` | 拾取 / 下药 / 中毒倒计时 / 死亡                   |
| `game/views/prop.tsx`         | 酒瓶视图（拾取后 `Show` 隐藏）                    |
| `game/views/hud.tsx`          | 持有道具与交互提示                                |

**交互链**（规划文档 4.7 的面朝格模型）：

1. 按 `Space` → 算出手心格（玩家面朝方向的下一格）
2. 手心格上有酒瓶 → 拾取
3. 手心格上有活着的客人且持有酒瓶 → 下药（消耗酒瓶，启动 4.5s 倒计时）
4. 倒计时归零 → 客人死亡，尸体留在原地

**设计要点**：

- **可交互物符号与瓦片符号分开**。道具是实体（有 `taken` 状态、参与帧循环），不是瓦片；其所在格必须是地板，否则玩家够不着。`parseLevel` 产出独立的 `propSpawns`。
- **交互键用计数器而非布尔标志**。布尔标志需要「消费后清零」的双边协议；计数器只需消费方记住上次看到的值即可判定边沿（`新值 > 旧值`），一帧内按多次也不会漏。
- **各系统自声明字段需求（`Enter<Need>`）来容纳异形实体**（原为 `useEntity<PropEntity>(...)`）。道具不是角色，形状不同；注册时传入 `interaction.enterProp`，初值由 `spawnProp` 换算。
- **死者由各系统各自跳过**，而非从池中移除。尸体要留在场景里被看见（M6 的目击输入），所以实体必须存活；`navigation` / `behaviour` / `locomotion` / `perception` 各自判 `dead` 早退。这是「一个字段，多个读者」的合理用法——写入者只有 interaction。
- **中毒者继续游荡直到毒发**（有意设计）。因此尸体位置不等于下药位置——玩家需要预判或跟随。为免等待期成为无反馈的黑箱，加了头顶的中毒标记（小绿点）。
- **尸体在渲染上可与活人一眼区分**：旋转 90° + 压暗冷色。M6 的目击判读依赖这个区分。

**实施中发现并修正的几点**：

- **客人未注册交互系统**：首版只在玩家的 `enters` 里加了 `interaction.enter`，结果客人的 `dead` / `poisonLeft` 全是 `undefined`。交互字段是**两类角色共有**的——玩家需要（持有与下药），客人同样需要（被下药、变尸体）。只有导航与行为是客人专属。
- **`interaction` 需要实体信号而非裸数据**：判定要同时用位置 / 朝向（读值）与 id（排除自己、写回持有状态），而实体数据本身不含 id。

**测试**（24 例，累计 189）：

- `world/__tests__/interaction.test.ts`（12）——四向面朝格 / 未知朝向不误移 / 触及距离含边界 / 背后与正面判定 / 正侧方两者都不算 / 重合不算背后 / 归一化不产生 NaN
- `game/__tests__/kill.test.ts`（12）——**端到端**：道具渲染 / 拾取成功且酒瓶消失 / 空手下药失败 / 持瓶下药成功且延迟后死亡 / **尸体留在原地不再移动** / 尸体渲染可区分 / 长按不重复触发 / 松开后可再次触发

端到端那条「尸体留在原地不再移动」是 M5 验收标准里最容易悄悄坏掉的部分：若某个系统忘了判 `dead`，尸体会自己走起来，而单测各自全绿。

**实测**：拾取 → held=booze 且地图少一个 `o`；下药 → poisonLeft=4.48 且酒瓶消耗；毒发 → 客人变尸体留在原地。

### M6：目击 → 恐慌 → 传播 → 报警（2026-09-28 完成）

**交付**：

| 模块                         | 内容                                               |
| ---------------------------- | -------------------------------------------------- |
| `game/systems/alarm.ts`      | 目击判定、恐慌置位、警报累加                       |
| `game/systems/navigation.ts` | `pickGoal` 按 mood 分派（恐慌 → 反向逃跑）         |
| `world/path.ts`              | `furthestCells`（距威胁最远的候选点）              |
| `game/views/hud.tsx`         | 警报值与目击者计数（含等级配色）                   |
| `game/types.ts`              | `Mood` 增加 `panic`；新增 `witnessed` / `fleeFrom` |

**设计要点**：

- **恐慌不需要额外的传播机制**。恐慌者会逃跑，逃跑者被旁人看见时同样触发恐慌——传播链从 M4 的感知系统自然长出来。这比维护一张「谁知道什么」的传播表简单，也不会出现两处状态不一致。
- **状态不可逆**：`witnessed` 一旦置位不再清除。若允许冷静，玩家就能靠等待消除暴露，题材的紧迫感会消失。
- **「去哪」的决策全在 navigation**。alarm 只置状态（`mood` / `fleeFrom` / `witnessed`）并清空旧路径；`pickGoal` 按 mood 分派策略：panic 者朝远离威胁处跑，其余人随机游荡。与 locomotion 按 `role` 分派意图来源是同一形态——每个系统只做自己那一层的决策。
- **去重是必需的**：按「观察者 → 它已反应过的异常源」记录。缺了这层，站着的目击者会每轮扫描都 +12，警报瞬间爆表。
- **玩家不入恐慌池**：玩家不会因看见自己的尸体而恐慌，也不该计入目击者。分派在注册侧完成（`alarm.enter({ role })`）——入池即代表「此人参与恐慌链」，判据是身份而非每帧数据。字段初值（`witnessed` / `fleeFrom`）两类角色都给，由 `alarm.spawn()` 产出。
- **恐慌者到达后不歇息**（`idleLeft = 0`）：否则会在逃跑途中停 0.8~3.5 秒，看起来像「吓傻了」。
- **`behaviour` 在 `witnessed` 为真时早退**：`mood` 归 alarm 管，否则状态机会把 panic 切回 wander，逃到一半就停下。

**实施中发现并修正的几点**：

- **传染链会污染测试**：其他客人游荡时看见尸体就会恐慌，而恐慌者又会被本用例的观察者看见，于是「A 看见尸体」变成「A 看见恐慌的 B」。测试需要把无关角色隔离到地图边角、彼此间隔大于视距。这不是产品缺陷，而是「传播链真的在工作」的副作用。
- **测试里「钉住」必须逐帧做**：客人会自动寻路并**边走边转向**，钉一次撑不过 8 帧（一个感知周期）——「背对尸体」的用例会因角色自己转身而失败，看起来像判定坏了。

**测试**（11 例，累计 200）：

`game/__tests__/alarm.test.ts`——初始为 0 / 看见尸体则恐慌并计入警报 / **背对不恐慌**（视线判定生效）/ **同一具尸体只计入一次**（去重）/ 恐慌不可逆 / **恐慌者让他人也恐慌**（传播链）/ 多人目击累加 / 玩家不恐慌也不计数 / 恐慌后立即出发 / 恐慌者实际移动。

**实测的平衡数据**（放置尸体后警报随时间的变化）：

| 尸体位置            | 首次目击       | 警报满值 | 说明                   |
| ------------------- | -------------- | -------- | ---------------------- |
| (16,11) 大厅中央    | 约 1s          | 约 8s    | 人流密集，迅速扩散     |
| (10,3) 上厅走道     | 约 1s          | 约 8s    | 同上                   |
| (16,3) 上厅角落     | 约 4s          | 约 25s   | 需等人走近             |
| (2,2) / (4,11) 死角 | 60s 内无人发现 | —        | **位置选择有实际收益** |

最后一行是这个玩法成立的关键：**把尸体藏在视觉死角能真正避免被发现**。若所有位置都会被迅速发现，潜行就只剩速度竞赛，没有空间意识可言。

**待调的平衡参数**（当前值 → 影响）：

| 参数                | 当前       | 位置                                    |
| ------------------- | ---------- | --------------------------------------- |
| `ALARM_PER_WITNESS` | 12         | `alarm.ts`（满值 100，即约 9 人次目击） |
| `PANIC_DURATION`    | 30s        | `alarm.ts`（恐慌持续时长）              |
| 视距 / 视锥半角     | 7 格 / 30° | `perception.ts`                         |
| 客人速度            | 78 px/s    | `actor.tsx`                             |

**M6 修正：三个导致「NPC 全体停滞」的 bug（2026-09-28 同日）**

实测反馈「走一会儿人就都停下不动」。定位到三个互不相关的缺陷叠加，且都只在长时间运行后才显现：

**1. 恐慌永不过期。** `behaviour` 在 `witnessed` 为真时直接早退（M6 首版为避免状态机把 `panic` 切回 `wander`），于是 `moodLeft` 再无人递减——`PANIC_DURATION`（30s）永远不会到期，`mood` 永久停在 `panic`。

根因是把**「记忆」与「情绪」混为一谈**：`witnessed` 该永久保留（我见过尸体），但 `panic` 是临时状态，该有结束。修正后 `behaviour` 照常递减 `moodLeft`，到期把 `mood` 切回 `wander` 并清空 `goal` / `path` / `fleeFrom`。

**2. 恐慌目标可能是自身所在格。** `furthestCells` 未排除调用方已站立的格，于是 `findPath(自身, 自身)` 返回空路径。修正为接受 `exclude` 参数（约束由调用方提供，它才知道当前格）。

**3. 空数组是 truthy。** 这是最隐蔽的一个：

```ts
e.path = path ? [...path] : []; // [] 是 truthy → 把「已在目标格」当成成功
e.goal = path ? goal : e.goal; // goal 被保留
```

NPC 站在目标格里时，`findPath` 返回 `[]`（起终点重合），代码却认为规划成功、保留同一个 `goal`；下一帧重新「规划到当前格」又得到空路径——**无限空转**。表现为静止 3 分钟以上。修正为显式判定 `path !== null && path.length > 0`，并在到达终点时清掉 `goal`。

**教训**：三个 bug 的症状完全一样（站着不动），但根因分别在状态机、目标选择、JS 陷阱三处。单点单测全绿，只有**长时程端到端模拟**能暴露——`stuck.test.ts` 由此而来，用「所有客人位置连续不变的帧数」作为指标。

修正后实测：最长静止帧 **11116 → 0**，恐慌正常到期（5 → 1 → 0），NPC 恢复游荡。

**测试新增 5 例（累计 205）**：`game/__tests__/stuck.test.ts`——无事件 5 分钟无僵死 / 恐慌后 5 分钟无僵死 / 恐慌到期归零而记忆保留 / 恐慌后恢复游荡（不会「既无路径也无目标」）/ 长时间运行不产生 NaN 坐标。

**交付**：

| `engine/game.ts`        | 修正**帧内 `stop()` 失效**（见下；现已迁至 `packages/engine`） |

**设计要点**：

- **重开靠声明式重建**。递增 `runId` 即改变全部实体 key，框架卸载旧条目、挂载新条目——实体池随 `onUnmount` 清空、`enter` 重新执行。不需要 `dispose`，也不必逐个字段手动复位（规划文档 4.6 的落地）。
- **判定只在 `playing` 阶段生效**，判定后立即 `stop()`。结算界面是静态的，继续跑帧只会让已死的人继续被杀。
- **胜负条件有优先度**：达成目标优先于被抓。否则「杀掉最后一个目标但警报恰好满值」会误判为失败。
- **击杀计数在判死处累加**（interaction），不由规则系统轮询——「谁死了」的真相源只有一处；规则系统只读计数、决定何时终局。
- **`rules` 排在系统流水线最后**：它读的是本轮结束时的击杀数与警报值，放前面会用上一帧的数据。
- **关卡目标取「击杀指定人数」制**（规划文档 8.4）：`killGoal = 2` 且刻意低于客人总数（6）——「杀光」在 6 人规模下没有取舍余地。

**实施中发现并修正的几点**：

- **帧内 `stop()` 完全失效**（引擎缺陷）。`loop()` 末尾无条件 `requestAnimationFrame(loop)`，于是帧内调用 `stop()` 后仍会继续跑——游戏结束后在后台空转。修正为重新排队前检查 `running`；同时引入 `inFrame` 处理「帧内 stop 再 start」，否则会排出两个回调、帧率翻倍。新增 2 例锁定（后随引擎迁移至 `packages/engine/src/__tests__/game.test.ts`）。
  > **后续（2026-10-02）**：这个守卫在引擎抽成独立包时又丢了一次（见 `saboteur 引擎迁移：切换到 engine 包.md` §3.1）。这正是「两套引擎同步维护」的代价——已通过迁移消除。
- **`class` 必须传信号才响应**。首版写 `class={[style.overlay, settled() ? style.visible : ""].join(" ")}`——这是**渲染时求值一次**的普通字符串，结算界面因此永远不显示。同理 `actor.tsx` 的尸体配色也不会切换。全部改为传派生信号。新增用例锁定（`kill.test.ts` 的「尸体换用不同的 class」）。
- **`gameState` 是模块级单例，同文件内跨用例共享**。上一例压过的时限、击杀数会带到下一例，导致一开局就 `timeout`。测试需在 `beforeEach` 复位全局状态——实体随组件卸载而清理，但信号不会。
- **`Show` 的注释锚点会污染指令子元素**。中毒 / 恐慌标记与 `StyleMemo` 的 `div` 并列时，隐藏状态下的注释锚点成为指令的直接子节点，框架每帧报 7×2=14 条「directive skipped non-Element child」。把标记移进该 `div` 内部即消除。
- **测试的「僵死」判据要排除终局**。警报满值只需约 6~8 秒，之后帧循环停止、一切静止是正确行为。长时程用例需以 `phase === "playing"` 为界，或把警报压回 0 以观察完整周期。

**测试**（20 例，累计 225）：

- `game/__tests__/rules.test.ts`（18）——目标配置 / 时限递减 / `timeout` / `caught` / `won` / **达成目标优先于被抓** / 终局后不再判定 / 击杀数由死亡累加 / 重开复位（阶段、计数、时限、警报、实体数不累积、可重复多局）/ R 键重开 / 结算三态文案
- `game/__tests__/engine/lifecycle.test.ts`（2）——（已随迁移删除，同一契约现在由 `packages/engine/src/__tests__/game.test.ts` 覆盖）

**实测完整对局**：


### 试玩反馈三则（2026-10-08）

用户实际游玩后报的三个问题。三条都不是「新功能」，而是**已有实现的缺陷**。

#### ① 重开一局后捡不了瓶子

**根因**：`playerEntity` 是**单槽注册表**，而重开是「先挂载新的、后卸载旧的」（实测顺序）。于是新玩家写入后，**旧玩家的 `onUnmount` 把它清成 `undefined`** → 交互系统第一行 `if (!entity) return` 静默失效。

**修法**：卸载时**只在「我还是当前的玩家」时才清空**：

```ts
onUnmount(() => {
  if (playerEntity()?.id === entity.id) playerEntity(undefined);
});
```

**同一 bug 家族还牵出第二个**：`interaction` 的 `heldItem` / `hint` 是**模块级信号**，不在实体上，声明式重建碰不到它们——不归零就会残留（新玩家空手，HUD 却显示「持有酒瓶」）。给 `interaction` 加 `reset()`，由 `restartRun()` 与 `alarm.reset()` 并列调用。

**教训（值得记）**：声明式重建（递增 `runId`）只覆盖**实体上的数据**。模块级信号必须由 `restartRun()` 显式复位——这是「重置」的两条并行路径，漏一条就是残留。两者都不是类型错误，`tsc` 全绿。

#### ② 必须正对着那一格才能操作

交互原本只查**面朝方向的相邻格**。实玩反馈「很别扭」——往往要反复转身对齐。

**修法**：候选格改为**两个**（脚下 + 面前），脚下优先。附带一个例外：**已持有同款时拾取是空操作**（只报提示），此时让位给下药——否则站在酒瓶上就没法给面前的客人下药（脚下格引入后才会出现的新情况）。

#### ③ 单位不显示朝向

**根因（本文件 §6.3 曾写错的同一件事）**：朝向一直用 `scale: -1 1` 表达，但占位形体**左右对称**——镜像对称形状是**静默失败**，DOM 里写着，屏幕上没有。

**修法**：改为一个**不对称的方位箭头**，`rotate` 到四个角度。死亡时隐藏（尸体已 `rotate 90deg` 放倒，箭头会指向错的位置）。

**测试的诚实边界**：这条改动**无法被单元测试证明「可见」**——happy-dom 没有布局引擎，把箭头换回对称方块后测试照样通过（已实测反证）。所以测试只锁定它能锁的（存在独立旋转层、四向四个不同角度、尸体无箭头），并在注释里**写明不能测什么**。

#### ④ 箭头根本不存在、红点与它重叠（同一次反馈的后续）

用户接着反馈「红点和箭头的位置有问题」。查下去发现**两个**问题，且第一个是**上一次修改时的事故**：

**问题一：`.facingArrow` 的样式规则根本不存在。**

`actor.tsx` 里写着 `class={style.facingArrow}`，但 `actor.module.scss` 里**没有** `.facingArrow` 规则——我上一轮中途跑过一次 `git checkout -- actor.module.scss`（想回退别的改动），把刚写好的箭头样式连带删了，而 TSX 的引用没跟着改。

后果：那个 `<span>` 拿不到任何样式（0×0，不可见），**而 `tsc` 全绿、21 条测试全绿**——因为「引用一个不存在的 CSS Module 类」在**类型上完全合法**。

**问题二（设计）：箭头与状态点都挤在「头顶正中」。**

`.poisonMark` / `.panicMark` 是 `top:-5px; left:50%`，箭头也是头顶正中。三者叠在一起。而且箭头**不会绕到朝向那一侧**——它停在头顶原地打转，朝东时箭头仍在头顶指向右，而不是在身体右侧。

**修法**：

- 箭头拆成**两层**：`.facing` 是与身体同尺寸的旋转层（`inset: 0`，旋转轴 = 身体中心），`.facingArrow` 画在它上缘并 `translateX(-50%)` 居中。于是箭头随朝向**绕到身体那一侧**，而不是原地打转。
- 状态点分到**左上 / 右上两个角**（`left:-4px` / `right:-4px`），与箭头永不相撞。

#### 一个值得单记的教训：**CSS Module 的错误在 Vitest 里测不出来**

排查时发现的这件事，比 bug 本身更重要。

**Vitest 默认不处理 CSS**：CSS Modules 被替换成一个 **Proxy**，访问**任何**属性都凭空生成一个类名：

| 表达式                                  | 测试环境（Vitest）                  | 生产构建               |
| :-------------------------------------- | :---------------------------------- | :--------------------- |
| `style.facingArrow`（规则存在）         | `"_facingArrow_03dee2"`             | `"_facingArrow_pg9yx"` |
| `style.facingArrow`（规则**不存在**）   | `"_facingArrow_03dee2"`（**假的**） | `undefined`            |
| `style.definitelyNotARealClass`（瞎编） | `"_definitelyNotARealClass_03dee2"` | `undefined`            |

所以任何「断言 `className` 不是 `undefined` / 是合法类名」的**运行时**测试**永远通过**，给出的是**假的安全感**。生产里那个 class 会变成字面量 `"undefined"`，静默失效。

**正确做法**：读**源文件**做静态比对——直接检查那条被违反的不变式（「`style.X` 引用的类必须在 SCSS 里有规则」）。见 `interaction.test.ts` 的「静态校验」describe。

> 附带一个**反证有效性的教训**：我第一版就是写成运行时断言，自认为在测「类存在」；**反向验证时（删掉规则）它照样通过**，才发现测错了东西。**「测试通过」只有在「反向验证会失败」时才有意义。**

### 12.2 难度现状与倾向

实测「放置尸体后警报满值耗时」：

| 尸体位置            | 首次目击       | 警报满值 |
| ------------------- | -------------- | -------- |
| 大厅中央 / 上厅走道 | 约 1s          | 约 8s    |
| 上厅角落            | 约 4s          | 约 25s   |
| 地图死角            | 60s 内无人发现 | —        |

**当前位置选择有实际收益**（死角能真正藏住尸体），这是玩法成立的关键。

**但整体难度偏高**：大厅里杀人后约 8 秒警报即满值，而单局时限是 150 秒。这来自两个因素的叠加：

1. `ALARM_PER_WITNESS = 12`（约 9 人次目击就满）
2. 视距 7 格 + 传播链——目击者逃跑时会把恐慌带给更多人

**可选的调参方向**（未实施，待手感确认）：

- 降低 `ALARM_PER_WITNESS`（如 8），或改为「只有第一手目击者计入、传播者不计入」
- 缩短 `SIGHT_RANGE`（如 5 格），让躲藏更可行
- 给警报加入**衰减**（长时间无症状则回落），当前是单调递增
- 增加「藏尸」交互（把尸体拖进柜子），这需要关卡里加入容器

**注意**：以上都是手感问题，**跑一次 `vp dev` 比看数据准得多**。

### 12.4 给接手者的几点提醒

- **`world/` 不得导入 `kiaao`，且不得认识任何游戏概念**。这是本项目最重要的架构约束（§2.2），它让寻路、视线、碰撞全部可脱离渲染单测。**实测：仓库里并没有固化它的 lint 配置**（`world/index.ts` 曾误称有）；目前靠人工遵守。地图符号的解读属 `game/`（§8.9）。
- **新增一只 NPC**：建 `game/npcs/<role>.ts`（户口本），在 `index.ts` 的 `actorDefs` 登记。**不必碰任何系统、也不必碰 `world/`**——装配层按能力推导要注册哪些系统，符号表从户口本汇总（§8.8 / §8.9）。漏写会在 `Record<Role, NpcDef>` 处报错。
- **`class` 必须传信号才响应**。写普通三元或数组拼接会在渲染时求值一次后固定——这是本项目中反复踩到的坑（§11 的 M7 一节）。
- **`gameState` 是模块级单例**。测试里跨用例共享，需在 `beforeEach` 复位。
- **长时程用例要排除终局**。警报满值约 6~8 秒就会停帧循环，之后静止是正确行为。
- **`entity()` 是渲染快照，活对象走 `frame(id)`**。需要写入实体时用后者——写信号会被下一帧 `flush` 覆盖（§5.2）。
- **`entity.id` 是唯一从信号上读的非信号属性**，且有真实用途（`frame(id)` / 排除自己）。不要把其它东西再挂上去（曾挂过 `state`，已删：它把系统的数据挂到了组件的句柄上）。
- **新增系统时**：字段需求用 `Enter<Pick<ActorEntity, ...>>` 声明，初值用 `spawn()` 纯函数产出，视图里组合。漏写字段会在 `define(...)(state)` 处报错。

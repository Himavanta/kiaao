# 异步组件注释占位符优化方案

**状态**：草案
**关联**：kiaao v4.1 异步组件模型
**前置依赖**：[DOM 节点多实例共享 — 改造方案](./multi-instance-on-node.md)

## 一、背景

### 1.1 当前异步组件的 wrapper 机制

当前异步组件在 `h()` 中检测到返回值是 Promise 时，创建一个 `<div style="display: contents">` 作为 wrapper。wrapper 从创建到卸载始终是组件的根节点，持有 `DISPOSE_KEY`。Promise resolve 后，`realDOM` 作为子节点插入 wrapper。

```
DOM 结构（resolve 后）：
<div style="display: contents">   ← wrapper（持有 DISPOSE_KEY）
  └── <div>真实内容</div>          ← realDOM（无组件实例标记）
```

### 1.2 wrapper 机制的问题

**引入额外 DOM 节点**：异步组件在 DOM 树中永久多了一层 `<div style="display: contents">`。虽然布局不可见，但影响 CSS 选择器（`:nth-child`、`>` 直接子代）和 DOM 遍历 API。

**与 Fragment 语义重叠**：Fragment 也是 `<div style="display: contents">`。当异步组件返回 Fragment 时，DOM 中出现两层透明包裹，进一步放大了 DOM 干扰。

**替换后的不一致**：如果 Promise resolve 后用 `realDOM` 替换 wrapper（之前的讨论方向之一），`when`/`each` 指令持有的 wrapper 引用会失效，引入了引用管理复杂度。

### 1.3 Set 方案提供的新可能

DOM 节点多实例共享改造方案（以下简称 Set 方案）将 `INSTANCE_KEY` 和 `DISPOSE_KEY` 从单值改为 Set，允许多个组件实例在同一个 DOM 节点上共存。这一改造解锁了一个关键能力：**组件的实例锚点不再需要一个独占的容器。** 一个轻量的注释节点足以承载实例关联。

## 二、新方案设计

### 2.1 核心思路

**用注释节点作为异步组件的占位符，取代 `<div style="display: contents">` wrapper。**

- 创建异步组件时，返回一个注释占位符 `createComment("")`，在注释上初始化 Set 并加入当前组件实例。
- Promise resolve 后，用 `realDOM` 替换注释（`comment.replaceWith(realDOM)`），并把注释上的 Set 迁移到 `realDOM` 上。
- `triggerMount` 在替换后的 `realDOM` 上递归触发。
- 当前异步组件自身的 `mountCallbacks` 在最后手动触发。

**最终 DOM 结构**：与同步组件完全一致。异步组件在 DOM 中不留下任何额外痕迹。

### 2.2 注释占位符的优势

**零 DOM 干扰**：注释节点不影响任何 CSS 选择器，不影响布局计算，不影响 `children` 遍历。它在 DOM 中的存在是“透明的”——比 `display: contents` 更彻底。

**与框架惯例一致**：kiaao 已有两处使用注释占位符：无效 tag 兜底返回 `createComment("")`，Portal 挂载时返回注释占位。异步组件使用注释占位符，与这些已有惯例保持一致。

**替换后完全干净**：`replaceWith` 将注释完全移出 DOM 树。不像 wrapper 方案那样留下永久容器。异步组件 resolve 后的 DOM 结构与同步组件完全相同。

### 2.3 为什么替换而不是保留注释

wrapper 方案中，wrapper 保留在 DOM 中是为了在卸载时能找到组件实例（`DISPOSE_KEY` 在 wrapper 上）。Set 方案下，`realDOM` 上的 Set 已经包含了组件实例关联，不再需要 wrapper 作为清理入口。注释在完成“占位”使命后可以被安全替换。

## 三、实现细节

### 3.1 异步组件流程（新）

```ts
if (result instanceof Promise) {
  // —— 异步组件 ——
  // 1. 创建注释占位符
  const placeholder = createComment("");

  // 2. 在注释上初始化 Set 并加入当前组件实例
  placeholder[DISPOSE_KEY] = new Set();
  placeholder[DISPOSE_KEY].add(createDisposeFn(instance));
  // 注释不需要 INSTANCE_KEY——triggerMount 不会遍历到它（或即使遍历到，Set 中当前实例尚未初始化）

  let disposed = false;
  instance.unmountCallbacks.push(() => {
    disposed = true;
  });

  // 3. 等待 Promise resolve
  result
    .then((realDOM) => {
      if (disposed) return;

      // 4. 防御性检查
      if (!(realDOM instanceof Node)) {
        if (__DEV__) console.warn("[kiaao] async component resolved with non-Node value:", realDOM);
        realDOM = createComment("async component resolved with invalid value");
      }

      // 5. 迁移 Set：把注释上的 DISPOSE_KEY Set 迁移到 realDOM
      const disposeSet = placeholder[DISPOSE_KEY];
      if (disposeSet) {
        if (!realDOM[DISPOSE_KEY]) {
          realDOM[DISPOSE_KEY] = new Set();
        }
        disposeSet.forEach((fn) => realDOM[DISPOSE_KEY].add(fn));
        disposeSet.clear();
      }

      // 6. 用 realDOM 替换注释
      placeholder.replaceWith(realDOM);

      // 7. 递归触发子树中所有同步子组件的 onMount
      triggerMount(realDOM);

      // 8. 触发当前异步组件自身的 onMount
      if (!instance[INITIALIZED_KEY]) {
        instance[INITIALIZED_KEY] = true;
        instance.mountCallbacks.forEach((fn) => safeCall(fn, "onMount"));
      }
    })
    .catch((err) => {
      if (disposed) return;
      console.error("[kiaao] async component error:", err);
    });

  return placeholder;
}
```

### 3.2 Set 迁移说明

注释上的 `DISPOSE_KEY` Set 包含当前异步组件实例的清理函数。`replaceWith` 后注释脱离文档，不再参与 `disposeNode` 的递归遍历。如果不迁移 Set，组件卸载时将找不到实例关联。

迁移过程：

1. 取出注释上的 `DISPOSE_KEY` Set
2. 如果 `realDOM` 上没有 `DISPOSE_KEY`，初始化一个空 Set
3. 将注释 Set 中的所有清理函数追加到 `realDOM` 的 Set 中
4. 清空注释的 Set

注意：这里不使用“合并 `INSTANCE_KEY` Set”的逻辑，因为注释上没有 `INSTANCE_KEY`（注释不需要在 `triggerMount` 遍历时被触发，异步组件的挂载回调是手动触发的）。如果未来的设计需要在注释上放 `INSTANCE_KEY`，迁移时需要同步处理。

### 3.3 卸载场景

**Promise resolve 前卸载**：
`disposeNode(placeholder)` → 遍历 placeholder 上的 `DISPOSE_KEY` Set → 执行清理函数 → `disposed` 标志位阻止 Promise 的 `.then()` 操作。

**Promise resolve 后卸载**：
`disposeNode(realDOM)` → 遍历 `realDOM` 上的 `DISPOSE_KEY` Set（已从注释迁移过来）→ 执行当前异步组件实例的清理函数 + 递归清理 `realDOM` 子树中的所有子组件。

**父组件卸载**：
`disposeNode(parentRoot)` 递归遍历到 placeholder（或替换后的 `realDOM`），后续同上。

## 四、与旧方案对比

| 维度                  | 旧方案（wrapper）                 | 新方案（注释 + 替换）                          |
| --------------------- | --------------------------------- | ---------------------------------------------- |
| 占位 DOM              | `<div style="display: contents">` | `<!-- -->`（注释节点）                         |
| resolve 后 DOM        | wrapper > realDOM                 | realDOM（与同步组件完全一致）                  |
| CSS 影响              | 影响 `:nth-child`、`>` 等选择器   | 无影响                                         |
| DOM 遍历影响          | `children` 等 API 包含 wrapper    | 无影响                                         |
| 嵌套异步 + Fragment   | 两层透明包裹                      | 一层包裹（仅 Fragment）                        |
| 与同步组件 DOM 一致性 | 不一致（多一层）                  | 完全一致                                       |
| 卸载入口              | wrapper 上的 `DISPOSE_KEY`        | 注释（或迁移后 realDOM）上的 `DISPOSE_KEY` Set |

## 五、与 Set 方案的协同

### 5.1 注释上的多实例共存

如果异步组件本身也是另一个组件的返回值（如 Portal 包裹异步组件），注释上的 `DISPOSE_KEY` Set 会包含多个组件实例的清理函数。迁移时，整个 Set 被迁移到 `realDOM` 上。卸载时，`disposeNode` 遍历 Set 中所有清理函数，确保每个组件实例都被正确销毁。

### 5.2 Fragment 不受影响

Fragment 仍然是 `<div style="display: contents">`。本次优化只影响异步组件的占位机制，不涉及 Fragment。Fragment 的透明包裹是 kiaao 对“无宿主元素片段”的折衷方案，其存在理由是独立于异步组件的。

### 5.3 与 Portal 的关系

Portal 返回注释占位符（当 `to` 目标不存在时）。如果 Portal 内部渲染一个异步组件，注释嵌套是合理的——外层注释（Portal 占位）和内层注释（异步组件占位）是两个不同的节点，不会冲突。Set 方案保证了两个注释上的实例关联各自独立。

## 六、边界情况

### 6.1 嵌套异步组件

```js
async function Parent() {
  await fetchA();
  return (
    <div>
      <AsyncChild /> {/* AsyncChild 有自己的注释占位符 */}
    </div>
  );
}
```

流程：

1. `Parent` 返回 Promise → 创建注释 A
2. 渲染 `<AsyncChild />` → `AsyncChild` 返回 Promise → 创建注释 B（作为 `<div>` 的子节点）
3. `Parent` 先 resolve → `realDOM` 替换注释 A → `triggerMount(realDOM)`
4. `triggerMount` 遍历到注释 B（此时 `AsyncChild` 可能尚未 resolve）
5. `AsyncChild` 后 resolve → 用 `realDOM_B` 替换注释 B → `triggerMount(realDOM_B)`

两个异步组件的注释各自独立，替换后 DOM 结构与同步嵌套组件完全一致。

### 6.2 异步组件返回 Fragment

```js
async function Comp() {
  const data = await fetch();
  return (
    <>
      <span>{data.a}</span>
      <span>{data.b}</span>
    </>
  );
}
```

`Comp` 返回 Promise，框架创建注释占位符。Promise resolve 后，`realDOM` 是 Fragment 的 `<div style="display: contents">`。`replaceWith` 将注释替换为这个 Fragment 容器。最终 DOM 中只有一层 Fragment 包裹，没有多余的异步 wrapper。

### 6.3 异步组件的 setter 触发

异步组件也是派生信号的 getter，支持 setter 触发重算。`setter(value)` 调用时，组件函数重新执行，返回新的 Promise。旧的注释已被替换，新的 Promise 创建新的注释占位符。这是异步组件 setter 行为的自然延伸，注释占位符机制不需要为此做特殊处理。

## 七、迁移指南

### 7.1 对现有代码的影响

**零影响。** 异步组件的公开 API 完全不变。开发者仍然写 `async function Comp(props, context) { ... }`，框架内部改用注释占位符。从外部看，行为完全一致——`onMount` 延迟到 Promise resolve 后触发，`onUnmount` 在任何阶段都能正常注册和触发。

### 7.2 对 CSS/选择器的影响

从有影响（`display: contents` 包裹带来的选择器干扰）变为**零影响**。注释节点对 CSS 完全透明。这是一个正向的破坏性变更——开发者之前可能需要为异步组件的包裹层调整选择器，现在不再需要。

### 7.3 对测试的影响

如果测试中依赖了异步组件 wrapper 的 DOM 结构（如 `container.firstChild` 是 wrapper 而非内容），需要更新。如果测试只关心最终渲染结果，不受影响。

### 7.4 实现时的注意事项

- `replaceWith` 之后，注释节点脱离文档。如果外部代码持有注释节点的引用，替换后该引用指向一个脱离文档的节点。这和当前 wrapper 方案中“wrapper 始终是根节点”的行为不同。一般来说，外部代码不应该持有组件返回节点的引用，但如果有（如 `when` 指令内部），需要确认不会因此出错。
- Set 迁移时使用 `forEach` + `add` 而不是直接赋值，以避免覆盖 `realDOM` 上已有的 Set（可能来自其他组件实例）。

## 八、设计哲学

这次优化是 Set 方案连锁效应的典型案例。当 DOM 节点能够承载多个组件实例后，“独占容器”就不再是必需品。一个注释节点足以完成占位任务，因为它在 DOM 中不留下任何痕迹。

这与 kiaao 一贯的设计取舍一致：**接受内部数据结构的微小复杂度增加（Set 替代单值），换取外部行为的简洁性（DOM 结构与同步组件完全一致）。**

# nodeMap 引用失效问题分析

你的担忧非常精准。这个问题确实存在，但它揭示了一个比“修复 renderEach”更根本的设计原则。

---

## 问题的本质

注释占位符 + `replaceWith` 的优化，核心代价是：**异步组件的 DOM 产出在生命周期中发生了节点替换。** 这与 wrapper 方案有本质区别——wrapper 方案中，组件的根节点从生到死都是同一个元素，外部持有者无需关心内部变化。

当 `renderEach` 的 `nodeMap` 缓存了一个注释节点，而这个注释节点被异步组件内部的 `replaceWith` 替换后，`nodeMap` 持有了一个脱离文档的过时引用。这不是 `renderEach` 的错，而是 **`replaceWith` 是一个破坏性操作，它改变了异步组件在 DOM 中的身份。**

---

## 你的修复思路的局限

用 `isConnected` 检查来处理过时引用，技术上可行。但有几个不够干净的地方：

**1. 它把异步组件的内部实现细节泄露给了 renderEach。** renderEach 不需要也不应该知道子节点是同步组件还是异步组件、是否发生了节点替换。它只知道“我有一个节点引用，我需要判断它是否还有效”。

**2. `isConnected` 检查是治标不治本。** 节点脱离文档不仅仅是 `replaceWith` 造成的——任何将节点从 DOM 中移除的操作都会导致 `isConnected` 为 false。renderEach 无法区分“节点被异步组件替换了”和“节点被其他逻辑移除了”，只能一刀切当作新节点处理，可能丢失本应复用的节点。

**3. 它引入了一个隐式的 GC 时机问题。** 旧注释何时被 GC？如果没有其他引用，它会在 `replaceWith` 后被回收。但如果 renderEach 的 `nodeMap` 仍然持有引用，旧注释就不会被 GC，导致内存泄漏。

---

## 更根本的思路：让异步组件主动更新外部引用

问题的根源不在于 renderEach 需要更聪明地检测失效引用，而在于 **`replaceWith` 发生后，异步组件没有通知任何持有旧引用的人“我的根节点变了”。**

wrapper 方案没有这个问题，因为 wrapper 从生到死都是同一个 DOM 元素。`replaceWith` 打破了这个不变性。要修复，最干净的方式是让异步组件**主动更新那些缓存了旧注释的地方**。

对于 `renderEach` 来说，这就意味着：异步组件 resolve 后，找到 `nodeMap` 中对应的条目，把值从旧注释更新为 `realDOM`。

### 具体方案

异步组件在 `replaceWith` 之后，检查旧注释上是否有 `nodeMap` 的关联信息，如果有，更新它。

```ts
// renderEach 内部，将节点存入 nodeMap 时
nodeMap.set(identity, node);
// 同时给节点打上标记，方便异步组件找到 nodeMap 中的条目
node[EACH_ITEM_KEY] = { nodeMap, identity };
```

```ts
// 异步组件 resolve 后
placeholder.replaceWith(realDOM);
// 迁移 nodeMap 引用
const itemInfo = placeholder[EACH_ITEM_KEY];
if (itemInfo) {
  itemInfo.nodeMap.set(itemInfo.identity, realDOM);
  realDOM[EACH_ITEM_KEY] = itemInfo;
}
```

这样做的好处：

- renderEach 的 sync 逻辑完全不变，不需要 `isConnected` 检查，不需要特殊分支
- nodeMap 中的引用始终指向当前有效的 DOM 节点
- 旧注释在 `replaceWith` 后脱离文档，`EACH_ITEM_KEY` 的引用也被清除，不再被 renderEach 持有，可以被 GC 正常回收

---

## 但这引入了一个新的依赖方向

renderEach 目前完全不知道异步组件的存在。上面的方案让异步组件和 renderEach 之间产生了双向感知——renderEach 在节点上留下标记，异步组件在替换时更新标记。

这在架构上不太干净。**renderEach 不应该为异步组件的内部行为负责，异步组件也不应该知道 renderEach 的存在。**

---

## 真正干净的方案：异步组件不使用 replaceWith，回归 wrapper

回到原点。`replaceWith` 带来的“DOM 完全干净”的优势，是以**破坏节点身份不变性**为代价的。这个代价在列表渲染场景中暴露了出来，但它在任何缓存 DOM 节点引用的场景中都会成为问题——不仅仅在 renderEach 中。

wrapper 方案没有这个问题，因为节点身份不变。注释占位符 + `replaceWith` 的优化，本质上是拿“DOM 结构干净”换“节点身份不稳定”。**在 kiaao 的设计哲学中，节点身份稳定比 DOM 结构干净更重要。**

kiaao 选择不引入虚拟 DOM，选择用 `display: contents` 包裹 Fragment，都体现了同一个原则：**节点在生命周期中保持身份不变，是比“零多余节点”更高的优先级。**

---

## 我的建议

**保留 wrapper 方案，放弃注释占位符 + replaceWith 的优化。**

理由：

1. wrapper 保证了组件根节点在生命周期中身份不变，所有外部引用始终有效
2. `display: contents` 的代价已经被仔细评估，且在 Fragment 和异步组件文档中已向开发者说明
3. 注释占位符优化带来的 DOM 简化，不值得用节点身份不稳定的风险来交换
4. 这与 kiaao 一贯的设计权衡一致——宁可多一层透明包裹，也不引入隐式的节点替换

异步组件文档中之前更新的注释占位符优化方案，建议回退。异步组件保持与当前实现一致的 wrapper 机制，不需要改动。

---

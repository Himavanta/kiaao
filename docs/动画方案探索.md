# 动画方案探索与 Motion 指令实现

**状态**：阶段总结 + 实现指南
**关联**：kiaao v4.2 自定义指令系统
**日期**：2026年6月14日

> **声明**：本文档中的代码示例均为示意伪代码，用于说明概念和设计模式。具体实现由开发者根据实际需求自行决定。

## 一、背景

### 1.1 问题的起点

kiaao 希望为开发者提供动画能力，特别是**进入动画**和**退出动画**。进入动画相对简单——元素插入 DOM 时，CSS 的 `animation` 属性会自动触发，JS 动画库可以在元素挂载后调用。但退出动画需要框架在移除 DOM **之前**等待动画完成——否则动画还没播放，元素就已经消失了。

最理想的使用体验是声明式的：

```jsx
<div when={visible}>
  <Motion from={{ opacity: 0 }} to={{ opacity: 1 }}>
    <div class="content">动画内容</div>
  </Motion>
</div>
```

当 `visible` 变为 false 时，框架应等待退出动画播放完毕再移除 DOM。

### 1.2 核心矛盾：异步挂载可行，异步卸载不可行

在 kiaao 中，挂载和卸载的触发点处于框架的不同层级：

|                  | 异步挂载                    | 异步卸载             |
| ---------------- | --------------------------- | -------------------- |
| 触发方           | Promise.then（框架外部）    | 派生回调（框架内部） |
| 与派生回调的关系 | 无关                        | 在派生回调内部       |
| 能否 await       | 能（Promise.then 天然支持） | 不能（派生回调同步） |
| 框架支持         | ✅ 已实现（异步组件）       | ❌ 不可行            |

**根本原因**：`when`/`each` 的 DOM 清理发生在**派生回调**中。派生回调是同步的——信号变化后立即同步执行所有下游派生。如果在 `disposeNode` 中等待退出动画的 Promise，派生回调就需要变成异步——这将破坏 kiaao 响应式系统的核心模型。

## 二、React / Vue / Solid 的退出动画处理方式

### 2.1 React：用户控制时序，库辅助状态管理

React **没有内置的退出动画支持**。社区库（如 `react-transition-group`）通过**延迟状态更新**来实现退出动画。

**时序流程**：

1. 用户有一个 `visible` 状态，但**不直接修改它**
2. 用户调用库提供的 API（如 `onExited`），在回调中才去 `setVisible(false)`
3. 库内部管理动画状态机：`entering` → `entered` → `exiting` → `exited`
4. 当外部通知“离开”时，库进入 `exiting` 状态，添加 CSS 类，等待 `transitionend` 事件
5. 事件触发后，库进入 `exited` 状态，调用 `onExited`
6. 此时用户才真正从 React 状态树中移除元素

**谁在控制等待？** 应用层代码，不是 React 核心。React 核心完全不知道有动画。

**与框架核心的关系**：库通过**不更新 React 状态**来保持旧 DOM 存在。React 的协调机制只看到状态变化后的新树，旧树在状态未变时一直存在。框架不做任何特殊处理。

### 2.2 Vue：框架内置，虚拟 DOM 异步提交

Vue 通过内置的 `<Transition>` 和 `<TransitionGroup>` 提供退出动画支持。

**时序流程**：

1. `<Transition>` 包裹一个由 `v-if`/`v-show` 控制的元素
2. 条件变为 false 时，Vue 检测到子元素即将被移除
3. **不立即移除 DOM**，而是添加 `v-leave-from` 和 `v-leave-active` 类
4. 在下一帧添加 `v-leave-to`
5. 监听 `transitionend` / `animationend` 事件
6. 事件触发后，才真正从 DOM 中移除元素

**谁在控制等待？** Vue 框架核心。虚拟 DOM 的协调阶段（Reconciliation）和提交阶段（Commit）是分离的——Vue 可以在协调阶段标记元素为“待移除”，然后在提交阶段异步执行移除。

**对 kiaao 的适用性**：不适用。kiaao 没有虚拟 DOM，没有协调阶段和提交阶段的分离。`h()` 直接操作真实 DOM，`when` 的清理流程在派生回调中同步完成。

### 2.3 Solid：应用层组件，信号驱动延迟

Solid 的 `Transition` 组件利用响应式原语在内部管理退出状态。

**时序流程**：

1. `Transition` 接收一个子函数，子函数读取外部信号并返回元素或 `null`
2. 当外部信号变化导致子函数返回 `null` 时，`Transition` 内部**不立即更新其内部信号**
3. 而是调用 `onExit` 回调，传入当前 DOM 元素和一个 `done` 函数
4. 开发者调用 `done()`（通常在动画完成后）
5. `done()` 内部更新 `Transition` 的内部信号，导致子函数重新执行
6. 此时返回 `null`，元素被移除

**谁在控制等待？** 应用层组件（`Transition`），利用 Solid 的信号系统。Solid 核心不需要异步 DOM 操作。

**对 kiaao 的适用性**：有参考价值。`Transition` 通过**延迟信号更新**来延长旧 DOM 的寿命，而不是在 DOM 操作中等待。这种模式可以在 kiaao 中实现。

### 2.4 三种模式的共同点

**“移除 DOM”这个动作不是由框架核心触发的，而是由开发者（或库）在动画完成后主动触发的。** 框架核心只负责“挂载”和“同步移除”，异步移除通过延迟状态/信号更新来实现。

核心模式可以总结为：

> **不要试图在框架核心中等待动画，而是让触发移除的信号延迟更新。**

## 三、方案探索

### 3.1 废弃的方案

在找到最终方案之前，我们探索了多个方向并逐一验证：

#### 方案 A：`disposeNode` 异步化 + 微任务调度

让 `disposeNode` 变成 `async`，`when`/`each` 的清理流程在微任务中异步执行，允许 `await` 退出动画的 Promise。

**废弃原因**：派生回调必须变成异步——改变 kiaao 响应式系统的核心模型。这是对框架架构的根本性改变。

#### 方案 B：Fire-and-Forget 异步移除

`disposeNode` 保持同步，但当 `onUnmount` 返回 Promise 且元素是直接卸载目标时，不立即移除元素，而是注册 Promise 回调在动画完成后移除。

**废弃原因**：`clearChildren` 不再可靠——容器在插入新内容前不能保证为空。新旧元素可能并存，需要额外的舞台管理。

#### 方案 C：框架层 Abort 机制

框架不等待 Promise，而是通过 `AbortController` 主动中止动画，立即移除元素。

**废弃原因**：退出动画被中止后不可见，无法实现用户期望的“优雅退出”。本质上放弃了框架层面的退出动画支持。

#### 方案 D：`hook` API — 信号写入拦截

在信号写入时插入异步等待——信号值延迟更新 → `when`/`each` 的清理流程被间接延迟 → 退出动画可以在 DOM 移除前播放 → 派生回调保持同步。

**废弃原因**：`hook` 会导致 `setter` 的返回值行为不一致——有时返回 `T`，有时返回 `Promise<T>`。开发者需要记忆“这个信号上有没有 hook”来决定是否 `await`。这与 kiaao 追求的“透明、可预测”背道而驰。同时，派生信号中的 hook 会导致依赖图中的级联更新异步化，增加追踪数据流的难度。

**核心教训**：任何修改信号写入行为的机制，都会影响信号模型的简单性和可预测性。退出动画的异步等待应该通过用户态代码控制，而不是框架核心机制。

### 3.2 最终方向：工厂函数模式 — 指令收集动画任务，用户控制时序

**核心思路**：不修改框架核心的信号模型。指令只负责收集动画任务。退出动画的异步等待由用户在调用信号 setter 之前主动触发。框架核心保持信号模型的纯粹性和可预测性。

这与 React 和 Solid 的思路一致——React 延迟状态更新，Solid 延迟信号更新，kiaao 通过工厂函数将动画等待和信号更新封装在一起，由用户明确控制时序。

## 四、工厂函数模式设计

### 4.1 核心定位

创建一个工厂函数，只接收一个参数——原始信号的 `setState`。返回两个东西：一个异步的 `trigger` 函数（用于在动画完成后更新信号），和一个指令（用于收集子元素上的动画任务）。动画的具体逻辑（`from`、`to`、`duration`）通过指令的 `props` 传入，不在工厂函数中处理。

```ts
function createMotionDirect(setState) {
  const effectList = new Set();

  const trigger = async (val) => {
    await Promise.allSettled(Array.from(effectList).map((fn) => fn()));
    setState(val);
  };

  const Motion = direct((el, props, ctx) => {
    // 进入动画：挂载后播放
    // 退出动画任务：注册到 effectList
    const task = () => someAnimation(el, props);
    effectList.add(task);
    ctx.onUnmount(() => effectList.delete(task));
  });

  return [trigger, Motion];
}
```

### 4.2 为什么这个方向更好

**信号模型保持简单**：原始的 `setState` 仍然是同步的、可预测的。框架没有修改任何信号行为。`trigger` 是一个用户态的包装函数，开发者明确知道它是异步的——因为它是你自己创建的函数，不是框架强加的行为。

**指令只做一件事：收集动画任务**。指令将动画 Promise 注册到 `effectList` 中。指令不负责等待，不负责时序。职责清晰。

**时序控制完全在用户手中**：`trigger` 是用户主动调用的。用户可以在调用 `trigger(false)` 之前做任何事——播放退出动画、等待网络请求——然后再更新信号。

**与 `when`/`each` 的解耦仍然是完整的**：`when={state}` 绑定的 `state` 是一个普通信号。它的更新时机由用户通过 `trigger` 控制。没有派生回调同步性的冲突。

**清理机制清晰**：指令通过 `ctx.onUnmount` 将动画任务从 `effectList` 中移除。如果元素在动画等待期间被移除（比如父组件卸载），任务被清理，避免等待一个无意义的动画。

**动画配置通过指令 props 传入**：`from`、`to`、`duration` 等参数在 JSX 中直接指定，工厂函数不需要关心动画细节，职责更单一。

### 4.3 处理快速连续调用：代际标记

如果用户快速点击“关闭”再“打开”，`trigger(false)` 和 `trigger(true)` 几乎同时调用。两次 `async` 函数的 `setState` 可能乱序到达——后发起的调用可能先完成，导致最终状态与用户期望相反。

**解决方案**：在 `createMotionDirect` 内部维护一个递增的 `tick` 计数器。每次 `trigger` 调用时记录当前 `tick`，在 `Promise.allSettled` 完成后检查 `tick` 是否与当前计数器一致。如果不一致，说明期间有新的 `trigger` 调用，当前这次调用应被忽略。

```ts
function createMotionDirect(setState) {
  const effectList = new Set();
  let tick = 0;

  const trigger = async (val) => {
    const myTick = ++tick;
    await Promise.allSettled(Array.from(effectList).map((fn) => fn()));
    if (myTick !== tick) return; // 被后续调用取代，跳过
    setState(val);
  };

  // ... Motion 指令
}
```

这确保只有最新一次 `trigger` 调用会最终调用 `setState`，避免竞态覆盖。此防护是框架外部实现，不涉及核心。

### 4.4 双 setter 使用约定

用户同时拥有两个写入 `visible` 的途径：原始的 `setVisible`（同步、无动画）和 `trigger`（异步、有动画）。如果用户误用 `setVisible` 直接关闭，会跳过退出动画。

**建议约定**：一旦创建了 `createMotionDirect`，组件中后续只通过返回的 `trigger` 来操作信号，原始 `setter` 仅保留用于传递给 `createMotionDirect`，不应再直接使用。这不是框架层面的约束，而是代码组织的最佳实践，应在文档和示例中体现。

### 4.5 模块级共享信号的安全性

工厂函数模式同样适用于模块级共享信号：

```ts
const [count, setCount] = use(0);
export const [set, Motion] = createMotionDirect(setCount);
```

当多个组件实例共享同一个 `Motion` 和 `effectList` 时，卸载操作（`ctx.onUnmount` → `effectList.delete`）与 `trigger` 的读取可能并发发生。分析三种时序：

- **`trigger` 在 `await` 阶段**：`Array.from(effectList)` 已创建快照，后续 `delete` 不影响已捕获的迭代——安全。
- **`trigger` 未调用时**：`delete` 正确移除了已卸载实例的任务——正确。
- **并发 `delete` 与 `Array.from`**：Set 迭代是快照语义，`Array.from` 在调用时已确定元素，后续 `delete` 不影响已生成的数组——安全。

**结论**：模块级共享信号使用工厂函数是安全的，无竞态问题。

## 五、Motion 指令实现

> **声明**：以下代码为示意伪代码，用于说明设计模式和概念。具体实现（包括动画库选择、参数设计、错误处理策略等）由开发者根据实际需求自行决定。

### 5.1 完整的 Motion 指令

```ts
import { direct } from "kiaao";
import { animate } from "motion";

function createMotionDirect(setState) {
  const effectList = new Set();
  let tick = 0;

  const trigger = async (val) => {
    const myTick = ++tick;
    const results = await Promise.allSettled(Array.from(effectList).map((fn) => fn()));
    if (myTick !== tick) return;

    for (const result of results) {
      if (result.status === "rejected") {
        console.warn("[Motion] animation failed:", result.reason);
      }
    }

    setState(val);
  };

  const Motion = direct((el, props, ctx) => {
    const { from, to, duration = 0.3 } = props;

    // 进入动画：挂载后播放
    if (from) Object.assign(el.style, from);
    ctx.onMount(() => {
      animate(el, to, { duration });
    });

    // 退出动画：注册任务到 effectList
    const task = () => animate(el, from, { duration }).finished;
    effectList.add(task);
    ctx.onUnmount(() => {
      effectList.delete(task);
    });
  });

  return [trigger, Motion];
}
```

**职责划分**：

- **`createMotionDirect`**：只接收 `setState`，管理 `effectList` 和代际标记，返回异步 `trigger` 和指令
- **`Motion` 指令**：从 `props` 中读取动画配置，通过 `ctx.onMount` 处理进入动画，将退出动画任务注册到 `effectList`
- **`trigger`**：调用时执行所有已注册的退出动画任务，完成后更新信号

### 5.2 JSX 用法

```jsx
function Comp(props, { use }) {
  const [visible, setVisible] = use(true);
  // 创建工厂函数后，后续只使用 set，不再直接调用 setVisible
  const [set, Motion] = createMotionDirect(setVisible);

  return (
    <div>
      <button onClick={() => set(!visible())}>Toggle</button>
      <div when={visible}>
        <Motion
          from={{ opacity: 0, transform: "translateY(20px)" }}
          to={{ opacity: 1, transform: "translateY(0)" }}
          duration={0.5}
        >
          <div class="content">动画内容</div>
        </Motion>
      </div>
    </div>
  );
}
```

**流程**：

1. 用户点击按钮 → `set(false)` 被调用
2. `trigger` 内部遍历 `effectList`，执行所有动画任务（并行）
3. 每个动画任务播放退出动画
4. `await Promise.allSettled` 等待所有动画完成
5. 动画全部完成后，调用 `setState(false)` 更新信号
6. `when={visible}` 条件变为 false → 派生回调同步触发
7. `clearChildren` 移除 DOM
8. 指令的 `onUnmount` 将动画任务从 `effectList` 中移除

**派生回调保持同步，`disposeNode` 保持同步。** 异步等待被封装在 `trigger` 函数中，发生在信号更新之前。

### 5.3 多子元素场景

```jsx
const [set, Motion] = createMotionDirect(setVisible)

<Motion from={{ opacity: 0 }} to={{ opacity: 1 }}>
  <div class="card">Card A</div>
  <div class="card">Card B</div>
  <div class="card">Card C</div>
</Motion>
```

指令遍历三个 `<div>`，在每个上注册动画任务。`effectList` 中有三个任务。`trigger(false)` 时，三个退出动画并行播放。所有动画完成后，`setVisible(false)` 才被调用。

### 5.4 CSS 动画变体

以下为示意伪代码，展示如何通过指令支持 CSS 动画：

```ts
const CssMotion = direct((el, props, ctx) => {
  const { enterClass, exitClass } = props;

  if (enterClass) {
    el.classList.add(enterClass);
  }

  // 退出动画任务通过工厂函数注册
  const exitTask = () => {
    return new Promise((resolve) => {
      el.classList.add(exitClass);
      el.addEventListener("animationend", resolve, { once: true });
    });
  };
});
```

### 5.5 进入动画独立使用

进入动画不需要工厂函数参与。可以单独创建一个只处理进入动画的指令：

```ts
const FadeIn = direct((el, props, ctx) => {
  const { from, to, duration = 0.3 } = props;
  if (from) Object.assign(el.style, from);
  ctx.onMount(() => {
    animate(el, to, { duration });
  });
});
```

## 六、后续优化方向

以下方向已在讨论中涉及，但未在当前版本采纳，记录备查：

### 6.1 Solid 模式的 `Transition` 组件

一个应用层的 `Transition` 组件，利用信号系统内部管理退出动画的状态，对外提供声明式 API。这不是框架核心需要做的事，而是一个扩展组件可以达成的效果。未来可以作为 `kiaao/transition` 扩展包提供。

### 6.2 微任务调度优化

`when`/`each` 的 DOM 变更从派生回调中移至微任务中异步执行。这可以避免同一同步任务中多次信号变化导致的多次 DOM 操作，实现自动批处理。但这会改变 kiaao 的 DOM 更新语义，需要谨慎评估。

### 6.3 工厂函数的工具包封装

将 `createMotionDirect` 等常用工厂函数封装为 `kiaao/motion` 扩展包，提供开箱即用的动画能力。核心框架保持极简，动画能力按需加载。

## 七、结论

退出动画的异步等待通过工厂函数模式实现。框架核心保持信号模型的纯粹性和可预测性，不引入任何信号层面的异步机制。指令系统提供元素级生命周期钩子用于注册/清理动画任务，工厂函数负责收集任务并控制信号更新的时序。代际标记机制确保快速连续调用时的竞态安全。

工厂函数只接收 `setState`，动画配置通过指令 `props` 传入，职责清晰，使用直观。

这种设计延续了 kiaao 的哲学：**机制在核心，策略在扩展。**

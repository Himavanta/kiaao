# 动画方案探索与 Motion 指令实现 v4.0

**状态**：阶段总结 + 实现指南  
**关联**：kiaao v4.2 自定义指令系统  
**日期**：2026年6月15日

> **声明**：本文档中的代码示例均为示意伪代码，用于说明概念和设计模式。代码块中的实现不完整，缺少边界处理、类型标注和错误兜底。具体实现由开发者根据实际需求自行决定。

## 一、背景

### 1.1 问题的起点

kiaao 希望为开发者提供动画能力，特别是 **进入动画** 和 **退出动画**。进入动画相对简单——元素插入 DOM 时，CSS 的 `animation` 属性会自动触发，JS 动画库可以在元素挂载后调用。但退出动画需要框架在移除 DOM **之前** 等待动画完成——否则动画还没播放，元素就已经消失了。

最理想的使用体验是声明式的：

```jsx
<div when={visible}>
  <Motion from={{ opacity: 0 }} to={{ opacity: 1 }}>
    <div class="content">动画内容</div>
  </Motion>
</div>
```

当 `visible` 变为 false 时，框架应等待退出动画播放完毕再移除 DOM。

### 1.2 核心矛盾：异步挂载可行，异步卸载不可行

在 kiaao 中，挂载和卸载的触发点处于框架的不同层级：

|                  | 异步挂载                    | 异步卸载             |
| ---------------- | --------------------------- | -------------------- |
| 触发方           | Promise.then（框架外部）    | 派生回调（框架内部） |
| 与派生回调的关系 | 无关                        | 在派生回调内部       |
| 能否 await       | 能（Promise.then 天然支持） | 不能（派生回调同步） |
| 框架支持         | ✅ 已实现（异步组件）       | ❌ 不可行            |

**根本原因**：`when`/`each` 的 DOM 清理发生在 **派生回调** 中。派生回调是同步的——信号变化后立即同步执行所有下游派生。如果在 `disposeNode` 中等待退出动画的 Promise，派生回调就需要变成异步——这将破坏 kiaao 响应式系统的核心模型。

### 1.3 新痛点：业务状态与动画状态的冲突

在早期方案中，`createMotion` 返回一个 `play` 函数，用户通过 `play(false)` 触发退出动画并延迟更新信号。这导致 **所有依赖该信号的 UI（如状态文案）都必须等动画完成才能变化**。例如点击关闭按钮后，文案应该立刻从“开”变成“关”，而不是等动画播完才变。

**解决方案**：**业务信号与动画信号分离**。业务信号（`state`）立刻更新，动画信号（`visible`）由 `createMotion` 内部通过派生延迟更新。`when` 绑定动画信号，退出动画在延迟期间播放。

## 二、React / Vue / Solid 的退出动画处理方式

### 2.1 React：用户控制时序，库辅助状态管理

React **没有内置的退出动画支持**。社区库通过 **延迟状态更新** 来实现退出动画——不更新 React 状态，旧 DOM 持续存在，动画完成后才真正移除。

### 2.2 Vue：框架内置，虚拟 DOM 异步提交

Vue 通过 `<Transition>` 提供退出动画支持，依赖虚拟 DOM 的协调阶段和提交阶段的分离。对 kiaao 不适用——kiaao 没有虚拟 DOM。

### 2.3 Solid：应用层组件，信号驱动延迟

Solid 的 `Transition` 组件通过 **延迟信号更新** 来延长旧 DOM 的寿命。对 kiaao 有参考价值——不是修改框架核心，而是在应用层利用信号系统实现。

### 2.4 三种模式的共同点

> **不要试图在框架核心中等待动画，而是让触发移除的信号延迟更新。**

## 三、方案探索

在找到最终方案之前，我们探索了多个方向并逐一验证（`disposeNode` 异步化、Fire-and-Forget 异步移除、框架层 Abort 机制、`hook` API 信号写入拦截等，均已废弃）。

最终方向：**业务信号与动画信号分离 + 工厂函数模式**——指令收集动画任务，派生延迟管理动画信号，用户直接操作业务信号。信号模型保持纯粹，不引入任何框架层面的异步机制。

根据适用场景不同，分离为两个独立的 API：

- **`createMotion`**：处理 `when` 模式（布尔值信号）
- **`createGroupMotion`**：处理 `each` 模式（数组信号）

## 四、`createMotion` — when 模式

### 4.1 核心思想

将 **业务状态** 和 **动画状态** 分离。业务状态（用户直接操作的信号）立刻更新，动画状态（`visible`）由 `createMotion` 内部通过派生延迟更新。`when` 绑定动画状态，Motion 指令在延迟期间播放退出动画。

### 4.2 API 设计

```ts
function createMotion(signal, context?): [visible, Motion];
```

- `signal`：业务信号的 getter（布尔值）
- `context`（可选）：组件 context。如果传入，使用 `context.use` 获取组件级信号；否则使用全局 `use`
- 返回：
  - `visible`：动画信号（派生自 `signal`，延迟更新），绑定到 `when`
  - `Motion`：指令组件，包裹动画元素

### 4.3 实现骨架（伪代码）

```ts
function createMotion(signal, context?) {
  const [getter, setter] = context ? context.use(signal) : use(signal);
  const elements = new Set<Element>();
  const propsMap = new Map<Element, { from: any; to: any; duration: number }>();
  let tick = 0;

  // 动画信号：初始值与业务信号相同
  const [visible, setVisible] = context ? context.use(signal()) : use(signal());

  // 派生：业务信号变化时，延迟更新动画信号
  const derived = context ? context.use : use;
  derived(signal, () => {
    const newValue = signal();
    const myTick = ++tick;

    // 从 propsMap 实时计算最大 duration（避免 Set 去重导致的 bug）
    const delay = Math.max(0, ...[...propsMap.values()].map((p) => p.duration)) * 1000;

    // 延迟后更新动画信号
    setTimeout(() => {
      if (myTick !== tick) return; // 中途反转，跳过
      setVisible(newValue);
    }, delay);
  });

  // Motion 指令
  const Motion = direct((el, props, ctx) => {
    const { from, to, duration = 0.3 } = props;
    propsMap.set(el, { from, to, duration });

    // 每次重挂载时触发
    ctx.onMount(() => {
      elements.add(el);

      // 进入动画
      if (to) {
        setMotionState(el, "entering");
        void animate(el, to, { duration }).finished.then(() => {
          setMotionState(el, "idle");
        });
      }

      // 注册退出动画监听派生（每次重挂载重新注册）
      ctx.use(signal, () => {
        const currentValue = signal();
        // from 守卫 + 类型和值检查
        if (!from || typeof currentValue !== "boolean" || !currentValue) return;
        if (getMotionState(el) === "exiting") return;
        setMotionState(el, "exiting");
        void animate(el, from, { duration }).finished.then(() => {
          setMotionState(el, "exited");
        });
      });
    });

    ctx.onUnmount(() => {
      elements.delete(el);
      propsMap.delete(el);
    });
  });

  return [visible, Motion];
}
```

**关键设计说明**：

- **移除 `Object.assign(el.style, from)`**：不再手动设置初始样式，避免污染元素的 inline style，由 motion 完全接管样式管理。
- **退出动画的 `ctx.use(signal, ...)` 移到 `ctx.onMount` 内部**：确保每次元素重新挂载时都重新注册派生，避免跨重挂载失效（之前导致“第一次退出 ✅，后续 ❌”的根本原因）。
- **延迟计算从 `propsMap` 实时获取最大 duration**：废弃 `durations` Set，避免相同 duration 被 Set 去重导致延迟计算为 0 的问题。
- **`from` 守卫**：如果用户只传了 `to` 没传 `from`，退出动画回调直接跳过，防止 `animate(el, undefined, ...)` 抛错。
- **延迟计算时序**：初始调用时 `propsMap` 为空，`delay = 0`，但 `setVisible(signal())` 为设置相同值（空操作），无害；后续 `propsMap` 已被指令填充，延迟正确。

### 4.4 使用示例

```jsx
function Comp(_, context) {
  const [state] = use(true);
  const [visible, Motion] = createMotion(state, context);

  return (
    <div>
      <button onClick={() => state(false)}>关闭</button>
      <span>当前状态：{state ? "开" : "关"}</span> {/* 立刻变化 */}
      <div when={visible}>
        {" "}
        {/* 绑定动画信号 */}
        <Motion from={{ opacity: 0 }} to={{ opacity: 1 }}>
          <div class="content">动画内容</div>
        </Motion>
      </div>
    </div>
  );
}
```

**流程**：

1. 用户点击“关闭” → `state` 立刻变为 `false` → 文案立刻更新
2. `createMotion` 内部派生检测到 `state` 变化 → 从 `propsMap` 计算最大 duration → 启动延迟定时器
3. Motion 指令内部 `ctx.use(state)` 感知到 `state` 为 `false` → 播放退出动画
4. 延迟到期 → `visible` 变为 `false` → `when` 移除 DOM
5. 派生回调保持同步，异步等待全部在派生延迟和动画中完成

### 4.5 中途反转

用户在退出动画期间反悔，再次点击打开：

```
1. state = false → 退出动画开始，延迟 300ms
2. 100ms 时 state = true → 代际标记递增 → 旧定时器被跳过
3. visible 保持 true，元素不退出了
```

Motion 指令内部的 `ctx.use(state)` 会再次触发，由于 `state` 为 `true`，退出动画逻辑不执行。如果需要中断正在播放的退出动画，可在 Motion 指令中维护 AbortController。

## 五、`createGroupMotion` — each 模式

### 5.1 API 设计

```ts
function createGroupMotion(signal, keyFn?, context?): [visibleItems, GroupMotion];
```

- `signal`：业务信号的 getter（数组）
- `keyFn`（可选）：与 `each` 的 `key` prop 相同的 key 函数。用于内部 diff 时做元素身份比对。若不传，则走全量退出路径
- `context`（可选）：组件 context
- 返回：
  - `visibleItems`：动画信号（派生自 `signal`，延迟更新），绑定到 `each`
  - `GroupMotion`：指令组件

### 5.2 实现骨架（伪代码）

```ts
function createGroupMotion(signal, keyFn, context?) {
  const [getter, setter] = context ? context.use(signal) : use(signal);
  const effectMap = new Map<Element, () => Promise<void>>();
  const propsMap = new Map<Element, { from: any; to: any; duration: number }>();
  let tick = 0;

  // 动画信号
  const [visibleItems, setVisibleItems] = context ? context.use(signal()) : use(signal());

  // 派生延迟
  const derived = context ? context.use : use;
  derived(signal, () => {
    const newValue = signal();
    const myTick = ++tick;
    // 从 propsMap 实时计算最大 duration
    const delay = Math.max(0, ...[...propsMap.values()].map((p) => p.duration)) * 1000;

    setTimeout(() => {
      if (myTick !== tick) return;
      setVisibleItems(newValue);
    }, delay);
  });

  const GroupMotion = direct((el, props, ctx) => {
    const { from, to, duration = 0.3 } = props;
    propsMap.set(el, { from, to, duration });

    // 设置 motion-key（仅当传了 keyFn 且 props.key 存在时）
    if (keyFn && props.key !== undefined) {
      el.dataset.motionKey = String(props.key);
    }

    // 进入动画
    ctx.onMount(() => {
      if (!to) return;
      setMotionState(el, "entering");
      void animate(el, to, { duration }).finished.then(() => {
        setMotionState(el, "idle");
      });
    });

    // 退出任务（由内部 play 调用）
    const task = () => {
      if (!from || getMotionState(el) === "exiting") return Promise.resolve();
      setMotionState(el, "exiting");
      return animate(el, from, { duration }).finished.then(() => {
        setMotionState(el, "exited");
      });
    };
    effectMap.set(el, task);

    ctx.onUnmount(() => {
      effectMap.delete(el);
      propsMap.delete(el);
    });
  });

  // 注意：完整实现需在派生回调中调用内部 play 函数处理 diff 和动画触发。
  // 为保持文档简洁，此处不展开完整实现。

  return [visibleItems, GroupMotion];
}
```

### 5.3 使用示例

```jsx
function Comp(_, context) {
  const [items] = use([
    { id: 1, text: "A" },
    { id: 2, text: "B" },
    { id: 3, text: "C" },
  ]);
  const keyFn = (v) => v.id;
  const [visibleItems, GroupMotion] = createGroupMotion(items, keyFn, context);

  const removeItem = (id) => {
    const newItems = items().filter((i) => i.id !== id);
    items(newItems); // 直接更新业务信号
  };

  return (
    <ul each={visibleItems} key={keyFn}>
      {" "}
      {/* 绑定动画信号 */}
      {(item) => (
        <GroupMotion
          key={keyFn(item())}
          from={{ opacity: 0, transform: "translateY(20px)" }}
          to={{ opacity: 1, transform: "translateY(0)" }}
        >
          <li>
            {item().text}
            <button onClick={() => removeItem(item().id)}>删除</button>
          </li>
        </GroupMotion>
      )}
    </ul>
  );
}
```

**流程**：

1. 用户点击删除 → `items` 立刻更新（业务信号） → 列表数据立刻变化（尽管 DOM 还未移除）
2. `createGroupMotion` 内部派生检测到变化 → 从 `propsMap` 计算最大 duration → 启动延迟定时器
3. 内部 diff 识别被移除的元素 → 播放退出动画
4. 延迟到期 → `visibleItems` 更新 → `each` 移除对应 DOM
5. 新增元素的进入动画由 `ctx.onMount` 自然触发

### 5.4 无 key 时的行为

当 `each` 不传 `key` 属性时，`createGroupMotion` 也不传 `keyFn`。此时走全量退出路径——`effectMap` 中的所有已注册元素播放退出动画，完成后更新信号，`each` 全量重建。

### 5.5 逐个退出场景的正确性

用户可以逐个点击删除列表项，每次信号更新是独立的调用。以五个元素 A、B、C、D、E 为例：

```
初始: [A, B, C, D, E]
删除 B → items([A, C, D, E]) → diff 识别 B 退出 → B 播放退出动画 → 延迟到期 → 更新 visibleItems
删除 D → items([A, C, E])    → diff 识别 D 退出 → D 播放退出动画 → 延迟到期 → 更新 visibleItems
删除 A → items([C, E])       → diff 识别 A 退出 → A 播放退出动画 → 延迟到期 → 更新 visibleItems
```

- **每次 diff 独立进行**：对比的是当时的旧数组和新数组，不会重复识别已删除的元素
- **`el[MOTION_STATE]` 防止重复触发**：如果同一元素由于快速双击被多次标记为退出，检测到状态为 `exiting` 时会跳过，避免重复动画
- **代际标记保证最终一致性**：快速连续调用时，只有最新一次信号更新的 `setter` 生效，过时的调用被丢弃
- **不需要队列机制**：每个元素的退出是独立的，并行等待所有正在退出的元素，完成后一次性更新信号

## 六、元素状态追踪

在元素上通过 Symbol key 追踪动画状态：

```ts
const MOTION_STATE = Symbol("kiaao.motion.state");

// 状态枚举：
// 'idle'      — 空闲
// 'entering'  — 正在进入
// 'exiting'   — 正在退出
// 'exited'    — 已退出
```

执行退出动画时，先通过 `el[MOTION_STATE]` 检查状态：

- 状态为 `exiting` 时跳过，避免重复触发同一元素的退出动画
- 状态为 `idle` 或 `entered` 时执行任务，并设置状态为 `exiting`
- 动画完成后设置状态为 `exited`

## 七、代际标记

维护递增的 `tick` 计数器。每次派生回调执行时记录 `myTick`，延迟到期后检查是否被后续调用取代。确保中途反转时的最终状态正确。

## 八、context 参数的可选性

`context` 改为可选参数：

- **有 context**：使用 `context.use(signal)` 获取组件级信号，组件卸载时自动清理
- **无 context**：使用全局 `use(signal)` 返回已有信号引用

这支持了模块级共享动画信号的使用场景。

## 九、后续优化方向

- **移动动画（FLIP）**：在 diff 结果中识别位置移动，添加 FLIP 动画支持
- **`kiaao/motion` 扩展包**：将 `createMotion` 和 `createGroupMotion` 封装为独立扩展
- **微任务调度**：`when`/`each` 的 DOM 变更移至微任务，实现自动批处理
- **动画中断**：退出动画期间用户反悔时，通过 AbortController 中断动画

## 十、结论

`createMotion` 和 `createGroupMotion` 通过 **业务信号与动画信号分离** 的设计，解决了“状态文案延迟更新”的痛点，同时保持了信号模型的同步和可预测。内部机制（任务收集、动画触发、延迟管理、元素状态追踪、并发控制）一致，只是触发方式从手动 `play()` 变为自动派生感知。

**关键变化**：

- 用户直接操作业务信号，业务 UI 立刻响应
- `when`/`each` 绑定动画信号，动画信号延迟更新
- 退出动画由 Motion 指令内部的 `ctx.use`（在 `onMount` 中注册）自动触发
- 延迟时长从 `propsMap` 实时计算所有已注册元素 duration 的最大值
- 移除了对 inline style 的污染，由 motion 库独立管理动画状态
- 对 `from` 做守卫，防止用户只传 `to` 时崩溃

这种设计延续了 kiaao 的哲学：**机制在核心，策略在扩展。**

# 动画方案探索与 Motion 指令实现

**状态**：阶段总结 + 实现指南
**关联**：kiaao v4.2 自定义指令系统
**日期**：2026年6月14日

## 一、背景

### 1.1 问题的起点

kiaao 希望为开发者提供动画能力，特别是**进入动画**和**退出动画**。进入动画相对简单——元素插入 DOM 时，CSS 的 `animation` 属性会自动触发，JS 动画库可以在元素挂载后调用。但退出动画需要框架在移除 DOM **之前**等待动画完成——否则动画还没播放，元素就已经消失了。

最理想的使用体验是声明式的：

```jsx
<div when={visible}>
  <Motion from={{ opacity: 0 }} to={{ opacity: 1 }}>
    <div class="content">动画内容</div>
  </Motion>
</div>
```

当 `visible` 变为 false 时，框架应等待退出动画播放完毕再移除 DOM。

### 1.2 核心矛盾：异步挂载可行，异步卸载不可行

在 kiaao 中，挂载和卸载的触发点处于框架的不同层级：

|                  | 异步挂载                    | 异步卸载             |
| ---------------- | --------------------------- | -------------------- |
| 触发方           | Promise.then（框架外部）    | 派生回调（框架内部） |
| 与派生回调的关系 | 无关                        | 在派生回调内部       |
| 能否 await       | 能（Promise.then 天然支持） | 不能（派生回调同步） |
| 框架支持         | ✅ 已实现（异步组件）       | ❌ 不可行            |

**根本原因**：`when`/`each` 的 DOM 清理发生在**派生回调**中。派生回调是同步的——信号变化后立即同步执行所有下游派生。如果在 `disposeNode` 中等待退出动画的 Promise，派生回调就需要变成异步——这将破坏 kiaao 响应式系统的核心模型。

## 二、React / Vue / Solid 的退出动画处理方式

### 2.1 React：用户控制时序，库辅助状态管理

React **没有内置的退出动画支持**。社区库（如 `react-transition-group`）通过**延迟状态更新**来实现退出动画。

**时序流程**：

1. 用户有一个 `visible` 状态，但**不直接修改它**
2. 用户调用库提供的 API（如 `onExited`），在回调中才去 `setVisible(false)`
3. 库内部管理动画状态机：`entering` → `entered` → `exiting` → `exited`
4. 当外部通知"离开"时，库进入 `exiting` 状态，添加 CSS 类，等待 `transitionend` 事件
5. 事件触发后，库进入 `exited` 状态，调用 `onExited`
6. 此时用户才真正从 React 状态树中移除元素

**谁在控制等待？** 应用层代码，不是 React 核心。React 核心完全不知道有动画。

**与框架核心的关系**：库通过**不更新 React 状态**来保持旧 DOM 存在。React 的协调机制只看到状态变化后的新树，旧树在状态未变时一直存在。框架不做任何特殊处理。

### 2.2 Vue：框架内置，虚拟 DOM 异步提交

Vue 通过内置的 `<Transition>` 和 `<TransitionGroup>` 提供退出动画支持。

**时序流程**：

1. `<Transition>` 包裹一个由 `v-if`/`v-show` 控制的元素
2. 条件变为 false 时，Vue 检测到子元素即将被移除
3. **不立即移除 DOM**，而是添加 `v-leave-from` 和 `v-leave-active` 类
4. 在下一帧添加 `v-leave-to`
5. 监听 `transitionend` / `animationend` 事件
6. 事件触发后，才真正从 DOM 中移除元素

**谁在控制等待？** Vue 框架核心。虚拟 DOM 的协调阶段（Reconciliation）和提交阶段（Commit）是分离的——Vue 可以在协调阶段标记元素为"待移除"，然后在提交阶段异步执行移除。

**对 kiaao 的适用性**：不适用。kiaao 没有虚拟 DOM，没有协调阶段和提交阶段的分离。`h()` 直接操作真实 DOM，`when` 的清理流程在派生回调中同步完成。

### 2.3 Solid：应用层组件，信号驱动延迟

Solid 的 `Transition` 组件利用响应式原语在内部管理退出状态。

**时序流程**：

1. `Transition` 接收一个子函数，子函数读取外部信号并返回元素或 `null`
2. 当外部信号变化导致子函数返回 `null` 时，`Transition` 内部**不立即更新其内部信号**
3. 而是调用 `onExit` 回调，传入当前 DOM 元素和一个 `done` 函数
4. 开发者调用 `done()`（通常在动画完成后）
5. `done()` 内部更新 `Transition` 的内部信号，导致子函数重新执行
6. 此时返回 `null`，元素被移除

**谁在控制等待？** 应用层组件（`Transition`），利用 Solid 的信号系统。Solid 核心不需要异步 DOM 操作。

**对 kiaao 的适用性**：有参考价值。`Transition` 通过**延迟信号更新**来延长旧 DOM 的寿命，而不是在 DOM 操作中等待。这种模式可以在 kiaao 中实现。

### 2.4 三种模式的共同点

**"移除 DOM"这个动作不是由框架核心触发的，而是由开发者（或库）在动画完成后主动触发的。** 框架核心只负责"挂载"和"同步移除"，异步移除通过延迟状态/信号更新来实现。

核心模式可以总结为：

> **不要试图在框架核心中等待动画，而是让触发移除的信号延迟更新。**

## 三、方案探索

### 3.1 废弃的方案

在找到最终方案之前，我们探索了多个方向并逐一验证：

#### 方案 A：`disposeNode` 异步化 + 微任务调度

让 `disposeNode` 变成 `async`，`when`/`each` 的清理流程在微任务中异步执行，允许 `await` 退出动画的 Promise。

**废弃原因**：派生回调必须变成异步——改变 kiaao 响应式系统的核心模型。这是对框架架构的根本性改变。

#### 方案 B：Fire-and-Forget 异步移除

`disposeNode` 保持同步，但当 `onUnmount` 返回 Promise 且元素是直接卸载目标时，不立即移除元素，而是注册 Promise 回调在动画完成后移除。

**废弃原因**：`clearChildren` 不再可靠——容器在插入新内容前不能保证为空。新旧元素可能并存，需要额外的舞台管理。

#### 方案 C：框架层 Abort 机制

框架不等待 Promise，而是通过 `AbortController` 主动中止动画，立即移除元素。

**废弃原因**：退出动画被中止后不可见，无法实现用户期望的"优雅退出"。本质上放弃了框架层面的退出动画支持。

### 3.2 最终方向：`hook` API — 信号写入拦截

**核心思路**：不修改 DOM 清理流程，而是修改触发清理的信号更新时机。在信号写入之前插入异步等待，信号值延迟更新 → `when`/`each` 的清理流程被间接延迟 → 退出动画可以在 DOM 移除前播放 → 派生回调保持同步。

**为什么这能解决核心矛盾**：派生回调仍然是同步的——信号变化时同步执行。但因为信号本身的更新被延迟了，派生回调在动画完成后才被触发，`disposeNode` 在派生回调中被同步调用时动画已经播放完毕。

这与 React 和 Solid 的思路一致——React 延迟状态更新，Solid 延迟信号更新，kiaao 通过 `hook` 在信号写入时插入异步等待。

## 四、`hook` API 设计

### 4.1 核心定位

`hook` 是独立的 API，不与 `use` 融合。它为一个信号注册写入钩子。当信号被写入且新值与当前值不同时，钩子先执行。钩子可以返回 Promise，框架等待所有钩子完成后才真正更新信号值。

```ts
import { hook } from "kiaao";

const stop = hook(signal, async (value, signal) => {
  // value: setter 传入的新值
  // signal: AbortSignal（用于处理并发写入的中断）
  await someAsyncOperation();
});
// 需要移除钩子时
stop();
```

**`hook` 传入 getter 而非 setter**：`hook` 的第一个参数是 `Getter<T>`（getter 函数）。框架通过 `signal[REACTIVE]` 定位到信号的内部状态，在内部拦截 `setter` 的行为。用户不需要传入 `setValue`，因为 `hook` 不直接调用 `setValue`——它拦截 `setValue` 被调用时的行为。

### 4.2 钩子池的挂载位置

钩子池挂载在信号内部状态的 `state.hooks` 上。每个信号通过 `define` 创建时，内部有一个 `state` 对象挂载在 `getter[REACTIVE]` 上。

```ts
interface SignalState<T> {
  value: T;
  subs: Set<DerivationState>;
  set: Setter<T>;
  stop: () => void;
  hooks?: Set<WriteHook<T>>; // 写入钩子池
  pendingAbort?: AbortController; // 当前待处理的 AbortController
}
```

**选择 `state` 而非全局注册表的原因**：

- 生命周期一致——钩子绑定到信号，信号销毁时钩子自然失效
- 不需要全局注册表——与 kiaao 的无全局状态原则一致
- 实现路径清晰——`hook(signal, fn)` 通过 `signal[REACTIVE]` 定位到 `state`，将 `fn` 添加到 `state.hooks`

### 4.3 设计决策

#### 只拦截写入，不拦截读取

读取拦截目前没有明确的用例。`getter` 已经返回当前值，加读取拦截只会增加 API 复杂度而没有实际收益。如果未来有场景需要 `hookRead`，可以独立添加。

#### 不修改数据流，只提供写入前等待

钩子不通过返回值或 `set` 回调来修改最终写入的值。所有钩子完成（`Promise.allSettled`）后，框架自动用**原始传入的值**更新信号。

这保证了：

- 钩子职责纯粹——只做副作用（动画、验证等），不参与数据流
- 多钩子不需要协调——同一信号上多个钩子并行执行，不需要决定哪个钩子的返回值生效
- API 表面积最小——不需要 `set` 回调

#### `value` 参数保留

钩子接收 `value` 参数（setter 传入的新值）。虽然退出动画是主要场景，但保留 `value` 让钩子可以根据新值判断方向（`true` → 进入动画，`false` → 退出动画），实现双向动画或通用拦截。

#### 值不变时短路

当 `set` 传入的值与当前值 `===` 相同时，不触发钩子，不通知下游。这与派生信号的短路机制一致——值没有变化，下游无感知。避免无效的钩子触发（如重复调用 `setVisible(false)` 时不应该再次播放退出动画）。

#### 多钩子并行执行

同一信号上可以注册多个钩子（例如多个 `Motion` 指令绑定了同一个 `signal`）。它们并行执行，框架等待 `Promise.allSettled` 所有钩子完成后才更新信号。

### 4.4 并发写入与 AbortController

用户快速连续调用 `setVisible` 时：

```
setVisible(false)  → 钩子开始播放退出动画（耗时 0.3 秒）
setVisible(true)   → 钩子开始播放进入动画（但退出动画还在进行）
```

两次钩子并发执行可能导致同一个元素上的两个动画互相冲突。

**解决方案**：框架在每次 `set` 时创建一个新的 `AbortController`，将 `signal` 传入钩子。如果新的 `set` 发生，框架中止上一次的 `AbortController`，然后启动新的钩子。

```ts
// setter 被调用时
function handleSet(newValue) {
  if (newValue === state.value) return; // 短路

  // 中止前一次的 AbortController
  if (state.pendingAbort) {
    state.pendingAbort.abort();
  }

  const controller = new AbortController();
  state.pendingAbort = controller;

  if (state.hooks && state.hooks.size > 0) {
    Promise.allSettled([...state.hooks].map((fn) => fn(newValue, controller.signal))).then(() => {
      state.value = newValue;
      state.pendingAbort = undefined;
      notifySubs(state);
    });
  } else {
    state.value = newValue;
    notifySubs(state);
  }
}
```

框架始终创建 AbortController 并传入 hook。对于不关心中断的钩子，可以直接忽略 `signal` 参数。对于需要中断的钩子（如动画），这是必需的能力。

### 4.5 派生信号的 `hook`

`hook` 同时支持定义信号和派生信号，保持两者的 API 完全同构。这是为了保持 kiaao 的核心原则：**定义信号和派生信号在 API 层面完全同构。** 开发者不需要区分"这个信号是定义的还是派生的"——拿到手就解构，解构就能读写。如果 `hook` 只对定义信号生效，就会破坏这种同构性。

**定义信号**：`hook` 在 `set` 时触发（新值与旧值不同时）。钩子完成后更新值并通知下游。

**派生信号**：`hook` 在重算之后、值确定变化时触发。不管重算是如何触发的（上游变化或直接调用 setter），都在重算之后、比较值是否变化之后执行 hook。

```
1. 派生信号的重算被触发（上游变化 / setter 调用）
2. 执行 computeFn，得到新值 newValue
3. 对比 newValue 和 cachedValue
4. 如果相同 → 短路，不触发 hook，不通知下游
5. 如果不同 → 触发 hook（异步等待）→ 等待完成后 → 更新 cachedValue → 通知下游
```

这与定义信号的行为完全一致：

|                    | 定义信号                | 派生信号                         |
| ------------------ | ----------------------- | -------------------------------- |
| hook 触发时机      | set 时，新值 !== 旧值   | 重算后，newValue !== cachedValue |
| hook 是否知道新值  | 是（set 传入的值）      | 是（computeFn 的返回值）         |
| hook 完成后        | 更新 value，通知下游    | 更新 cachedValue，通知下游       |
| 值不变时           | 不触发 hook，不通知下游 | 不触发 hook，短路                |
| 上游变化触发的重算 | 不适用（无上游）        | 同样触发 hook（值变化时）        |

开发者不需要区分信号的类型——`hook(signal, fn)` 在任何信号上行为一致：值变化前等待，值不变时跳过。

### 4.6 钩子释放时机

`hook` 返回一个清理函数 `stop()`。调用后从 `state.hooks` 中移除对应的钩子。指令在 `onUnmount` 中调用 `stop`，保证元素移除时钩子不再触发。

**指令的 `onUnmount` 不负责动画**——它只负责清理钩子（`stop()`）。动画的播放由 `hook` 中的异步回调负责，动画完成后的信号更新由框架负责。

### 4.7 `hook` 的应用场景不限于退出动画

- **保存草稿**：`setContent(value)` → `hook` 钩子 → 自动保存到 localStorage → 更新信号
- **表单验证**：`setName(value)` → `hook` 钩子 → 异步校验 → 通过后才更新信号
- **乐观更新回滚**：`setOptimistic(true)` → `hook` 钩子 → 等待服务端确认 → 确认后再更新为最终值

### 4.8 TypeScript 类型

```ts
export function hook<T>(
  signal: Getter<T>,
  fn: (value: T, signal: AbortSignal) => void | Promise<void>,
): () => void;
```

- `signal`：要拦截写入的信号（getter 函数）。框架通过 `signal[REACTIVE]` 定位到信号的内部状态。
- `fn`：钩子函数，接收新值 `value` 和 `AbortSignal`。
- 返回：清理函数 `stop()`，调用后从 `state.hooks` 中移除钩子。

## 五、Motion 指令实现

### 5.1 完整的 Motion 指令

```ts
import { direct, hook } from "kiaao";
import { animate } from "motion";

const Motion = direct((el, props, context) => {
  const { from, to, duration = 0.3, signal: targetSignal } = props;

  // 设置初始样式
  if (from) Object.assign(el.style, from);

  // 进入动画：元素挂载后播放
  if (to) {
    context.onMount(() => {
      animate(el, to, { duration });
    });
  }

  // 退出动画：通过 hook 在信号写入前播放
  if (targetSignal) {
    const stop = hook(targetSignal, async (value, { signal: abortSignal }) => {
      // value 为 false 表示元素即将退出
      if (!value && from) {
        await animate(el, from, { duration, signal: abortSignal }).finished;
      }
      // value 为 true 表示元素即将进入（处理快速切换场景）
      if (value && to) {
        await animate(el, to, { duration, signal: abortSignal }).finished;
      }
    });
    context.onUnmount(stop);
  }
});
```

### 5.2 JSX 用法

```jsx
function Comp(props, { use }) {
  const [visible, setVisible] = use(true);

  return (
    <div>
      <button onClick={() => setVisible(!visible())}>Toggle</button>
      <div when={visible}>
        <Motion
          from={{ opacity: 0, transform: "translateY(20px)" }}
          to={{ opacity: 1, transform: "translateY(0)" }}
          duration={0.5}
          signal={visible}
        >
          <div class="content">动画内容</div>
        </Motion>
      </div>
    </div>
  );
}
```

**流程**：

1. 用户点击按钮 → `setVisible(false)`
2. `hook` 检测到新值 `false` !== 当前值 `true` → 执行钩子
3. 钩子内部调用 `animate` 播放退出动画
4. 动画完成后，框架更新 `visible` 的值为 `false`
5. `when={visible}` 条件变为 false → 派生回调同步触发
6. `clearChildren` 移除 DOM
7. 指令的 `onUnmount` 调用 `stop()` 清理钩子

**派生回调保持同步，`disposeNode` 保持同步。** 异步等待被封装在 `hook` 中，发生在信号更新之前。

### 5.3 CSS 动画变体

如果用户想用 CSS 动画替代 JS 动画：

```ts
const CssMotion = direct((el, props, context) => {
  const { enterClass, exitClass, signal: targetSignal } = props;

  // 进入动画：CSS animation 在元素插入 DOM 时自动触发
  if (enterClass) {
    el.classList.add(enterClass);
  }

  // 退出动画：通过 hook 在信号写入前等待 CSS 动画完成
  if (targetSignal && exitClass) {
    const stop = hook(targetSignal, async (value, { signal: abortSignal }) => {
      if (!value) {
        el.classList.add(exitClass);
        await new Promise((resolve) => {
          el.addEventListener("animationend", resolve, { once: true, signal: abortSignal });
        });
      }
    });
    context.onUnmount(stop);
  }
});
```

### 5.4 多子元素场景

```jsx
<Motion from={{ opacity: 0 }} to={{ opacity: 1 }} signal={visible}>
  <div class="card">Card A</div>
  <div class="card">Card B</div>
  <div class="card">Card C</div>
</Motion>
```

指令遍历三个 `<div>`，在每个上注册钩子和动画。三个卡片各自独立播放进入/退出动画。`hook` 在同一个 `visible` 信号上注册了三次，三次钩子并行执行。同一信号上的多个钩子都被触发，并行完成动画后框架才更新信号值。

### 5.5 错误处理

```ts
const Motion = direct((el, props, context) => {
  // ...

  if (targetSignal) {
    const stop = hook(targetSignal, async (value, { signal: abortSignal }) => {
      try {
        if (!value && from) {
          await animate(el, from, { duration, signal: abortSignal }).finished;
        }
      } catch (err) {
        // AbortError: 正常中断，不处理
        if (err.name === "AbortError") return;
        // 其他错误：打印警告
        console.warn("[Motion] animation error:", err);
      }
    });
    context.onUnmount(stop);
  }
});
```

## 六、后续优化方向

以下方向已在讨论中涉及，但未在当前版本采纳，记录备查：

### 6.1 Solid 模式的 `Transition` 组件

一个应用层的 `Transition` 组件，利用信号系统内部管理退出动画的状态，对外提供声明式 API。这不是框架核心需要做的事，而是一个扩展组件可以达成的效果。未来可以作为 `kiaao/transition` 扩展包提供。

### 6.2 `hookRead` 读取拦截

如果未来有场景需要在信号读取时执行副作用（如性能埋点、访问计数），可以添加 `hookRead` API。语法与 `hook` 一致。

### 6.3 微任务调度优化

`when`/`each` 的 DOM 变更从派生回调中移至微任务中异步执行。这可以避免同一同步任务中多次信号变化导致的多次 DOM 操作，实现自动批处理。但这会改变 kiaao 的 DOM 更新语义，需要谨慎评估。

## 七、结论

退出动画的异步等待通过在信号写入前拦截来实现。`hook` API 在信号层面提供"写入前等待"的能力——当信号被写入且值确实发生变化时，钩子先执行异步操作，操作完成后才更新信号值。`when`/`each` 的清理流程被间接延迟，派生回调保持同步。

`hook` 的设计保证了：

- **派生回调保持同步**——不改变响应式核心模型
- **定义信号和派生信号完全同构**——`hook(signal, fn)` 在任何信号上行为一致
- **值不变时短路**——避免无效的钩子触发
- **并发写入通过 AbortController 处理**——快速切换时旧动画被中止，新动画立即开始

动画由用户控制时序（通过 `setVisible`），框架提供 `hook` 作为等待机制，指令系统提供元素级生命周期钩子。

这种设计延续了 kiaao 的哲学：**机制在核心，策略在扩展。**

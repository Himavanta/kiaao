# Kiaao 框架架构演进探讨：从 DOM 依赖到 Owner 树模型

**文档版本**：1.2  
**讨论参与者**：Himavanta（kiaao 作者）、AI 助手（两位）  
**讨论背景**：Kiaao 是由 Himavanta 开发的一款**探索性、纯运行时**前端响应式框架。目前处于快速迭代阶段，接受破坏性变更。本次讨论以业界成熟的 SolidJS 框架的底层架构作为“参照系”，深入剖析 Kiaao 现有设计（信号与 DOM 强绑定）在**性能、Fragment 实现、水合（Hydration）、异步组件处理**等方面的根本性瓶颈，并探讨将其重构为 **Owner（作用域）树架构**的可行性、技术路径与收益评估。

**关联文档**：[跨端架构改造方案讨论](./跨端架构改造方案讨论.md)——本文与跨端文档互为补充。跨端文档侧重平台抽象层设计（PlatformAdapter），本文侧重生命周期管理从 DOM 到 Owner 树的范式转移。两者是同一件事的两个剖面。

## 第一部分：前端“无虚拟 DOM”框架的两大流派

在 React 等传统框架使用虚拟 DOM（VDOM）进行 Diff 比对时，新兴的响应式框架为了追求极致性能，选择了“无 VDOM”路线。但这之下又分化出了两个截然不同的技术流派：

1.  **编译时优化派（代表：SolidJS、Svelte）**：
    - 借助编译器（Babel 插件等）在**构建阶段**分析代码中的响应式依赖。
    - 将 JSX 或模板语法直接编译为高效的、精准操控真实 DOM 的 JavaScript 代码。
    - 运行时依赖内存中的“Owner 树”来管理副作用的生命周期（挂载与卸载）。

2.  **纯运行时派（代表：Kiaao 现状）**：
    - **不依赖任何编译插件**，所有逻辑在浏览器中实时执行。
    - 通过显式的 API（Kiaao 的 `use`）声明依赖，**拒绝“自动收集依赖”的魔法**。
    - 将响应式信号（Signal）的订阅关系和清理函数**直接挂载（绑定）在浏览器的 DOM 节点上**，依赖 DOM 树的父子结构来管理生命周期。

## 第二部分：参照系——SolidJS 的底层架构深度解析

由于我们的讨论中频繁以 SolidJS 作为对比基准，这里必须将其底层运作机制完整拆解，以便后续理解“为什么 Solid 能做某些事，而 Kiaao 做起来很难”。

### 2.1 组件定义：函数只执行一次，没有“实例”

- 在 Solid 中，组件本质上只是一个**执行一次**的工厂函数。当状态（Signal）变化时，**组件函数不会重新执行**（不像 React 那样重新 Render）。
- Solid **不存在**类似 React Fiber 节点那样的“组件实例对象”来挂载到内存中。函数执行完就销毁了，只留下返回的真实 DOM 节点和背后的响应式逻辑。

### 2.2 Fragment（多根节点）的处理：编译时“扁平化”

- **核心机制**：Solid 的编译器在编译阶段遇到 `<></>` 或 `<Fragment>` 时，会**直接移除**该标签，并将内部的所有子节点提取出来。
- **运行时表现**：组件函数返回的不再是一个单一的 VNode，而是一个**子节点数组**。
- **插入与清理**：父组件接收到这个数组后，会将数组内的元素**逐个**平铺插入到父容器中。在 DOM 树上，Fragment **没有任何对应的根 DOM 节点**（不存在包裹 div）。

### 2.3 Owner 树：内存中的“户籍管理册”

这是 Solid 最核心的设计，也是本次讨论的重点参照物。Owner 树并非扁平的全局池，而是一棵**与 DOM 树平行但独立存在于 JS 内存中的树结构**。

- **构建时机**：在组件函数**执行调用时**（即函数入栈出栈时）动态构建，**与 DOM 节点是否插入到页面（appendChild 时机）无关**。
- **存储内容**：Owner 节点存储的是该作用域下的清理函数队列（`onCleanup`）、子 Owner 链表（`subOwners`），以及**单向持有**该作用域创建的真实 DOM 节点引用。
- **单向引用原则**：Owner 持有 DOM 引用（以便卸载时移除），但 DOM 节点**绝不反向持有** Owner。这避免了内存泄漏。

### 2.4 依赖清理（卸载）：绝对不碰 DOM 树

- 当 Solid 需要卸载一个组件时（例如条件渲染变为 false），它的执行流程是：**从内存中的 Owner 树向下递归** -> 遍历子 Owner -> 执行所有清理回调 -> 断开 Signal 的订阅关系 -> **最后**根据 Owner 持有的 DOM 引用执行 `removeChild`。
- **关键结论**：清理逻辑的时间复杂度是 **O(1)**（链表断开）或 O(log N)（遍历子 Owner），**与 DOM 树的规模完全无关**，因此性能极佳。

### 2.5 状态更新：完全不遍历 Owner 树

- 这是开发者最容易误解的点。Solid 的状态更新（`setSignal`）**不会**遍历 Owner 树去做 Diff。
- **实际机制**：Signal 内部维护了一个**观察者列表（Observer List）**。状态变化时，直接精准通知列表中的 `createEffect` 和 `createMemo`，只更新那一个具体的 DOM 节点属性或文本。更新逻辑和 Owner 树是**解耦的**。

### 2.6 水合（Hydration）的实现基础：编译时坐标

- Solid 实现高效水合的关键在于**编译时产生的元信息**。编译器知道每个动态绑定的“坐标”（例如：第 3 个 div 的第 2 个文本节点）。
- 服务端渲染（SSR）时，这些坐标被序列化在 HTML 中。客户端水合时，**无需重新执行整个组件树逻辑**，只需要根据坐标找到对应的 DOM 节点，将序列化的状态值注入进去，并绑定事件监听。**极少涉及 DOM 遍历**。

## 第三部分：Kiaao 现有架构解析（基于 `/src` 源码）

有了 Solid 的参照，我们再回头看 Kiaao 的现状。

### 3.1 核心设计原则

1.  **纯运行时，零编译依赖**：不依赖 Babel，所有逻辑在浏览器中确定。
2.  **显式声明（Explicit over Implicit）**：通过唯一的 `use` API 创建所有状态（普通信号、派生信号），依赖关系通过参数**显式**传入。
3.  **组件工厂函数**：组件只执行一次，返回 DOM。变化时只改 DOM，不重跑组件。
4.  **原生控制流**：通过 DOM 元素的 `when` 和 `each` 属性控制渲染，而非包装组件。
5.  **响应式绑定在 DOM 上**（本次讨论的核心痛点来源）。

### 3.2 关键实现机制（DOM 强绑定）

- **组件实例挂在节点上**（`component.ts` / `attachInstance`）：通过 `INSTANCE_KEY` 属性将组件实例集合挂在 DOM 节点上。
- **Effect 清理挂在节点上**（`process-children.ts` / `addLocalEffect`）：渲染信号文本时，将 `stop` 函数直接存在 DOM 节点的 `LOCAL_EFFECTS` 属性中。
- **清理依赖 DOM 树递归**（`component.ts` / `disposeNode`）：卸载时，**深度优先遍历**待卸载的 DOM 子树，读取每个节点上的 `LOCAL_EFFECTS` 并执行 `stop`。
- **Fragment 使用 `display: contents`**：因为子组件可能返回多节点，为了能插入父容器，Kiaao 被迫用 `<div style="display: contents">` 作为“幽灵”包裹容器，使其在视觉上消失。

## 第四部分：Kiaao 现状的深层痛点剖析

结合 Solid 的原理，Kiaao 现有架构的瓶颈变得极为清晰。

### 4.1 性能问题（DOM 遍历清理）

- **复杂度**：`disposeNode` 的清理是 **O(N)**（N 为 DOM 子树节点数）。卸载大型列表（如 10000 项）时，JS 主线程需遍历所有节点，可能导致动画掉帧或输入卡顿。
- **内存泄漏风险**：由于节点持有 Effect，Signal 也持有 Effect（双向引用）。若某 DOM 节点被外部变量意外持有，`disposeNode` 遍历不到它，其 Effect 永远不会被 `stop`，Signal 的观察者列表残留，造成内存泄漏。

### 4.2 Fragment 的“不优雅”（`display: contents`）

- **语义与兼容性**：在 `<table>`、Flex/Grid 布局中，`display:contents` 会导致渲染错误；Safari 早期版本有严重 Bug。
- **额外开销**：该“幽灵” div 依然真实存在于 DOM 树中，导致 `disposeNode` 遍历时多出无谓的跳转。
- **根源**：因为没有 Owner 树来承载“无根节点”的逻辑，这是运行时框架试图处理多根节点的“不得已的 hack”。

### 4.3 水合（Hydration）实现难度极高

- 当前 Kiaao 仅有 `renderToString`（服务端吐 HTML），**未实现客户端水合**。
- 若基于现有 DOM 绑定实现水合，客户端必须**重新执行全部组件函数**，生成新的 DOM 逻辑，然后去匹配服务端已存在的 DOM 树。由于没有编译时坐标，必须大量遍历 DOM 来“对号入座”，极易引发**水合不匹配（Hydration Mismatch）**导致页面闪烁。

### 4.4 异步组件（Lazy / Suspense）无法安全处理

- 父组件必须等待异步子组件 resolve 拿到 DOM 节点后才能插入。若父组件在等待途中被卸载，子组件尚未插入 DOM，`disposeNode` **根本找不到它**，导致 fetch 请求无法取消，Signal 订阅无法清理，造成严重资源泄漏。

## 第五部分：解决方案探索——引入 Owner（作用域）树架构

为了解决上述所有问题，讨论聚焦于将 Kiaao 的核心清理机制从“依赖 DOM 树”重构为“依赖 Owner 树”。

### 5.1 什么是 Owner 树？（重述以保持文档自包含）

Owner 树是位于 JS 内存中的、与 DOM 结构完全解耦的作用域树。每个组件执行时生成一个 Owner 节点，持有子 Owner、清理函数队列，并**单向持有**该作用域生成的真实 DOM 节点引用。

### 5.2 重构后的收益（针对痛点的一一映射）

| 现有痛点                  | 引入 Owner 树后的解法                                                                                                                     |
| :------------------------ | :---------------------------------------------------------------------------------------------------------------------------------------- |
| **性能（O(N) DOM 遍历）** | 卸载时仅遍历内存中的 Owner 链表，**完全不触碰 DOM 树**。时间复杂度降为 O(1)（链表断开）。                                                 |
| **内存泄漏（双向引用）**  | 改为 **Owner → DOM** 单向持有。DOM 节点被外部引用时，只要 Owner 断开，GC 即可正常回收，Effect 随 Owner 同步销毁。                         |
| **Fragment 不优雅**       | 组件返回 `Owner` 而非 DOM 数组。父组件直接平铺插入该 Owner 持有的 `domRefs`。**Fragment 在 DOM 层面彻底消失**，无需 `display:contents`。  |
| **水合实现困难**          | 有了稳定的 Owner 树结构，可在 SSR 时生成基于 Owner 路径的稳定 ID。客户端水合时通过 ID 精准注入数据和事件，**完全绕过 DOM 遍历匹配**。     |
| **异步组件**              | 在启动异步请求前**预先创建占位 Owner（Placeholder）**。若父级在加载中被卸载，直接 `dispose` 占位 Owner，可取消 fetch 并清理所有挂起状态。 |

## 第七部分：针对 Kiaao 的详细重构路径建议

基于讨论共识，Kiaao 正处于可接受破坏性变更的探索期，建议按以下步骤向 Owner 树演进：

1.  **保留核心灵魂（绝不妥协）**：保留 `use` 的**显式依赖声明**机制。不模仿 Solid 的自动收集。这是 Kiaao 作为“透明、可控”框架的核心竞争力。

2.  **实现基础 Owner 核心**：
    - 定义 `Owner` 数据结构：`{ subOwners: [], cleanups: [], domRefs: [], parent: Owner | null }`。
    - 利用 `try/finally` 或全局变量 `currentOwner` 栈，在组件函数执行前入栈，执行后出栈。

3.  **改造 `h()` 函数**：创建真实 DOM 节点后，执行 `currentOwner.domRefs.push(node)`，将该节点的**移除责任**归属给当前 Owner，而非挂载清理函数到节点上。

4.  **移除 `display:contents` 并重写 Fragment**：
    - Fragment 组件返回一个 **空的 Owner 对象**（或专门标志）。
    - 父组件检测到子组件返回的是 Owner 时，遍历 `owner.domRefs` 并平铺插入到父容器中。

5.  **重写清理逻辑（关键一步）**：
    - **废除** `disposeNode`（DOM遍历函数）。
    - 实现 `disposeOwner(owner)`：深度优先遍历 `owner.subOwners` 链表 -> 执行 `cleanups` -> 断开 Signal 订阅 -> **最后**循环 `owner.domRefs` 调用 `removeChild`。

6.  **为水合铺路**：
    - 在 `renderToString` 阶段，利用 Owner 树的深度路径（如 `0-2-1`）生成每个动态绑定节点的**唯一 ID**，并序列化到 HTML 注释或属性中。
    - 客户端水合时，直接通过 `querySelector` 配合 ID 找到 DOM 节点，注入初始数据，绑定事件。**完全跳过建立绑定的 DOM 遍历过程**。

7.  **处理异步（Suspense 基础）**：
    - 实现 `createPlaceholderOwner`。在异步 `import()` 或 `fetch` 之前立即生成该 Owner。
    - 若父级 Owner 在异步等待中被释放，则调用 `disposeOwner(placeholder)`，其内部的清理逻辑会取消正在进行的异步操作。

## 第八部分：核心结论

1.  **定性**：Kiaao 当前的“DOM 绑定清理方案”是一种在纯运行时框架下诞生的**反模式（Anti-pattern）**。它将本应由 JS 内存管理的生命周期复杂度，错误地转嫁给了浏览器的 DOM 树，从而在性能、内存、Fragment 兼容性、水合实现、异步处理五大维度都产生了难以逾越的结构性障碍。

2.  **解药**：Solid 的 **Owner 树架构**是解决上述所有问题的“银弹”。它并非简单的性能优化，而是一次**底层范式的转移**——将“以 DOM 为中心”的管理模式，切换为“以内存作用域为中心”的管理模式。

3.  **愿景**：重构后的 Kiaao 将完美结合 **“纯运行时的透明/可调试性”** 与 **“工业级的内存/性能管理”**。通过保留显式的 `use` API 并引入 Owner 树，Kiaao 可以在不牺牲其独特开发体验的前提下，获得媲美 SolidJS 的底层性能，并为未来实现 SSR 水合、跨端渲染（Native/Canvas）打下坚实的基础。

4.  **时机**：鉴于 Kiaao 目前处于探索性阶段，引入破坏性变更的成本最低。**建议立即着手进行 Owner 树架构的重构**，这是该项目从“有趣的原型”迈向“健壮的生产级框架”的必经之路。

## 第九部分：基于 Solid 最新源码的审视与修正

> 本部分由另一位 AI 助手在审阅 Solid 最新源码（`solid-next`，对应 Solid v2.0 开发分支）后补充。本部分不推翻原文档的核心判断，而是对 Solid 的机制细节做必要修正，并基于此修正对重构路径提出调整建议。

### 9.1 关于 Solid Owner 树的机制修正

原文档对 Solid 的 Owner 树做了几处关键简化，这些简化不影响结论方向，但会影响实施路径的精确度。

#### 修正 1：Owner 树没有 `domRefs`

原文档说 Owner 节点持有 `domRefs`（该作用域创建的真实 DOM 节点引用）。查看 Solid 最新源码（`solid-signals/src/core/owner.ts`），Owner 节点的实际字段是：

```ts
interface Owner {
  _firstChild: Owner | null; // 子 Owner 节点
  _nextSibling: Owner | null; // 兄弟 Owner 节点
  _prevSibling: Owner | null;
  _disposal: (() => void) | (() => void)[]; // 清理回调
  _parent: Owner | null;
  _childCount: number;
  // ... 没有 domRefs
}
```

**Solid 清理 DOM 的方式**不是通过 Owner 持有 DOM 引用然后 `removeChild`。DOM 节点由渲染层（`dom-expressions` 的 `insertExpression` 函数）维护在一个 `current` 数组中，通过 marker 边界管理。Owner 树只负责**清理副作用**（断开 Signal 订阅、执行 `onCleanup`）。DOM 的移除由渲染层的 `cleanChildren()` 直接操作。

**这意味着什么**：Owner 树的价值不在「持有 DOM 引用以便 O(1) 移除」，而在**给所有副作用一个独立于 DOM 树的作用域归属**。清理仍然需要渲染层配合，不是 Owner 树自己就能完成的事。

#### 修正 2：Solid Fragment 的核心不是编译

原文档说 Solid Fragment 的实现是「编译时扁平化」。编译确实让这个流程更高效，但**即使没有编译器**（使用 `@solidjs/h` hyperscript），Solid 同样能处理多根节点。原因是 Solid 的运行时从底层就支持数组：

- `JSX.Element` 类型定义为 `Element | Element[]`
- `insertExpression()` 原生接受数组作为输入
- 父组件接收到的 children 如果是数组，直接平铺插入到 marker 边界内

**关键不在于编译器，在于运行时对数组的一等支持。** kiaao 当前 `h()` 返回 `Element`、`handleSyncComponentResult` 对数组的处理是「创建一个容器来装」，而不是「让父级直接吸收」。

#### 修正 3：Solid 水合仍然依赖 DOM 标记

原文档说 Solid 水合「极少涉及 DOM 遍历」。实际源码显示 Solid 水合同样依赖 Comment 标记对（`$` 和 `/`），`getNextMarker()` 函数仍然会遍历兄弟节点来找到动态边界。Solid 的优势不在于「完全绕过 DOM」，而在于「标记对让 DOM 遍历的范围被精确限定在已知的动态区间内」，而非全量遍历。

### 9.2 对原文档结论的再评价

| 原文档判断                    | 重新评价              | 说明                                                                                                                         |
| ----------------------------- | --------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| kiaao 的 DOM 绑定清理是反模式 | ✅ 判断正确           | 生命周期与 DOM 树强绑定的确带来了 Fragment/水合/跨端三方面的阻碍                                                             |
| Owner 树是解药                | ⚠️ 方向正确但表述过强 | Owner 树解决的是**生命周期管理**的问题，DOM 的创建/更新/移除仍然需要渲染层配合。Owner 树不是「银弹」，而是必要但不充分的条件 |
| 重构后 Fragment 可无容器      | ✅ 方向正确           | 但前提是 `h()` 需要支持 `Node[]` 返回值，且所有消费端需要适配                                                                |
| 水合难度从极高降到中等        | ✅ 更现实的评估       | 有了 Owner 树后可以序列化路径 ID，但 DOM 标记对的匹配仍然需要                                                                |
| 异步组件占位 Owner            | ✅ 这是真收益         | 是当前架构无法解决的问题，Owner 树能干净解决                                                                                 |

### 9.3 三个问题与一个根因

回顾整个讨论过程，我们是从三个独立方向（Fragment、水合、跨端）分别切入的，最终汇集到了同一个根因：

```
Fragment 问题
  因为清理靠 DOM 树遍历
  → 多根组件需要一个容器节点来挂元数据
  → Fragment 必须有 wrapper

水合问题
  因为 DOM 是生命周期的宿主
  → h() 必须创建新节点才能挂上 INSTANCE_KEY/LOCAL_EFFECTS
  → 无法认领现有 DOM

跨端问题
  因为 disposeNode 递归遍历 childNodes
  → 整个生命周期管道的操作对象是 DOM 树
  → 换平台就得重写整条管道
      ↓
  根因：生命周期以 DOM 树为宿主
      ↓
  Owner 树的核心改变：把生命周期的宿主从 DOM 树迁回 JS 内存
```

一旦做到这一步，三个问题会自然松绑：

- Fragment 不需要 wrapper——Owner 知道有哪些节点要清理
- 水合不需要完全重建——现有 DOM 节点可以被「认领」到已有的 Owner 下
- 跨端不需要重写生命周期管道——adapter 只管「怎么创建/操作节点」，不管「什么时候清理」

### 9.4 关于重构路径的调整建议

原文档第七部分给出了 7 步重构路径。结合对 Solid 实际机制的审视和跨端文档的分析，调整如下：

| 步骤 | 原文档描述                                     | 调整                                                                                                                                                       | 理由                                                                                                           |
| ---- | ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 1    | 保留 `use` 显式声明                            | ✅ 维持                                                                                                                                                    | 这是 kiaao 的灵魂，不可动摇                                                                                    |
| 2    | 实现基础 Owner 核心                            | ✅ 维持，但数据结构需要调整                                                                                                                                | Owner 不需要 `domRefs`，需要的是子树管理 + cleanup 队列 + 占位 Owner 支持                                      |
| 3    | `h()` 创建 DOM 后 `owner.domRefs.push(node)`   | ⚠️ 调整为：`h()` 改为支持 `Node` 和 `Node[]` 双返回值，Owner 不持有 DOM 引用，而是提供统一的 `registerDisposal` 接口供 `when`/`each`/process-children 使用 | Owner 持有 DOM 引用不是必需的，渲染层通过 adapter 管理 DOM；Owner 的核心职责是生命周期归属                     |
| 4    | 移除 `display:contents`，Fragment 返回空 Owner | ⚠️ 调整为：Fragment 改为返回 `children` 数组，由 `h()` 在组件模式下吸收数组成员。Owner 的创建是组件调用的副产品，不是 Fragment 的返回值                    | Fragment 是一个渲染层概念，不应该感知 Owner                                                                    |

| 6    | 水合铺路                                       | ⏳ 维持远期定位                                                                                                                                            | 需要 Owner 树稳定 + adapter 接口定义后才能做                                                                   |
| 7    | 异步组件占位 Owner                             | ✅ 可独立先做，不与核心改造耦合                                                                                                                            | 这是 Owner 树最直接的早期收益场景                                                                              |

### 9.5 与跨端文档的关系

[跨端架构改造方案讨论](./跨端架构改造方案讨论.md) 和本文是同一件事的两个剖面：

```
跨端文档 → 平台抽象层（adapter）
  定义：创建节点、操作树、设置属性、管理事件
  解决：浏览器/Lynx/未来平台之间的 API 差异
            ↕ 互补
本文     → 生命周期管理层（Owner 树）
  定义：作用域归属、副作用清理、异步安全

```

两条线可以独立推进，但最终需要汇合：

- adapter 提供 `setMetadata(node, key, value)` 和 `getMetadata(node, key)` 来挂载运行时元数据
- Owner 树提供 `registerDisposal(cleanup)` 和 `createPlaceholder()` 来管理生命周期
- 两者在 `h()` 和 `component.ts` 中交汇

### 9.6 作者对当前讨论的定性

> 以下内容基于与 Himavanta 的直接交流整理。

kiaao 已经经历过数次「接近于推倒重来」级别的重构。本次讨论的内容不是在追求理想的架构，而是在不断迭代中发现了三个具体的阻碍——Fragment、水合、跨端——而当前的模型（生命周期绑定 DOM 树）同时成为了这三个方向的阻碍。这不是「要不要改」的问题，而是当前模型已经撑不住了。

对此我（本文档补充者）的看法是：

**原文档的核心判断方向正确——Owner 树（或等价的作用域生命周期管理）是解决之道。但需要消解两个误解：**

1. **Owner 树不是银弹，是必要基础设施。** 它解决的是生命周期归属问题。DOM 的创建/更新/移除仍然需要渲染层（adapter + renderer）来完成。Owner 树的价值在于：当你要清理时，不需要遍历 DOM 来找谁该被清理；Owner 树已经知道。

2. **重构不是全有或全无的选择。** 可以分阶段引入——先做 Owner 树核心 + 异步组件占位 Owner（收益明确、范围可控），再根据情况推进 Fragment 改造和 adapter 迁移。每一步的收益都可以独立验证。

**我的建议：不要急于一步到位，而是先画出当前架构中「依赖 DOM 树遍历来管理生命周期」的全部接触面，然后逐一判断每个接触面可以用什么机制替代。** 这个「接触面地图」比任何抽象讨论都更有助于确定实施的优先级和边界。

## 第十部分：后续讨论——扁平 Owner 池与边界判定

> 本部分记录了在第九部分基础上继续讨论的成果。修正了对 Owner 树与依赖收集关系的理解，提出了扁平 Set 结构的 Owner 池方案，并最终确认了 Owner 边界在 kiaao 现有架构中已有天然映射。

### 10.1 关键修正：Owner 树 ≠ 依赖收集

在讨论中，最初有一个隐含的误解——认为 Solid 的 Owner 树依赖于自动依赖收集机制，因此与 kiaao 的哲学冲突。查阅 Solid 最新源码后发现这是两个正交的机制：

```ts
// Solid 的 createComponent
createComponent(Comp, props) {
  // 1. 创建新 Owner（推入 owner 栈） ← 这是生命周期管理
  return untrack(() => Comp(props));
  //       ↑ untrack 确保组件函数内部不会自动订阅信号  ← 这是依赖收集
}
```

**Owner 树的边界建立在「调用栈」上，不是建立在「信号读取栈」上。** 组件 A 调用组件 B → B 的 Owner 成为 A 的 Owner 的子节点。这由函数调用关系决定，不需要「自动追踪信号读取」那种魔法。

依赖收集是 `createEffect` / `createMemo` 层面的机制——它们追踪哪些信号被读取了——与 Owner 树是解耦的两层。所以 **Owner 树本身不违反 kiaao 的「不自动收集依赖」原则。**

### 10.2 但 kiaao 的 Owner 树面临不同的问题

尽管 Owner 树和依赖收集是正交的，kiaao 要在运行时构建 Owner 树仍然有一个障碍——**Owner 树依赖 `currentOwner` 全局栈**，而 kiaao 之前尝试的全局组件实例栈正是因此被废弃的。

`context.use` 设计文档中的记录（参见 `context.use — 组件级派生自动清理 & toUse 吸收 & toValue 重命名 方案.md`）：

> 任何依赖「同步执行期间」的自动机制，在异步组件面前必然失效。这与之前废弃全局组件实例栈的原因同根同源——框架不能依赖调用时机来推断归属。

Owner 树的入栈出栈和全局组件实例栈本质上是同一类机制——依赖函数执行的同步性来确定父子关系。一旦出现异步（`await`、`setTimeout`、`requestAnimationFrame`），`currentOwner` 在 await 前后可能指向另一个作用域，导致「异步回调里创建的东西不知道归谁管」。

### 10.3 替代方案：扁平 Set 结构的 Owner 池

针对全局栈的问题，在讨论中提出了一种替代方案：**扁平 Set 结构，不做树。**

```ts
// 没有 _firstChild / _nextSibling / _prevSibling 指针
// 没有 currentOwner 全局栈

interface Owner {
  id: number;
  parentId: number | null; // 显式引用，不依赖栈
  cleanups: (() => void)[];
  domRefs: Set<Node>;
  disposed: boolean;
}

const ownerPool: Map<number, Owner> = new Map();
```

**核心区别**：Owner 的父子关系通过显式的 `parentId` 声明，而非通过全局栈在函数调用时自动推断。

#### 收益

| 场景     | 树结构的问题                     | 扁平 Set 的解法                                     |
| -------- | -------------------------------- | --------------------------------------------------- |
| 异步组件 | await 后 `currentOwner` 可能已变 | Owner 是显式创建的对象，可在任何时刻注册 `parentId` |
| Portal   | 树结构假设子树在同一处 DOM       | `domRefs` 可以在任意位置，Owner 池不受 DOM 树约束   |
| Fragment | 需要容器节点来挂 Owner 元数据    | Owner 直接持有 `domRefs`，不需要容器                |
| 调试     | 需要递归遍历树                   | `ownerPool` 直接列出所有活跃 Owner                  |
| 清理     | 需要沿 `_firstChild` 链递归      | 按 `parentId` 收集所有后代，批量清理                |

#### 代价

唯一的实际代价是「找出某个 Owner 的所有子节点」需要扫描池（或维护反向索引）。但考虑实际场景——同时活跃的 Owner 数量不会超过数千个——在全量 Set 上按 `parentId` 过滤在 JS 引擎中是微秒级的操作。这不是问题。

### 10.4 关于 `context.h` 的讨论

讨论中曾考虑一个方案：把 Owner 感知的 `h` 版本通过 `context` 传入，让组件显式调用 `context.h` 而不是全局 `h`。

```ts
function Comp(props, { use, h }) {
  return h("div", null, h("span", null, count));
}
```

这确实能解决 Owner 归属问题——`context.h` 明确知道当前 Owner 是谁——不需要全局栈。

**但结论是不行**：

1. **JSX 编译后的 `jsx()` 调用走的是全局 `h()`**，不走 `context.h`。要让 JSX 用户也用上，要么改 JSX 运行时（不能，它是静态编译的），要么用户不能写 JSX。这对开发者体验是致命打击。

2. 即使不考虑 JSX，`context.h` 也有 spread 问题：指令内部的 `h()` 调用、工具函数内部的 `h()` 调用、第三方库的 `h()` 调用——它们拿不到 `context`，只能走全局 `h`。

3. 结论：`context.h` 理论上能解决问题，但实践中需要对整个生态加装「上下文透传」，复杂度不可接受。

### 10.5 关键的观察：Owner 边界已经存在于 kiaao 的现有架构中

这是讨论中最重要的发现。回头审视 kiaao 当前的代码：

```ts
// h.ts 中组件模式的路径
function h(tag, props, ...children) {
  // ...
  // 组件模式
  const instance = createComponentInstance(); // ← Owner 边界在这里
  const context = createContext(instance);
  const result = Comp(compProps, context);
  return handleSyncComponentResult(result, instance); // ← 资源注册在这里
}
```

`h()` 执行完组件函数、拿到返回的 node、正要返回给父级时——**在这个位置，`handleSyncComponentResult` 清楚地知道：**

- 「这是一个组件调用的结果」→ **新 Owner 应该在这里创建**
- 「这是哪个组件的返回值」→ **`parentId` 可以从调用栈的上二级获取**（通过 `context` 链或实例栈）

同样的逻辑适用于：

| 位置                                 | 当前做的事                          | Owner 模式等价操作                     |
| ------------------------------------ | ----------------------------------- | -------------------------------------- |
| `handleSyncComponentResult`          | `attachInstance(node, instance)`    | 创建 Owner + `owner.domRefs.add(node)` |
| `handleAsyncComponentResult`         | 创建 wrapper + `DISPOSE_KEY`        | 创建占位 Owner + await 后注册 node     |
| `createWhenElement` → `renderBranch` | `clearChildren(el)` → `disposeNode` | `disposeOwner(branchOwner)` → 重建     |
| `renderEach` → `sync`                | `disposeNode(node)` → 移除          | `disposeOwner(itemOwner)` → 移除       |
| `processChildren` 信号文本绑定       | `addLocalEffect(textNode, stop)`    | `owner.cleanups.push(stop)`            |

**Owner 边界的划分就是 kiaao 已经存在的组件边界和动态区域边界——不需要发明新概念。** 组件模式中 `createComponentInstance()` 的位置、`when` 分支切换的位置、`each` 列表项创建的位置——这些已经隐含了 Owner 的边界。

### 10.6 核心结论

**`h()` 不需要改签名，不需要 `context.h`。** Owner 的注册发生在 `h()` 执行完之后、node 返回给父级之前的这个「间隙」里——由 `component.ts`、`when.ts`、`each.ts` 这些已经知道边界在哪的框架层代码来执行。

- `h()` 照旧：创建节点、绑定信号属性、处理 children
- 组件框架层（`handleSyncComponentResult` 等）接管：创建 Owner、把 node 注册到 Owner
- 清理层接管：`disposeOwner(owner)` 替代 `disposeNode(node)`——效果等价，但遍历的是 Owner 池而非 DOM 树
- 扁平 Set 结构消除了全局栈依赖，用显式 `parentId` 替代隐式入栈出栈

这个方案不需要用户代码做任何改动——JSX 照写，`h()` 照旧，`use()` 照旧。变化完全发生在框架内部。

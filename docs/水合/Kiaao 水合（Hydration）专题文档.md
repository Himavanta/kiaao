# Kiaao 水合（Hydration）专题文档

**状态**：设计草案  
**版本**：1.0  
**日期**：2026-06-30

---

## 1. 背景

水合（Hydration）是指在服务端渲染（SSR）输出的静态 HTML 基础上，客户端重新建立框架运行时结构的过程。它包括：

- 复用已有 DOM 节点，而非重新创建
- 恢复事件绑定
- 建立 Owner 树和响应式信号关联
- 确保后续客户端更新与 SSR 输出一致

当前 Kiaao 已具备 SSR 能力（通过 `server/` 适配器），控制流组件经过重构后可在 SSR 下正确输出完整节点树，为水合奠定了基础。

---

## 2. 当前架构对水合的支撑

经过本轮重构，以下特性为水合提供了关键支持：

| 特性                 | 作用                                                               |
| -------------------- | ------------------------------------------------------------------ |
| 同步首次渲染         | 控制流组件不再依赖 `onMount`，SSR 和客户端首次渲染路径完全一致     |
| 统一 HResult         | `{ owner, nodes, pending, cleanups }`，边界清晰                    |
| `adoptResult` 机制   | 明确节点所有权和 Owner 挂接逻辑                                    |
| `RenderAdapter` 接口 | 所有 DOM 操作通过 adapter 代理，水合行为可在此层注入               |
| `setRenderMode`      | 已有 `"hydrate"` 模式占位，适配器内部可通过 `getRenderMode()` 判断 |

---

## 3. 水合需解决的核心问题

### 3.1 DOM 复用

`h()` 的 DOM 分支默认调用 `adapter.el(tag)` 创建新元素。水合模式下应复用 SSR 输出的已有 DOM 节点，而非新建。

### 3.2 事件恢复

SSR 输出的 HTML 不包含事件处理器。水合时需重新执行 `setProps` 中的事件绑定逻辑，`adapter.on` 应正常工作。

### 3.3 状态同步

服务端渲染时可能产生特定的信号状态（初始值、派生值等）。客户端需从服务端序列化的数据中恢复这些状态，避免 hydration mismatch。

### 3.4 控制流一致性

SSR 输出的条件分支（`Show`、`Case`、`Each`）必须与客户端首次渲染一致。由于控制流已同步首次渲染，此条件自然满足。

### 3.5 Portal 处理

SSR 下 Portal 可能内联渲染内容。水合时需将内容移动到目标容器，并正确管理生命周期。

---

## 4. 节点匹配策略（讨论）

### 方案 A：标记匹配

SSR 输出时为每个节点附加唯一标记（如 `data-kiaao-id`），水合时客户端通过标记查找对应节点。

**优点**：鲁棒性高，不依赖渲染顺序。  
**缺点**：增加 SSR 输出体积，文本/注释节点的标记实现复杂。

### 方案 B：顺序匹配

SSR 和客户端首次渲染的节点产生顺序完全一致。水合时客户端按相同顺序遍历 DOM 容器子节点和 `h()` 产生的节点列表，顺序匹配后直接复用。

**优点**：无需额外标记，实现简单。  
**缺点**：严格要求 SSR 与客户端渲染顺序一致；若存在动态内容（如异步组件），可能错位。

### 当前倾向

优先采用**顺序匹配**策略，因为当前架构已保证同步首次渲染的一致性。后续视需要可引入标记作为补充（如处理异步边界）。

## 5. 适配器行为调整

水合模式下，`browserAdapter` 内部通过 `getRenderMode() === "hydrate"` 判断，调整以下方法：

| 方法                      | 正常模式      | 水合模式                                         |
| ------------------------- | ------------- | ------------------------------------------------ |
| `el(tag)`                 | 创建新元素    | 从容器中按顺序取出已有元素                       |
| `text(text)`              | 创建文本节点  | 取出已有文本节点，必要时校验/更新内容            |
| `comment(text)`           | 创建注释节点  | 取出已有注释节点                                 |
| `append(parent, child)`   | 执行插入      | 跳过（DOM 结构已存在）                           |
| `before(ref, child)`      | 执行插入      | 跳过（首次渲染走返回 nodes 路径，不调用 before） |
| `setProp(el, key, value)` | 设置属性/事件 | 正常执行（恢复事件绑定）                         |
| `on/off`                  | 正常执行      | 正常执行                                         |
| `remove`                  | 正常执行      | 正常执行                                         |
| `replace`                 | 正常执行      | 按需执行                                         |

## 6. 状态序列化

需设计一种机制将服务端信号状态传递至客户端：

- SSR 渲染结束时，收集所有组件实例的信号状态（定义信号和派生信号的值）。
- 序列化为 JSON，通过 `<script>window.__Kiaao_STATE__ = {...}</script>` 注入 HTML。
- 客户端 `createApp` 在水合模式下读取 `__Kiaao_STATE__`，初始化信号时优先使用服务端值。

此功能可在基础水合完成后迭代。

---

## 7. 实施路线

### 第一阶段：基础水合

- `browserAdapter` 增加水合模式分支（`el`/`text`/`comment` 复用节点，`append`/`before` 跳过）。
- `createApp` 支持水合入口（接收容器元素，遍历子节点供 adapter 消费）。
- 事件绑定恢复。
- 控制流组件水合验证。

### 第二阶段：Portal 水合

- Portal 组件在水合模式下将内联内容移动至目标容器。

### 第三阶段：状态序列化

- `renderToString` 收集状态。
- 客户端状态恢复机制。

---

## 8. 开放问题

1. **顺序匹配的边界**：若 SSR 输出中包含异步组件占位符（当前不支持 SSR 异步），顺序匹配可能错位。需明确异步组件在水合阶段的行为。
2. **文本节点内容校验**：水合时是否需要检查文本节点内容一致性？若不一致（hydration mismatch），应如何降级？
3. **错误边界**：水合失败时的回退策略（降级为客户端完整渲染，还是抛出错误？）。

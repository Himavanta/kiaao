# 动态路由方案

**状态**:探索中,待讨论
**日期**:2026-07-23
**依赖**:[路由 API 方案](./路由API方案.md)、未来的 Suspense 机制、lazy 组件机制

## 一、背景

### 场景

中后台管理项目中,用户可访问的路由列表需**从服务端动态获取**:

1. 用户登录 → 拿到 token
2. 调用 `GET /api/menus` → 服务端返回该用户可访问的路由列表(通常是菜单树)
3. 根据返回数据构造 routes
4. 渲染路由视图

**关键特征**:

- 路由表在**应用启动后、渲染前**从服务端获取
- 获取后通常**固化**(同一会话内不再变化)
- 路由表内容依赖用户权限,无法预先在代码里写死

### 当前方案的局限

[路由 API 方案](./路由API方案.md) 中的 `define` 只接受**静态 `Route[]`**:

```ts
const AppView = define({
  routes: [
    { path: "", component: Home },
    { path: "dashboard", component: DashboardView },
  ],
});
```

`define` 调用时 routes 固化,后续无法变更。这覆盖了静态路由场景,但无法直接支持服务端动态路由。

### 为什么不并入路由 API 方案

动态路由的解决牵涉到:

- 是否扩展 `<Case>` 支持响应 mappingTable 变化(核心控制流改动)
- 是否引入信号 routes 类型联合
- 异步初始化模式(define 时机、loading 处理)
- 可能需要 lazy 配合(路由组件本身异步加载)
- 与未来 Suspense 机制的配合

这些超出了"路由层自身 API 重设计"的范围,涉及渲染层和数据层,因此单独成方案讨论。

## 二、需求分析

### 真实场景拆解

**场景 A:一次性异步初始化**

- 用户登录后拉取一次路由表,之后整个会话内不再变化
- 这是最常见的中后台模式
- 本质是"异步初始化",不是"运行时动态变化"

**场景 B:运行时动态变更**

- 路由表在运行时可能增删(如管理员动态启用某功能模块)
- 罕见,且通常可以通过刷新页面解决
- 本质是"响应式路由表"

**场景 C:路由组件本身异步加载**

- 路由表结构静态,但每个 route 的 component 是 lazy 的(代码分割)
- 这是 lazy/Suspense 的问题,不是动态路由的问题
- 不在本方案范围

本方案主要聚焦 **场景 A**,场景 B 作为可能的扩展考虑。

## 三、方案探索

### 方案 D:延迟 define(用户侧管理)

`define` 保持静态 routes,用户通过信号 + onMount 在异步获取后再调用 define:

```tsx
const { define, push, current, search } = createRouter({
  fallback: Loading,
});

function App() {
  const view = use(null); // 初始无 view

  ctx.onMount(async () => {
    const menus = await fetch("/api/menus").then((r) => r.json());
    view(define({ routes: menusToRoutes(menus) }));
  });

  return (
    <Show when={() => view()} fallback={<Loading />}>
      {() => h(view(), undefined)}
    </Show>
  );
}
```

**优点**:

- `define` API 保持简单(静态 `Route[]`)
- 动态路由是应用层关注点,用 kiaao 已有原语(`use` + `onMount` + `<Show>`)解决
- 不污染路由层
- 符合 kiaao "信号即一切"哲学

**缺点**:

- 用户需写样板代码(onMount + 信号 + Show)
- view 信号持有的是组件函数,类型上稍显奇怪(`Signal<ComponentFunction | null>`)
- 多个嵌套视图都要动态化时,样板代码重复

### 方案 B1:routes 接受信号

扩展 `define` 的 routes 类型,接受信号:

```tsx
const routes = use([]); // 初始空
const AppView = define({ routes }); // 传信号

fetch("/api/menus").then((menus) => {
  routes(menusToRoutes(menus)); // 信号更新 → view 响应
});

function App() {
  return <AppView />; // 初始空 routes → fallback;routes 到了 → 渲染真实路由
}
```

**优点**:

- 用户代码非常自然——define 一次,后续只更新信号
- fallback 自动处理"路由表为空"的状态(显示 loading 或 404)
- 无需用户手动管理 view 切换

**缺点**:

- 类型联合复杂:`routes: Route[] | Signal<Route[]>`
- routeMap 派生重算:`use(routesSig, () => buildMap(routesSig()))`
- **`<Case>` 需扩展支持响应 mappingTable 变化**(核心难点)

### 方案 F:define 内部动态创建 Case(保持控制流组件纯净)

**核心思路**:不扩展 `<Case>`(保持 children 只接受静态值),而是在 `define` 返回的 AppView 组件内部,响应 routes 信号变化,手动 dispose 旧 Case + adopt 新 Case。

#### 动机

方案 B1 要求扩展 `<Case>` 支持响应式 mappingTable,但 Case/Show/Each 是核心控制流组件,若支持信号 children 应一致支持(否则 API 不对称),这扩大了改动范围与风险。

方案 F 把动态性局限在路由层(define 内部),核心控制流组件保持纯净,API 一致。

#### 实现思路

```ts
function define(defOptions) {
  const { base, fallback } = defOptions;

  return (props, ctx) => {
    const segment = use(current, () => extractSegment(current(), base));
    const anchor = getAdapter().comment("define");
    ctx.owner.elements.add(anchor);

    // 静态 routes:直接渲染 Case(原方案)
    if (!isUse(defOptions.routes)) {
      const routeMap = buildMap(defOptions.routes);
      return h(Case, { value: segment }, routeMap, fallback);
    }

    // 动态 routes:手动管理 Case 生命周期
    const routesSig = defOptions.routes;
    let currentCaseHr: HResult | null = null;

    const renderCase = () => {
      if (currentCaseHr?.owner) disposeOwner(currentCaseHr.owner);
      const routeMap = buildMap(routesSig());
      currentCaseHr = adoptBranch({
        parentOwner: ctx.owner,
        anchor,
        Component: () => h(Case, { value: segment }, routeMap, fallback),
      });
    };

    renderCase();
    subscribeSignal(ctx.owner, routesSig, renderCase);

    return createHResult({ owner: ctx.owner, nodes: [anchor] });
  };
}
```

#### 工作机制

1. routes 是信号时,define 内部创建 anchor + 订阅 routesSig
2. routes 变化时,renderCase 被调用:
   - dispose 旧 Case 的 owner(销毁整个子树)
   - 用新 routes 构造 routeMap
   - adoptBranch 创建新 Case(重新匹配 segment,渲染对应分支)
3. `<Case>` 本身完全不知道 routes 是信号——它收到的永远是静态 routeMap

#### 与扩展 `<Case>` 的对比

| 维度                | 扩展 `<Case>`(B1)                      | 方案 F(define 内部动态创建) |
| ------------------- | -------------------------------------- | --------------------------- |
| `<Case>` 改动       | +20 行,处理 5 种情况                   | **不动**                    |
| 谁响应 routes 变化  | `<Case>` 内部订阅 mappingTable         | define 用 `subscribeSignal` |
| routes 变化时的行为 | 智能判断:只重渲染 component 变了的分支 | **整个 Case 销毁重建**      |
| 状态保留            | 可选(A1 重渲染 / A2 保持)              | **无**(整个子树重建)        |
| 复杂度位置          | 核心控制流                             | 路由层 define               |
| 影响面              | 所有 Case 使用者                       | 仅路由层                    |
| API 一致性          | 需考虑 Show/Each 同步扩展              | 不影响 Show/Each            |
| 实现难度            | 中(5 种情况 + 类型 + 测试)             | 中(manual dispose/adopt)    |

#### 优点

1. **保持核心纯净**:Case/Show/Each 不被动态需求污染,API 简单一致
2. **影响面隔离**:即使动态路由出问题,也不影响 `<Show>`/`<Each>` 稳定性
3. **复用已有机制**:adoptBranch/disposeOwner/subscribeSignal 都是现有原语
4. **符合分层**:路由层的问题在路由层解决,不上升到核心层
5. **场景适配**:中后台主要是场景 A(初始化),整体重建无损失(本来就没状态)

#### 缺点

1. **整个子树重建(状态丢失)**:routes 变化时,当前页面的组件状态(列表数据、滚动位置、表单输入等)全部丢失
   - 场景 A(一次性初始化):可接受(初始化时显示 fallback,无状态)
   - 场景 B(运行时动态变更):用户需自行用信号持久化状态,否则丢失
2. **define 实现复杂度上升**:约 +30 行手动生命周期管理
3. **仍是 dispose/adopt 重型操作**:routes 频繁变化会有性能开销(但路由表通常只变一次)
4. **复用了控制流组件的内部原语**:adoptBranch/disposeOwner 本是 `<Show>`/`<Each>` 的内部工具,define 直接调用相当于绕过 `<Case>` 自己实现了一遍——有重复实现的味道

#### 关键技术点:派生返回 HResult 的 DOM 替换

方案 F 之所以可行,是因为它**不依赖"派生信号返回新 HResult 自动替换 DOM"这种通用机制**(kiaao 目前没有)。而是在 define 内部手动调用 adoptBranch/disposeOwner,借力控制流组件的内部原语完成 DOM 替换。

这也是方案 F 的微妙之处:它把控制流的实现细节"泄漏"到了路由层。如果未来 adoptBranch/disposeOwner 的签名变化,define 需同步修改。

#### 适用场景评估

| 场景               | 方案 D       | 方案 B1        | 方案 F            |
| ------------------ | ------------ | -------------- | ----------------- |
| 场景 A(初始化)     | ✓ 样板代码多 | ✓ 需扩展 Case  | ✓ 最简洁          |
| 场景 B(运行时变更) | ✓ 样板代码多 | ✓ 智能更新     | △ 状态丢失        |
| 嵌套动态路由       | △ 样板爆炸   | ✓ 每层独立信号 | ✓ 每层独立 define |
| 保持核心纯净       | ✓            | ✗ 扩展 Case    | ✓                 |

#### 待深入讨论的问题

1. **整体重建的接受度**:场景 B 下状态丢失是否可接受?用户是否应该被建议"用信号持久化状态"?
2. **原语泄漏的可接受度**:define 直接调用 adoptBranch/disposeOwner 是否合理?是否应该把这些原语正式导出为公共 API?
3. **与方案 B1 的取舍**:方案 F 牺牲了状态保留,换取核心纯净。这个交换值得吗?
4. **是否需要混合策略**:静态 routes 走原方案,动态 routes 走方案 F——这种分支是否会让 API 不一致?

### 方案 G:Show 包裹 Case + bool 翻转(借力 Show 生命周期)

**核心思路**:不扩展 `<Case>`,也不在 define 内部手动调用 adoptBranch/disposeOwner(避免方案 F 的原语泄漏),而是用 `<Show>` 包裹 Case,通过派生一个 bool 信号让 routes 每次变化都触发 Show 切换,从而借力 Show 内置的 dispose/adopt 机制重建 Case。

#### 动机

方案 F 虽然不扩展核心,但直接调用了 adoptBranch/disposeOwner/subscribeSignal 这些控制流组件的内部原语,有"原语泄漏"问题。方案 G 用现有的 `<Show>` 完全封装了生命周期管理,define 内部无需触碰底层原语。

#### 实现思路

```ts
function define(defOptions) {
  const { base, fallback } = defOptions;

  return () => {
    const segment = use(current, () => extractSegment(current(), base));

    // 不管 routes 是静态还是信号,use 都能转成信号(统一处理)
    const routesSig = use(defOptions.routes);

    // 派生 bool 信号:routes 每次变化都翻转
    let toggle = false;
    const boolSig = use(routesSig, () => {
      toggle = !toggle;
      return toggle;
    });

    // Show 的两个分支都是同一个 Case 渲染函数
    // bool 翻转触发 Show 切换 → dispose 旧 Case + adopt 新 Case
    // 新 Case 调用时读取 routesSig() 最新值构建 routeMap
    const renderCase = () => {
      const routeMap = buildMap(routesSig());
      return h(Case, { value: segment }, routeMap, fallback);
    };

    return h(Show, { value: boolSig }, [renderCase, renderCase]);
  };
}
```

#### 工作机制

1. `use(defOptions.routes)` 把静态 routes 或信号 routes 统一转为信号
2. 派生 `boolSig`:routes 变化时 toggle 翻转,bool 值变化
3. `<Show>` 订阅 boolSig,bool 变化时切换分支:
   - dispose 旧分支(旧 Case 及其子树)
   - adopt 新分支(调用 renderCase,读取最新 routesSig 构建 routeMap)
4. `<Case>` 本身完全不知道 routes 是信号——它收到的永远是静态 routeMap
5. 静态 routes 场景:routesSig 永远不变,boolSig 不翻转,Show 不切换,等同于直接渲染 Case

#### 关键洞察:bool 翻转借力 Show 生命周期

`<Show>` 的 when 是布尔语义(truthy/falsy),routes 对象永远 truthy,无法直接用 routes 作为 when。但通过派生一个 bool 信号,把"routes 变化"转化为"布尔翻转",就借用了 Show 内置的 dispose/adopt 机制完成 Case 重建。

两个分支代码相同(都是 renderCase),区别仅在 Show 切换时重新调用 renderCase 读取最新 routesSig。

#### 影响范围:仅当前层级及后代

routes 信号是每个 define 内部独立创建的:

```tsx
const AppView = define({ routes: appRoutesSig });
const DashboardView = define({ base: "/dashboard", routes: dashboardRoutesSig });
```

- AppView 的 routes 变化 → 只触发 AppView 内部 boolSig 翻转 → 只切换 AppView 的 Show
- DashboardView 的 routes 不变 → DashboardView 内部 boolSig 不翻转 → DashboardView 的 Show 不切换

**但需注意**:AppView 的 Show 切换会 dispose 旧 Case(包括 DashboardView 子树),新 Case 重新渲染时会重新执行 DashboardView 的组件函数。由于 DashboardView 的 routes 信号未变,重新渲染的 Case 用相同 routeMap,视觉上无变化——但 DashboardView 内部状态(如本地信号)会丢失。

#### 优点

1. **完全用现有机制**:`use` + 派生 + `<Show>`,不扩展任何核心组件
2. **无原语泄漏**:define 内部不直接调用 adoptBranch/disposeOwner,生命周期由 Show 封装
3. **define 实现简洁**:约 +15 行,比方案 F 更简洁
4. **语义清晰**:bool 翻转触发 Show 切换,逻辑直接(虽是技巧但可读)
5. **静态/动态统一**:`use(defOptions.routes)` 无论传入静态还是信号都变信号,API 统一,无分支判断
6. **支持场景 A 和 B**:routes 任何变化都触发切换(场景 B 有状态丢失)
7. **影响面隔离**:routes 变化只影响当前层级的 Show,不波及其他层级

#### 缺点

1. **bool 翻转的 hack 味**:`toggle = !toggle` 是技巧,派生函数有副作用(修改外部变量)。kiaao 派生通常期望纯函数,这里为"变化即翻转"语义引入副作用
2. **两个分支代码重复**:可用同一个 renderCase 函数引用避免重复,但概念上 Show 期望两个不同分支
3. **整体重建(状态丢失)**:与方案 F 相同,routes 变化时当前层级 Case 及后代整体 dispose + 重建。场景 A 无此问题(初始化时无状态),场景 B 需用户用信号持久化状态
4. **Show 的 dispose/adopt 频率**:routes 频繁变化会频繁切换 Show,有性能开销(但路由表通常只变一次)
5. **派生信号初始计算**:boolSig 首次执行时 toggle 从 false 变 true,这是初始化的副作用,需确认不影响首次渲染逻辑

#### 与方案 F 的对比

| 维度       | 方案 F(define 内部动态创建)  | 方案 G(Show 包裹 + bool 翻转) |
| ---------- | ---------------------------- | ----------------------------- |
| 核心改动   | 无                           | 无                            |
| 原语泄漏   | 有(adoptBranch/disposeOwner) | **无**                        |
| 实现简洁度 | 中(手动生命周期)             | **高**(Show 封装)             |
| 样板代码   | 中                           | 少                            |
| 场景 A     | ✓                            | ✓                             |
| 场景 B     | ✓(重建)                      | ✓(重建)                       |
| 状态保留   | ✗                            | ✗                             |
| 语义清晰度 | 中(手动 dispose)             | 中(bool 翻转技巧)             |
| 风险       | 原语签名变化影响 define      | Show 行为依赖(稳定)           |

方案 G 在大多数维度优于或等同于方案 F,主要赢在"无原语泄漏"和"实现更简洁"。

5. **是否需要方案 G + B1 混合**:短期用 G(无核心改动),长期若需状态保留再升级到 B1?

## 四、`<Case>` 扩展支持响应式 mappingTable 的深入研究

### 4.1 当前 `<Case>` 的工作机制

```ts
// src/core/case.ts 核心结构
const childList = normalizeChildList(props.children);
const [mappingTable, fallbackComponent] = childList; // 一次性解构

let currentResult: HResult | null = null;
let prevKey: unknown = undefined;

const resolveComponent = (rawValue) => {
  const key = isString(rawValue) ? rawValue : String(rawValue);
  return mappingTable[key] ?? fallbackComponent; // 闭包读 mappingTable
};

const renderBranch = (isInitial) => {
  const newValue = toValue(props.value);
  if (newValue === prevKey) return; // key 不变跳过
  prevKey = newValue;
  if (currentResult?.owner) disposeOwner(currentResult.owner); // dispose 旧分支
  const Component = resolveComponent(newValue); // resolve 新组件
  if (isNotNil(Component)) {
    currentResult = adoptBranch({ parentOwner, anchor, Component, skipInsert: isInitial }); // 创建新分支
  } else {
    currentResult = null;
  }
};

renderBranch(true); // 首次渲染
subscribeSignal(context.owner, props.value, () => renderBranch(false)); // 订阅 value 信号
```

**关键观察**:

- `mappingTable` 是普通对象,在组件函数执行时通过解构获取,**之后闭包固定**
- `subscribeSignal` 只订阅 `props.value`,不订阅 `props.children`
- dispose + adoptBranch 是重型操作(涉及 owner 树、DOM 插入、triggerMount)

### 4.2 扩展目标

让 `<Case>` 响应 mappingTable 变化:

```tsx
const routes = use({});
// routes 变化时,Case 自动更新分支
<Case value={segment}>{routes}</Case>;
```

### 4.3 核心难点分析

#### 难点 1:变化的"语义"不明确

mappingTable 变化时,**应该做什么**?有几种可能:

**情况 A:当前 key 对应的 component 变了**

```ts
// 旧:{ users: UsersV1 }
// 新:{ users: UsersV2 }
// 当前 key = "users"
```

- 需要 dispose UsersV1 分支 + 创建 UsersV2 分支?
- 还是保持 UsersV1(因为 key 没变)?
- **直觉**:component 变了应该重新渲染,但这可能不是用户预期(状态丢失)

**情况 B:当前 key 从表中消失**

```ts
// 旧:{ users: UsersV1 }  当前 key = "users"
// 新:{ dashboard: Dashboard }  没有 users
```

- dispose 当前分支?
- 走 fallback?
- **直觉**:走 fallback(当前 key 未命中)

**情况 C:当前 key 仍在表中,component 未变**

```ts
// 旧:{ users: UsersV1, dashboard: Dashboard }
// 新:{ users: UsersV1, settings: Settings }  users 仍在,component 未变
// 当前 key = "users"
```

- 不做任何事(最优)
- **直觉**:跳过,key 和 component 都没变

**情况 D:新增了 key,但当前 key 未变**

```ts
// 旧:{ users: UsersV1 }
// 新:{ users: UsersV1, dashboard: Dashboard }  新增 dashboard
// 当前 key = "users"
```

- 不做任何事(当前显示的不受影响)
- **直觉**:跳过

**情况 E:mappingTable 变化,但当前 key 没变、component 也没变**

- 不做任何事

**这些情况需要明确处理策略**,且要高效判断"是否需要重渲染"。

#### 难点 2:信号粒度问题

`mappingTable` 是一个对象,信号更新是**整体替换**(用户 `routes(newMap)`)。框架无法知道"哪个 key 变了",只能拿到新旧两个对象。

要判断情况 C/D(当前 key 的 component 是否变了):

```ts
const oldComp = oldMap[currentKey];
const newComp = newMap[currentKey];
if (oldComp === newComp) {
  // 情况 C/D:跳过
} else {
  // 情况 A:重渲染
}
```

这需要**保留旧 mappingTable 的引用**做对比。可行,但增加状态。

#### 难点 3:dispose/adoptBranch 的时机与副作用

renderBranch 内部的 dispose + adoptBranch 会触发:

- 旧 owner 的 onUnmount 清理
- 新 owner 的 onMount
- DOM 节点的 remove/insert
- triggerMount 递归

如果 mappingTable 频繁变化(如开发时热更新),这些副作用会反复触发。**对路由场景影响小**(路由表通常只变一次),但对通用 `<Case>` 是性能隐患。

#### 难点 4:`subscribeSignal` 的扩展

当前 `subscribeSignal` 只订阅一个信号。若 mappingTable 也是信号,需要订阅两个:

- value 信号 → renderBranch
- mappingTable 信号 → ???(新的处理逻辑)

新增的 mappingTable 订阅回调不能直接复用 renderBranch,因为:

- value 变化:dispose + 用新 key resolve + adopt
- mappingTable 变化:判断当前 key 的 component 是否变了,决定是否重渲染

**需要两个不同的回调**。

#### 难点 5:类型签名扩展

当前:

```ts
children: ControlFlowChildren<Record<string, ComponentFunction>, ComponentFunction>;
```

扩展后:

```ts
children:
  | Record<string, ComponentFunction>                          // 静态
  | Signal<Record<string, ComponentFunction>>                 // 信号
  | [Record<string, ComponentFunction> | Signal<...>, ComponentFunction?]  // 带 fallback
```

类型联合膨胀,且 `normalizeChildList` 后要处理多种情况。

#### 难点 6:与 fallback 的交互

fallback 也可以是信号吗?

```tsx
<Case value={sig} fallback={fallbackSig}>
  {routesSig}
</Case>
```

理论上应该一致对待,但这让复杂度再上一台阶。**建议 fallback 保持静态**,只 mappingTable 支持。

#### 难点 7:首次渲染的时机

如果 mappingTable 是信号,初始值可能是空对象 `{}`:

```ts
const routes = use({});  // 初始空
<Case value={segment}>{routes}</Case>
```

首次渲染时:

- value = "users"
- mappingTable = {} → resolveComponent 返回 fallback
- 渲染 fallback

之后 routes 信号更新:

- mappingTable = { users: Users }
- 当前 key = "users" → 新增了对应 component
- 需要**从 fallback 切换到 Users 分支**

这要求 mappingTable 变化回调能触发"从 fallback 到真实分支"的切换,逻辑与普通分支切换不同。

### 4.4 扩展方案设计:最小侵入式扩展

**核心思路**:保持 `<Case>` 现有逻辑,增加一个"mappingTable 变化"的额外订阅,只处理"当前 key 对应 component 变化"的情况。

```ts
export function Case(props, context) {
  const adapter = getAdapter();
  const anchor = adapter.comment("case");
  context.owner.elements.add(anchor);

  const childList = normalizeChildList(props.children);
  const [mappingTableOrSignal, fallbackComponent] = childList;

  // 判断 mappingTable 是否为信号
  const isMappingSignal = isUse(mappingTableOrSignal);
  const getMappingTable = () =>
    isMappingSignal ? toValue(mappingTableOrSignal) : mappingTableOrSignal;

  let currentResult: HResult | null = null;
  let prevKey: unknown = undefined;
  let prevComponent: ComponentFunction | undefined = undefined; // 新增:追踪上次 component

  const resolveComponent = (rawValue) => {
    const key = isString(rawValue) ? rawValue : String(rawValue);
    const table = getMappingTable(); // 每次读取最新
    return table[key] ?? fallbackComponent;
  };

  const renderBranch = (isInitial) => {
    const newValue = toValue(props.value);
    if (newValue === prevKey) return;
    prevKey = newValue;
    if (currentResult?.owner) disposeOwner(currentResult.owner);
    const Component = resolveComponent(newValue);
    prevComponent = Component; // 记录
    if (isNotNil(Component)) {
      currentResult = adoptBranch({
        parentOwner: context.owner,
        anchor,
        Component,
        skipInsert: isInitial,
      });
    } else {
      currentResult = null;
    }
  };

  renderBranch(true);
  subscribeSignal(context.owner, props.value, () => renderBranch(false));

  // 新增:订阅 mappingTable 信号
  if (isMappingSignal) {
    subscribeSignal(context.owner, mappingTableOrSignal, () => {
      // mappingTable 变化:检查当前 key 的 component 是否变了
      const currentComponent = resolveComponent(prevKey);
      if (currentComponent === prevComponent) return; // 情况 C/D/E:跳过
      // 情况 A/B:重渲染
      if (currentResult?.owner) disposeOwner(currentResult.owner);
      prevComponent = currentComponent;
      if (isNotNil(currentComponent)) {
        currentResult = adoptBranch({
          parentOwner: context.owner,
          anchor,
          Component: currentComponent,
          skipInsert: false,
        });
      } else {
        currentResult = null;
      }
    });
  }

  const nodes = currentResult ? [...(currentResult as HResult).nodes, anchor] : [anchor];
  return createHResult({ owner: context.owner, nodes });
}
```

### 4.5 扩展的特点

**优点**:

- 改动集中在 `<Case>` 内部,约 +20 行
- 不影响静态 mappingTable 的性能(判断一次 isUse)
- 保留了"key 不变且 component 不变时跳过"的优化
- 复用现有 adoptBranch/disposeOwner 机制

**缺点**:

- `prevComponent` 新增状态
- 两个 subscribeSignal 订阅(value + mappingTable),回调不同
- mappingTable 变化时仍可能触发 dispose/adopt(情况 A/B),有性能开销

### 4.6 难度评估

| 维度           | 评估 | 说明                                                                    |
| -------------- | ---- | ----------------------------------------------------------------------- |
| **代码改动量** | 小   | `<Case>` 内 +20 行,其他文件不动                                         |
| **逻辑复杂度** | 中   | 需处理 5 种情况,但核心是"比较 component 引用"                           |
| **风险**       | 中   | 改动核心控制流,影响所有用 `<Case>` 的地方(`<Show>`/RouterView/用户代码) |
| **测试难度**   | 中高 | 需覆盖 5 种情况 + 与 value 变化的组合                                   |
| **类型扩展**   | 中   | 类型联合,但不复杂                                                       |
| **性能影响**   | 低   | 静态路径只多一次 isUse 判断;动态路径有额外订阅                          |

**总体难度:中等**。不是不可能,但需要谨慎处理边界情况和测试。

### 4.7 关键决策点

#### 决策 1:情况 A(component 变了)如何处理?

**选项 A1**:dispose 旧 + adopt 新(状态丢失)

- 简单,符合"component 变了就重渲染"直觉
- 但用户可能不希望状态丢失(如 Users 列表已加载的数据)

**选项 A2**:保持旧分支,忽略 component 变化

- 只有 key 变化才重渲染
- mappingTable 变化只影响"未来切换到新 key 时用哪个 component"
- **但这语义奇怪**:用户改了 routes 表,当前显示的不变,切走再切回才发现变了

**倾向 A1**(dispose + adopt),因为:

- 与 key 变化的行为一致
- 状态保留不是 `<Case>` 的职责(用户应该在组件内用信号持久化状态)
- A2 的语义会让用户困惑

#### 决策 2:fallback 是否也支持信号?

**建议不支持**。fallback 保持静态,理由:

- 减少 API 表面
- fallback 通常全局固定(如 404 组件)
- 动态 fallback 场景罕见

#### 决策 3:是否限制 mappingTable 的更新粒度?

用户可能这样写:

```ts
const routes = use({ a: A });
routes({ a: A, b: B }); // 新增 b
routes({ a: A }); // 删除 b
routes({ a: A2 }); // 替换 a
```

每次都是整体替换。框架无法知道"只新增了 b",必须全量对比。

**是否提供增量更新 API**?

```ts
routes.add("b", B);
routes.remove("a");
```

**建议不提供**。整体替换足够,增量 API 增加复杂度,且与"routes 是普通对象"的简洁性冲突。

#### 决策 4:嵌套 Case 的递归更新

如果 Case 内部的 component 又是包含 Case 的视图,外层 Case 重渲染会触发内层 Case 重建。这可能导致:

- 整个子树 dispose + 重建
- 性能开销大(尤其大型中后台)

**这是 A1 策略的代价**。但路由场景下,mappingTable 变化通常只发生一次(初始化),之后稳定。所以可接受。

#### 决策 5:与路由 API 的集成

如果 `<Case>` 支持动态 mappingTable,`define` 可以这样扩展:

```ts
function define(defOptions) {
  const { base, fallback } = defOptions;
  return () => {
    const segment = use(current, () => extractSegment(current(), base));
    // routes 可静态可信号
    return h(
      Case,
      { value: segment },
      isUse(defOptions.routes) ? defOptions.routes : buildMap(defOptions.routes),
      fallback ?? defaultFallback,
    );
  };
}
```

但这要求 `buildMap` 的结果也是信号(如果 routes 是信号),或让 `<Case>` 接受 Route[] 信号内部 buildMap。

**设计选择**:

- **选择 1**:`define` 的 routes 接受 `Route[] | Signal<Route[]>`,`<Case>` 接受 `Record<> | Signal<Record<>>`,define 内部转换
- **选择 2**:`<Case>` 只接受 `Record<> | Signal<Record<>>`,define 负责把 Route[] 信号转成 Record 信号

选择 2 更清晰(职责分离)。

### 4.8 一致性问题:Case/Show/Each 的 children 信号支持

若决定支持 children 传信号,**Case/Show/Each 三个控制流组件应一致支持**,否则 API 不对称会让用户困惑:

- `<Case>`:children 是 mappingTable,支持 `Signal<Record<string, ComponentFunction>>`
- `<Show>`:children 是单个组件/惰性函数,支持 `Signal<ComponentFunction>` 或 `Signal<() => VNode>`
- `<Each>`:children 是列表项渲染函数,支持 `Signal<T[]>`(实际上 Each 的 each 属性已经是信号,这是另一回事)

**一致支持的含义**:

- 三个组件都新增 isUse 判断 + subscribeSignal
- 类型签名都扩展联合类型
- 测试覆盖都增加动态场景

**这扩大了改动范围**,但也带来一致性收益。需权衡:

- 只扩展 `<Case>`:改动小,但 API 不一致
- 全部扩展:改动大,但 API 一致

**待讨论**:是否全部扩展?还是先只扩展 `<Case>` 验证可行性,再推广?

## 五、待讨论的问题

### 1. 场景优先级

是否只聚焦场景 A(一次性异步初始化)?场景 B(运行时动态变更)是否需要支持?

- 若只 A:方案 D 足够,无需扩展 `<Case>`;方案 F 也适用且更简洁
- 若需 B:必须扩展 `<Case>`(方案 B1)或接受方案 F 的状态丢失

### 2. 方案选择:D / B1 / F

三个方案各有取舍,需要根据场景优先级和核心纯净度偏好决定:

| 方案                     | 核心改动    | 状态保留   | 样板代码 | 适用场景                 |
| ------------------------ | ----------- | ---------- | -------- | ------------------------ |
| D(延迟 define)           | 无          | ✓          | 多       | 场景 A,嵌套少            |
| B1(扩展 Case)            | Case +20 行 | 可选       | 少       | 场景 A+B,接受核心改动    |
| F(define 内部动态创建)   | 无          | ✗ 整体重建 | 中       | 场景 A 为主,接受原语泄漏 |
| G(Show 包裹 + bool 翻转) | 无          | ✗ 整体重建 | 少       | 场景 A 为主,无原语泄漏   |

**核心权衡**:

- D vs G:都用已有机制且无核心改动,G 样板少但状态丢失
- F vs G:都不改核心且状态丢失,G 无原语泄漏、实现更简洁
- B1 vs G:B1 智能更新(状态可选保留)但改核心;G 不改核心但整体重建
- G 是 D/F/B1 之外的优选:在"不改核心 + 不泄漏原语 + 简洁"三方面平衡最好

### 3. `<Case>` 扩展的可接受性(仅方案 B1 相关)

扩展 `<Case>` 支持动态 mappingTable:

- 影响面:核心控制流组件,被 `<Show>`/`<Each>`/RouterView 等使用
- 风险:生命周期管理复杂化,可能引入 bug
- 收益:支持响应式路由表、动态分支切换

若选方案 F 或 G,此问题不存在。

### 4. Case/Show/Each 一致性(仅方案 B1 相关)

若扩展 children 信号支持,三个控制流组件是否同步扩展?

- 只 Case:API 不对称
- 全部:改动范围扩大

若选方案 F 或 G,此问题不存在(控制流组件不动)。

### 5. lazy 与 Suspense 的依赖

场景 A 的 loading 状态:

- 方案 D 用 `<Show fallback={<Loading />}>` 处理,简单
- 方案 F/G 由 define 的 fallback 处理(routes 为空时 Case 走 fallback)
- 但路由组件本身若也是 lazy,加载期间需要 Suspense

动态路由方案是否应等 Suspense 落地后再设计?还是先做方案 D/F/G 的简单版本?

### 6. 嵌套动态路由

中后台常见嵌套:

```
/dashboard                → DashboardLayout
/dashboard/users          → Users (动态)
/dashboard/users/:id      → UserDetail (动态)
```

若每层都动态:

- 方案 D:每层都要 onMount + 信号 + Show,样板代码爆炸
- 方案 B1:每层 routes 独立信号,相对简洁
- 方案 F:每层独立 define + 信号 routes,与 B1 相当
- 方案 G:每层独立 define + 信号 routes,与 B1/F 相当,且无原语泄漏

### 7. 方案 F 的原语泄漏问题(仅方案 F 相关)

方案 F 在 define 内部直接调用 adoptBranch/disposeOwner/subscribeSignal,这些本是控制流组件的内部原语。

- 是否应该把这些原语正式导出为公共 API?
- 还是保持内部,define 作为路由层的特例直接使用?
- 未来原语签名变化时,define 需同步修改——这种耦合可接受吗?

若选方案 G,此问题不存在(Show 封装了生命周期,define 不直接调用原语)。

### 8. 方案 G 的 bool 翻转副作用(仅方案 G 相关)

方案 G 的派生函数修改外部 toggle 变量,偏离纯函数语义:

- kiaao 派生通常期望纯函数,这里为"变化即翻转"语义引入副作用
- 是否有更优雅的实现?(如框架提供"变化即触发"的派生模式)
- 派生信号初始计算时 toggle 翻转一次,是否影响首次渲染?
- 两个分支相同的 Show 语义是否合理?是否需要专门的 `<Keyed>` 组件?

### 9. 服务端返回的路由数据格式

服务端通常返回菜单树:

```json
[
  {
    "path": "dashboard",
    "component": "Dashboard",
    "children": [{ "path": "users", "component": "Users" }]
  }
]
```

`component` 是字符串(组件名),需在前端映射到实际组件:

```ts
const componentMap = { Dashboard, Users, UserDetail };
function menusToRoutes(menus) {
  return menus.map((m) => ({
    path: m.path,
    component: componentMap[m.component],
    // 嵌套如何处理?
  }));
}
```

是否需要在路由层提供"组件名 → 组件"的注册机制?还是用户自己处理?

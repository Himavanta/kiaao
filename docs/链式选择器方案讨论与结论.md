# 链式选择器方案讨论与结论

**状态**：已否决  
**日期**：2026-06-07  
**讨论参与者**：框架作者、AI

---

## 一、背景与动机

### 1.1 当前行为

`define` 返回的原始 getter 支持选择器重载：

```javascript
const [user, setUser] = define({ profile: { name: "tom", age: 18 } });

user(); // 全量快照
user((v) => v.profile); // 返回派生函数，可继续用于 h() 绑定
user((v) => v.profile.name); // 深层选择
```

但 `derive` 返回的函数，以及 `user(v => ...)` 生成的派生函数，**不支持**再次传入选择器：

```javascript
const profile = user((v) => v.profile); // 派生函数
profile(); // 返回 profile 对象
profile((v) => v.name); // ❌ 当前不支持
```

### 1.2 提出的增强

让所有响应式函数（原始 getter、选择器派生函数、`derive` 返回的函数）都支持 `(selector?)` 重载，实现链式选择：

```javascript
const currentStyle = active((v) => (v ? { color: "white" } : { color: "black" }));

// 期望：从派生函数中继续选择
<div>current color: {currentStyle((v) => v.color)}</div>;
```

**期望收益**：

- 减少不必要的 `derive` 包装
- 让响应式 API 风格更统一
- 符合“显式选择器”的哲学

## 二、技术分析

### 2.1 依赖图谱的拓扑变化

**当前架构**：依赖图谱是**扁平的两层结构**

```
信号 (define) ──→ 选择器函数 ──→ effect (DOM 更新 / watch)
            ──→ derive ──→ effect
```

每个订阅都是从信号直接到消费端，依赖关系清晰、可追踪。

**如果引入链式选择**：图谱将变为**多层递归结构**

```
信号 ──→ 选择器A ──→ 选择器B ──→ 选择器C ──→ effect
```

这会带来三个深层问题：

**a) 对账的重复计算**

当信号更新时，选择器A、B、C 都会被触发对账。如果 B 和 C 直接依赖信号（为了避免创建中间信号），则 B 和 C 内部会重复执行 A 的逻辑。一次信号更新可能导致同一段选择器逻辑被执行多次。

**b) 依赖追踪的“锚点”漂移**

`user(v => v.profile).(v => v.name)` 内部的第二个派生函数，它依赖的究竟是 `user` 信号还是 `profile` 的中间值？

- 如果依赖 `user`：当 `user` 的 `profile` 之外的属性变化时，也会触发对账，违背精准更新原则。
- 如果依赖中间信号：框架必须在每次链式调用时隐式创建中间信号来保持依赖精度，引入内存开销和生命周期管理问题。

**c) 级联更新的顺序**

多层依赖在同一个同步更新周期中如何保证执行顺序？如果 A 更新后 B 还没更新，C 读到的是旧值还是新值？这在当前扁平的依赖图谱中不会出现。

### 2.2 与 `derive` 的边界模糊

`derive` 的核心价值是**缓存 + 拦截**，解决“昂贵计算被多处消费”的问题。

如果链式选择不加限制地存在：

```javascript
// 重复计算：profileGetter 被创建两次，逻辑执行两次
const nameGetter = user(v => v.profile).(v => v.name);
const avatarGetter = user(v => v.profile).(v => v.avatar);
```

用户可能写出上述代码而不意识到中间结果没有被缓存。正确的做法是：

```javascript
const profileGetter = derive(() => user((v) => v.profile));
const nameGetter = profileGetter((v) => v.name); // 现在 profileGetter 需要支持选择器
```

但如果同时提供链式选择，用户很容易跳过 `derive` 直接链式调用，然后遇到性能问题才回头加 `derive`。这会形成一个微妙的陷阱：**语法上允许的写法，性能上不一定是合理的**。

### 2.3 与选择器声明性的张力

选择器的设计初衷是**声明“我依赖什么”**：

```javascript
user((v) => v.profile.name); // 清晰：我依赖 user.profile.name
```

链式选择可能鼓励“逐步点选”的编码风格：

```javascript
user(v => v.profile).(v => v.name)  // 语义等价，但产生了两个选择器注册和两次对账
```

框架无法自动优化这种等价性，因为 `v => v.profile` 和 `v => v.name` 是两个独立的函数引用。

### 2.4 主流框架的设计选择

| 框架        | 是否支持链式选择 | 设计理由                                                                                                                |
| ----------- | ---------------- | ----------------------------------------------------------------------------------------------------------------------- |
| **SolidJS** | 否               | `createMemo` 返回 `() => T`，不可继续传选择器。深层访问必须写 `createMemo(() => user().profile.name)`，保持依赖扁平化。 |
| **Vue**     | 否               | `computed` 返回 `ComputedRef<T>`，通过 `.value` 访问。深层访问通过模板编译器展开为单一依赖链。                          |
| **React**   | 无响应式系统     | 不需要此特性。                                                                                                          |

主流框架刻意保持依赖图谱的扁平化，因为**响应式系统的正确性比灵活性更重要**。

## 三、反对理由总结

1. **对账复杂度增加**：链式选择会导致同一信号更新时，多个选择器函数重复执行相同的中间逻辑。

2. **依赖图谱结构复杂化**：从扁平两层变为多层递归，引入“中间值的缓存失效”、“多级依赖去重”、“级联更新顺序”等分布式系统中的经典难题。

3. **`derive` 的边界模糊**：用户可能写出性能不佳的链式调用，而不意识到需要 `derive` 来缓存中间结果。

4. **与 kiaao 哲学有张力**：kiaao 强调“显式、可预测”。链式选择让“谁依赖谁”这个本该一目了然的关系，变成需要顺着函数调用链回溯的隐式依赖。

5. **当前单层选择器已足够**：深层访问直接写 `user(v => v.profile.name)` 即可。跨信号组合用 `derive` 明确声明。没有实际场景是单层选择器无法覆盖而必须用链式选择来解决的。

---

## 四、最终结论

**决议**：不引入链式选择器。

**替代方案**：

- 深层属性访问：使用单层选择器 `user(v => v.profile.name)`。
- 跨信号组合：使用 `derive(() => obj1().field + obj2().field)` 显式声明。
- 从派生值中继续选择：先用 `derive` 创建中间派生节点，再通过中间节点访问（这需要中间节点支持选择器——但当前也不支持，保持所有派生节点为扁平即可）。

**未来重新讨论的条件**：

1. 出现足够多的真实用例，证明当前方案确实导致显著的代码冗余或性能问题。
2. 找到一种实现方案，能保持依赖图谱的扁平化，同时提供链式选择的语法便利（例如编译时的自动展开）。
3. 社区或用户提出新的视角，推翻上述反对理由中的核心假设。

---

## 五、与 kiaao 哲学的关系

不做链式选择，不是能力缺失，而是**克制的设计**。

kiaao 的核心承诺是：**开发者显式声明依赖，框架高效执行更新**。`derive` 是显式声明“这是一个派生节点”，`user(v => v.name)` 是显式声明“我依赖这个路径”。保持依赖图谱的扁平化，让每一步数据流都可见、可追踪、可优化，比提供看似便捷但隐式引入中间状态链式语法更重要。

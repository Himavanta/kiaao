# kiaao 开发记录

## 项目概况

**kiaao**：超轻量级、零编译、无虚拟 DOM 的响应式前端框架。

- 核心概念：4 个（define / derive / effect / h）
- 总 API：11 个（Teleport / lazy / romise / onMount / onUnmount / mount / unmount + 4 核心）
- 控制流：通过 `h()` 的原生属性指令 `when`/`each` 实现
- 设计哲学：显式选择器订阅，纯运行时细粒度更新
- 代码量目标：约 385-445 行

### 关键实现决策

- **Getter 设计**：`getter(selector)` 返回 `() => R` 响应式函数（非立即求值），挂载 `IS_REACTIVE` Symbol
- **依赖追踪**：信号内部 `Map<selectorFn, Set<DepEntry>>`，effect 维护 `ownedDeps` 双向引用（Vue 3 范式）
- **清理机制**：effect 重跑前清理旧 dep、重跑中重新收集；stop 函数从所有信号中移除条目
- **derive**：内部用 `define` 做版本信号，内部 `effect` 监听上游，值不变时跳过版本 bump
- **notifySignal 安全**：快照 deps 后再迭代，避免 effect 重跑时修改 Map 导致死循环
- **组件生命周期**：`h(component)` 创建实例压栈，`onMount/onUnmount` 注册到栈顶实例，`mount/unmount` 递归遍历 DOM 树触发
- **映射表模式**：children 为 `{ [key]: () => VNode }` 普通对象时自动识别，key 相同时跳过 DOM 更新，替代 `SKIP_UPDATE` 外部机制

### 2026-06-10 Phase 8 — when 指令扩展（else + 映射表模式）+ RouterView 重构

- **`when` 指令扩展**：新增 `else` 属性和映射表模式
  - `else` 属性：布尔模式下 `when` 条件为 falsy 时代替清空，渲染 `else` 内容
  - 映射表模式：`children` 为 `{ [key]: () => VNode }` 普通对象时自动进入，`when` 返回 key 匹配分支
  - 同一 key 时内部短路，不做任何 DOM 操作（替代 `SKIP_UPDATE` 机制）
  - key 未命中时走 `else` 回退，无 `else` 则清空
  - 分支函数惰性求值：只在对应 key 首次匹配或切换时调用
  - 映射表模式忽略 `each`（开发环境输出警告）

- **SSR 映射表模式支持**
  - `hSSR` 新增映射表模式：解析 `when` 获取 key，在 `children[0]` 映射表中查找分支并序列化
  - `else` 属性支持：布尔模式和映射表模式均适用
  - `stripDirectives` 新增 `else` 剥离，避免落入 HTML attribute

- **`createWhenElement` 内部重构**
  - 签名从位置参数改为对象参数（`createWhenElement(options)`），解决参数膨胀
  - 新增 `isPlainObject` 工具函数（排除 Node、数组、SSRSafe），放置在 `ssr-helpers.ts`
  - 模式优先级：映射表 > hasEach > 惰性 > 静态
  - 修复映射表模式子节点清理时没有从宿主元素移除的 Bug（缺少 `fragment.append(child)` 导致无限循环）
  - `isPlainObject` 中 `v instanceof Node` 加上 `typeof Node !== "undefined"` 守卫，兼容 SSR 环境

- **RouterView 重构**
  - 利用映射表模式替代手动的 `prevSegment` + `SKIP_UPDATE` 机制
  - 路由表初始化为 `{ [path]: () => h(component) }` 映射表
  - `when` 返回 `extractSegment()` 的结果作为 key，`else` 作为 fallback
  - 删除不再使用的 `matchRoute` 函数和 `SKIP_UPDATE` 引用
  - 代码量减少 40% 以上

- **设计文档**
  - 新增 `docs/when 指令扩展与 RouterView 重构方案.md`

### 2026-06-07 Phase 5.1 — 代码审查后优化

- **抽取 `setProps` 工具函数**（`src/dom.ts`）
  - 将 createWhenElement、createEachElement、普通元素路径三处重复的 EVENT_RE / IS_REACTIVE / 静态三段属性设置逻辑合并为统一函数
  - 减少约 25 行重复代码，一处修改属性处理逻辑三处受益

- **移除指令内部的 INSTANCE_KEY/DISPOSE_KEY**（`src/dom.ts`）
  - 深度推演六大场景（顶层挂载、组件返回、嵌套指令、子节点生命周期、triggerMount 遍历、effect 清理路径）
  - 核心发现：指令创建的所有 effect 都通过 `addLocalEffect` 注册到 `LOCAL_EFFECTS`，`instance.effectStops` 始终为空
  - 指令的 `instance` 在任何路径下都不执行有效操作，存在与否不影响功能正确性
  - 移除后代码更干净：不创建空实例、不挂无用元数据、不被外层组件模式覆盖时产生困惑

- **`setComponent`/`setError` 简化**（`src/components.ts`）
  - `setError(err)` 可简化：Error 实例不是函数类型，不会被 setter 误判为 updater
  - `setComponent(fn)` 不能简化：组件函数本身就是函数类型，会被 setter 的 `typeof updater === "function"` 判断误认为 updater 模式，必须保留 `() =>` 包装。这是 `define` setter 设计本身的固有歧义

### 2026-06-08 Attribute vs Property 区分分析

- 发现 `setProp` 统一走 `setAttribute` 的问题：`innerHTML`、`value`、`checked` 等属性必须走 property 赋值才能正确工作
- **`innerHTML`**：`setAttribute('innerHTML', ...)` 创建无用 attribute，内容不渲染
- **`value`（表单元素）**：`setAttribute` 只设初始值，用户交互后 framework 再 `setAttribute` 不影响 property，导致显示不更新
- **`checked`**：同 value，`setAttribute` 只设 defaultChecked
- **`indeterminate`**：根本没有对应 attribute，只能用 property
- **状态**：已完成（见 `docs/Attribute 与 Property 区分问题分析.md` 定稿文档）
- **文档**：`docs/Attribute 与 Property 区分问题分析.md`

# kiaao 自定义指令系统改造方案 v1.1

**状态**：定稿
**关联**：kiaao v4.2
**前置依赖**：组件 Context 与异步组件规范、多实例共享 DOM 节点方案

---

## 一、背景与动机

### 1.1 当前局限

kiaao 目前缺少一种标准化的方式，让开发者为原生 DOM 元素附加可复用的行为（动画、表单验证、手势、ResizeObserver 等）。现有的 `when`/`each` 指令是框架内置的，无法扩展。开发者只能通过组件包装或手动在 `onMount`/`onUnmount` 中操作 DOM 来实现类似效果，这导致了代码冗余和职责混淆。

### 1.2 设计目标

- **最小核心**：框架核心仅提供创建和识别指令的机制，不内置任何具体指令
- **元素级生命周期**：指令拥有独立于组件的 `onMount`/`onUnmount`/`use`，随元素的挂载和卸载自动管理
- **可组合性**：多个指令可以同时作用于同一元素，通过嵌套使用自然表达
- **退出动画支持**：指令的 `onUnmount` 可以返回 Promise，框架在元素被移除前等待其完成，实现退出动画
- **智能等待策略**：仅当元素是直接卸载目标（而非因父元素卸载而被连带移除）时，才等待退出动画，避免阻塞父级卸载

## 二、核心设计

### 2.1 指令的创建与识别

通过 `direct` 函数创建一个指令。`direct` 为传入的函数添加一个内部标记 `DIRECT_KEY`，`h()` 通过检测此标记区分指令和组件。

```ts
import { direct } from "kiaao";

const MyDirective = direct((el, props, context) => {
  // el: 当前绑定的原生 DOM 元素
  // props: JSX 传入的属性（包括 children）
  // context: 元素级生命周期方法 { onMount, onUnmount, use }
});
```

### 2.2 指令签名

```ts
type DirectiveFunction = (
  el: Element,
  props: Record<string, any> & { children?: any },
  context: DirectiveContext,
) => void;

interface DirectiveContext {
  onMount(fn: () => void): void;
  onUnmount(fn: () => void | Promise<void>): void;
  use: typeof use; // 元素级信号，元素移除时自动清理
}
```

- **`el`**：指令绑定的单个原生 DOM 元素。当指令包含多个子元素时，指令函数会被多次调用，每次传入一个子元素。
- **`props`**：JSX 中写在指令上的属性，包含一个特殊的 `children` 属性。
- **`context`**：元素级生命周期上下文，直接绑定到当前 `el`，无需显式传入元素。

### 2.3 多子元素支持

指令允许包含多个子元素。框架在指令模式下会遍历 `props.children`（已由 `h()` 处理为扁平数组），对每个是 `Element` 的子元素调用指令函数。非 `Element` 的子元素（文本节点、注释、信号函数、布尔值等）会被跳过，并在开发模式下输出警告。

```jsx
<FadeIn>
  <div>A</div>
  <div>B</div>
</FadeIn>
```

这里 `FadeIn` 指令会被调用两次，分别作用于 `<div>A</div>` 和 `<div>B</div>`。

**空 children 场景**：若所有子节点都是非 Element（如纯文本、条件渲染返回的 null），指令函数不会被调用。框架不做特殊处理——没有可操作的元素自然无事可做。

### 2.4 元素级生命周期

- **`context.onMount(fn)`**：注册的回调在元素被插入 DOM 后由 `triggerMount` 调用。此时元素已存在于文档中，可安全读取布局信息、播放 JS 动画。
- **`context.onUnmount(fn)`**：注册的回调在元素被移除前由 `disposeNode` 调用。若回调返回 Promise，且当前元素是触发卸载的“根节点”（见后文），则框架等待 Promise resolve 后再移除元素。
- **`context.use(...)`**：与组件级 `use` 语法完全一致，但创建的信号/派生绑定到当前元素的生存周期。元素被移除时，这些资源自动清理，无需手动管理。

### 2.5 指令的嵌套与执行顺序

多个指令可以嵌套使用，每个指令为一层：

```jsx
<Motion from={{ opacity: 0 }} to={{ opacity: 1 }}>
  <Validate rules={...}>
    <input />
  </Validate>
</Motion>
```

`h()` 的执行顺序是从内到外：先创建 `<input>`，然后 `Validate` 指令在 `<input>` 上注册钩子，然后 `Motion` 指令再注册钩子。指令的 `onMount` 钩子按注册顺序触发（Validate 先，Motion 后）。这与 DOM 树的父子层级无关——嵌套指令都绑定在同一个元素上，只有注册先后之分。

`onUnmount` 钩子并行执行（`Promise.all`），不保证先后顺序，因为指令之间不应有隐含的顺序依赖。

### 2.6 指令的返回值被忽略

指令函数可以返回一个值，但框架会忽略它。指令不能通过返回新元素来修改 DOM 结构，因为框架始终使用原始的 children 继续构建视图。指令的唯一正规途径是通过 `el` 直接操作 DOM 和通过 `context` 注册生命周期钩子。

### 2.7 指令的 props 响应式更新

指令函数只在元素创建时执行一次。如果 `props` 中包含信号值，后续信号变化不会触发指令重新执行。指令应在内部使用 `context.use` 订阅信号来处理响应式更新。这与组件函数“只执行一次”的哲学一致。

### 2.8 SSR 兼容性

SSR 模式下指令**不执行**。`hSSR` 在遇到指令标记的函数时，跳过指令逻辑，直接返回 children 的 SSR 输出。指令的动画、事件监听等在 SSR 中没有意义。指令作者可通过 `getRenderMode()` 检测渲染模式并做降级处理。

## 三、退出动画与异步等待策略

退出动画需要框架在移除元素前等待动画完成。我们引入 `root` 参数来智能区分等待场景。

### 3.1 问题场景

假设一个对话框由 `when` 控制显隐，对话框内部某个元素有退出动画。当用户关闭对话框时（`when` 条件变 false），用户期望对话框立即消失，而不是等待内部元素的动画播放完毕。此时内部元素属于“间接卸载”，不应等待其退出动画。

### 3.2 `root` 参数

`disposeNode` 新增一个 `root` 参数，表示本次卸载的“根节点”——即触发卸载的最顶层元素。只有当前处理的节点等于 `root` 时，才等待指令 `onUnmount` 返回的 Promise。

```ts
async function disposeNode(node: Node, root: Node | null);
```

- `root` 非 null 且 `node === root`：该节点是直接卸载目标，等待其退出动画。
- `root` 为 null 或 `node !== root`：该节点是被连带移除的后代或手动卸载，不等待任何退出动画。

多个 `onUnmount` 回调返回 Promise 时，使用 `Promise.all` 并行等待所有完成。

### 3.3 各调用方的 root 传递

- **`when` 指令**：遍历宿主元素的直接子节点，对每个子节点调用 `disposeNode(child, child)`。每个子节点自己就是 root。
- **`each` 指令**：移除某个列表项时，调用 `disposeNode(itemElement, itemElement)`。列表项自己就是 root。被移除项的退出动画独立进行，与其他项的增删移动并行。
- **`unmount` 函数**：调用 `disposeNode(root, null)`。`root` 为 null，所有退出动画均不等待，确保组件立即卸载。

### 3.4 递归过程中的 root 透传

`disposeNode` 在递归处理子节点时，`root` 参数原样传递给子节点，不做修改。因此一个子节点的后代元素在递归中，`root` 仍然是该子节点本身，后代元素的卸载被视为间接卸载，不会等待动画。

### 3.5 示例流程

```
<div when={showDialog}>          <!-- 宿主元素 -->
  <div class="dialog">
    <span class="animated-text">Hello</span>  <!-- 有退出动画指令 -->
  </div>
</div>
```

当 `showDialog` 变为 false 时：

1. `when` 获取宿主元素的子节点：`<div class="dialog">`。
2. 调用 `disposeNode(dialogDiv, dialogDiv)`。
3. 递归进入 `dialogDiv` 的子节点：`<span class="animated-text">`。
   - 调用 `disposeNode(span, dialogDiv)`，注意 `root` 仍为 `dialogDiv`。
   - `span` 上有退出动画指令，但 `span !== dialogDiv`，所以**不等待**动画。
4. 回到 `dialogDiv` 层，假设 `dialogDiv` 本身没有指令钩子，则正常清理。
5. 对话框立即移除，内部的动画被跳过。

### 3.6 `disposeNode` 异步化的影响

`disposeNode` 从同步函数变为异步函数，所有调用方（`unmount`、`when`、`each`）均需 `await` 其完成。对于没有指令钩子或无需等待的节点，`await` 立即返回，行为与同步无异。此为**破坏性变更**，用户代码中直接调用 `unmount` 并同步依赖后续 DOM 状态的逻辑需改为 `await unmount(root)`。

## 四、与现有机制的集成

### 4.1 `h()` 的改动

在 `h()` 中，当 `tag` 是函数且带有 `DIRECT_KEY` 标记时，进入指令模式：

1. 计算 `props`（合并 rest children 到 `props.children`）。
2. 遍历扁平化后的 `children`，对每个是 `Element` 的子元素调用指令函数。跳过非 Element 子元素并在开发模式警告。
3. 忽略指令函数的返回值，继续将原始 `children` 返回。指令的返回值（单个 Node 或数组）在框架内部被正确消费——作为组件根元素时，多子元素由 Fragment 包裹透明节点；作为普通元素的子节点时，被 `processChildren` 扁平化处理。

### 4.2 `triggerMount` 的改动

`triggerMount` 在遍历 DOM 树时，除了处理组件的 `INSTANCE_KEY`，还需检查元素上是否有指令注册的 `onMount` 回调。这些回调存储在一个内部的 Symbol 属性中，按注册顺序执行。

### 4.3 `disposeNode` 的改动

如第三节所述，增加 `root` 参数并改为异步函数。内部清理顺序：

1. 递归处理子节点
2. 清理 `LOCAL_EFFECTS`（包括指令的 `context.use` 创建的信号）
3. 执行指令的 `onUnmount`（根据 root 判断是否等待 Promise）
4. 执行 `DISPOSE_KEY`（组件的 `onUnmount`）

指令的 `onUnmount` 在组件的 `onUnmount` 之前执行，且指令的信号先于指令的 `onUnmount` 停止。这保证了元素级动画先播放，组件级清理后执行。

### 4.4 元素级 `use` 的实现

指令的 `context.use` 调用原始 `use` 创建信号/派生，然后将返回的 `stop` 函数注册到元素的 `LOCAL_EFFECTS` 集合中。`disposeNode` 在清理时原本就会停止 `LOCAL_EFFECTS`，因此元素级信号自动随元素清理。

### 4.5 与组件根元素的关系

组件可以直接返回被指令包裹的元素。若组件根元素同时拥有 `INSTANCE_KEY` 和指令钩子，清理顺序见 4.3。若指令包含多个子元素且作为组件根标签，Fragment 会包裹透明节点。

## 五、边缘情况处理

| 场景                    | 处理方式                                                                         |
| ----------------------- | -------------------------------------------------------------------------------- |
| Fragment 作为指令子节点 | 指令只看到一个容器元素，不做特殊处理。用户需将指令放在 Fragment 内部每个元素上。 |
| 指令包裹异步组件        | 指令绑定到异步组件的 wrapper。真实内容渲染后，wrapper 的退出动画仍正常触发。     |
| when 切换时新旧动画衔接 | 不干预。旧节点退出动画与新节点进入动画各自独立。                                 |
| each 列表项退出动画     | 每个被移除项的退出动画独立并行，不影响新增和移动项。                             |

## 六、使用示例

### 6.1 退出动画指令

```ts
const FadeOut = direct((el, props, context) => {
  context.onUnmount(() => {
    return animate(el, { opacity: [1, 0] }, { duration: props.duration || 0.3 }).finished
  })
})

function Comp() {
  return (
    <div when={visible}>
      <FadeOut duration={0.5}>
        <div class="content">我会淡出</div>
      </FadeOut>
    </div>
  )
}
```

### 6.2 同时绑定进入和退出动画

```ts
const Motion = direct((el, props, context) => {
  const { from, to, duration = 0.3 } = props;
  Object.assign(el.style, from);
  context.onMount(() => animate(el, to, { duration }));
  context.onUnmount(() => animate(el, from, { duration }).finished);
});
```

### 6.3 表单验证指令

```ts
const Validate = direct((el, props, context) => {
  const check = () => {
    /* 校验逻辑 */
  };
  el.addEventListener("input", check);
  context.onUnmount(() => el.removeEventListener("input", check));
});
```

## 七、与规范的一致性

| spec.md 现有约定       | 指令方案是否一致 | 说明                     |
| ---------------------- | ---------------- | ------------------------ |
| 组件只运行一次         | ✅               | 指令函数也只执行一次     |
| 依赖显式声明           | ✅               | context.use 遵循相同规则 |
| 闭包即作用域           | ✅               | 指令本身用闭包隔离       |
| 无全局生命周期导入     | ✅               | 通过 context 传入        |
| LOCAL_EFFECTS 清理机制 | ✅               | 复用已有机制             |
| disposeNode 同步       | ❌               | 变为异步，破坏性变更     |

## 八、设计哲学总结

指令系统延续了 kiaao 一贯的原则：**机制在核心，策略在扩展**。框架只提供元素级生命周期的原语（挂载、卸载、信号绑定），具体的动画、验证等逻辑由外部库或用户代码实现。通过 `root` 参数实现的智能等待策略，解决了退出动画与用户体验的冲突，让开发者在享受动画表现力的同时不被框架的内部机制所困扰。

# kiaao 自定义指令系统改造方案 v1.3

**状态**：定稿
**关联**：kiaao v4.2
**前置依赖**：组件 Context 与异步组件规范、多实例共享 DOM 节点方案

## 一、背景与动机

### 1.1 当前局限

kiaao 目前缺少一种标准化的方式，让开发者为原生 DOM 元素附加可复用的行为（动画、表单验证、手势、ResizeObserver 等）。现有的 `when`/`each` 指令是框架内置的，无法扩展。开发者只能通过组件包装或手动在 `onMount`/`onUnmount` 中操作 DOM 来实现类似效果，这导致了代码冗余和职责混淆。

### 1.2 设计目标

- **最小核心**：框架核心仅提供创建和识别指令的机制，不内置任何具体指令
- **元素级生命周期**：指令拥有独立于组件的 `onMount`/`onUnmount`/`use`，随元素的挂载和卸载自动管理
- **可组合性**：多个指令可以同时作用于同一元素，通过嵌套使用自然表达
- **资源自动清理**：指令创建的信号和注册的清理回调随元素生命周期自动管理，无需手动干预

## 二、核心设计

### 2.1 指令的创建与识别

通过 `direct` 函数创建一个指令。`direct` 为传入的函数添加一个内部标记 `DIRECT_KEY`，`h()` 通过检测此标记区分指令和组件。

```ts
import { direct } from "kiaao";

const MyDirective = direct((el, props, context) => {
  // el: 当前绑定的原生 DOM 元素
  // props: JSX 传入的属性（包括 children）
  // context: 元素级生命周期方法 { onMount, onUnmount, use }
});
```

### 2.2 指令签名

```ts
type DirectiveFunction = (
  el: Element,
  props: Record<string, any> & { children?: any },
  context: DirectiveContext,
) => void;

interface DirectiveContext {
  onMount(fn: () => void): void;
  onUnmount(fn: () => void): void;
  use: typeof use; // 元素级信号，元素移除时自动清理
}
```

- **`el`**：指令绑定的单个原生 DOM 元素。当指令包含多个子元素时，指令函数会被多次调用，每次传入一个子元素。
- **`props`**：JSX 中写在指令上的属性，包含一个特殊的 `children` 属性。
- **`context`**：元素级生命周期上下文，直接绑定到当前 `el`，无需显式传入元素。`context` 的生命周期方法始终作用于当前正在处理的元素。

### 2.3 多子元素支持

指令允许包含多个子元素。框架在指令模式下会遍历 `props.children`（已由 `h()` 处理为扁平数组），对每个是 `Element` 的子元素调用指令函数。非 `Element` 的子元素（文本节点、注释、信号函数、布尔值等）会被跳过，并在开发模式下输出警告，提醒开发者指令只作用于原生元素。

```jsx
<FadeIn>
  <div>A</div>
  <div>B</div>
</FadeIn>
```

这里 `FadeIn` 指令会被调用两次，分别作用于 `<div>A</div>` 和 `<div>B</div>`。

**空 children 场景**：若所有子节点都是非 Element（如纯文本、条件渲染返回的 null），指令函数不会被调用。框架不做特殊处理——没有可操作的元素自然无事可做。

### 2.4 元素级生命周期

#### `context.onMount(fn)`

注册的回调在元素被插入 DOM 后由 `triggerMount` 调用。此时元素已存在于文档中，可安全读取布局信息、播放 JS 动画。

`triggerMount` 在遍历 DOM 树时，除了处理组件的 `INSTANCE_KEY`，还需检查元素上是否有指令注册的 `onMount` 回调。这些回调存储在一个内部的 Symbol 属性中，按注册顺序执行。

#### `context.onUnmount(fn)`

注册的回调在元素被移除前由 `disposeNode` 调用。**`fn` 是同步的，不应返回 Promise。** 指令的 `onUnmount` 用于清理资源（移除事件监听、断开 Observer、停止定时器等），不负责异步等待。

**退出动画的异步等待能力由独立的 `hook` API 提供**（参见第八节）。`hook` 在信号写入时拦截，延迟信号更新，从而间接延迟 `when`/`each` 的清理流程。指令系统本身不参与退出动画的时序控制。

#### `context.use(...)`

与组件级 `use` 语法完全一致，但创建的信号/派生绑定到当前元素的生存周期。元素被移除时，这些资源自动清理，无需手动管理。

指令的 `context.use` 调用原始 `use` 创建信号/派生，然后将返回的 `stop` 函数注册到元素的 `LOCAL_EFFECTS` 集合中。`disposeNode` 在清理时原本就会停止 `LOCAL_EFFECTS`，因此元素级信号自动随元素清理。

**清理顺序**：`disposeNode` 在处理元素时，先清理 `LOCAL_EFFECTS`（包括指令的 `context.use` 创建的信号），然后执行指令的 `onUnmount` 回调，最后执行 `DISPOSE_KEY`（组件的 `onUnmount`）。这意味着指令的信号先于指令的 `onUnmount` 被停止——但信号的当前缓存值仍然可以通过 `getter()` 读取，对于需要在 `onUnmount` 中读取信号值的场景是安全的。

### 2.5 指令的嵌套与执行顺序

多个指令可以嵌套使用，每个指令为一层：

```jsx
<Motion from={{ opacity: 0 }} to={{ opacity: 1 }}>
  <Validate rules={...}>
    <input />
  </Validate>
</Motion>
```

`h()` 的执行顺序是从内到外：先创建 `<input>`，然后 `Validate` 指令在 `<input>` 上注册钩子，然后 `Motion` 指令再注册钩子。指令的 `onMount` 钩子按注册顺序触发（Validate 先，Motion 后）。这与 DOM 树的父子层级无关——嵌套指令都绑定在同一个元素上，只有注册先后之分。文档中"内层指令"指先注册的指令，"外层指令"指后注册的指令。

`onUnmount` 钩子并行执行，不保证先后顺序，因为指令之间不应有隐含的顺序依赖。

### 2.6 指令的返回值被忽略

指令函数可以返回一个值，但框架会忽略它。指令不能通过返回新元素来修改 DOM 结构，因为框架始终使用原始的 children 继续构建视图。指令的唯一正规途径是通过 `el` 直接操作 DOM（例如设置样式、添加事件监听）和通过 `context` 注册生命周期钩子。如果开发者选择使用 `el.replaceWith(...)` 等破坏性操作，则需要自行承担所有后果。

### 2.7 指令的 props 响应式更新

指令函数只在元素创建时执行一次。如果 `props` 中包含信号值，后续信号变化不会触发指令重新执行。指令应在内部使用 `context.use` 订阅信号来处理响应式更新。这与组件函数"只执行一次"的哲学一致。

### 2.8 SSR 兼容性

SSR 模式下指令**不执行**。`hSSR` 在遇到指令标记的函数时，跳过指令逻辑，直接返回 children 的 SSR 输出。指令的动画、事件监听等在 SSR 中没有意义。指令作者可通过 `getRenderMode()` 检测渲染模式并做降级处理。

## 三、与 `h()` 的集成

### 3.1 `h()` 的改动

在 `h()` 中，当 `tag` 是函数且带有 `DIRECT_KEY` 标记时，进入指令模式：

1. 计算 `props`（合并 rest children 到 `props.children`）。
2. 遍历扁平化后的 `children`，对每个是 `Element` 的子元素调用指令函数。跳过非 Element 子元素并在开发模式警告。
3. 忽略指令函数的返回值，继续将原始 `children` 返回。

**`h()` 的返回类型保持 `Element` 不变。** 指令的返回值（单个 Node 或数组）在框架内部被正确消费——作为组件根元素时，多子元素由 Fragment 包裹透明节点；作为普通元素的子节点时，被 `processChildren` 扁平化处理。不需要修改 `h()` 的类型签名。

**指令作为组件根标签，多子元素时 Fragment 的处理**：

```jsx
function Comp() {
  return (
    <FadeIn>
      <div>A</div>
      <div>B</div>
    </FadeIn>
  );
}
```

`FadeIn` 是指令，它接收两个 `<div>` 作为 children。指令遍历处理这两个子元素后，返回它们（一个数组）。`h()` 的组件模式接收到返回值——一个数组。当前 kiaao 对多根元素的处理是通过 Fragment 包裹透明节点，所以最终 DOM 是：

```html
<div style="display: contents">
  <!-- Fragment 包裹 -->
  <div>A</div>
  <!-- 带有 FadeIn 的钩子 -->
  <div>B</div>
  <!-- 带有 FadeIn 的钩子 -->
</div>
```

### 3.2 组件模式与指令模式的区分

`h()` 在遇到 `typeof tag === 'function'` 时，先检查 `tag[DIRECT_KEY]`。如果存在，进入指令模式；否则进入组件模式。指令模式不创建组件实例，不压入 `currentComponent` 栈，不触发组件生命周期。

### 3.3 指令包裹组件

```jsx
<FadeIn>
  <MyComponent />
</FadeIn>
```

`MyComponent` 的 `h()` 调用返回一个 Node。指令以该 Node 为 `el` 调用。如果 `MyComponent` 是异步组件（返回 Promise），在 resolve 之前 `<MyComponent />` 的位置是一个 wrapper `<div style="display:contents">`，指令此时接收到的就是这个临时 wrapper。指令绑定到 wrapper 上，当 wrapper 被移除或替换时，指令的钩子自然触发。这是正确的行为——指令不感知异步组件的内部状态，只感知传入它的 DOM 节点的生命周期。

## 四、与现有生命周期机制的集成

### 4.1 `triggerMount` 的改动

`triggerMount` 在递归遍历 DOM 树时，除了处理组件的 `INSTANCE_KEY`（现在为 Set），还需检查元素上是否有指令注册的 `onMount` 回调。这些回调存储在一个内部的 Symbol 属性中，按注册顺序执行。

### 4.2 `disposeNode` 的改动

**`disposeNode` 保持同步。** 指令的 `onUnmount` 回调同步执行，不返回 Promise。

`disposeNode` 的内部清理顺序：

1. 递归处理子节点
2. 清理 `LOCAL_EFFECTS`（包括指令的 `context.use` 创建的信号）
3. 执行指令的 `onUnmount` 回调
4. 执行 `DISPOSE_KEY`（组件的 `onUnmount`）

指令的 `onUnmount` 在组件的 `onUnmount` 之前执行。指令的信号（`context.use`）在指令的 `onUnmount` 之前被停止——但信号的当前缓存值仍然可以通过 `getter()` 读取。

### 4.3 指令的 `context.use` 清理归属

指令在元素上使用 `context.use`，信号注册到元素的 `LOCAL_EFFECTS`。`disposeNode` 清理 `LOCAL_EFFECTS` 时，这些信号被自动停止。由于 `LOCAL_EFFECTS` 的清理在指令 `onUnmount` 之前，指令信号先被停止——这是合理的：元素级资源先释放，指令的清理回调后执行。

### 4.4 与组件根元素的关系

组件可以直接返回被指令包裹的元素。若组件根元素同时拥有 `INSTANCE_KEY`（组件实例关联）和指令钩子，清理顺序见 4.2 节。

## 五、边缘情况处理

| 场景                          | 处理方式                                                                                                                       |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Fragment 作为指令子节点       | 指令只看到一个 Fragment 容器元素（`<div style="display:contents">`），不做特殊处理。用户需将指令放在 Fragment 内部每个元素上。 |
| 指令包裹异步组件              | 指令绑定到异步组件的 wrapper。真实内容渲染后，wrapper 的清理仍正常触发。                                                       |
| 指令作为组件根标签，多子元素  | Fragment 自动包裹透明节点。                                                                                                    |
| 空 children                   | 无 Element 可操作，指令函数不被调用，不产生警告。                                                                              |
| 信号函数作为子节点            | 信号函数由 `h()` 处理创建文本占位，指令跳过。                                                                                  |
| 嵌套指令的 onUnmount 执行顺序 | 并行执行，不保证先后顺序。                                                                                                     |

## 六、使用示例

### 6.1 进入动画指令（JS 动画）

```ts
import { direct } from 'kiaao'
import { animate } from 'motion'

const FadeIn = direct((el, props, context) => {
  const { duration = 0.3 } = props
  Object.assign(el.style, { opacity: 0 })
  context.onMount(() => {
    animate(el, { opacity: 1 }, { duration })
  })
})

function Comp() {
  return (
    <FadeIn duration={0.5}>
      <div class="content">我会淡入</div>
    </FadeIn>
  )
}
```

### 6.2 退出动画指令

退出动画通过 `hook` API 实现（参见第八节）。指令本身不处理退出动画的时序。

### 6.3 表单验证指令

```ts
const Validate = direct((el, props, context) => {
  const check = () => {
    /* 校验逻辑 */
  };
  el.addEventListener("input", check);
  context.onUnmount(() => el.removeEventListener("input", check));
});
```

### 6.4 ResizeObserver 指令

```ts
const ObserveSize = direct((el, props, context) => {
  const observer = new ResizeObserver((entries) => {
    props.onResize?.(entries[0].contentRect);
  });
  observer.observe(el);
  context.onUnmount(() => observer.disconnect());
});
```

## 七、与规范的一致性

| spec.md 现有约定       | 指令方案是否一致 | 说明                                         |
| ---------------------- | ---------------- | -------------------------------------------- |
| 组件只运行一次         | ✅               | 指令函数也只执行一次                         |
| 依赖显式声明           | ✅               | context.use 遵循相同规则                     |
| 闭包即作用域           | ✅               | 指令本身用闭包隔离                           |
| 无全局生命周期导入     | ✅               | 通过 context 传入                            |
| LOCAL_EFFECTS 清理机制 | ✅               | 复用已有机制                                 |
| disposeNode 同步       | ✅               | 保持同步，退出动画通过 hook API 在信号层处理 |

## 八、退出动画与 `hook` API

### 8.1 核心矛盾

在 kiaao 中，`when`/`each` 的 DOM 清理发生在派生回调中。派生回调是同步的——信号变化后立即同步执行所有下游派生。如果在 `disposeNode` 中等待退出动画的 Promise，派生回调就需要变成异步——这将破坏 kiaao 响应式系统的核心模型。

### 8.2 为什么异步挂载可行，异步卸载不可行

|                  | 异步挂载                    | 异步卸载             |
| ---------------- | --------------------------- | -------------------- |
| 触发方           | Promise.then（框架外部）    | 派生回调（框架内部） |
| 与派生回调的关系 | 无关                        | 在派生回调内部       |
| 能否 await       | 能（Promise.then 天然支持） | 不能（派生回调同步） |
| 框架支持         | ✅ 已实现（异步组件）       | ❌ 不可行            |

挂载和卸载之所以不对称，是因为它们的触发点处于框架的不同层级。

### 8.3 解决方案：`hook` API — 信号写入拦截

**核心思路**：不修改 DOM 清理流程，而是修改触发清理的信号更新时机。`hook` 在信号写入时插入异步等待——信号值延迟更新 → `when`/`each` 的清理流程被间接延迟 → 退出动画可以在 DOM 移除前播放 → 派生回调保持同步。

这与 React 和 Solid 的思路一致——React 延迟状态更新，Solid 延迟信号更新，kiaao 通过 `hook` 在信号写入时插入异步等待。

### 8.4 `hook` API 设计

#### 核心定位

`hook` 是独立的 API，不与 `use` 融合。它为一个信号注册写入钩子。当信号被写入且新值与当前值不同时，钩子先执行。钩子可以返回 Promise，框架等待所有钩子完成后才真正更新信号值。

```ts
import { hook } from "kiaao";

const stop = hook(signal, async (value, signal) => {
  // value: setter 传入的新值
  // signal: AbortSignal（用于处理并发写入的中断）
  await someAsyncOperation();
});
// 需要移除钩子时
stop();
```

#### 钩子池的挂载位置

钩子池挂载在信号内部状态的 `state.hooks` 上。每个信号通过 `define` 创建时，内部有一个 `state` 对象挂载在 `getter[REACTIVE]` 上。钩子池作为 `state` 的一个字段存在：

```ts
interface SignalState<T> {
  value: T;
  subs: Set<DerivationState>;
  set: Setter<T>;
  stop: () => void;
  hooks?: Set<WriteHook<T>>; // 写入钩子池
  pendingAbort?: AbortController; // 当前待处理的 AbortController
}
```

**选择 `state` 而非全局注册表的原因**：

- 生命周期一致——钩子绑定到信号，信号销毁时钩子自然失效
- 不需要全局注册表——与 kiaao 的无全局状态原则一致
- 实现路径清晰——`hook(signal, fn)` 通过 `signal[REACTIVE]` 定位到 `state`，将 `fn` 添加到 `state.hooks`

#### 只拦截写入，不拦截读取

读取拦截目前没有明确的用例。`getter` 已经返回当前值，加读取拦截只会增加 API 复杂度。如果未来有场景需要 `hookRead`，可以独立添加。

#### 不修改数据流，只提供写入前等待

钩子不通过返回值或 `set` 回调来修改最终写入的值。所有钩子完成（`Promise.allSettled`）后，框架自动用原始传入的值更新信号。

这保证了：

- 钩子职责纯粹——只做副作用（动画、验证等），不参与数据流
- 多钩子不需要协调——同一信号上多个钩子并行执行
- API 表面积最小——不需要 `set` 回调

#### 值不变时短路

当 `set` 传入的值与当前值 `===` 相同时，不触发钩子，不通知下游。这与派生信号的短路机制一致——值没有变化，下游无感知。避免无效的钩子触发（如重复调用 `setVisible(false)` 时不应该再次播放退出动画）。

#### 多钩子并行执行

同一信号上可以注册多个钩子（例如多个 `Motion` 指令绑定了同一个 `signal`）。它们并行执行，框架等待 `Promise.allSettled` 所有钩子完成后才更新信号。

#### 并发写入与 AbortController

用户快速连续调用 `setVisible` 时，框架在每次写入时创建一个新的 `AbortController`。如果新的写入发生，框架中止上一次的 `AbortController`。

```ts
// setter 被调用时
function handleSet(newValue) {
  if (newValue === state.value) return; // 短路

  // 中止前一次的 AbortController
  if (state.pendingAbort) {
    state.pendingAbort.abort();
  }

  const controller = new AbortController();
  state.pendingAbort = controller;

  if (state.hooks && state.hooks.size > 0) {
    Promise.allSettled([...state.hooks].map((fn) => fn(newValue, controller.signal))).then(() => {
      state.value = newValue;
      state.pendingAbort = undefined;
      notifySubs(state);
    });
  } else {
    state.value = newValue;
    notifySubs(state);
  }
}
```

框架始终创建 AbortController 并传入 hook。对于不关心中断的钩子，可以直接忽略 `signal` 参数。

#### 钩子释放时机

`hook` 返回一个清理函数 `stop()`。调用后从 `state.hooks` 中移除对应的钩子。指令在 `onUnmount` 中调用 `stop`，保证元素移除时钩子不再触发。

#### `hook` 的应用场景不限于退出动画

- **保存草稿**：`setContent(value)` → hook 钩子 → 自动保存到 localStorage → 更新信号
- **表单验证**：`setName(value)` → hook 钩子 → 异步校验 → 通过后才更新信号

### 8.5 派生信号的 `hook`

`hook` 同时支持定义信号和派生信号，保持两者的 API 完全同构。

**定义信号**：`hook` 在 `set` 时触发（新值与旧值不同时）。钩子完成后更新值并通知下游。

**派生信号**：`hook` 在重算之后、值确定变化时触发。不管重算是如何触发的（上游变化或直接调用 setter），都在重算之后、比较值是否变化之后执行 hook。

```
1. 派生信号的重算被触发（上游变化 / setter 调用）
2. 执行 computeFn，得到新值 newValue
3. 对比 newValue 和 cachedValue
4. 如果相同 → 短路，不触发 hook，不通知下游
5. 如果不同 → 触发 hook（异步等待）→ 等待完成后 → 更新 cachedValue → 通知下游
```

这与定义信号的行为完全一致：

|                    | 定义信号                | 派生信号                         |
| ------------------ | ----------------------- | -------------------------------- |
| hook 触发时机      | set 时，新值 !== 旧值   | 重算后，newValue !== cachedValue |
| hook 是否知道新值  | 是（set 传入的值）      | 是（computeFn 的返回值）         |
| hook 完成后        | 更新 value，通知下游    | 更新 cachedValue，通知下游       |
| 值不变时           | 不触发 hook，不通知下游 | 不触发 hook，短路                |
| 上游变化触发的重算 | 不适用（无上游）        | 同样触发 hook（值变化时）        |

开发者不需要区分信号的类型——`hook(signal, fn)` 在任何信号上行为一致：值变化前等待，值不变时跳过。

### 8.6 TypeScript 类型

```ts
export function hook<T>(
  signal: Getter<T>,
  fn: (value: T, signal: AbortSignal) => void | Promise<void>,
): () => void;
```

- `signal`：要拦截写入的信号（getter 函数）。框架通过 `signal[REACTIVE]` 定位到信号的内部状态。
- `fn`：钩子函数，接收新值 `value` 和 `AbortSignal`。
- 返回：清理函数 `stop()`，调用后从 `state.hooks` 中移除钩子。

### 8.7 曾讨论但未采纳的方案

| 方案                              | 问题                                                 |
| --------------------------------- | ---------------------------------------------------- |
| `disposeNode` 异步化 + 微任务调度 | 派生回调需要变成异步，改变核心响应式模型             |
| Abort 机制（无 hook）             | 退出动画被中止后不可见，无法实现优雅退出             |
| Fire-and-Forget 异步移除          | `clearChildren` 不再可靠，新旧元素可能并存           |
| `root` 参数智能等待               | 在派生回调同步的约束下，`await` 无法在派生回调中使用 |

## 九、设计哲学总结

指令系统延续了 kiaao 一贯的原则：**机制在核心，策略在扩展**。框架只提供元素级生命周期的原语（挂载、卸载、信号绑定），具体的动画、验证等逻辑由外部库或用户代码实现。

退出动画的异步等待不在指令系统的职责范围内——它是信号层面需要解决的问题。`hook` API 通过在信号写入前插入异步等待，在不改变派生回调同步性的前提下，实现了退出动画的声明式支持。

这种分层设计保持了框架核心的极简，同时为未来的扩展留下了足够的空间。

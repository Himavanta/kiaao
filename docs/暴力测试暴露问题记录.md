## P0 — 需要优先修复

### 1. disposeOwner 后 DOM 元素未清理

**触发条件**：组件 Owner dispose 后，其 `elements` 中的 DOM 节点应被移出 DOM 树。

```
测试: dispose-owner.test.ts > elements are removed from DOM after dispose
```

**框架响应**：部分场景下 `removeNode(el)` 未能将元素移出父容器。因为 `handleDomMode` 返回的 HResult `owner = null`，没有任何 Owner 跟踪该元素。`disposeOwner(result.owner!)` 中 `owner` 是 `null`，`null.elements` 是空集 → 元素永远不被移除。

**关联根因**：`handleDomMode` 返回 `createHResult(null, [el])` —— 元素没有挂到任何 Owner 上。这是 `nestBind` 架构设计的结果（DOM 元素不创建 Owner）。

**是否修复**：否（设计如此，需确认是否要改）

---

### 2. dispose 后信号订阅未停止

**触发条件**：Owner dispose 后，其 `cleanups` 中的信号绑定 stop 函数应被调用，停止派生追踪。

```
测试: lifecycle.test.ts > lifecycle — dispose guard > signal subscription stops after dispose
测试: dispose-owner.test.ts > disposeOwner — idempotence > signal subscriptions are cleaned up on dispose
```

**框架响应**：`subscribeSignal` 创建的派生注册了 `state.stop` 到 `owner.cleanups`，`disposeOwner` 执行 `cleanups` 时调用了 stop。但某些路径下派生仍会响应信号变化（如 `use()` 在全局 scope 创建的派生未注册 stop 到任何 Owner）。

**是否修复**：否（需要排查具体路径）

---

### 3. `nestBindPrimitive` 不处理 `true` 值

**触发条件**：`true` 作为 `h()` 的 children 传入。

```
测试: h-defense.test.ts > null/undefined are filtered, true renders as text
```

**框架响应**：`nestBindPrimitive` 只过滤 `isNil`（null/undefined），`true` 进入 `String(true)` → `"true"` 文本节点。用户明确表示 `true` 不需要过滤，但渲染为 "true" 文本可能不是预期行为。JSX 中 `{true}` 通常被理解为无输出。

**是否修复**：视行为定义而定

## P1 — 行为不一致

### 4. 组件实例间 onMount 触发条件不明确

**触发条件**：两个兄弟组件在同一容器 div 内。

```
测试: lifecycle.test.ts > fires once per component instance, not shared
```

**框架响应**：`mount(result)` 调用 `triggerMount(result.owner!)`。当两个组件是 `h("div", null, h(CompA), h(CompB))` 时，`result.owner` 是组件 A 的 Owner（因为组件 B 也是通过同一个 `h()` 调用创建的... 实际是 `handleComponent` 处理哪个的 owner？需要排查）。

**是否修复**：否（需排查）

---

### 5. 空字符串 tag 的行为

**触发条件**：`h("", null, ...)`

```
测试: h-defense.test.ts > empty string tag does not crash
```

**框架响应**：`adapter.el("")` 在 DOM 中创建空标签元素 `< >`，行为未定义。应返回 comment 节点或报错。

**是否修复**：否（低优先级）

---

### 6. 100 个 children 全部渲染但 nestBind 性能

**触发条件**：向 `h("div", null, ...100 个字符串...)`

```
测试: h-defense.test.ts > 100 children all render
```

**框架响应**：渲染成功。但测试当前失败，怀疑是 `mount` 函数中的 `triggerMount` 路径问题。

**是否修复**：否（需排查）

```
signal.test.ts > deep nested derivation chain
```

**框架响应**：值未正确传播到最深层的派生。

**是否修复**：否（signal 系统待审查）

---

### 8. SSR 模式下派生只计算一次

**触发条件**：SSR 模式下 `use(signal, fn)` 的派生

```
signal.test.ts > derivation in SSR mode computes once
```

**框架响应**：SSR 模式通过 `adapter.createStaticDerived` 跳过依赖追踪，派生只计算初始值，不会响应信号变化。这可能正确也可能错误，取决于设计意图。

**是否修复**：需确认设计意图

---

### 9. 路由测试缺少 triggerMount

**触发条件**：`h(RouterView, { routes })` 后直接读取 `textContent`

```
router.test.ts > 全部 25 个测试
```

**框架响应**：路由内容依赖 `triggerMount` 触发渲染，测试未调用 triggerMount 导致 `textContent` 为空。

**是否修复**：需要在测试中添加 `triggerMount` 调用

---

### 10. SSR style 对象序列化格式

**触发条件**：`{ color: "red" }` 作为 style prop 在 SSR 中序列化

```
ssr.test.ts > handles style object serialization
```

**框架响应**：输出 `{"color":"red"}`（JSON 序列化）而非 `color: red`（CSS 样式字符串）。

**是否修复**：否（需要决定 SSR style 的输出格式）

## 一、先说清定位：它不是教科书 ECS，也不是教科书 OOP

这个项目里反复出现「ECS」这个词。**本文要纠正它**——按定义核对，它不是经典 ECS：

| 经典 ECS 的定义性特征                               | 本引擎                                                  | 结论 |
| :-------------------------------------------------- | :------------------------------------------------------ | :--- |
| 组件**分列存储**（SoA，如 `Float32Array` 各一张表） | ❌ `Map<EntityId, { state }>`——**一个实体一个完整对象** | 不是 |
| archetype / query（按组件组合筛选）                 | ❌ 没有。系统靠**注册时声明**（`enter`）                | 不是 |
| 组件是纯数据，行为完全在系统                        | ⚠️ 大体是，但**实体可以带方法**（`state.onFrame`）      | 部分 |

同时它也不是经典 OOP：没有 `class`、没有 `this`、没有继承。`guard.ts` 的「方法」是**闭包捕获 `state`** 的普通函数。

**准确的说法是两句话**：

> **存储是 OOP 式**（AoS：一个实体 = 一个对象，字段齐全）。
> **调度是 ECS 式**（系统 opt-in：实体不知道自己被谁处理，系统声明「我要谁」）。

这个杂交不是妥协——它是本引擎的核心设计，第三节展开。

## 二、两种范式的分工：一份代码 vs 这只个体

引擎里所有机制最终都落在一条分界上。这条分界是**实测得来**的（§8.10），判据只有一个：

> **这段逻辑是「一份代码服务所有实体」，还是「只有个别实体有」？**

|              | 数据在哪             | 谁决定行为 | 适合                         | 引擎入口            |
| :----------- | :------------------- | :--------- | :--------------------------- | :------------------ |
| **共享机制** | 实体字段（系统读写） | 系统       | 位移、寻路、感知、碰撞       | `createPool`        |
| **私有行为** | 实体自己（闭包）     | 实体方法   | 私有记忆、个体计时、专属反应 | `createActorSystem` |

**两者不冲突，是分工。** 判据的第二半（同样实测）：

> **阶段顺序敏感** → 必须走系统（多个池，按阶段遍历所有实体）。
> **实体内部、顺序无关** → 可以走方法（一个池，逐个喊「到你了」）。

原因：若把 `perceive` 放进实体的每帧方法，就退化成「实体优先」的顺序——先跑的实体会看到别人**上一帧**的位置（实测差 1.67px，即一帧位移）。系统化的多池遍历保住了「阶段优先」的语义。

**所以 `createActorSystem` 只服务后者。** 这是它的边界，不是它的缺陷。

## 三、核心：两个对称的工厂

```
engine/
├── game.ts        createGame / createDefine      帧循环 + 实体登记
├── pool.ts        createPool                     数据归系统（系统决定怎么处理）
├── actor.ts       createActorSystem              数据归实体（实体自己决定做什么）
├── events.ts      createEvent                    事件队列
└── directives.ts  StyleMemo                      表现层
```

`createPool` 与 `createActorSystem` **对称得刚好**：都是「一个池 + 一个 `enter` + 一个 `update`」，差别只有一处——

> `createPool` 的 `update` **知道**要对实体做什么（比如 `x += vx * dt`）。
> `createActorSystem` 的 `update` **不知道**，它只喊一声「到你了」，做什么由实体的方法定义。

这就是「异质实体」的组织方式：**同质部分走系统，个体部分走方法。**

### 为什么是创建函数，不是常量

```ts
// ❌ 模块级常量：所有游戏实例共享一个池，测试互相污染
export const actor = createActorSystem();

// ✅ 创建函数：每次调用建自己的池
export function createActorSystem(): ActorSystem;
```

`createPool` 内部建的是 `Set<EntityId>`。模块级常量会让两次 `createGame` 共享同一个池——一处卸载漏了，stale id 就累积到别处。这与其他入口（`createGame` / `createPool` / `createEvent`）的约定一致。

### 命名

`actor` 不是随口起的：**Actor model**（Erlang / Akka）的术语就是「独立实体、各有状态与行为、不需外部指挥」。

| 位置         | 名字                                                     |
| :----------- | :------------------------------------------------------- |
| 引擎导出     | `createActorSystem`（与 `createX` 一致）                 |
| 游戏实例     | `const actor = createActorSystem()`                      |
| 实体上的钩子 | `onFrame`（**不要叫 `update`**——与系统的 `update` 混淆） |

saboteur 已有 `Actor`（视图组件）/ `ActorEntity`（类型）/ `actor`（实例），彼此不冲突。

## 四、设计原则：不要用你担心的误用来削减核心的能力

**这是本文最想留下的一条。** 它来自一次真实的分歧：

> 设计 hook 签名时，我提议只传 `delta`（保守）或传 `ctx`（全能）。
> 用户否决了保守方案：「你不用担心 ctx 的全能。**你要相信使用核心的人。**」

**采纳。** 理由：

1. **保守设计有隐藏代价**——`delta` 是「我预判了你只需要这些」。一旦某天有个场景需要 `random` 或 `grid`，核心就无能为力，使用者只能绕过它（自己造机制），那比「能力多而没用」更糟。
2. **它的对立面不是「全能」，是「职责重叠」**。真正要避免的是 `ctx` 与状态对象的上下文**做同一件事**（两个机制同一用途）。这与「参数有几个」无关。
3. **核心应当给能力，不给纪律**。纪律（用哪个范式、什么时候用）是使用者的判断——引擎提供两个对称入口，不替游戏决定。

同源的先例：`define` 允许实体带**系统不认识的私有字段**（`& Record<string, unknown>`）。当时的选择也是「不限制」——因为私有字段正是 OOP 路线需要的。

## 五、这份核心「稳定」的含义

说要「稳定」，指的不是「不再改」，而是三件事：

| 稳定的含义         | 具体                                                                                |
| :----------------- | :---------------------------------------------------------------------------------- |
| **机制不再增**     | 五个入口对应五种职责，各有明确边界；新需求先问「能不能用已有机制表达」              |
| **范式是一等公民** | 两种范式各有入口，游戏**选用**而非「只能走一条路」                                  |
| **边界写清楚**     | 每个机制在文档里说明「它做什么、不做什么」（如 `createActorSystem` 不负责阶段顺序） |

**一个不稳定的信号**：出现「机制 A 也能做、机制 B 也能做」的重叠区。例如给 hook 传完整上下文、且该上下文与状态对象等价——那时两个机制就重复了，应当合并或删一个。

## 七、实施记录

### 7.1 `createActorSystem` 已落地（2026-10-08）

| 项       | 结果                                                                                                  |
| :------- | :---------------------------------------------------------------------------------------------------- |
| 位置     | `packages/engine/src/actor.ts`（~60 行有效代码）                                                      |
| 导出     | `index.ts` 同时导出值（`createActorSystem`）与类型（`ActorContext` / `ActorSystem` / `HasFrameHook`） |
| 钩子签名 | `onFrame?: (ctx: ActorContext<T>) => void`——**收 `ctx` 而非 `delta`**（§四 的原则）                   |
| 上下文   | `{ frame, delta }`，两样都是方法靠闭包拿不到的                                                        |
| saboteur | 删本地 `systems/actor.ts`，改为 `import { createActorSystem } from "engine"`                          |

**测试**（`engine/src/__tests__/actor.test.ts`，8 例）：池独立、每帧调用一次、`delta` 传对、无钩子跳过、未注册不生效、卸载出池、空池不崩、`ctx.frame` 可用、**多实体共享同一个 ctx**。

**一个实测发现（已修）**：第一版的「卸载后出池」用例**抓不到池泄漏**——它是断言「`onFrame` 不再被调」，但卸载时 `gamePool` 也删了实体，`frame(id)` 返回 `undefined`，`?.` 静默跳过。**池泄没泄漏，行为完全一样**（真实代价是 `Set` 无界增长，不是行为错误）。改成**直接观察遍历**（探子帧管理器记录访问过的 id）后，破坏性验证才通过。

**顺带发现的真缺口**：`createPool` 在引擎里**零测试**（它是两个机制共同的基础，「装载/卸载配对」从未被直接验证）。已补 `engine/src/__tests__/pool.test.ts`（4 例）。

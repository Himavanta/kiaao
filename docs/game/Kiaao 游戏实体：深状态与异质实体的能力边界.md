## 一、压力源：要支撑什么

`saboteur` 的最终预期是**大量异质 NPC**：每个 NPC 可能有相当深度的自有内容——观察、缔结关系、性格差异、定时碰头、无线通讯。这些不是边角，是玩法主体。

它对引擎提出两个要求：

| 要求         | 意味着                                       |
| :----------- | :------------------------------------------- |
| **深状态**   | 单个实体字段多且结构复杂（记忆表、关系图）   |
| **异质实体** | 不同实体行为差别大，需要「定义在一处」的载体 |

本文不讨论「saboteur 怎么写」，只回答：**当前引擎支撑这类用法时，能力在哪、代价是什么、边界在哪。**

## 二、能力：已经可用的（实测）

### 2.1 `state` 上可以放方法（OOP 的载体）

```ts
const state = {
  x: 0,
  hp: 3,
  isLive: true,
  kill() {
    state.isLive = false; // 闭包捕获 state 自己
  },
};
const entity = define(ctx, movement.enter)(state);
```

实测：

```text
kill() 前 isLive: true
kill() 后 isLive: false | frame 看到: false
```

**不需要任何新 API**。方法也**不需要 `frame` / `id`** 参数——闭包捕获 `state` 就够。

### 2.2 `enter` 里建「名字 → id」映射（跨实体查找的载体）

```ts
const enter: Enter<Named> = (id, ctx, state) => {
  ctx.onMount(() => byName.set(state.name, id));
  ctx.onUnmount(() => byName.delete(state.name));
};
```

实测：两个 NPC 通过名字互相找到并改对方状态——

```text
byName 映射: bob,alice
alice.greeted: true | bob.greeted: true
```

**时序前提已实测**：实体在挂载期全部入池，第一帧即可见彼此（不是「边挂边跑」）。隔离探针挂 3 个看到 3 个；真实 App 里 `mount` 完成后（未跑任何帧）`listActors()` 已是 7。

### 2.3 活对象：系统直接读写

`frame(id)` 返回可变状态对象本身，`e.x += 1` 立即生效，无需回调包装。这是 D2 迁移（`packages/engine`）的核心改动，也是 §2.1 能成立的前提。

## 三、代价与边界（实测）

### 3.1 每帧无条件全量提交 ⇒ 派生重算随实体数线性增长

`flush` 无条件遍历整个实体池：

```ts
// packages/engine/src/game.ts
function flush() {
  for (const entry of gamePool.values()) entry.flush(); // ← 全部，不区分是否写过
}
```

每个 `entry.flush()` 是 `signal({ ...state })`——**新对象引用**，必然触发订阅它的所有派生。

实测（零变更，跑 30 帧）：

| 实体数 | 派生重算次数 | 每帧 |
| -----: | :----------- | :--- |
|      1 | 30           | 1    |
|      5 | 150          | 5    |
|     20 | 600          | 20   |

**派生重算 = 实体数 × 帧数。** 与是否真的改过无关。

**DOM 写入仍被 memo 截断**（同一派生值不变则不往下传），所以抖动不在 DOM 层，而在**纯计算**：

```text
零变化跑 3 帧：compute=4（每帧重算） DOM write=1（memo 截断）
```

对 20 个实体、每个派生只读一两个字段的场景，这个成本可忽略。但**「大量 NPC × 深状态」正好放大它**。

### 3.2 与旧引擎对照：「无越界不写」这条纪律已经失效

ECS 设计文档 §6 有一条纪律：

> **无越界不写**：boundary 等系统先读判断、有变更才写——避免无谓的信号传播。

规划文档也据此写了「静态池纪律」：_不动的实体绝不写帧数据_。

**这条纪律在新引擎里不再成立。** 对照实测（同一逻辑，两种引擎，跑 5 帧）：

|                        | 系统不写        | 系统每帧写同值 |
| :--------------------- | :-------------- | :------------- |
| **旧引擎**（写时拷贝） | 一级派生 **+0** | +5             |
| **新引擎**（活对象）   | 一级派生 **+5** | +5             |

旧引擎**只有被写过的实体才进 cache、才在帧末提交**；没写过的实体零提交、零传播。新引擎用活对象换掉了变更追踪，于是**「不写」不再有任何收益**。

> **这是迁移的代价，此前未被记录。** 旧引擎的 `{{ flush 只遍历 cache }}` 是隐式的脏标记；活对象模型下无法知道谁变过，只剩全量提交。

### 3.3 陷阱：嵌套容器「能传播」是假象

ECS 设计文档 §5.4 有一条规定：

> **实体数据里的嵌套结构必须整体替换，不可原地修改**（浅拷贝保护顶层，不保护嵌套）。

实测发现**这条规定在当前引擎里被掩盖了**：

```text
[实体 state 内原地改 Map] 派生值确实更新了   ← 看起来违规也没事
[全局信号内原地改 Map]    派生值不更新       ← 符合文档预期
```

原因是 §3.1：**每帧无条件提交顶掉了原地修改的问题**。派生虽然读到的是同一个 `Map` 引用，但每帧都被重新执行，于是「看到」了新内容。

**这是个耦合陷阱**：

- 两个事实（无条件提交 / 嵌套就地改）互相兜底
- 谁要是为省算力把 `flush` 改成**选择性提交**（只提交写过的），**原地改嵌套就会静默失效**
- 而 `packages/saboteur` 现在正有原地改的写法（`accounted` 在系统闭包里不受影响，但一旦搬进实体就会踩中）

### 3.4 `state.id` 不可用

```text
sig.id  = Symbol()       ← 挂在信号上
state.id = undefined     ← state 上没有
```

`id` 由 `define` 内部生成，只挂在返回值上。**因此实体方法内无法「按 id 找自己」**——需要排除自己的遍历只能由系统做（系统有池，池里有 id）。

按名字查可以绕过（`byName.get("alice")` 能拿到**别人的** id），但**自己的**拿不到。

### 3.5 嵌套容器的派生：每帧重算，下游被截断

```text
零变更 3 帧后：container 派生 = 4（每帧重算）  downstream = 1（引用未变 → 截断）
```

派生**返回嵌套容器**时，即使内容变了，返回值仍是同一引用 → 下游不会重算。**这意味着「把整个记忆表派生给视图」这种写法不会工作**（除非整体替换）。

## 四、对「深状态」设想的含义

把上面的边界叠到 §一 的压力源上：

| 设想                              | 引擎现状            | 隐含代价                                    |
| :-------------------------------- | :------------------ | :------------------------------------------ |
| 每个 NPC 有深状态（记忆表、关系） | ✅ 活对象支持       | 每帧全量提交 → 派生重算 × NPC 数            |
| 各自独特行为（方法）              | ✅ 已支持           | 方法会被 `flush` 拷进渲染信号（无害，但脏） |
| 按名字互相查找                    | ✅ `enter` 建表可行 | 同名会静默覆盖（`Map.set` 语义）            |
| 关系/碰头/通讯这类跨实体玩法      | ❌ 无先例           | 机制需要自建；**认知数据存哪**未定          |
| 「最后已知位置」这类记忆          | ⚠️ 取决于存哪       | 存实体 → 踩 §3.3 的耦合陷阱                 |

**最关键的一条**：`saboteur` 现在只有 7 个实体，派生重算 7 次/帧。若 NPC 数量与每实体派生的数量同时上翻（「很多 NPC × 每个很深」），§3.1 的成本会以**乘积**增长。

**这不是 bug，是模型的代价**——但需要在设计 NPC 深度时知道它。

## 五、候选方向（未验证，不可当结论）

### 5.1 选择性提交：用浅比较换回「不写不传播」

现状 `flush: () => signal({ ...state })`。候选：

```ts
flush: () => {
  const next = { ...state };
  if (!shallowEqual(next, lastSubmitted)) signal(next); // 值真变了才提交
  lastSubmitted = next;
};
```

- **换回**：未变更的实体不触发传播（恢复 §3.2 旧引擎的收益）
- **代价**：每实体每帧一次 O(字段数) 浅比较
- **风险**：与 §3.3 耦合——若同时做了这个优化，**原地改嵌套会立刻失效**，两处必须一起改
- **未验证**：浅比较的成本是否真低于被省下的派生重算，取决于派生复杂度

### 5.2 派生粒度下探

现在是「实体信号级」派生（一个字段变 → 订阅该实体的全部派生重算）。候选：为高频字段单独建信号。

- 这与 `docs/game/游戏示例 style 细粒度更新方案探索.md` 的方向一致（那里是「派生返回原始值」而非整对象）
- **未验证**：多一层信号的数量成本

### 5.3 保持现状

如果实测表明成本可忽略（20–50 个实体、每实体 3–5 个派生），**什么都不做是合理选择**。

**本文不主张任何一种**——§3.1 的成本目前只有数量级，没有真实场景的 profile。

# 响应式系统设计讨论纪要

> 本文档记录了 `kiaao` v4.0 响应式系统设计期间的重要讨论内容、架构决策背后的哲学思考，以及一些因定位不适而未被写入正式规范的有价值结论。  
> 供核心开发者参考，不面向最终用户。

---

## 一、架构原则

这些原则是在与 AI 助手的反复讨论中逐渐明晰的，它们不是凭空设定，而是从作者对现有框架痛点的反思中自然生长出来的。

### 1.1 所有权明确性

> 谁创建，谁负责。

- `use` 创建的派生节点，其订阅由框架内部管理。
- 组件或 DOM 节点承载的派生，其销毁由 `disposeNode` / `unmount` 递归触发。
- 模块级全局派生不会被自动销毁，因为它们不属于任何组件——这是开发者的责任。

框架不试图“智能”地管理所有资源的生命周期，而是在创建和销毁之间建立清晰、可追溯的所有权链条。

### 1.2 数据转换一致性

> 同样的语法，同样的语义。

- `use(user, () => user().name)` 和 `use(count, () => count() * 2)` 使用完全相同的语法。
- 没有“简单派生”和“复杂派生”之分，没有快捷方式与完整路径之分。

`getter(selector)` 被废除的深层原因即在于此：它引入了一种看似便利、实则语义不一致的派生方式，迫使用户额外判断“这个信号是原始信号还是选择器派生信号”。

### 1.3 框架不推断意图

> 如果你没说，我就不知道。

- 依赖列表必须显式传入——框架绝不根据执行栈自动收集依赖。
- 回调函数有返回值就是数据，没返回值就是 `undefined` 数据——框架不区分“计算属性”和“副作用”，统一按派生处理。
- 框架不检测循环依赖、不自动清理未使用的订阅、不猜测用户的“真实意图”。

这三条原则是作者拒绝主流框架大量“魔法”的根本依据。

## 二、`reverse()` 的视觉优雅性

在派生模式的内部实现中，参数顺序的解析使用了 `ars.reverse()`：

```js
const [func, ...deps] = ars.reverse();
```

尽管存在“就地修改参数数组”的理论风险，但实际调用场景中 `ars` 是函数内部的 `arguments` 序列化数组，不存在外部引用。作者认为这种写法比 `slice` 配合下标更直观可读，更符合“最后一个参数是计算函数，其余是依赖”的视觉倒序逻辑。

**此为最终决定，后续实现遵循此写法。**

---

## 三、对 `use` 返回值的命名约定

在纯 JavaScript 环境下，用户可能写出：

```js
const stop = use(count, () => {
  console.log(count());
});
```

这里的 `stop` 是 `Getter<void>`，调用它只会返回 `undefined`，但变量名容易让人误解为“停止函数”。框架无法在运行时约束命名，因此文档中建议遵循以下非强制性约定：

- 派生信号（无论有无返回值）使用**名词**命名：`const name = use(user, () => user().name)`
- 不接收返回值的派生**不要赋值**：`use(signal, () => { ... })`

---

## 四、为什么放弃开发环境运行时校验

早期讨论中曾提议：在开发模式下，检查 `computeFn` 内部实际访问的信号是否与声明的依赖列表一致，并发出警告。

此提议被彻底否决，原因：

1. 任何对“实际访问了哪些信号”的检测都必须在运行时执行 `computeFn` 时进行收集。
2. 这种收集依赖执行栈，正是 `kiaao` 设计哲学所拒绝的“自动依赖收集陷阱”。
3. 即使只作为非侵入式警告，其底层机制也与框架的核心原则相悖。

**结论：`kiaao` 不提供任何形式的运行时依赖使用校验，无论是警告还是错误。**

---

## 五、惰性求值的未来方向

当前所有派生均为立即求值（创建时执行一次，依赖变化时立即重算）。若未来需要“被读取时才计算”的惰性派生，无需引入新 API。

可通过**多层派生缓存中断**实现：将昂贵计算封装在一个上游派生中，通过另一个轻量派生控制其读取时机，利用值比较短路机制达到惰性效果。

此为 v4.x 或 v5 的潜在扩展方向，不在当前版本范围内。

---

## 六、开发工具与状态存储的分离

响应式信号的核心状态通过闭包存储，以保证安全性和无序列化问题。

调试工具（DevTools）可通过独立的全局 `WeakMap<SignalFn, InternalState>` 来挂载调试信息，完全与核心逻辑解耦：

- 生产环境下 `WeakMap` 可被 tree-shake 移除。
- SSR 序列化时不受调试状态污染。
- 信号被垃圾回收后，`WeakMap` 条目自动清除。

此方案已确认，将在后续 DevTools 设计时采纳。

---

## 七、设计方法的本质总结

本次重构的核心并非简单地“删除几个 API”，而是将框架的复杂性从 **“概念数量”** 转移到 **“概念深度”** 上。

| 维度             | v3.4                                 | v4.0                |
| ---------------- | ------------------------------------ | ------------------- |
| API 数量         | 4 核心 + 辅助                        | 1 核心 + 辅助       |
| 用户需区分的概念 | 定义 / 派生 / 副作用 / 选择器派生    | 定义 / 派生         |
| 用户的核心决策   | 用什么 API？能继续派生吗？有缓存吗？ | 我依赖谁？怎么算？  |
| 文档解释重点     | 四个 API 的行为差异                  | 一个 API 的两种用法 |

用户的注意力从“选用哪个工具”转移到“数据如何流动”，这正是框架哲学的具象化。

# kiaao 框架哲学

框架是用来表达思想的，不是用来隐藏它的。

kiaao 是一个纯运行时的响应式 UI 框架。它不代理你的数据，不替你收集依赖，不反复运行你的组件函数。它只做一件事：在你明确声明依赖关系之后，精确地更新 DOM。

- 所有数据都是信号，所有信号都由 `use` 产生。不存在原始值与响应式值的区别。
- 依赖必须显式声明。异步回调里访问信号不会产生任何隐式绑定——因为没有魔法。
- 派生就是计算。有返回值就是数据，没返回值就是数据为 `undefined` 的派生。没有副作用的概念。
- 组件函数只执行一次。状态变化时，框架直接更新 DOM 节点，不重新渲染，不进行树形 Diff。
- 无 Proxy、无编译器（JSX 编译除外）、无虚拟 DOM。调试时看到的就是真实的值，控制台里看到的就是真实的函数。

如果你曾因框架的“智能”而感到失控，如果你想要的是透明、可预测和完全的掌控，kiaao 是为你准备的。

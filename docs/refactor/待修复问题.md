# 待修复：两个严重问题

## 问题 A：组件返回组件时 INSTANCE_KEY/DISPOSE_KEY 被覆盖

### 场景

```tsx
function Comp() {
  return h(Portal, { to: "#target", children: () => h("span") });
}
```

### 根因

`h(Portal, ...)` 返回的 Comment 节点上已经挂了 Portal 组件实例的 `INSTANCE_KEY` 和 `DISPOSE_KEY`（含 `onUnmount` 清理逻辑）。外层 `h(Comp)` 把**同一个节点**上的这两个标记**覆盖**成了 Comp 的实例。

```
h(Comp)
  → h(Portal, ...)
    → Portal 返回 Comment
    → Comment[INSTANCE_KEY] = Portal 的实例 ✅
    → Comment[DISPOSE_KEY] = Portal 的 dispose（含 cleanup）
  → h() 收到 Comment
    → Comment[INSTANCE_KEY] = Comp 的实例 ← 覆盖 ❌
    → Comment[DISPOSE_KEY] = Comp 的 dispose ← 覆盖 ❌
    → Portal 的 onUnmount 丢失 → cleanup 永不执行
```

### 影响

- Portal 的内容在组件卸载时不会被清理
- 任何直接返回另一个组件结果的组件都会遇到同样的问题
- 如果外层组件和内层组件都注册了生命周期，内层的完全丢失

### 安全的情况

```tsx
// ✅ 安全：Child 返回 span，Wrapper 返回 div，不同节点
function Wrapper() { return h("div", null, h(Child)); }

// ❌ 泄漏：Comp 和 Portal 共用同一个 Comment 节点
function Comp() { return h(Portal, ...); }
```

### 待决定

修复方案：当节点上已存在 `DISPOSE_KEY` 时，不覆盖。

```ts
// h.ts 同步组件路径
if (result instanceof Node) {
  if (!(result as any)[DISPOSE_KEY]) {
    (result as any)[INSTANCE_KEY] = instance;
    (result as any)[DISPOSE_KEY] = createDisposeFn(instance);
  }
}
```

但这样外层组件的生命周期永远不会触发。是否符合预期？——外层组件直接返回内层组件的结果，它本来就没有自己的 DOM 节点，它的生命周期应该由谁管理？

## 问题 B：组件内创建的派生在卸载后仍响应

### 场景

```ts
function Comp(_: any, { onMount }: any) {
  onMount(() => {
    use(signal, () => {
      /* 每次 signal 变化执行 */
    });
  });
  return h("p");
}
```

组件卸载后，`use(signal, fn)` 创建的派生仍然活跃——`signal` 变化时 `fn` 仍会执行。

### 根因

v4 移除了 `effectStops` 机制。`use()` 创建的派生没有任何生命周期关联，不会在组件卸载时自动停止。开发者需要在 `onUnmount` 中通过 signal 的内部 `stop()` 手动清理。

### 影响

- 组件卸载后的信号回调执行可能导致已销毁 DOM 的操作
- 派生订阅关系永远残留（内存泄漏）
- 用户必须显式管理派生生命周期，与 v4 的"简单"承诺冲突

### 可能的方向

**方向 A**：在 `h()` 组件模式中暴露一个注册函数，`use()` 在派生创建时检测到活跃组件上下文，自动将 `state.stop` 注册到组件的 `unmountCallbacks`。用一个模块级变量 `_currentCleanup` 作为桥接。

**方向 B**：把 `use()` 放在 `onMount` 中调用本身就有设计隐患——`onMount` 的回调执行时机晚于组件函数返回，此时组件的上下文已消失。应在组件函数顶层调用 `use()`，而非在 `onMount` 内。

**方向 C**：恢复全局组件栈的简化版本，仅在 `h()` 的同步组件模式中维护，`use()` 通过它注册清理。

**方向 D**：在 `use()` 中检查所依赖的信号是否有订阅者已被 dispose，该方案不可行（信号是独立于组件的）。

---

## 优先级

两个都是真实 bug，但影响范围不同：

- **A 立即修复**：Portal 的内存泄漏明确且直接。修复方案简单（加 `!DISPOSE_KEY` 检查）。
- **B 需要讨论**：涉及 v4 的设计哲学。最直接的"修复"是引导用户不在 `onMount` 中创建派生。

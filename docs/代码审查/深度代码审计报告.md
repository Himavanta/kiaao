## 1. 架构设计问题

### 1.1 🔴 `createApp` Owner 树被破坏

**文件：** `src/core/create-app.ts`
**位置：** 第 25-28 行

```ts
if (appOwner) {
  rootOwner.children.push(appOwner);
  appOwner.parent = rootOwner;
  rootOwner.elements = appOwner.elements; // ← 覆盖了 rootOwner.elements
}
```

`rootOwner.elements = appOwner.elements` 将根 Owner 的 elements 引用指向子 Owner 的 elements。这意味着：

- `rootOwner` 的任何自有元素都会被覆盖（如果有的话）
- `rootOwner` 和 `appOwner` 共享同一个 `Set`，`disposeOwner(rootOwner)` 时执行 `rootOwner.elements.clear()` 也会清空 `appOwner.elements`
- Owner 树的 parent/children 关系承诺被破坏：elements 应该按 Owner 层级归属

**修复方向：** 不应覆盖 elements，保留各自层级。`disposeOwner(rootOwner)` 遍历整棵子树即可清理所有元素，不需要共享引用。

---

### 1.2 🔴 `handleDomMode` 返回 `createHResult(null, [el])`——Owner 链断裂

**文件：** `src/core/h.ts`
**位置：** 第 42、52、66 行

`createWhenElement` 和 `createEachElement` 内部都创建了 `containerOwner`，其中注册了信号属性绑定的 cleanups。但这些 Owner 在函数执行完毕后**无人接管**——`handleDomMode` 返回 `createHResult(null, [el])`，Owner 为 null。

这意味着：

- `createWhenElement` 内部的 `containerOwner` 永远不被 dispose
- `renderEachOnElement` 内部的 `containerOwner.cleanups` 不被执行
- 信号属性绑定泄漏

**当前状态：**

- `createWhenElement` → `containerOwner.cleanups` 含属性信号 stop，**永不执行**
- `createEachElement` → `setProps(el, props, cleanups)` 的 cleanups 被传入 `orphanCleanups` 并通过 HResult 返回 ✅
- `renderEachOnElement` → `containerOwner.cleanups` 含 each stop，`{ nodes, stop }` 返回后 **未被消费**

**修复方向：** `createWhenElement` 和 `renderEachOnElement` 的 Owner 需要连接到外部 Owner 树，或者其 cleanups 通过 HResult 返回。`createEachElement` 已修复路径，但 `createWhenElement` 和 `renderEachOnElement` 返回值未被消费。

### 1.3 🟠 `Fragment` 返回类型不一致

**文件：** `src/core/h.ts` 第 27 行

```ts
export function Fragment(props: { children?: any }): any {
  return props.children;
}
```

`Fragment` 直接返回 `props.children`，可以是任何类型。在组件模式中，`handleComponent` 调用 `mergeResults(result, owner)`，其中 `result` 可能是 `HResult | HResult[]`。`mergeResults` 处理 `HResult` 和 `Node`，但 `Fragment` 返回原始 children（可能是 `HResult[]`、`Node[]`、字符串等）。`mergeResults` 将结果包装为数组 `isArray(items) ? items : [items]`，然后遍历。对于 `Fragment` 返回的 `HResult[]`，每个元素会被正确识别。但对于返回的 `Node[]`，每个 Node 会被直接 `push`。但对于嵌套数组（如 `[[hr1, hr2], hr3]`），`mergeResults` 不处理递归。

**修复方向：** `mergeResults` 应递归展平结果（或 `Fragment` 自行展平）。或者 `ComponentFunction` 返回类型定为 `HResult`（非数组），Fragment 返回 `HResult` 包装的 nodes。

---

### 1.4 🟠 `h.ts` 底部 import

**文件：** `src/core/h.ts` 第 126-127 行

```ts
import { createWhenElement, createEachElement } from "./directives.ts";
```

ESM imports 会被提升到文件顶部，但放在文件末尾是反直觉的非标准做法。可能引发以下问题：

- 阅读者难以发现依赖
- 循环依赖在此位置的行为与顶部不同（虽然当前无循环依赖）

**修复方向：** 移至文件顶部。

## 2. 生命周期 & 内存泄漏

### 2.1 🔴 `registerEachCleanup` 在非响应式 eachFn 时注册了 cleanup，但 `stop` 返回值未被消费

**文件：** `src/core/directives.ts`
**位置：** `renderEachOnElement` 返回值

```ts
// renderEachOnElement 返回
return { nodes, stop: () => cleanupEachMaps(itemOwners, itemSignalMap, itemNodeMap) };
```

但**没有任何调用方使用 `stop`**：

- `createEachElement`：`renderEachOnElement({...})` 返回值被丢弃
- `createWhenElement` 的 `renderEachMode`：`const { nodes } = renderEachOnElement({...})` 只解构了 `nodes`

这意味着 `renderEachOnElement` 创建的 `containerOwner.cleanups` 中注册的每个项目 Owner 清理函数永远不会被调用。每当 `sync()` 发生时，新的 `itemOwners` 被创建，旧的通过 `disposeRemovedItems` 清理（在 `sync` 内部），但首次渲染的项目的 Owner 从不会被 dispose。

**修复方向：** `createEachElement` 需要将 `stop` 注册到某个可访问的 Owner（或通过 HResult 返回）。`renderEachMode` 需要将 `stop` 注册到 `branchOwner.cleanups`。

---

### 2.2 🔴 `createWhenElement` `containerOwner` 泄露

**文件：** `src/core/directives.ts`
**位置：** `createWhenElement` 第 149-196 行

`createWhenElement` 内部创建了 `containerOwner`，注册了 `setProps` 的信号 cleanups 和 when 派生信号的 stop。但 `containerOwner` 从不被 dispose：

```ts
const containerOwner = createOwner();
containerOwner.elements.add(el);
setProps(el, props, containerOwner.cleanups);
// ... 注册 signal stops ...
subscribeWhenFn(whenFn, renderBranch, containerOwner);
// containerOwner 不返回，不 dispose
return el;
```

函数返回后，`containerOwner` 成为孤立对象，其 `cleanups` 中的信号 stop 永远不执行。

**修复方向：**

1. `createWhenElement` 应接收外部 Owner（或 cleanups 数组），将 cleanups 注册到外部
2. 或函数返回 `{ el, owner }` 让调用方管理

---

### 2.3 🟡 `clearElement` 不调用 dispose

**文件：** `src/core/directives.ts` 第 68 行

```ts
function clearElement(el: Element): void {
  while (el.firstChild) el.removeChild(el.firstChild);
}
```

在 `renderBranch` 中，`clearElement(el)` 在 `disposeOwner(branchOwner)` 之后调用。`disposeOwner` 已经通过 `owner.elements` 移除了所有跟踪的节点。`clearElement` 清理的是未被 Owner 跟踪的剩余节点。

**问题：** 如果存在未被 Owner 跟踪的节点（例如由用户代码直接插入的），它们在被 `clearElement` 移除时**不会触发任何生命周期清理**。旧版本的 `disposeNode` DOM 遍历能捕获这些。

**严重性：** 实践中不大可能发生（框架代码应跟踪所有节点），但作为防御性编程应该处理。

## 3. Signal 系统问题

### 3.1 🟠 `createSafeSignal` 返回旧格式 tuple

**文件：** `src/core/component.ts` 第 27-35 行

```ts
function createSafeSignal() {
  const noop = () => {};
  (noop as any)[REACTIVE] = { value: undefined, subs: new Set(), set: noop, stop: () => {} };
  return [() => undefined, noop]; // ← 返回 [getter, setter] 而非 Signal<T>
}
```

在 Signal API 统一后，所有信号返回 `Signal<T>`（一个可调用函数）。但 `createSafeSignal` 返回旧的 `[getter, setter]` 元组。调用方 `createContextUse` 返回 `any`，所以类型不会报错。但如果消费者尝试调用这个返回值（例如 `result()` 读取），数组不可调用，会抛出 `TypeError: result is not a function`。

**触发条件：** 组件销毁后，子组件或效果尝试调用 `context.use(signal)` 返回的"信号"。

**修复方向：** 改为返回 `Signal<T>`（一个无操作函数）。

```ts
function createSafeSignal() {
  const signal = () => undefined;
  (signal as any)[REACTIVE] = {
    value: undefined,
    subs: new Set(),
    stop: () => {},
  };
  return signal as Signal<any>;
}
```

---

### 3.2 🟡 `registerSignalStop` 在非 `register` 路径返回类型不一致

**文件：** `src/core/signal.ts` 第 37-51 行

```ts
export function registerSignalStop(args: any[], register: (stop: () => void) => void): any {
  const result = (use as (...a: any[]) => any)(...args);
  if (isSingle(args) && isUse(args[0]) && result === args[0]) {
    return result; // 返回 Signal<T>
  }
  const stop = (result as any)[REACTIVE]?.stop;
  if (isFunction(stop)) {
    register(stop);
  }
  return result; // 也返回 Signal<T>
}
```

两种路径都返回 `Signal<T>`（函数），一致。✅

但 `isSingle(args) && isUse(args[0])` 检查需要两个条件同时满足。当 `args` 只有一个元素且是信号时，结果为信号本身，不注册清理。但当 `args` 是 `[signal, fn]`（派生模式），即使第一个参数是信号，也会创建新的派生信号并注册清理。这是正确的行为。

---

### 3.3 🟡 `Signal<T>` 的 setter 类型不够精确

**文件：** `src/core/types.ts` 第 57-59 行

```ts
export interface Signal<T> {
  (): T;
  (value: T | ((prev: T) => T)): void;
}
```

`Signal<T>` 定义了读写重载。但重载的返回类型问题：当调用 `signal(v)` 时返回 `void`，但实际上信号函数体执行 `return;`（即返回 `undefined`）。精度足够。

但 `signal()` 的返回类型是 `T`，而 `createSafeSignal` 返回的假信号返回 `undefined`。这在某些类型检查场景下会暴露。

### 3.4 🟢 `derivationMode` SSR 分支

**文件：** `src/core/signal.ts` 第 170-173 行

```ts
if (currentRenderMode === "ssr") {
  const value = (func as (v?: any) => T)(undefined);
  return definitionMode(value);
}
```

SSR 模式下派生信号退化为一次性计算的值。这是有意设计，但：

## 4. 类型安全

### 4.1 🔴 `any` 过度使用

以下类型本应为具体类型但使用了 `any`：

| 位置                                                              | 当前类型 | 应使用                        |
| ----------------------------------------------------------------- | -------- | ----------------------------- |
| `component.ts` `createContext(owner: any)`                        | `any`    | `Owner`                       |
| `component.ts` `createContextUse(owner: any)`                     | `any`    | `Owner`                       |
| `component.ts` `mergeResults(items: any[], owner: any)`           | `any[]`  | `(HResult \| Node)[]`         |
| `component.ts` `handleAsyncComponent(..., owner: any)`            | `any`    | `Owner`                       |
| `component.ts` `handleComponent(..., props: Record<string, any>)` | `any`    | 类型参数                      |
| `direct.ts` `createDirectiveContext(owner: any)`                  | `any`    | `Owner`                       |
| `directives.ts` `appendResult(..., owner: any)`                   | `any`    | `Owner`                       |
| `directives.ts` 所有 Map `<any, any>`                             | `any`    | 具体类型参数                  |
| `h.ts` `handleDomMode(tag: string, props: any)`                   | `any`    | `Record<string, any> \| null` |
| `h.ts` `handleDirectiveMode(..., props: any)`                     | `any`    | `Record<string, any>`         |

**影响：** TypeScript 的类型检查在这些位置退化为 JavaScript 级别的检查，无法捕获类型错误。

**修复方向：** 逐步替换 `any` 为具体类型，从 `Owner` 类型开始（最核心，使用最广）。

---

### 4.2 🟠 `(signal as any)[REACTIVE]` 模式遍地开花

全代码库 15+ 处使用 `(something as any)[REACTIVE]` 来访问信号内部状态。例如：

- `signal.ts:92`: `(result as any)[REACTIVE]?.stop`
- `signal.ts:121`: `(fn as any)[REACTIVE] = state`
- `component.ts:33`: `(noop as any)[REACTIVE]`
- `dom/props.ts:68`: `(derived as any)[REACTIVE]?.stop`
- `directives.ts`: 6+ 处

```ts
// 建议的封装：
import type { SignalState } from "./types.ts";

export function getSignalState<T>(signal: Signal<T>): SignalState<T> | undefined {
  return (signal as any)[REACTIVE];
}
```

这样所有外部代码变为 `getSignalState(signal)?.stop`，类型安全且无需 `as any`。

---

### 4.3 🟠 `Owner.elements` 类型为 `Set<unknown>`

**文件：** `src/core/types.ts` 第 91 行

```ts
elements: Set<unknown>;
```

在 DOM 平台上 elements 是 `Node`，在 SSR 平台上是 `SSRNode`。使用 `unknown` 避免了 DOM 类型污染 core 层，但代价是在 DOM 层使用 `owner.elements.add(node)` 时需要 `as any` 隐式转换。

**建议：** 泛型化 `Owner<T>`，core 层用 `Owner<unknown>`，DOM 层用 `Owner<Node>`。但这会大幅增加类型复杂度。当前方案是合理的折中。

## 5. DOM / SSR 层问题

### 5.1 🔴 `portal.ts` 引用了不存在的 `adapter.querySelector`

**文件：** `src/dom/portal.ts` 第 15 行

```ts
const target = isString(props.to)
  ? (adapter.querySelector(props.to) as HTMLElement | null)
  : props.to;
```

`RenderAdapter` 接口上没有 `querySelector` 方法。这是已知的编译错误。

**修复方向：**

- 在 `RenderAdapter` 中添加 `querySelector(selector: string): unknown` 方法
- 或直接将 Portal 实现为浏览器专用（直接调用 `document.querySelector`）

---

### 5.2 🟠 `SSRAdapter.setProp` 输出了不应输出的 `children` 属性

**文件：** `src/server/adapter.ts` 第 160-188 行

`setProp` 检查了 `null/false/true/on*/prop*/attr*`，但没有跳过 `children`。虽然 `handleDomMode` 的 `setProps` 已跳过 `children` key，但当组件 props 直接通过 adapter 设置时，`children` 可能被输出为 HTML 属性。

**验证路径：** `handleComponent` → `tag(compProps, context)` → 组件内部可能直接调用 adapter.setProp → children 可能泄漏到 HTML。

**修复方向：** SSR adapter 的 `setProp` 中跳过 `key === "children"`。

---

### 5.3 🟡 `renderToString` 中 adapter 被全局替换

**文件：** `src/server/index.ts` 第 24 行

```ts
setAdapter(ssrAdapter);
```

`setAdapter` 设置的是全局 adapter。如果两个 `renderToString` 调用并发（在服务端可能出现），它们会互相覆盖 adapter。虽然 JavaScript 是单线程的，但异步操作（如 await）期间可能被中断。如果 `renderToString` 内部有 `await`（当前无），这就是竞态条件。

**当前影响：** 无（同步执行）。但未来如果引入异步渲染，这是一个隐患。

**修复方向：** 使用 `AsyncLocalStorage` 或 `request-local` 上下文传递 adapter，而非全局变量。

## 6. 边界情况 & 潜在 Bug

### 6.1 🟠 `processChildren` 中 `flat(Infinity)` 与 `isArray` 死代码

**文件：** `src/core/process-children.ts` 第 30-33 行

```ts
for (const child of children.flat(Infinity)) {  // flat 已展平所有层级
  ...
  if (isArray(child)) {  // ← 恒为 false——所有嵌套数组已被 flat 展平
    const sub = processChildren(child);  // ← 死代码
    ...
  }
```

`Array.prototype.flat(Infinity)` 递归地展平所有嵌套数组，所以循环体内永远不会遇到数组。内部的 `isArray` 分支完全不可达。

**修复方向：** 移除 `flat(Infinity)`（它创建了新数组且隐藏了递归），用递归 `processChildren` 处理嵌套，或者移除死代码分支。

---

### 6.2 🟠 `mergeResults` 不处理嵌套数组

**文件：** `src/core/component.ts` 第 84-103 行

```ts
function mergeResults(items: any[], owner: any): Node[] {
  const allNodes: Node[] = [];
  const list = isArray(items) ? items : [items];
  for (const item of list) {
    if (isHResult(item)) { ... }
    else if (isNode(item)) { allNodes.push(item); }
  }
  return allNodes;
}
```

如果组件返回 `[[hr1, hr2], hr3]`（Fragment 嵌套 Fragment 等场景），`isArray` 包裹使得顶级数组被迭代，但 `[[hr1, hr2], hr3]` 中的 `[hr1, hr2]` 既不是 `HResult` 也不是 `Node`——它被静默忽略。

**触发场景：** `Fragment({ children: [Fragment({ children: [<A/>, <B/>] }), <C/>] })`。

**修复方向：** `mergeResults` 应递归展平，或将 `ComponentFunction` 返回类型限制为 `HResult`（而非 `HResult[]`）。

---

### 6.3 🟡 `recomputeDerivation` 中 `setterValue` 的语义

**文件：** `src/core/signal.ts` 第 221-234 行

```ts
function recomputeDerivation<T>(state: DerivationState<T>, setterValue?: any): void {
  let newResult: T;
  try {
    newResult = state.computeFn(setterValue);
  } catch (err) { ... }
  if (newResult !== state.cachedValue) {
    state.cachedValue = newResult;
    const subs = [...state.subs];
    for (const sub of subs) { recomputeDerivation(sub, undefined); }
  }
}
```

`setterValue` 仅在手动设置派生信号时传递（`signal(newValue)`）。但触发器 `triggerDerivations` 和后续传播都传递 `undefined`。这意味着：手动设置派生信号只影响第一层——其子派生不会传播"手动设置"的能力。这可能是正确的（派生信号的 setter 只影响该节点），但值得明确文档化。

---

### 6.4 🟡 `appendResult` 中 Array path 重复 `isNode` 检查

**文件：** `src/core/directives.ts` 第 38-44 行

```ts
} else if (isArray(result)) {
  for (const node of result) {
    if (isNode(node)) {
      el.append(node);
      owner.elements.add(node);
    }
  }
}
```

与 `handleDirectiveMode` 中的 `flatChildren` 相似，这里也是数组解包。但 `appendResult` 不展平嵌套数组——如果 `result` 是 `[node1, [node2, node3]]`，内部的数组不会被递归处理。

从调用链分析，`appendResult` 接收来自 `mappingTable[key]()`、`elseFn()`、`children[0]()` 等的返回值。这些通常返回单个 Node 或 HResult。数组情况可能不会出现，但如果是 Fragment 场景，就可能出现嵌套数组。

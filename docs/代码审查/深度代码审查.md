# kiaao 框架深度代码审查

> 日期：2026-06-24
> 范围：`src/` 全部 29 个源文件

## 1. 架构层面

### 1.1 🔴 全局可变状态：`_adapter`

`_adapter` 是一个模块级可变变量：

```ts
let _adapter: RenderAdapter | null = null;
export function setAdapter(adapter: RenderAdapter): void {
  _adapter = adapter;
}
```

这是全库最危险的架构决策。理由：

- **SSR 并发不安全**：`renderToString` 设置全局 adapter，服务端多请求时竞态
- **隐式全局依赖**：`src/core/` 中的函数调用 `getAdapter()` 但调用方不感知依赖了哪个 adapter
- **测试污染**：一个测试文件 `setAdapter(browserAdapter)` 后，后续测试文件如果没重设就会用错 adapter

**建议**：将 adapter 作为参数传递（类似 React 的 `createRoot(container)` 模式），或使用 AsyncLocalStorage（SSR 场景）。

```ts
// 方案：adapter 成为 createApp/h 的可选参数
export function h(tag, props?, children?, adapter?: RenderAdapter): HResult;
export function createApp(hr: HResult, adapter?: RenderAdapter): App;
```

这会让 API 变复杂。折中方案：**运行时检查 + 警告**，在非浏览器环境调用 DOM adapter 操作时报错。

---

### 1.2 🟠 `RenderAdapter` 接口的抽象层次

接口方法签名全部用 `unknown` 和 `Function`：

```ts
interface RenderAdapter {
  createElement(tag: string): unknown;
  addEventListener(el: unknown, type: string, handler: Function): void;
  ...
}
```

`Function` 类型过于宽松——不限制参数个数和返回值类型。如果 Lynx 的 event handler 签名与 DOM 不同（例如 Lynx 可能传额外的原生事件对象），`Function` 无法在编译期捕获不兼容用法。

**建议**：为各种 handler 定义具体类型：

```ts
type EventHandler = (event: any) => void;
interface RenderAdapter {
  addEventListener(el: unknown, type: string, handler: EventHandler): void;
}
```

但目前所有 adapter 实现都用 `EventListener`（DOM）或空操作（SSR），`Function` 是最小公共接口。这个问题的根本在于 adapter 需要抽象的平台差异太大。

---

### 1.3 🟠 `Owner.elements` 类型为 `Set<unknown>`

Owner 的 elements 集合用于 dispose 时从 DOM 移除节点。但 `unknown` 类型意味着：

- `owner.elements.add(node)` 接受任何值——可能误加非节点
- `removeNode(el)` 内部调用 `_adapter?.remove(node)`——SSR 下是空操作

**建议**：保持 `unknown`（跨平台需要），但在 DOM 层包装一个类型安全的 add helper。

## 2. 信号系统

### 2.1 🟠 `Signal<T>` 作为函数——优雅但冷门

`Signal<T>` 通过函数重载实现读写一体：

```ts
const count = use(0);
count(); // 读 → 0
count(1); // 写 → 1
count((p) => p + 1); // 更新函数 → 2
```

这种设计（SolidJS 风格）比 `[getter, setter]` 元组更简洁。但有代价：

- **TypeScript 类型推断限制**：`count` 的类型是 `Signal<number>`，写操作时 `count("string")` 不会被 TypeScript 拒绝（因为 `T | ((prev: T) => T)` 中包含 `string`）
- **可发现性差**：新用户不知道 `count` 是个函数，看到 `count(1)` 会疑惑

**建议**：无——这是 API 的选择而非缺陷。在文档中重点说明。

### 2.2 🟡 `SignalState<T>` 中 `subs` 类型不精确

```ts
interface DefinitionState<T> {
  subs: Set<DerivationState<any>>; // any → unknown？
}
```

`DerivationState<any>` 使用 `any`——但派生信号并不知道其子派生信号的值类型。这是正确的（子派生可以是任意类型）。保持 `any`。

## 3. API 设计

### 3.1 🔴 导出类型缺失

`src/index.ts` 导出的类型：

```
Children, UseFunction, Context, DirectiveFunction, DirectiveContext
```

**未导出但有用的类型**：

- `Signal<T>` — 用户需要它来注解变量类型
- `HResult` — 用户可能想查看或组合 HResult
- `Owner` — 高级用户可能想操作 Owner 树
- `Props` / `NullableProps` — 组件属性类型
- `RenderAdapter` — 跨平台适配器实现者需要
- `ComponentFunction` — 自定义组件类型

```ts
// 用户场景：给组件 props 加类型
import { type Props } from "kiaao";
function MyComponent(props: Props & { name: string }) { ... }
```

**建议**：审查并补充缺失的导出。

### 3.2 🟠 `Children` 类型已经过时

```ts
export type Children = Node | Node[];
```

`h()` 现在返回 `HResult`，不是 `Node | Node[]`。这个类型是旧 API 的残留。它不再反映实际返回值。

**建议**：删除或用 `HResult` 替代。

### 3.3 🟡 `h()` 的 3 重重载

```ts
export function h(tag: DirectiveFunction, props?, ...children): HResult;
export function h(tag: string | ComponentFunction, props?, ...children): HResult;
export function h(tag: any, props?, ...children): HResult;
```

3 个重载让类型系统能区分指令和其他标签。但：

- 指令和组件的 props 签名不同（指令 props 是 `Props & { children?: any }`，组件 props 是 `P`）
- 实现签名用 `tag: any` 收口——`any` 会吞噬所有类型检查
- 如果用户传了非法 tag（例如数字），重载解析会匹配到最后一个 `any` 重载，不会得到编译错误

**建议**：可以考虑用泛型约束 tag 类型，但当前设计是实用主义的折中。

## 4. 代码质量

### 4.1 🟠 `handleDomMode` 的 `props: any` 反模式

```ts
function handleDomMode(tag: string, props: any, children: any[]): HResult {
  if (isDefined(props?.when)) {
    const { when, each, key, else: elseFn, ...rest } = props;
```

`props: any` 是因为需要解构 `when`/`each`/`key`/`else` 这些可能不存在的属性。`Record<string, any>` 不允许解构未知属性名。

**问题**：这个 `any` 传播到整个函数体——`rest` 也是 `any`，传到 `createWhenElement` 的 options 里也是 `any`。

**建议**：局部用 `(props as any)` 而不是整个参数用 `any`：

```ts
function handleDomMode(tag: string, props: Record<string, unknown>, children: any[]): HResult {
  const p = props as any; // 只在需要解构的地方转换
  if (isDefined(p?.when)) {
    const { when, ...rest } = p;
```

---

### 4.2 🟠 `directives.ts` 中的重复模式

`createItemDOMNodes` 中有三个平行的分支处理 HResult/Node/Array：

```ts
if (isHResult(node)) {
  /* 处理 HResult */
} else if (isNode(node)) {
  /* 处理 Node */
} else if (isArray(node)) {
  /* 遍历 Node[] */
}
```

`appendResult` 中有相同的三路分支。`renderEachOnElement` 的 sync 中也有。

这是**运行时多态**——用 `if/else` 替代了类型系统的分支。每次新增一个可渲染类型都需要在所有地方加分支。

**建议**：考虑引入 `toNodes(result)` 统一函数：

```ts
function toNodes(result: any): Node[] {
  if (isHResult(result)) return [...result.nodes];
  if (isNode(result)) return [result];
  if (isArray(result)) return result.filter(isNode);
  return [];
}
```

---

### 4.3 🟡 `processChildren` 中 SSR 节点检测脆弱

```ts
if (isObject(child) && "type" in (child as any)) {
  nodes.push(child as Node);
  continue;
}
```

通过检查 `"type" in child` 来判断是否是 SSR 节点——如果普通对象刚好有 `type` 属性（例如 `{ type: "text", value: "hello" }`），会被误判为 SSR 节点。

**建议**：使用 Symbol 标记或 SSR adapter 的类型字段：

```ts
const SSR_NODE = Symbol("kiaao.ssr.node");
nodes.push(child as Node);
```

## 5. 错误处理与边界情况

### 5.1 🔴 没有错误边界机制

整个框架没有任何错误边界（error boundary）概念：

```ts
try {
  result = tag(compProps, context);
} catch (e) {
  console.error("[kiaao] component error:", e);
  disposeOwner(owner);
  const comment = getAdapter().createComment("component error") as Node;
  return createHResult(owner, [comment]);
}
```

组件抛出异常时：

1. 控制台打印错误
2. 用注释节点 `<!-- component error -->` 替换整个组件
3. 用户无法恢复或显示降级 UI

React 有 Error Boundary，Vue 有 `errorCaptured`。kiaao 目前没有。

**影响**：生产环境中一个子组件的错误会导致整块 UI 变成不可见的注释节点。

**建议**：在 Context 上增加 `onError` 回调，让父组件能捕获子组件错误。

---

### 5.2 🟠 `handleAsyncComponent` 竞态条件

```ts
promise
  .then((rawResult) => {
    if (owner.disposed) return; // ✅ 已处理
    // ...
    triggerMount(owner);
  })
  .catch((err: Error) => {
    if (owner.disposed) return; // ✅ 已处理
    console.error("[kiaao] async component error:", err);
  });
```

问题：如果 `.then()` 执行过程中组件被 dispose（例如用户快速导航离开），`rawResult` 已经被处理了一半——`mergeResults` 已经创建了子 Owner 并链接到 `owner.children`，但随后 `owner.disposed` 才被标记。子 Owner 成为内存泄漏。

**建议**：在 `mergeResults` 前检查 `owner.disposed`。或者将 disposed 检查放在每次操作之前。

### 5.3 🟡 `disposeOwner` 不会从父 Owner 的 children 中移除自己

```ts
export function disposeOwner(owner: Owner): void {
  // ...清理内部...
  owner.children.length = 0; // ✅ 清空子节点
  // ❌ 但没从 parent.children 中移除自己
}
```

dispose 后的 Owner 仍然作为子节点挂在父 Owner 的 `children` 数组中。`triggerMount` 遍历时会跳过已 dispose 的节点（有 `visited` 保护），但父 Owner 的 `children` 数组里积累了许多已 dispose 的幽灵节点。

长期运行的应用（SPA 中频繁切换页面），`children` 数组会不断增长。

**建议**：dispose 后从 parent.children 中移除：

```ts
if (owner.parent) {
  const idx = owner.parent.children.indexOf(owner);
  if (idx !== -1) owner.parent.children.splice(idx, 1);
}
```

## 6. 性能

### 6.1 🟠 `processChildren` 中的 `children.flat(Infinity)` 已修复

之前已修复——不再使用 `flat(Infinity)`，改为递归调用。✅

### 6.2 🟡 `renderEachOnElement` 每次 sync 创建新 Set 和 Map

```ts
const sync = () => {
  const source = toValue(eachFn);
  const items = isArray(source) ? source : [];
  const newKeys = new Set<any>();
  const currentKeys = new Set(itemOwners.keys());
```

每次 sync 创建 `newKeys` 和 `currentKeys` Set。如果数据频繁变化（例如动画驱动的数组），这会造大量短期对象，增加 GC 压力。

**建议**：对高频场景影响不大——这是标准 JS 模式。保留。

**建议**：清理废弃的测试文件，统一测试运行配置。

## 8. 开发体验

### 8.1 🟡 中英文混用

代码注释使用中文（符合 AGENTS.md），但代码标识符使用英文。这种混用在开源项目中不常见——国际贡献者无法阅读中文注释。

**建议**：核心公共 API 的文档注释用英文，实现细节用中文可保持。

### 8.2 🟡 `package.json` 入口需要审查

当前 `package.json` 的 exports 配置：

```json
{
  "exports": {
    ".": "...",
    "./server": "...",
    "./motion": "..."
  }
}
```

需要确保 `"motion"`、`"router"`、`"server"` 等子路径的导出完整。特别是 `.d.ts` 文件的生成是否正确——之前就有 `Getter` 导出残留导致 dts 生成失败。

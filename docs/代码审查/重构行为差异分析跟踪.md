# 重构行为差异分析及修复跟踪

> 创建日期：2026-06-23
> 范围：对比 `/Users/seven/Desktop/mine/kiaao-main`（重构前）与当前 `src/`（重构后）的行为差异
> 注意：本文档仅关注**行为不一致**，不涉及 API 签名变更

---

## 总体结论

重构在架构层面完成了 Owner 树、HResult、Signal API 统一三大目标，但引入了多个行为层面的退化。以下按严重程度排序。

---

## 1. 🔴 each 指令：DOM 节点不复用，每次全量重建

**影响程度：严重 — 破坏用户输入状态（焦点丢失、滚动丢失、表单输入丢失）**

**旧代码行为（`dom/each.ts`）：**

- `nodeMap` 按 identity 缓存已渲染的 DOM 节点
- 数组变化时，identity 匹配的节点**原地复用**（仅重排位置）
- `syncCleanupRemoved` 只销毁消失的条目
- 输入框在内嵌 each 中能保持焦点和值

**新代码行为（`core/directives.ts` `renderEachOnElement`）：**

- `sync()` 开头执行 `while (anchor.previousSibling) container.removeChild(...)` **无条件清空全部子节点**
- 然后对每个条目**重新调用 `childFn` 从头创建 DOM**
- `itemOwners` Map 虽然按 key 缓存了 Owner，但 DOM 每次全量销毁重建

**修复要点：**

- 新 each 需恢复按 identity 复用 DOM 节点的逻辑
- 移除 `sync()` 开头的无条件清空，改为增量更新（新增、删除、移动）
- 注意 HResult 兼容性——旧 each 处理的不是 HResult，新 each 需要处理 `childFn` 返回 HResult 的情况

---

## 2. 🔴 when 指令分支清理：子节点未 dispose 直接移除

**影响程度：严重 — 信号/事件监听器泄漏**

**旧代码行为（`dom/when.ts` `clearChildren`）：**

```ts
function clearChildren(el: Element): DocumentFragment {
  const removed = createFragment();
  let child: Node | null;
  while ((child = firstChild(el))) {
    disposeNode(child); // ← 先 dispose：触发 onUnmount、清理 LOCAL_EFFECTS
    removed.append(child);
  }
  return removed;
}
```

**新代码行为（`core/directives.ts` `renderBranch`）：**

```ts
// 清空分支时：
while (el.firstChild) el.removeChild(el.firstChild); // ← 直接移除，没有 dispose！
```

然后在 `disposeOwner(branchOwner)` 中通过 `owner.elements` 移除节点——但 `owner.elements` 只记录了通过 `branchOwner.elements.add(node)` 显式添加的节点，并非所有 DOM 子节点。

**修复要点：**

- `renderBranch` 中清空旧分支时应通过 `adapter.remove()` 或遍历 `branchOwner.elements` 先 dispose 再移除
- 考虑用 `disposeOwner(branchOwner)` 完成后 `while (el.firstChild) el.removeChild(...)` 但让 disposeOwner 负责 cleanup

---

## 3. 🟠 style 属性：对象赋值为全量替换而非增量更新

**影响程度：中等 — 破坏与第三方库的兼容性，内联样式意外丢失**

**旧代码行为（`dom/props.ts` `setStyleProp`）：**

```ts
function setStyleProp(el: Element, value: any): boolean {
  if (isObject(value)) {
    removeAttr(el, "style");
    Object.assign((el as HTMLElement).style, value);  // ← 增量更新每个样式属性
    return true;
  }
  ...
}
```

`Object.assign(el.style, { backgroundColor: 'red' })` 只设置指定的属性，不影响其他内联样式。

**新代码行为（`dom/props.ts` `setProp`）：**

```ts
if (isObject(value)) {
  const cssText = Object.entries(value)
    .map(([k, v]) => `${k.replace(/[A-Z]/g, ...)}: ${v}`)
    .join("; ");
  adapter.setProp(el, rawKey, cssText);  // ← 整体设置 style 属性，覆盖全部
}
```

通过 `adapter.setProp(el, rawKey, cssText)` → 走到 adapter 的 `el.setAttribute('style', cssText)`，**覆盖全部内联样式**。

**修复要点：**

- 恢复 `Object.assign(el.style, value)` 的方式增量更新
- 仅在 SSR 模式下使用 cssText 序列化
- 或者 adapter 中针对 `style` 属性做增量处理

---

## 4. 🟠 setProps 信号清理：调用方不传 cleanups 数组则泄漏

**影响程度：中等 — 当 setProps 不传入 cleanups 数组时信号绑定泄漏**

**旧代码行为（`dom/props.ts` `setProps`）：**

```ts
if (isUse(value)) {
  const [derived] = use(value, () => {
    setProp(el, key, value());
  });
  addLocalEffect(el, (derived as any)[REACTIVE].stop);
  // ← 始终将 stop 注册到 DOM 节点，后续 disposeNode 必定清理
}
```

**新代码行为（`dom/props.ts` `setProps`）：**

```ts
if (isUse(value)) {
  const derived = use(value, () => {
    setProp(el, key, value());
  });
  const stop = (derived as any)[REACTIVE]?.stop;
  if (stop) {
    if (cleanups) cleanups.push(stop); // ← cleanups 为可选参数，不传入则丢弃
  }
}
```

以下调用方没有传入 cleanups 数组：

- `core/directives.ts` `createWhenElement`: `setProps(el, props, containerOwner.cleanups)` ✅ 传了
- `core/directives.ts` `createEachElement`: `setProps(el, props)` ❌ 没传
- `core/h.ts` `handleDomMode`: `setProps(el, ...props, orphanCleanups)` ✅ 传了

**修复要点：**

- `createEachElement` 补传 cleanups 数组
- 考虑在 `directives.ts` 中将 props 的信号 stop 注册到相应的 Owner

## 5. 🟠 createEachElement props 信号泄漏

**影响程度：中等 — each 容器元素的信号 prop 不会清理**

**旧代码行为（`dom/each.ts` `createEachElement`）：**

```ts
const el = createElement(tag);
setProps(el, props);
// each 的 container 节点的信号 prop cleanup 通过 addLocalEffect 注册到 el
```

**新代码行为（`core/directives.ts` `createEachElement`）：**

```ts
const el = adapter.createElement(tag) as Element;
setProps(el, props); // ← 无 cleanups 参数
const childFn = children[0];
renderEachOnElement(el, eachFn, childFn, keyFn);
// renderEachOnElement 内部创建了 containerOwner，但 setProps 的 leak 未纳入
```

**修复要点：**

- `createEachElement` 构建 containerOwner 后，传入其 cleanups 数组

## 6. 🟡 生命周期回调异步错误处理

**影响程度：低 — 不影响正常流程，仅错误日志丢失**

**旧代码行为（`dom/component.ts` `safeCall`）：**

```ts
function safeCall(fn: () => void | Promise<void>, label: string): void {
  try {
    const result = fn();
    if (isPromise(result)) {
      result.catch((err) => console.error(`[kiaao] ${label}:`, err));
    }
  } catch (err) {
    console.error(`[kiaao] ${label}:`, err);
  }
}
```

同步和异步错误都被捕获并记录。

**新代码行为（`core/owner.ts` `disposeOwner`/`triggerMount`）：**

```ts
for (const cb of owner.unmountCallbacks) {
  try {
    cb();
  } catch (e) {
    // ← 仅捕获同步错误，异步 Promise rejection 未处理
    console.error("[kiaao] onUnmount error:", e);
  }
}
// triggerMount 同理
```

**修复要点：**

- 恢复 `safeCall` 模式，处理 `fn()` 返回 Promise 时的 rejection

## 7. 🟡 SSR adapter setProp 缺少属性处理

**影响程度：低 — SSR 输出可能不准确（样式对象、布尔属性）**

**旧代码行为（`dom/ssr-serialize.ts` `serializeAttr`）：**

- `style` 对象：序列化为 cssText
- `aria-*` / `data-*`：强制输出
- `FORCE_ATTRIBUTE`：true 时输出 bare attribute（如 `<input disabled>`）
- `prop:` 前缀：不输出

**新代码行为（`server/adapter.ts` `setProp`）：**

- `prop:` 前缀：正确跳过 ✅
- `attr:` 前缀：正确去掉前缀 ✅
- 布尔值：`true` 直接转为 `"true"` 字符串 ❌（应该输出 bare attribute）
- `style` 对象：需要调用方自行序列化 ✅（已由 props.ts 处理）
- FORCE_ATTRIBUTE 判断：缺失 ❌
- aria/data 判断：缺失 ❌

**修复要点：**

- SSR adapter 的 setProp 中处理 `FORCE_ATTRIBUTE`、`aria-/data-`、布尔值语义

---

## 8. 🟡 createWhenElement 的 `el.firstChild` 清空方式

**影响程度：低 — 内存泄漏风险，同第 2 点但位置不同**

```ts
// core/directives.ts createWhenElement renderBranch:
while (el.firstChild) el.removeChild(el.firstChild);
```

这段代码在 SSR 模式下执行时，`el` 是 SSRElement 对象（非真正的 DOM 元素）。SSRElement 的 `firstChild` 是 undefined，`removeChild` 也是 undefined，会抛运行时错。但实际上 SSR 不执行 when 指令的派生订阅——`isUse(whenFn)` 在 SSR 模式下 `getRenderMode()` 为 "ssr" 时，`use` 函数返回的信号不是响应式的。所以这条路径在 SSR 下不会走到 `renderBranch()`。但如果被意外触发则会崩溃。

---

## 9. 🟢 mount/unmount 回调的 disposed 检查不一致

**影响程度：无（已正确处理）**

注意到新代码的 `createContext` 在 `owner.disposed` 时返回空操作，而旧代码使用 `DISPOSED_KEY` Symbol。两者行为一致，只是实现机制不同。

---

## 10. 🟢 safeCall vs try/catch 错误处理一致性

**影响程度：无（已正确处理，仅风格差异）**

记录在此仅作为已确认事项——旧代码使用 `safeCall` 辅助函数，新代码直接在 `disposeOwner` 和 `triggerMount` 中使用 `try/catch`。功能等价。

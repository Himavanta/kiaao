# 代码深度审查跟踪

**目标**：按超一流开源项目标准全面审视 kiaao 代码
**方法**：逐文件审查，识别所有可优化点
**状态**：审查中

---

## 审查维度

| 维度          | 说明                                  |
| ------------- | ------------------------------------- |
| 🎯 类型安全   | TypeScript 严格度、类型推导、泛型使用 |
| 🧪 测试质量   | 边界覆盖、测试可读性、运行速度        |
| ⚡ 性能       | 不必要的分配、闭包泄漏、批量操作      |
| 🎨 API 一致性 | 命名风格、参数顺序、错误提示          |
| 📚 文档完整性 | JSDoc 覆盖度、注释质量、中英文混用    |
| 🔧 错误处理   | 用户友好错误、防御性编程、边界恢复    |
| 📦 模块化     | 依赖方向、循环引用、关注点分离        |
| 🧹 代码整洁   | 重复模式、复杂表达式、可读性          |

## 审查结果

### 1. 🎯 类型安全

#### 1.1 `h()` 函数重载覆盖不完整

**文件**：`src/dom/h.ts`
**问题**：`h()` 有 3 个重载（指令、组件、实现），但实现签名使用 `tag: any`，失去了类型检查。同时，`handleDirectiveMode` 内使用 `(tag as DirectiveFunction)` 转型。

**建议**：用泛型约束 + 条件类型替代 `any`，或在实现签名中保留联合类型。

**优先级**：🟢 低（runtime 安全，类型安全可加强）

---

#### 1.2 `src/dom/each.ts` 中 `keyFn` 参数类型不精确

**文件**：`src/dom/each.ts:113`
**问题**：`renderEach` 的 `eachFn` 类型为 `(() => any[]) | (() => any)`，丢失了具体元素类型。`keyFn` 返回 `any`。

**建议**：引入泛型 `<T>` 约束 each 条目类型。

**优先级**：🟢 低

---

#### 1.3 `normalizeEachSource` 返回值类型过于宽松

**文件**：`src/dom/each.ts:22`
**问题**：返回 `Array<[any, any, number]>`——第一维是 key，第二维是 value，第三维是 index。应使用具名类型或至少用对象。

**建议**：定义 `type EachEntry = { key: any; value: any; index: number }`。

**优先级**：🟢 低

---

### 2. 🧪 测试质量

#### 2.1 缺少 `ssr-serialize.ts` 的独立单元测试

**文件**：`tests/dom/`
**问题**：`serializeCssText`、`serializeAttr`、`serializeAttrs`、`stripDirectives` 均无独立测试——仅通过 SSR 集成测试间接覆盖。这些纯函数非常适合单元测试。

**测试示例**：

```ts
test("serializeCssText converts object to inline style", () => {
  expect(serializeCssText({ color: "red", fontSize: "14px" })).toBe("color: red; font-size: 14px");
});
```

**优先级**：🟡 中

---

#### 2.2 缺少 `registerSignalStop` 的独立测试

**文件**：`src/reactive/core.ts`（新增函数）
**问题**：`registerSignalStop` 作为共享工具函数，没有独立的单元测试，仅通过组件和指令的集成测试覆盖。

**优先级**：🟡 中

---

#### 2.3 测试文件缺少边界情况

**全局问题**：

- `processChildren` 没有测试超深层嵌套数组导致栈溢出的行为
- `disposeNode` 没有测试节点被多次 dispose 的安全性（幂等性）
- `recomputedDerivation` 没有测试派生函数抛出异常后下游派生的行为
- `use` 传入 `Symbol`、`BigInt` 等极端类型
- `h()` 传入极大的 children 数组（性能边界）

**优先级**：🟢 低

---

### 3. ⚡ 性能

#### 3.1 `children.flat(Infinity)` 在深层嵌套时可能较慢

**文件**：`src/dom/h.ts:97`（`handleDirectiveMode`）
**问题**：`children.flat(Infinity)` 递归遍历整个数组。对于极深嵌套（如 100+ 层）可能造成栈溢出或性能问题。且每次 `h()` 调用都创建新数组。

**建议**：限制平铺深度为 2-3 层（JSX 通常不会超过 2 层嵌套），或使用迭代而非递归的扁平化。

```ts
// 平铺 2 层足够覆盖 JSX 常见场景
const flatChildren = children.flat(2);
```

**优先级**：🟢 低（实际场景很少超过 2 层嵌套）

---

#### 3.2 `serializeAttrs` 中每次循环都调用 `isUse`

**文件**：`src/dom/ssr-serialize.ts:77`
**问题**：`serializeAttrs` 在循环中对每个属性调用 `isUse(val)`。SSR 场景下大多数属性是静态值，`isUse` 对一个非信号函数调用 `in` 操作符检查 Symbol。

**建议**：`isUse` 已经很快（一次 `in` 检查），非热点路径，不优化。

**优先级**：🟢 忽略

---

#### 3.3 `hSSRWhenTag` 中 `cleanProps` 闭包每次调用都重复计算

**文件**：`src/dom/ssr-render.ts:52`
**问题**：`const cleanProps = () => serializeAttrs(stripDirectives(props))` 是一个闭包，但每次分支中调用时都重新计算。映射表模式下可能调用 2-3 次相同的结果。

**建议**：在分支入口处缓存 `const attrs = serializeAttrs(stripDirectives(props))`。

**优先级**：🟢 低（SSR 场景，非热点）

---

### 4. 🎨 API 一致性

#### 4.1 错误消息风格不统一

**全局问题**：错误消息前缀风格不一致：

- `[kiaao] derive error...` ✓
- `[kiaao] use(...): ...` ✓
- `[kiaao] each source...` ✓
- `[kiaao] each item render error:` ✓
- `[kiaao] When using mapping table mode...` (首字母大写不一致)
- `[kiaao] directive skipped non-Element child:` ✓

检查发现 `when.ts` 中的警告消息首字母大写：

```
`[kiaao] When using mapping table mode, the 'each' prop is ignored.`
```

其他消息以小写开头。应统一。

**优先级**：🟢 低

---

#### 4.2 部分函数有 JSDoc，部分没有

**全局问题**：

- 公有 API（`use`、`h`、`mount`、`unmount`、`direct`）有完整 JSDoc ✓
- 内部工具函数（`createContextUse`、`handleDirectiveMode`、`syncItemSignal` 等）有 JSDoc ✓（上一轮重构中新增）
- `recomputedDerivation` 有 JSDoc ✓
- `triggerDerivations` 无 JSDoc

**优先级**：🟢 低

---

### 5. 🔧 错误处理

#### 5.1 组件同步函数抛错无保护

**文件**：`src/dom/h.ts`（组件模式）
**问题**：`tag(compProps, context)` 无 try-catch。如果组件函数同步抛出异常，整个 `h()` 调用会终结。对比指令模式同样无保护（与预期一致——这是故意设计，用户应自己处理组件错误）。

但对比 Vue/React，框架层捕获渲染错误并提供错误边界。kiaao 选择不封装是对的（"透明、可预测"理念），但可以记录该设计决策。

**优先级**：🟢 低（设计如此）

---

#### 5.2 `syncItemSignal` 中使用 `rawValue != null`（宽松比较）

**文件**：`src/dom/each.ts:55`
**问题**：`const isReactive = rawValue != null && isUse(rawValue)` 使用了 `!=` 而非 `!==`。`!=` 会将 `null` 和 `undefined` 等同处理。虽然这里语义正确（检查是否非 null/undefined），但团队约定应统一使用 `!==`。

**其他位置**：

- `ssr-serialize.ts:87` — `val == null || val === false` ✓（用 `==` 检查 null/undefined 是常见模式）
- `ssr-helpers.ts:39` — `renderSSRChild` 中 `child == null` ✓

`!= null` 是一个常见模式（同时检查 null 和 undefined），但项目中其他地方使用的是 `== null`。应统一。

**优先级**：🟢 低

---

#### 5.3 `hSSRWhenTag` 中 `cleanProps` 闭包捕获 `props` 引用

**文件**：`src/dom/ssr-render.ts:52`
**问题**：`cleanProps` 捕获的是 `props` 引用，而非其当前值的快照。虽然 `hSSRWhenTag` 执行期间 `props` 不会变化，但如果未来代码在调用后被修改（目前不会），闭包会看到意外值。这是 JavaScript 闭包常见陷阱。

**建议**：在函数入口处创建快照：`const baseAttrs = serializeAttrs(stripDirectives(props))`，然后直接使用 `baseAttrs`。

**优先级**：🟢 低

---

### 6. 📦 模块化

#### 6.1 `ssr-helpers.ts` 仍然是一个混合模块

**文件**：`src/dom/ssr-helpers.ts`
**问题**：尽管已将序列化和渲染逻辑拆分出去，`ssr-helpers.ts` 仍然包含 `SSRSafe` 类型定义、`VOID_ELEMENTS` 常量、`renderSSRChild` 等多类内容。这都是 SSR 相关的，但类型和常量在逻辑上是独立的。

**建议**：可进一步拆分，但当前状态合理——这些是 SSR 模块的基础设施。

**优先级**：🟢 低

---

#### 6.2 `dom-utils.ts` 包含无关的 location/query 工具

**文件**：`src/dom/dom-utils.ts`
**问题**：该文件混合了 DOM 操作（`createElement`、`setAttr`）、DOM 遍历（`firstChild`、`parentNode`）、以及 location/query 工具（`getPathname`、`pushState`、`qs`、`parseSearch`）。后者只在 `router/index.ts` 中使用。

**建议**：将 location/query 工具移至 `router/index.ts` 或独立的 `src/router/utils.ts`。

**优先级**：🟡 中

---

### 7. 🧹 代码整洁

#### 7.1 `recomputeDerivation` 中冗余注释

**文件**：`src/reactive/core.ts`
**问题**：

```ts
if (newResult !== state.cachedValue) {
  state.cachedValue = newResult;
  // 通知下游
  const subs = [...state.subs];
  for (const sub of subs) {
    recomputeDerivation(sub, undefined);
  }
}
// 短路：值未变则不通知下游
```

`// 短路：值未变则不通知下游` 注释表达的是 `if` 条件本身已经说清楚的事情。多余。

**优先级**：🟢 低

---

#### 7.2 `processChildren` 中 `if (child instanceof Node)` 比 `isUse` 更常见

**文件**：`src/dom/process-children.ts`
**问题**：循环中检查 `isUse(child)` 优先于 `child instanceof Node`，但实践中 Node 类型更常见（JSX 编译结果）。这意味着大部分子节点都经过了 `isUse` 检查（一个函数调用 + Symbol 属性检查）后才被识别为 Node。

**建议**：调换顺序——先检查最可能的分支：

```ts
if (child instanceof Node) { ... }
else if (isUse(child)) { ... }
else { ... }
```

**优先级**：🟡 中（微优化，但习惯好）

---

#### 7.3 `processChildren` 中 `child == null || typeof child === "boolean"` 重复出现在多个位置

**文件**：`src/dom/process-children.ts`、`src/dom/ssr-helpers.ts`（`renderSSRChild`）
**问题**：两个函数都处理"跳过 null/undefined/boolean"的逻辑。如果有新的可跳过类型（如 Symbol？），需要两处同步修改。

**建议**：提取为 `isSkippableChild(v)` 共享函数。

**优先级**：🟢 低

---

### 8. 其他发现

#### 8.1 `Portal` 组件 SSR 输出丢失内容

**文件**：`src/dom/portal.ts`
**问题**：Portal 的 SSR 变体返回 `<!-- portal placeholder -->`，忽略子节点。这是合理的（Portal 是客户端功能），但没有在文档中说明。

**优先级**：🟢 低

---

#### 8.2 `mount` 函数只 `append` 不 `prepend`，且无 `replace` 模式

**文件**：`src/dom/component.ts`
**问题**：`mount(root, container)` 使用 `container.append(root)`，如果容器已有内容，会追加到末尾。其他框架通常提供 `mount(root, container, position?)` 能力。

**建议**：这是设计决策——不增加复杂度。保持现有行为。

**优先级**：🟢 低

# Kiaao Lynx 双线程架构可行性分析

**日期**：2026-07-19
**状态**：方案评估，待决策

---

## 背景

kiaao 当前 Lynx 适配器采用**主线程直连模式**——所有代码在 Lynx 主线程（Lepus 引擎）运行，通过 `__CreateElement`、`__InsertElementBefore` 等原生 API 直接操作元素树，每个操作后立即调用 `__FlushElementTree`。

此模式存在致命问题：**Show 组件切换分支时（dispose 旧分支 + 创建新分支），Lynx native 层会在同父节点下的 destroy+create 操作中崩溃。** 该 bug 从 SDK 1.4.0 到 3.9.0 均存在，任何 API 组合（`__RemoveElement` / `__AppendElement` / `__ReplaceElement`）均触发。

vue-lynx 使用**后台线程 + op buffer 架构**，能安全实现 destroy+create。本文档分析 kiaao 迁移到此类架构的可行性。

---

## 架构对比

### 当前：主线程直连模式

```
┌─ 主线程（Lepus）──────────────────┐
│                                   │
│  kiaao 响应式系统                  │
│    use() → signal 同步传播         │
│     ↓                             │
│  h() → __CreateElement            │
│     ↓                             │
│  adapter.remove → __RemoveElement + __FlushElementTree  ← 每个操作立即 flush
│  adapter.before → __InsertElementBefore + __FlushElementTree
│  adapter.setProp → __SetAttribute + __FlushElementTree
│                                   │
└───────────────────────────────────┘
```

- 优点：实现简单，代码直接
- 致命缺陷：destroy+create 闪退

### 目标：后台线程 + op buffer 模式

```
┌─ 后台线程（PrimJS）───────────────┐    ┌─ 主线程（Lepus）───────────────┐
│                                   │    │                                │
│  kiaao 响应式系统                 │    │ 全局钩子                       │
│    use() / signal / derivation    │    │   processData                  │
│    ↓                              │    │   renderPage                   │
│  h() → ShadowElement（影子树）    │    │   runWorklet                   │
│    ↓                              │    │                                │
│  所有 adapter 方法只 push op：    │    │  ops-apply 执行器              │
│    pushOp(CREATE, id, type)       │    │   CREATE → __CreateElement     │
│    pushOp(INSERT, pid, cid, aid)  │    │   INSERT → __AppendElement     │
│    pushOp(REMOVE, pid, cid)       │    │   REMOVE → __RemoveElement     │
│    pushOp(SET_STYLE, id, {...})   │    │   SET_STYLE → __SetInlineStyles│
│    ↓                              │    │   ...                          │
│  scheduleFlush() ──────────────┐  │    │   ↓                            │
│    callLepusMethod(            │  │    │  __FlushElementTree()  ← 一次性│
│      'kiaaoPatchUpdate', ←─────┼──┼───→│                                │
│      { ops: [...] })           │  │    │                                │
│                                │  │    │                                │
└────────────────────────────────────┘    └────────────────────────────────┘
```

- 关键：所有 op 在主线程的**一个 `callLepusMethod` 调用**内原子处理
- 对 native 层来说，不存在"先删再插"的中间状态

## 可预见的问题

### 1. kiaao 响应式无 batch 概念——flush 时机

kiaao 的 `use` 是**同步传播**的：

```
signal(x) → 所有派生立即同步重算 → DOM 操作立即被 adapter 捕获为 op
```

不存在 Vue 的 `nextTick` 或 SolidJS 的 batch。op buffer 什么时候 flush 给主线程？两种方案：

**方案 A：每次信号写入后自动 flush**

```
signal(x) → 同步重算 → ops 累积 → scheduleFlush()
```

多次连续 signal 写入（如 `count(1); count(2)`）需要合并为一次 flush。可用 Promise 微任务合并：

```ts
let scheduled = false;
function scheduleFlush() {
  if (scheduled) return;
  scheduled = true;
  Promise.resolve().then(() => {
    flushOps();
    scheduled = false;
  });
}
```

**问题**：后台线程是否支持 `Promise` / 微任务？Lynx 后台线程是 PrimJS，基本 JS 特性应可用，但需验证。

**方案 B：显式 batch API**

```ts
import { batch } from "kiaao/lynx/bg";

batch(() => {
  signalA(val1);
  signalB(val2);
}); // 函数返回后一次性 flush
```

需要改 core 的响应式系统，兼容 DOM/SSR 平台，改动大。

**推荐**：先试方案 A，复杂度最低。

### 2. 构建工具链——历史上因 `lynxCoreInject` 问题卡住

2026-07-02 尝试 Rspeedy 双入口时遇到：

- 后台入口需要 AMD 包装（`RuntimeWrapperWebpackPlugin` → `__init_card_bundle__`）
- AMD 包装需要 `lynxCoreInject` 参数，但此参数只在后台线程注入
- [源代码](https://github.com/lynx-family/lynx-stack/blob/main/packages/webpack/runtime-wrapper-webpack-plugin)中有相关处理

**当前状况**：`@lynx-js/runtime-wrapper-webpack-plugin` 版本更新至 0.2.0，可能已修复相关问题。**这是整个方案的最大未知数。**

### 3. 后台线程 API 限制

后台线程是 PrimJS，不是完整的浏览器环境：

| API                          | 主线程    | 后台线程 |
| ---------------------------- | --------- | -------- |
| `__CreatePage`               | ✅        | ❌       |
| `__CreateElement` 等         | ✅        | ✅       |
| `setTimeout` / `setInterval` | ?         | ?        |
| `Promise`                    | ?         | ?        |
| `queueMicrotask`             | ❌(1.4.0) | ?        |
| `requestAnimationFrame`      | ✅        | ❌       |
| `console.log`                | ?         | ?        |

kiaao 当前 App.tsx 中用了 `requestAnimationFrame`——双线程下此类 API 必须移除或桥接到主线程。

### 4. 事件系统

当前事件绑定是 adapter 直接调 `__AddEvent` + `{ type: "worklet", value: handler }`。

双线程下，事件处理有两种模式：

- **模式 A**（vue-lynx）：后台线程注册 handler sign，主线程持有关联表。事件触发时主线程通过 `runWorklet` 调 handler → 路由到后台线程
- **模式 B**：事件仍在主线程处理（`main-thread:bindtap`），直接在主线程执行。kiaao 当前就是 worklet 模式，实际上已兼容

**倾向模式 B**：事件处理逻辑不变，不需要额外改动。

### 5. Each 组件的 diff 算法

`Each` 通过节点引用比较来决定是否需要移动/删除/插入元素。影子树中节点引用是 `ShadowElement` 实例，可以正常比较。`prev`/`next`/`parent` 等指针在影子树上维护。**不构成问题。**

### 6. Owner 生命周期与元素引用

当前 `Owner.elements` 存储 `FiberElement`（原生元素引用）。双线程下：

- 后台线程的 `Owner.elements` 存储 `ShadowElement` 引用
- 主线程侧通过 `elementRegistry`（id → FiberElement 映射）访问原生元素
- `disposeOwner` 在后台线程执行，产生的 REMOVE ops 通过 op buffer 发送到主线程执行

**逻辑兼容**，需改 `Owner.elements` 的类型从 `Set<FiberElement>` 到 `Set<ShadowElement>`。

### 7. 两个 adapter 维护成本

主线程直连模式（当前）和双线程模式是两个 adapter，但 70% 的逻辑可共享：

```
共享部分：
  - 事件匹配正则（events.ts）
  - style camelToKebab 转换
  - JSX 类型声明

差异部分：
  - 元素创建（el/text/comment）
  - 元素操作（append/remove/before/replace/clear）
  - 属性设置（setProp/setText）
  - 节点遍历（isNode/isElement）
```

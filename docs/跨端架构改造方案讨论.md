# 跨端架构改造方案讨论

> 撰写日期：2026-06-15
> 状态：讨论阶段 / 待决策

---

## 一、背景与动机

### 1.1 现状

kiaao 当前架构中，`src/reactive/` 层完美隔离了浏览器 API，是纯净的平台无关逻辑。但 `src/dom/` 层的所有 14 个文件均直接引用了浏览器全局 API（`document.createElement`、`addEventListener`、`Node`、`Element` 等），与浏览器平台深度耦合。

### 1.2 目标

1. **跨端支持**：为 Lynx（字节跳动跨端框架）提供适配
2. **孤岛水合架构**：在可预见的未来实现服务端渲染后的客户端水合（hydration）
3. **保持框架核心精炼**：不因平台抽象引入过度复杂性

### 1.3 约束

- 不要为「可能的未来」过度设计，但 Lynx 是确定的第二个平台
- 孤岛水合在可预见的未来是必须的
- 框架的 API 签名应尽可能对现有用户透明

## 三、Lynx 平台分析

### 3.1 与浏览器的关键差异

| 维度                  | 浏览器                                   | Lynx                                                         | 对框架的影响                                         |
| --------------------- | ---------------------------------------- | ------------------------------------------------------------ | ---------------------------------------------------- |
| 文本节点              | 有独立 `Text` 节点                       | 无，文本是 `<text>` 元素的属性/子 span                       | `createTextNode` + `textContent` 需要 adapter 级抽象 |
| 注释节点              | 有 `Comment` 节点                        | 不存在                                                       | `when`/`each` 的锚点机制需要替代方案                 |
| `display: contents`   | CSS 支持                                 | 不存在                                                       | Fragment 需要新的兜底策略                            |
| HTML 元素类型         | 完整 HTML + SVG 标签集合                 | Lynx 特有元素集（`view`, `text`, `image`, `scroll-view` 等） | 标签名映射 + void 元素判断                           |
| Attribute vs Property | 两者有本质区别                           | 不存在区分，一切皆属性                                       | FORCE_ATTRIBUTE 等策略仅浏览器需要                   |
| 事件模型              | `addEventListener` 标准                  | 触控优先，绑定机制不同                                       | 事件绑定需 adapter 化                                |
| 线程模型              | 主线程 + Workers                         | JS 线程与渲染线程分离，部分 API 异步桥接                     | 调度策略可能需要适配                                 |
| SVG                   | 完整支持                                 | 不支持                                                       | SVG 判断下沉到 browser adapter                       |
| Style                 | CSS 对象 + 字符串                        | 样式系统不同，部分 CSS 属性无效                              | `setStyle` 适配                                      |
| DOM 树遍历            | 完整 `parentNode/childNodes/nextSibling` | 受限或不支持                                                 | 遍历操作需 adapter 化                                |

### 3.2 对抽象层的核心挑战

when/each 指令依赖于「在 DOM 树中插入不可见的锚点节点来标记动态内容位置」——浏览器用 `Comment` 节点天然支持，但 Lynx 没有等价的机制。

**可能的替代方案**：

- **选项 A**：用不可见零尺寸 `view` 元素作标记，通过位置索引管理动态区间
- **选项 B**：每个宿主元素维护内部子节点映射表，用 slot ID 索引
- **选项 C**：使用 `[startMarker, endMarker]` 双元素区间标记

## 四、孤岛水合分析

### 4.1 水合的基本流程

```
服务端渲染静态 HTML → 客户端加载 JS
→ 水合（将信号绑定到已有 DOM，不重新创建节点）
→ 激活响应式更新
```

### 4.2 对框架的能力要求

| 能力               | 说明                                      | 与当前设计的冲突                                |
| ------------------ | ----------------------------------------- | ----------------------------------------------- |
| 认领现有点         | `mount()` 接受已有 DOM 根节点，不重复创建 | 当前 `h()` 总是 `createElement`                 |
| 遍历认领           | 水合游标（stream）机制，逐节点匹配和认领  | 新增概念                                        |
| 信号绑定到现有节点 | 信号派生绑定到已有文本/元素节点           | 当前总是新建                                    |
| `when`/`each` 水合 | 初始渲染时不重建，只绑定                  | 当前 `when` 总是 `clearChildren → renderBranch` |
| 水合不匹配处理     | SSR 输出与客户端数据不一致时的降级        | 新增容错机制                                    |
| 跨孤岛信号通信     | 多个水合孤岛间共享状态                    | 模块级信号已天然支持 ✅                         |
| 部分水合           | 每个孤岛独立水合，不互相阻塞              | 需要独立 mount 边界                             |

### 4.3 水合与现有 RenderMode 的关系

当前已有两种渲染模式：

- `"dom"` — 客户端正常 DOM 创建
- `"ssr"` — 服务端一次性计算 + 字符串输出

水合应是第三种模式：**`"hydrate"`**，其行为介于两者之间：

```
mode: "dom"     → createElement + 创建派生 + triggerMount
mode: "ssr"     → 一次性计算 + 字符串拼接
mode: "hydrate" → claimNode + 创建派生（绑定到现有节点）+ triggerMount（立即触发）
```

## 五、设计讨论

### 5.1 Adapter 接口抽象层级

#### 方案 A：DOM 风格抽象

```
createElement(tag) → PlatformElement
createTextNode(text) → PlatformNode
createComment(text) → PlatformNode
appendChild(parent, child)
insertBefore(parent, child, ref)
removeChild(parent, child)
setAttribute(el, key, value)
...
```

**优点**：

- 与当前 `dom-utils.ts` 直接对应，迁移成本低
- 操作语义清晰，渲染层改动最小

**缺点**：

- 对 Lynx 不友好：`createComment` 无法映射，`createTextNode` 也不自然
- 本质上是「DOM API 的浅层包装」，没有真正抽象语义

#### 方案 B：渲染语义级抽象

```
createElement(type) → PlatformElement
createText(value) → PlatformText
createPlaceholder(slotId) → PlatformPlaceholder  ← 语义化锚点
insertChild(parent, child, index?)                ← 按位置而非引用节点
replaceRange(parent, start, end, newChildren[])   ← 区间替换（when/each 核心）
setProp(el, key, value)
addEvent(el, type, handler)
setStyle(el, key, value)
...
```

**优点**：

- 对 Lynx 友好：`createPlaceholder` 可映射为索引号或不可见 view
- `replaceRange` 抽象了 when/each 的核心操作
- 水合的 claim 逻辑可以自然融入

**缺点**：

- 与当前渲染层代码的映射关系需要仔细设计
- 渲染层需要为每个平台「编译」语义操作为平台操作
- 接口设计更难一次做好

#### 初步倾向

**方案 B**。理由是 Lynx 的存在使得方案 A 的 `createComment` 等方法会产生无法消除的阻抗不匹配。语义级抽象虽然前期设计成本高，但对两个平台的表达力都更好。

### 5.2 Adapter 定位方式

#### 方案 1：全局单例

```ts
setAdapter(adapter)
getAdapter() → adapter
```

- ✅ 用户代码无需传递 adapter，`h()` 内部直接取
- ✅ 与现有 API 签名兼容
- ❌ 隐式依赖，测试需注意状态重置

#### 方案 2：显式注入

```ts
h(tag, props, children, adapter);
// 或
const renderer = createRenderer(adapter);
renderer.h(tag, props, children);
```

- ✅ 显式、可测试、无全局状态
- ❌ API 签名变化大，JSX 无法传递额外参数
- ❌ 与 JSX 自动运行时不兼容

#### 初步倾向

**方案 1**。JSX 编译后调用 `h()` 无法传入 adapter，全局单例是对 JSX 兼容的唯一方式。浏览器端默认自动注册，`setAdapter` 仅在需要切换平台时调用一次，全局状态的风险可控。

### 5.3 组件级 use 的归属问题

当前 `context.use` 的实现（`registerSignalStop` + 将 `stop` 注册到 `unmountCallbacks`）是纯响应式的，没有平台耦合。它不调用任何 DOM API，只是向数组 push 函数。**组件级 use 不需要修改**。

### 5.4 `renderMode` 的归属

当前 `setRenderMode` / `getRenderMode` 放在 `reactive/core.ts`，但它本质上是平台概念。讨论：

- 保留在 reactive 层：因为派生在 SSR 模式下需要退化为一次性计算，这确实是响应式核心的行为
- 移到 platform 层：作为 adapter 的属性（`adapter.mode`），更自然

**初步倾向**：模式切换影响派生行为，保留在 reactive 层。但 adapter 可以**读取**当前模式（通过 `getRenderMode()`）来调整自己的节点创建策略。水合时，reactive 的 mode 为 `"dom"`（派生正常响应），但 adapter 的 create 行为变为 claim。

### 5.5 原子性 vs 可组合的接口拆分

接口拆分粒度讨论：

**粗粒度**：一个 `PlatformAdapter` 接口包含所有方法

- ✅ 简单，无需多重分发
- ❌ 每个平台必须实现全部方法

**细粒度**：拆分为多个独立接口（`NodeOps`、`EventOps`、`StyleOps`、`RouterOps`...），adapter 是组合

- ✅ 灵活性高，平台可实现部分能力
- ❌ 复杂度高，渲染层的引用路径深

**倾向**：粗粒度起步。当某个方法在不同平台的行为差异确实大到需要独立单元测试时再拆分。YAGNI。

### 5.6 Fragment 跨端语义

当前 Fragment 在浏览器上渲染为 `<div style="display: contents">`。

跨端考虑：

- **浏览器**：维持现状
- **Lynx**：`display: contents` 不存在。两种可能：
  - 扁平化：Fragment 返回原始子节点数组，父级直接吸收
  - 极简容器：用透明 `view` 包裹
- **SSR**：不输出外部 wrapper

**这需要在 Fragment 的跨端实现上做平台分叉**，可能是 adapter 的方法之一（`createFragmentContainer(children)`）。

## 六、待决策事项

### 决策 1：Adapter 接口抽象层级

选择方案 A（DOM 风格抽象）还是方案 B（渲染语义级抽象）？

- 方案 A 迁移成本低，但对 Lynx 的适配会留下「为不存在之物建模」的痕迹
- 方案 B 设计成本高，但对两个平台的表达力都更好

### 决策 2：Adapter 定位方式

选择全局单例还是显式注入？

- 全局单例对 JSX 兼容最好，但有隐式依赖
- 显式注入更纯粹但与 JSX 运行时冲突

### 决策 3：水合机制的启动位置

水合是在 `mount()` 层面控制（`hydrate(component, domNode)`），还是在 `h()` 层面通过 adapter 的 `mode: "hydrate"` 透明控制？

### 决策 4：Lynx 锚点机制方向

when/each 在缺少 `Comment` 节点的平台上采用哪种锚点方案？

- 元素级标记 + 位置索引
- 双指针区间标记
- 虚拟子节点管理器

### 决策 5：Fragment 跨端语义

Fragment 在 Lynx 上的行为（扁平化 vs 极简容器）？

## 七、实施步骤（草案）

### 阶段 1：平台抽象层基础设施

1. 定义 `src/platform/types.ts` — `PlatformAdapter` 接口
2. 实现 `src/platform/adapter.ts` — `setAdapter` / `getAdapter`
3. 从 `dom-utils.ts` 提取浏览器实现为 `src/platform/browser/index.ts`
4. 创建 SSR adapter `src/platform/server/index.ts`

### 阶段 2：渲染层改造

5. 创建 `src/renderer/` 目录
6. 逐个将 `src/dom/` 文件迁移到 `src/renderer/`，用 adapter 替换直接 DOM 操作
7. `local-effect.ts` 迁移（无改动）
8. `process-children.ts` → 改 adapter 调用
9. `component.ts` → 改 adapter 调用
10. `props.ts` → 浏览器策略下沉到 browser adapter
11. `directive.ts` → 改 adapter 调用
12. `when.ts` / `each.ts` → 改 adapter 调用（锚点用 `createPlaceholder`）
13. `h.ts` → 移除 hSSR 分支，统一走 adapter
14. `fragment.ts` / `portal.ts` / `lazy.ts` → 少量适配

### 阶段 3：入口 & 路由改造

15. `src/router/` → 从 adapter 获取 location/history
16. `src/motion/` → 确认是否需要改造
17. `src/index.ts` → 自动注册 browser adapter
18. `src/server/index.ts` → 自动注册 SSR adapter
19. 删除旧的 `src/dom/` 目录

### 阶段 4：Lynx 适配

20. 创建 `src/platform/lynx/index.ts` — Lynx adapter 实现
21. Lynx 端验证 when/each 锚点方案
22. Lynx 端验证 Fragment 行为

### 阶段 5：水合机制

23. 定义 `RenderMode` 新增 `"hydrate"` 模式
24. 实现 HydrationStream（DOM 游标）
25. 实现 `hydrate()` API
26. 处理水合不匹配降级

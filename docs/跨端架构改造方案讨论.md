## 一、背景与动机

### 1.1 现状

kiaao 当前架构中，`src/reactive/` 层完美隔离了浏览器 API，是纯净的平台无关逻辑。但 `src/dom/` 层的所有 14 个文件均直接引用了浏览器全局 API（`document.createElement`、`addEventListener`、`Node`、`Element` 等），与浏览器平台深度耦合。

### 1.2 目标

1. **跨端支持**：为 Lynx（字节跳动跨端框架）提供适配
2. **孤岛水合架构**：在可预见的未来实现服务端渲染后的客户端水合（hydration）
3. **保持框架核心精炼**：不因平台抽象引入过度复杂性

### 1.3 约束

- 不要为「可能的未来」过度设计，但 **Lynx 是确定的第二个平台**
- **孤岛水合在可预见的未来是必须的**
- 框架的公开 API 签名应尽可能对现有用户保持透明
- 每次修改都需要理解和审慎考虑，不急于一时定案

## 三、现有位置管理机制分析

> 本节的来由：在设计 adapter 接口时，需要先理解当前代码实际是如何管理动态节点位置的。我最初错误以为是用 `insertBefore(ref)` 参数引用，进而提出了 `insertAt(index)` 的抽象。阅读源码后发现实际机制不同，下文为修正后的理解。

### 3.1 each 指令的位置管理

`each.ts` 的核心模式：**锚点参考系**。

```ts
// 1. 创建锚点节点（Comment 节点），追加到容器尾部
const anchor = createComment("each");
container.append(anchor);

// 2. 新节点插入到锚点之前
anchor.before(node);

// 3. 判断是否需要移动节点
const needsMove =
  prevNode === null
    ? firstChild(container) !== node // 队列头：检查是否是第一个子节点
    : prevSibling(node) !== prevNode; // 非队列头：检查前一个兄弟是否匹配
```

**关键设计点**：

| 概念     | 实现（浏览器）                   | 语义                               |
| -------- | -------------------------------- | ---------------------------------- |
| 锚点     | `Comment` 节点                   | 始终位于动态区间末尾的固定参考点   |
| 插入     | `anchor.before(node)`            | 在参考点之前插入（而非在索引位置） |
| 位置判断 | `prevSibling(node) !== prevNode` | 通过实际 DOM 遍历确认节点顺序      |
| 批量移除 | `createFragment()` 暂存后清除    | 用 DocumentFragment 批量移除       |

**为什么用锚点参考系而不是索引？**

锚点参考系的优点：

- 插入/删除不会影响参考点的位置（参考点始终在尾部）
- 不需要维护索引号的一致性（索引在插入/删除后会变化）
- 节点的实际 DOM 位置就是最可靠的「当前顺序」

### 3.2 when 指令的位置管理

`when.ts` 的模式更简单——**先清空再填充**：

```ts
// 每次条件变化时清空所有子节点，再重新渲染
function clearChildren(el: Element): DocumentFragment {
  const removed = createFragment();
  let child: Node | null;
  while ((child = firstChild(el))) {
    disposeNode(child);
    removed.append(child);
  }
  return removed;
}
```

### 3.3 对 adapter 设计的启示

位置管理不需要 `insertAt(parent, child, index)` 这种索引式抽象，而是需要：

```ts
// 锚点参考系原语
createPlaceholder(id: string): PlatformPlaceholder;
  // 浏览器：createComment(id)
  // Lynx：需要替代机制（见第??节 #锚点机制待定）

insertBeforeRef(parent, child, ref): void;
  // 浏览器：parent.insertBefore(child, ref) 或 ref.before(child)
  // Lynx：映射为索引定位

previousSibling(node): PlatformNode | null;
  // 用于判断节点的实际顺序是否与预期一致

firstChild(parent): PlatformNode | null;
  // 用于判断某个节点是否是容器的第一个子节点
```

## 四、Fragment 容器必要性分析

> 本节的来由：我最初认为 `display: contents` 容器是一种「hack」，建议 Fragment 扁平化返回 children。用户指出 kiaao 是无 VDOM 的，需要一个确定存在的节点来挂载状态关联。我重新审视了全部相关代码后确认这个判断是正确的。下文为详细分析。

### 4.1 为什么要容器节点

kiaao 没有虚拟 DOM，所有组件实例的元数据直接挂在真实 DOM 节点上：

```ts
// src/dom/component.ts
export function attachInstance(node: Node, instance: ComponentInstance): void {
  if (!(node as any)[INSTANCE_KEY]) {
    (node as any)[INSTANCE_KEY] = new Set<ComponentInstance>();
  }
  if (!(node as any)[DISPOSE_KEY]) {
    (node as any)[DISPOSE_KEY] = new Set<() => void>();
  }
  (node as any)[INSTANCE_KEY].add(instance);
  (node as any)[DISPOSE_KEY].add(createDisposeFn(instance));
}
```

然后 `triggerMount` 和 `disposeNode` 通过递归遍历 DOM 树来找到这些元数据：

```ts
// triggerMount 递归遍历
const instances = (node as any)[INSTANCE_KEY];
// ....触发 onMount
for (const child of node.childNodes) {
  triggerMount(child);
}

// disposeNode 递归遍历
// 顺序：子节点 → LOCAL_EFFECTS → 指令 onUnmount → 组件 DISPOSE_KEY → INSTANCE_KEY
```

### 4.2 容器节点的场景

| 场景                         | 问题                          | 容器方案                                 |
| ---------------------------- | ----------------------------- | ---------------------------------------- |
| 组件返回数组（多根）         | `attachInstance` 需要唯一节点 | 用 `<div style="display:contents">` 包裹 |
| `<></>` Fragment             | 同上                          | 同上                                     |
| 异步组件（`async function`） | Promise resolve 前需要占位    | 同上 wrapper                             |
| `lazy()` 加载组件            | 同上                          | 同上                                     |

**结论**：容器节点不是 hack，是 kiaao 无 VDOM 架构下的**必要设计**。它解决的核心问题是——组件实例的元数据（`INSTANCE_KEY`、`DISPOSE_KEY`）需要一个确定存在的 DOM 节点作为宿主。

### 4.3 Lynx 的影响

`display: contents` 是浏览器 CSS 行为，Lynx 不存在。这意味着：

- Lynx 上的 Fragment 容器节点将**可见**（除非 Lynx 有等价的布局隐藏能力）
- 这是需要接受的跨端差异——React Native 的 `<></>` 在 Android 上也是可见的 `View`
- adapter 接口需要提供 `createFragmentContainer()`，每个平台按各自能力实现

### 4.4 设计决定

**Fragment 保持容器节点模式，不做扁平化**。adapter 提供 `createFragmentContainer()` 方法。

## 五、Lynx 平台分析

### 5.1 已知差异

| 维度                  | 浏览器                       | Lynx                                    | 对框架的影响                            | 确定性    |
| --------------------- | ---------------------------- | --------------------------------------- | --------------------------------------- | --------- |
| 文本节点              | 有独立 `Text` 节点           | 无，文本是 `<text>` 元素的属性/子 span  | `createTextNode` + `textContent` 需抽象 | ✅ 确定   |
| 注释节点              | 有 `Comment` 节点            | 不存在                                  | 锚点机制需替代方案                      | ✅ 确定   |
| `display: contents`   | CSS 支持                     | 不存在                                  | Fragment 容器可见                       | ✅ 确定   |
| 元素类型              | 完整 HTML + SVG              | Lynx 特有（`view`, `text`, `image` 等） | 标签映射 + void 元素列表                | ✅ 确定   |
| Attribute vs Property | 本质区别                     | 一切皆属性                              | `FORCE_ATTRIBUTE` 仅浏览器需要          | ✅ 确定   |
| 事件模型              | `addEventListener`           | 触控优先，机制不同                      | 事件绑定需抽象                          | ✅ 确定   |
| 线程模型              | 主线程 + Workers             | JS/渲染线程分离，部分 API 异步桥接      | 调度策略待评估                          | ⚠️ 待调研 |
| 节点元数据            | 任意 JS 属性（Symbol key）   | V8 引擎，理论上支持 Symbol key          | `setMetadata/getMetadata` 抽象          | ⚠️ 待验证 |
| DOM 树遍历            | 完整 `parentNode/childNodes` | 受限或不支持                            | 遍历操作需确定 Lynx 能力边界            | ❌ 待调研 |

### 5.2 锚点机制的跨端方案

**核心矛盾**：when/each 依赖「在 DOM 树中插入不可见节点作为位置参考」，浏览器用 `Comment` 实现，Lynx 没有 `Comment`。

**可能方案**：

| 方案          | 浏览器                         | Lynx                              | 权衡                                   |
| ------------- | ------------------------------ | --------------------------------- | -------------------------------------- |
| A：不可见元素 | Comment                        | 零尺寸 `view`（如有）             | 如果 Lynx 不支持零尺寸，会留下可见标记 |
| B：内部索引表 | 不改造                         | 宿主元素维护 slot→[nodeList] 映射 | two-tier 实现，逻辑复杂度高            |
| C：双标记区间 | 两个 Comment 做 `[start, end]` | 两个零尺寸 view 做区间            | 元素用量翻倍，但区间语义清晰           |

**遗留问题**：Lynx 是否支持零尺寸/不可见元素？在确认之前，adapter 接口设计需要兼容多种锚点实现方式。**（标为待决策）**

## 六、孤岛水合分析

### 6.1 水合基本流程

```
服务端渲染静态 HTML → 客户端加载 JS
→ 水合（将信号绑定到已有 DOM，不重新创建节点）
→ 激活响应式更新
```

### 6.2 对框架的能力要求

| 能力               | 说明                                      | 与当前设计的冲突                                | 优先级 |
| ------------------ | ----------------------------------------- | ----------------------------------------------- | ------ |
| 认领现有点         | `mount()` 接受已有 DOM 根节点，不重复创建 | 当前 `h()` 总是 `createElement`                 | 核心   |
| 遍历认领           | 水合游标（stream）机制，逐节点匹配和认领  | 新增概念                                        | 核心   |
| 信号绑定到现有节点 | 信号派生绑定到已有文本/元素节点           | 当前总是新建 text/comment                       | 核心   |
| `when`/`each` 水合 | 初始渲染时不重建，只绑定                  | 当前 `when` 总是 `clearChildren → renderBranch` | 核心   |
| 水合不匹配处理     | SSR 输出与客户端数据不一致时的降级        | 新增容错机制                                    | 重要   |
| 跨孤岛信号通信     | 多个水合孤岛间共享状态                    | 模块级信号已天然支持 ✅                         | 已有   |
| 部分水合           | 每个孤岛独立水合，不互相阻塞              | 需要独立 mount 边界                             | 核心   |
| Fragment 容器水合  | SSR 时容器已存在，水合时认领而非重建      | 当前总是 create                                 | 核心   |

### 6.3 水合与现有 RenderMode 的关系

当前已有两种渲染模式（定义在 `src/reactive/core.ts`）：

```
type RenderMode = "dom" | "ssr" | "hydrate";
                          ↑                           ↑
                    已有，派生退化为一次性计算    新增
```

三种模式在 adapter 层面的含义：

```
mode: "dom"     → adapter 的 create* 方法创建新节点
mode: "ssr"     → adapter 的 create* 方法返回序列化字符串（现有 hSSR 路径）
mode: "hydrate" → adapter 的 create* 方法认领已有节点
```

### 6.4 水合适配器的设计方向

约定：`hydrate()` 是一个独立的 API，**不是** `mount()` 的模式参数。

```ts
function hydrate(
  component: ComponentFunction,
  container: PlatformElement,
  props?: any,
): PlatformElement {
  // 1. 创建 DOM 游标（遍历容器现有 DOM）
  const stream = new HydrationStream(container);

  // 2. 创建 hydration adapter（包装 browser adapter）
  const hydrateAdapter = {
    ...baseAdapter,
    createElement(tag) {
      return stream.claimElement(tag) ?? baseAdapter.createElement(tag);
    },
    createText(value) {
      return stream.claimText() ?? baseAdapter.createText(value);
    },
    createPlaceholder(id) {
      return stream.claimPlaceholder() ?? baseAdapter.createPlaceholder(id);
    },
    mode: "hydrate",
  };

  // 3. 全局切换到 hydration adapter
  const prev = setAdapter(hydrateAdapter);

  // 4. 调用 h() 走 adapter 路径，自动走 claim 路径
  //    h() 本身不需要知道「水合」概念
  const root = h(component, props);

  // 5. 恢复 adapter
  setAdapter(prev);

  // 6. 触发 onMount（DOM 已存在，立即触发）
  triggerMount(root);

  return root;
}
```

关键洞察：**h() 本身不需要知道「水合」这个概念**。它只通过 adapter 的 `createElement` 获取节点——至于 adapter 是新建还是认领，h() 不关心。水合和正常的 DOM 创建在 h() 看来是同构的。这就是 adapter 模式的价值所在。

### 6.5 待解决的问题

| 问题           | 说明                                                                                                      |
| -------------- | --------------------------------------------------------------------------------------------------------- |
| 认领失败降级   | 如果 streaming 中下一个节点不是期待的 tag，是立即创建新节点降级，还是抛异常？                             |
| when/each 水合 | 水合时 when 需要「走一遍但只认领不创建」。each 需要在初始渲染时认领列表项而不新建。具体如何实现？         |

## 七、设计讨论与决策记录

### 7.1 Adapter 接口抽象层级

#### 讨论历程

| 轮次 | 方案                                                                     | 提出方      | 结论                                    |
| ---- | ------------------------------------------------------------------------ | ----------- | --------------------------------------- |
| 1    | A：DOM 风格抽象（createComment、insertBefore 等）                        | AI          | ❌ 对 Lynx 不友好                       |
| 2    | B：渲染语义级抽象（insertAt、replaceRange 等）                           | AI          | ⚠️ 后因位置管理重新理解而修正           |
| 3    | 折中：节点原语 + 位置索引                                                | AI          | ❌ 提出后被用户指出位置管理实际机制不同 |
| 4    | C：锚点参考系抽象（createPlaceholder、insertBeforeRef、previousSibling） | 🔄 当前方向 | ✅ 更贴合实际代码，对两个平台都友好     |

#### 当前倾向

**方案 C：锚点参考系抽象**。

核心接口雏形：

```ts
interface PlatformAdapter {
  // ── 节点创建 ──
  createElement(tag: string): PlatformElement;
  createText(value: string): PlatformTextNode;
  createPlaceholder(slotId: string): PlatformPlaceholder;
  // 浏览器：createComment(id)
  // Lynx：待定（见#锚点机制待定）
  // SSR：不输出（序列化时跳过）
  // 水合：认领已有 Comment 节点或等价物

  createFragmentContainer(): PlatformElement;
  // 浏览器：<div style="display: contents">
  // Lynx：普通 view（可见）
  // SSR：不输出
  // 水合：认领已有容器

  // ── 树操作（锚点参考系）──
  appendChild(parent: PlatformParent, child: PlatformNode): void;
  insertBeforeRef(parent: PlatformParent, child: PlatformNode, ref: PlatformNode): void;
  // 浏览器：ref.before(child) 或 parent.insertBefore(child, ref)
  // Lynx：ref 为锚点平台对象，内部索引定位
  removeChild(parent: PlatformParent, child: PlatformNode): void;

  // ── 遍历（用于位置判断）──
  parentNode(node: PlatformNode): PlatformNode | null;
  firstChild(parent: PlatformParent): PlatformNode | null;
  previousSibling(node: PlatformNode): PlatformNode | null;
  isConnected(node: PlatformNode): boolean;

  // ── 元数据（组件实例关联的核心）──
  setMetadata(node: PlatformNode, key: symbol, value: any): void;
  getMetadata(node: PlatformNode, key: symbol): any;
  // 浏览器：node[key] = value / node[key]
  // Lynx：如果 Lynx 节点是 JS 对象则同样适用
  // 如果 Lynx 节点是桥接对象不可附加属性，需 Map<Node, Map<symbol, any>> 兜底

  // ── 属性/事件/样式 ──
  setProp(el: PlatformElement, key: string, value: unknown): void;
  removeProp(el: PlatformElement, key: string): void;
  addEvent(el: PlatformElement, type: string, handler: Function): void;
  removeEvent(el: PlatformElement, type: string, handler: Function): void;
  setStyle(el: PlatformElement, key: string, value: string | number): void;

  // ── 平台环境 ──
  readonly location?: { pathname: string; search: string };
  readonly history?: { pushState(data: any, title: string, url: string): void };
  querySelector?(selector: string): PlatformElement | null;
  addGlobalEventListener?(type: string, handler: Function): void;

  // ── 渲染模式 ──
  mode: "dom" | "ssr" | "hydrate";
}
```

**来由**：

- 阅读 `each.ts` 后发现实际位置管理基于 `anchor.before(node)` + `prevSibling`，而非索引号
- 确认 Fragment 容器是必要设计而非 hack
- 元数据挂载（`INSTANCE_KEY`、`DISPOSE_KEY`）是框架生命周期的基石，需要抽象

**遗留问题**：

- 接口方法的完整列表是否够完备？是否有遗漏的核心操作？
- `PlatformNode` / `PlatformElement` / `PlatformPlaceholder` / `PlatformTextNode` 的类型层级如何设计？
- 是否需要 `NodeType` 枚举来区分不同类型？
- `setProp` 的浏览器端实现现在包含 FORCE_ATTRIBUTE、SVG、aria/data、事件、前缀等复杂策略，这些是否全部下沉到 browser adapter？

### 7.2 Adapter 定位方式

**决策：全局单例**（`setAdapter` / `getAdapter`）。

**理由**：

1. JSX 编译后调用 `h()`，无法传递 adapter 参数
2. 浏览器端默认自动注册，无需用户操作
3. `setAdapter` 仅在以下场景调用：切换平台、SSR 启动、水合启动
4. 测试中通过 `setAdapter(mockAdapter)` + `afterEach(() => setAdapter(browserAdapter))` 管理

**遗留问题**：

- 是否需要 `withAdapter(adapter, fn)` 临时切换辅助函数（上下文管理器风格）？

### 7.3 水合启动位置

**决策：独立 `hydrate()` API**，不在 `h()` 层面控制。

**理由**：

1. `h()` 无需感知水合概念——它通过 adapter 获取节点，adapter 透明决定创建还是认领
2. 水合的复杂性（游标管理、降级策略、不匹配检测）封装在 `hydrate()` 内
3. 与现有 `mount()` 保持平行关系：`mount()` 做创建 + 挂载 + triggerMount，`hydrate()` 做认领 + 绑定 + triggerMount

**遗留问题**：

- `hydrate()` 的完整签名（是否支持 option 对象用于水合不匹配策略配置？）

### 7.4 Fragment 跨端语义

**决策：保留容器节点模式**，不做扁平化。

**理由**：

1. 无 VDOM 架构下需要容器承载组件实例元数据（`INSTANCE_KEY`、`DISPOSE_KEY`）
2. `triggerMount` 和 `disposeNode` 依赖 DOM 树遍历找到这些元数据
3. Lynx 上没有 `display: contents`，容器可见是跨端可接受的折中

**adapter 方法**：`createFragmentContainer()` → 浏览器返回 `div style=display:contents`，Lynx 返回普通 view。

### 7.5 RenderMode 的归属

**决策：保留在 `reactive/` 层**，adapter 通过 `getRenderMode()` 读取。

**理由**：

- `RenderMode` 控制派生的行为（SSR 模式下退化为一次性计算），这属于响应式核心的职责
- adapter 可以读取当前模式（`getRenderMode()`）来调整自己的行为
- 水合时：reactive mode = `"dom"`（派生正常响应），但 adapter mode = `"hydrate"`（create 变为 claim）

### 7.6 接口拆分粒度

**决策：粗粒度起步**（一个 `PlatformAdapter` 接口包含所有方法）。

**理由**：

- 当前只有两个平台（浏览器 + Lynx），无需过早拆分
- 粗粒度的优点是引用路径短：`getAdapter().createElement(tag)`，不挑路径
- 当某个方法组的行为差异大到需要独立测试时再拆分

## 附录：理解修正记录

### 2026-06-15 修正

**修正 1：位置管理机制**

之前认为：`each.ts` 使用类似 `insertBefore(parent, child, ref)` 的参数引用模型，进而提出了 `insertAt(index)` 的索引式抽象。

实际代码是：

- 锚点参考系模式：一个始终存在的锚点节点（Comment）位于容器尾部
- `anchor.before(node)` 插入到锚点之前
- `prevSibling(node) !== prevNode` 判断顺序

修正方向：adapter 接口从「索引式」改为「锚点参考系」（`createPlaceholder` + `insertBeforeRef` + `previousSibling`）。

**修正 2：Fragment 容器的必要性**

之前认为：`<div style="display: contents">` 是为了隐藏容器而采用的浏览器 hack，可以扁平化替代。

实际是：容器节点承载组件实例元数据（`INSTANCE_KEY`、`DISPOSE_KEY`），`triggerMount` 和 `disposeNode` 通过 DOM 树递归找到这些元数据。这是无 VDOM 架构下的必要设计，不是 hack。

修正方向：保留容器模式，adapter 提供 `createFragmentContainer()`，Lynx 上容器可见是可接受的跨端折中。

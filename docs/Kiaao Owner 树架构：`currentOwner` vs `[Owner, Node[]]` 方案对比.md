# Kiaao Owner 树架构：`currentOwner` vs `[Owner, Node[]]` 方案对比

**状态**：决策参考
**日期**：2026年6月23日
**版本**：1.0

## 一、背景

Kiaao 正在进行 Owner 树架构重构，将生命周期宿主从 DOM 树迁回 JS 内存。在实现路径上，存在两种方案：

- **方案 A（`currentOwner`）**：保留 `h()` 返回 `Node[]`，通过模块级变量 `currentOwner` 在同步执行期间传递当前组件的 Owner 引用。
- **方案 B（`[Owner, Node[]]`）**：修改 `h()` 返回值为 `[Owner, Node[]]` 元组，通过函数返回值显式传递所有权信息，彻底消除全局上下文变量。

本文档从多个维度对两种方案进行全面对比，为最终决策提供参考。

## 二、方案概述

### 方案 A：`currentOwner`（模块级变量）

`h()` 返回类型保持 `Node[]`。组件嵌套时，`handleComponent` 在调用子组件函数前将当前 Owner 存入模块级变量 `currentOwner`，子组件内部调用 `h()` 时通过读取 `currentOwner` 获取当前上下文。父子 Owner 关系在 `handleComponent` 内部通过读取 `currentOwner` 隐式建立。

```ts
// 核心机制
let currentOwner: Owner | null = null;

function handleComponent(tag, props) {
  const owner = createOwner();
  const prev = currentOwner;
  currentOwner = owner; // 设置当前上下文
  const nodes = tag(props, context);
  currentOwner = prev; // 恢复
  // 父子关系已通过 currentOwner 隐式建立
  return nodes;
}
```

### 方案 B：`[Owner, Node[]]`（返回值传递）

`h()` 返回类型变更为 `[Owner, Node[]]` 元组。组件嵌套时，父组件从子组件的返回值中直接提取 `childOwner`，显式执行 `parent.children.push(child)` 建立父子关系。不需要任何全局变量。

```ts
// 核心机制
function handleComponent(tag, props) {
  const owner = createOwner();
  const [childOwner, nodes] = tag(props, context);
  // 显式建立父子关系
  owner.children.push(childOwner);
  childOwner.parent = owner;
  return [owner, nodes];
}
```

## 三、多维度对比

### 3.1 全局状态

| 维度                | 方案 A                              | 方案 B                     |
| ------------------- | ----------------------------------- | -------------------------- |
| 模块级变量          | 有（`currentOwner`）                | **无**                     |
| 状态作用域          | 同步 `h()` 调用期间                 | 不适用                     |
| 跨异步边界安全      | 是（异步回调中不读 `currentOwner`） | **天然安全**（无全局状态） |
| 多 `createApp` 安全 | 是（单线程，栈式管理）              | **天然安全**               |

方案 A 的 `currentOwner` 是经过严格作用域限定的最小化全局状态——只在同步执行期间有效，不跨异步边界。方案 B 从根本上不存在全局状态。

### 3.2 父子关系建立

| 维度       | 方案 A                           | 方案 B                   |
| ---------- | -------------------------------- | ------------------------ |
| 建立方式   | 隐式（通过 `currentOwner` 推断） | **显式**（从返回值提取） |
| 代码可读性 | 需理解 `currentOwner` 栈机制     | **高**（直观的父子挂载） |
| 调用方感知 | 不感知（`h()` 内部处理）         | 感知（需解构元组）       |

方案 B 的父子关系建立逻辑更加透明——任何阅读 `handleComponent` 代码的人都能直接看到 `owner.children.push(childOwner)`。方案 A 的逻辑隐藏在 `currentOwner` 的 push/pop 中。

### 3.3 框架代码改动面

| 维度              | 方案 A                                | 方案 B                             |
| ----------------- | ------------------------------------- | ---------------------------------- |
| `h()` 签名        | 不变                                  | **变更**（返回 `[Owner, Node[]]`） |
| `processChildren` | 不变                                  | **需适配**（从元组中提取节点）     |
| `handleDomMode`   | 不变                                  | **需适配**                         |
| 指令系统          | 不变                                  | **需适配**                         |
| `when`/`each`     | 不变                                  | **需适配**                         |
| JSX 运行时        | 不变                                  | **需适配**（类型签名变更）         |
| `createApp`       | 不变                                  | **需适配**                         |
| 改动范围          | **小**（集中在 Owner 核心和组件处理） | **大**（几乎全部核心模块）         |

方案 A 的改动面集中在 Owner 核心逻辑和 `handleComponent`/`handleAsyncComponent`。方案 B 的改动面覆盖了框架的几乎所有核心模块。

### 3.4 概念复杂度

| 维度               | 方案 A                         | 方案 B                               |
| ------------------ | ------------------------------ | ------------------------------------ |
| 对框架使用者的影响 | **无**                         | **无**（对外 API 不变）              |
| 对框架维护者的影响 | 低（需理解 `currentOwner` 栈） | 中（需理解 `[Owner, Node[]]` 元组）  |
| 调试体验           | 中（需追踪模块级变量）         | **高**（Owner 树直接在返回值中可见） |

两种方案对框架使用者均透明。方案 B 在调试时更加直观——在控制台可以看到 `h()` 的返回值中直接携带 Owner 信息。

### 3.5 性能

| 维度             | 方案 A                       | 方案 B                                  |
| ---------------- | ---------------------------- | --------------------------------------- |
| 父子关系绑定次数 | 每组件一次                   | 每组件一次（相同）                      |
| 额外对象分配     | 无                           | **每次 `h()` 调用分配一个双元素数组**   |
| 节点清理         | 每个节点一次 `removeElement` | **优化后相同**（父 Owner 不持有子节点） |
| 整体运行时开销   | 基准                         | 略高于基准（约 1%~3%）                  |

方案 B 的主要性能开销在于每次 `h()` 调用额外分配一个长度为 2 的临时数组。现代 JS 引擎对短生命周期小数组的分配和回收优化良好，整体开销可忽略。

### 3.6 跨语言实现友好度

| 维度             | 方案 A                         | 方案 B                                    |
| ---------------- | ------------------------------ | ----------------------------------------- |
| 需要模拟的机制   | 全局上下文栈（`currentOwner`） | **无**                                    |
| 实现难度         | 中（需线程安全的上下文传播）   | **低**（纯函数返回值）                    |
| 对语言特性的要求 | 闭包 + 可变状态                | **闭包 + 函数返回值**（所有语言原生支持） |

方案 B 的核心机制——函数返回值传递所有权——是所有编程语言的原生能力。方案 A 的全局上下文栈在其他语言中需要模拟，虽然技术上可行，但增加了实现复杂度和文档成本。

### 3.7 水合（Hydration）

| 维度             | 方案 A                                 | 方案 B                              |
| ---------------- | -------------------------------------- | ----------------------------------- |
| Owner 树重建     | 依赖 `currentOwner` 栈完整模拟组件嵌套 | **不依赖全局状态**，可跳过中间层    |
| 节点认领         | 需要额外映射（`Map<Node, Owner>`）     | **更自然**（返回值携带 Owner 信息） |
| 与水合 ID 的配合 | 可行                                   | **更顺畅**                          |

两种方案均可实现水合，但方案 B 在“节点认领”和“归属映射”方面提供了更清晰的所有权信息。水合 adapter 的 `createElement` 可以认领已有 DOM 节点，直接将其放入返回值元组中向上传递。

### 3.8 SSR

两种方案在 SSR 中均无本质阻碍。SSR 的核心流程是同步执行组件函数并序列化节点树，两种方案的差异仅在于返回值类型，不影响序列化逻辑。

### 3.9 实施风险

| 维度       | 方案 A           | 方案 B                         |
| ---------- | ---------------- | ------------------------------ |
| 改动范围   | 小（集中在核心） | **大**（覆盖几乎所有模块）     |
| 回归风险   | 低               | **高**（大面积改动易引入 bug） |
| 调试复杂度 | 低               | **中**（需排查所有适配点）     |
| 实施周期   | 短               | **长**                         |

方案 B 的实施周期更长，回归风险更高，因为几乎所有消费 `h()` 返回值的模块都需要适配新的元组格式。

## 四、方案 B 的性能与复杂度深入分析

### 4.1 额外对象分配的具体影响

方案 B 每次 `h()` 调用创建一个双元素数组。在典型的深层嵌套组件树中：

- 10 层嵌套 × 每层 5 个元素 ≈ 50 次 `h()` 调用 ≈ 50 个临时数组。
- 10000 项列表 × 每项 3 个元素 ≈ 30000 个临时数组。

每次数组分配约 32~64 字节（取决于 JS 引擎），总体内存开销在 KB~MB 级别。这些数组生命周期极短（在函数返回后即无引用），会被新生代 GC 快速回收。在实际场景中，此开销通常可忽略。

### 4.2 优化策略

**关键优化**：父组件不将子组件的根节点重复添加到自己的 `elements`。只通过 `children` 数组持有子 Owner 引用。子组件自己负责清理自己的 `elements`。这消除了节点重复引用问题，使方案 B 的清理行为与方案 A 完全一致。

### 4.3 概念复杂度的具体体现

方案 B 引入的 `[Owner, Node[]]` 元组可以理解为 kiaao 自己的“VNode”——携带所有权信息的**已解析真实节点容器**，不进行 Diff。框架维护者需要理解这个概念，但框架使用者完全不需要感知。

消费方代码的变化示例：

```ts
// 方案 A
const nodes = h("div", props, ...children);
processChildren(nodes, owner);

// 方案 B
const [childOwner, nodes] = h("div", props, ...children);
owner.children.push(childOwner);
childOwner.parent = owner;
processChildren(nodes, owner);
```

## 五、总结与建议

### 5.1 核心权衡

| 方案 A 的优势              | 方案 B 的优势                |
| -------------------------- | ---------------------------- |
| 改动范围小，实施风险低     | 彻底消除全局状态             |
| 实施周期短                 | 父子关系显式化，代码可读性高 |
| 概念复杂度低               | 跨语言实现最友好             |
| 性能略优（无额外数组分配） | 水合实现更自然               |

### 5.2 建议

- **如果追求最低风险和最快落地**：选择方案 A。`currentOwner` 经过严格作用域限定，足够可靠。可以在 Owner 重构完成并稳定后，再评估是否迁移到方案 B。
- **如果追求架构纯粹性和长期可维护性**：选择方案 B。一次性彻底消除全局上下文，为多语言实现和跨端渲染提供最干净的基础。代价是更大的改动面和稍长的实施周期。

**两种方案都不存在“错误”——只是在“务实”和“纯粹”之间做选择。** 最终的 Owner 树架构（树形结构、`createApp`、异步注释占位、Fragment 无容器、跨端 adapter）在两种方案下均可实现。
